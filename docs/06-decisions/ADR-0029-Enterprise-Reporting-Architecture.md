# Context

MachineryManagerEnterprise generates numerous business documents throughout the lifetime of the system, including:

- Work Orders
- Machinery Reports
- Preventive Maintenance Reports
- Inspection Reports
- Financial Reports
- Inventory Exports
- Operational Statistics

The reporting subsystem must remain:

- cross-platform;
- maintainable;
- deterministic;
- independent of presentation technologies;
- suitable for automation.

---

# Problem

Traditional designer-based reporting systems introduce several long-term architectural issues:

- external report files;
- version synchronization problems;
- business logic migration into templates;
- reduced source-code traceability.

The project therefore requires a modern reporting architecture fully aligned with Clean Architecture.

---

# Decision Drivers

The reporting architecture shall provide:

- PDF generation
- Excel generation
- Cross-platform execution
- Source-controlled report definitions
- Excellent automation support
- High rendering quality
- Long-term maintainability
- Low operational complexity

---

# Decision

MachineryManagerEnterprise adopts the following reporting architecture.

| Responsibility | Technology |
|---------------|------------|
| PDF Generation | QuestPDF |
| Excel Generation | ClosedXML |

FastReport and RDLC are intentionally excluded.

---

# Reporting Architecture

```text
Application Layer

        │

 Report Services

        │

 ┌──────┴─────────┐

 ▼                ▼

QuestPDF      ClosedXML

 ▼                ▼

 PDF          Excel
```

The reporting technologies remain implementation details of the Infrastructure Layer.

---

# Layer Responsibilities

## Domain Layer

The Domain Layer shall never reference reporting libraries.

---

## Application Layer

The Application Layer:

- prepares report data;
- defines report contracts;
- coordinates report generation.

It does not construct PDF or Excel documents directly.

---

## Infrastructure Layer

Infrastructure implements:

- QuestPDF document generation;
- ClosedXML workbook generation.

Business rules remain outside the reporting implementation.

---

# Report Services

Each report shall be generated by a dedicated service.

Example:

```text
GenerateWorkOrderPdf

GenerateInspectionReportPdf

GenerateMaintenanceReportPdf

GenerateInventoryWorkbook

GenerateFinancialWorkbook
```

Each service owns one report responsibility.

---

# PDF Strategy

QuestPDF shall generate:

- Work Orders
- Inspection Reports
- Maintenance Reports
- Financial Reports
- Printable Business Documents

PDF layouts shall be implemented entirely in C#.

---

# Excel Strategy

ClosedXML shall generate:

- Data exports
- Analytical workbooks
- Financial spreadsheets
- Inventory exports
- Operational exports

Excel workbooks shall also be implemented entirely in C#.

---

# Report Definition Strategy

Report definitions shall:

- remain under source control;
- be code-first;
- avoid XML templates;
- avoid visual report designers.

This guarantees deterministic builds and easier code review.

---

# Report Data Flow

```text
Domain

   │

Application DTO

   │

Report Service

   │

QuestPDF / ClosedXML

   │

Generated Document
```

The reporting engines consume DTOs only.

They never access repositories or domain objects directly.

---

# Dependency Rules

Reporting services may depend upon:

- DTOs
- Application interfaces
- Infrastructure abstractions

Reporting services shall not depend directly upon:

- Controllers
- Views
- UI Components

---

# Dependency Injection

All reporting services shall be registered through Dependency Injection.

No manual instantiation shall occur outside composition root configuration.

---

# Background Processing

Reports may be generated by:

- Background Workers
- Scheduled Jobs
- Application Services
- API Requests

The architecture supports both synchronous and asynchronous report generation.

---

# Automation

Report generation shall support:

- CI validation
- Batch processing
- Scheduled reporting
- Automated export generation

No interactive designer shall be required during execution.

---

# Cross Platform

Approved platforms:

| Platform | Support |
|----------|:-------:|
| Windows | ✅ |
| Linux | ✅ |
| macOS | ✅ |

The reporting architecture is platform independent.

---

# Security

Reports shall not:

- contain hidden business rules;
- access infrastructure directly;
- retrieve data independently.

Authorization remains outside the reporting subsystem.

---

# Benefits

The selected architecture provides:

- Code-first reporting
- Excellent maintainability
- Cross-platform execution
- Strong source control integration
- Deterministic document generation

---

# Consequences

Positive

- Fully maintainable reporting
- Excellent automation
- No designer dependency
- Excellent architectural consistency

Negative

- Developers construct layouts programmatically
- No drag-and-drop report designer

These trade-offs are acceptable because long-term maintainability is prioritized.

---

# Alternatives Considered

## FastReport

Rejected.

Designer-based architecture increases maintenance complexity.

---

## RDLC

Rejected.

Legacy technology with limited cross-platform support.

---

## Mixed Reporting Technologies

Rejected.

Using multiple reporting engines for identical responsibilities unnecessarily increases complexity.

# Decision Outcome

**Accepted**

MachineryManagerEnterprise adopts a fully code-first reporting architecture using:

- QuestPDF for PDF document generation.
- ClosedXML for Excel workbook generation.

Designer-based reporting technologies are excluded from the approved architecture.
