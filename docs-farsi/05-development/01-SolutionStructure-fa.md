# ۱. هدف

این سند ساختار کلی راهکار (Solution Structure) پروژه **MachineryManagerEnterprise** را تعریف می‌کند.

هدف از ساختار راهکار، اطمینان از این است که هر پروژه دارای مسئولیت شفاف، وابستگی‌های قابل پیش‌بینی و قابلیت نگهداری بلندمدت باشد.

ساختار راهکار بالاترین سطح سازمانی کد منبع است.

---

# ۲. اهداف

راهکار باید:

- دغدغه‌های کسب‌وکار را تفکیک کند؛
- زیرساخت را ایزوله نماید؛
- از توسعه ماژولار پشتیبانی کند؛
- امکان آزمون مستقل را فراهم سازد؛
- وابستگی شدید (Coupling) را کاهش دهد؛
- قابلیت نگهداری را بهبود بخشد.

---

## پیکربندی متمرکز ساخت (Central Build Configuration)

راهکار از پیکربندی متمرکز MSBuild استفاده می‌کند:

- فایل `Directory.Build.props` شامل ویژگی‌های مشترک MSBuild است که بین همه پروژه‌ها به اشتراک گذاشته می‌شود.
- فایل `Directory.Packages.props` نسخه‌های پکیج‌های NuGet را به صورت متمرکز مدیریت می‌کند.
- تمامی فایل‌های پروژه این تنظیمات را به صورت خودکار ارث‌بری می‌کنند.
- فایل‌های پروژه نباید ویژگی‌های مشترک MSBuild یا نسخه‌های پکیج را تکرار کنند.

تمامی ویژگی‌های عمومی MSBuild از `Directory.Build.props` به ارث برده می‌شوند.

فریم‌ورک هدف (`TargetFramework`) به صورت متمرکز در `Directory.Build.props` تعریف شده است.

فایل‌های پروژه فردی نباید `TargetFramework` را مجدداً تعریف کنند مگر اینکه صریحاً مستند شده باشد.

فایل‌های پروژه‌های فردی تنها باید شامل پیکربندی‌های اختصاصی پروژه باشند، مانند:

- انتخاب SDK
- OutputType
- UserSecretsId
- تنظیمات اختصاصی Razor
- ProjectReference
- PackageReference

---

# ۳. سبک معماری

راهکار از اصول زیر پیروی می‌کند:

- طراحی دامنه-محور (DDD)
- معماری پاک (Clean Architecture)
- معماری برش عمودی (Vertical Slice Architecture - در صورت لزوم)
- وارونگی وابستگی (Dependency Inversion)
- اصول SOLID

---

# ۴. سازماندهی راهکار

راهکار به چندین پروژه با مسئولیت‌های کاملاً شفاف تقسیم شده است.

یک سازماندهی نمونه در سطح بالا در زیر نشان داده شده است:

```text
MachineryManagerEnterprise.sln

│
├── src
│
├── tests
│
├── docs
│
├── build
│
└── tools
```

---

# ۵. پروژه‌های سورس (Source Projects)

کد منبع به لایه‌های منطقی تقسیم می‌شود:

```text
src

BuildingBlocks

Modules

Host
```

هر پروژه دارای یک مسئولیت واحد و مشخص است.

---

## بلاک‌های ساختمانی (BuildingBlocks)

```text
BuildingBlocks

MachineryManager.SharedKernel

MachineryManager.Contracts

MachineryManager.Abstractions

MachineryManager.UI
```

لایه BuildingBlocks شامل کامپوننت‌های قابل استفاده مجدد است که بین تمامی ماژول‌ها به اشتراک گذاشته می‌شوند.

منطق کسب‌وکار هرگز نباید در BuildingBlocks پیاده‌سازی شود.

---

## ماژول‌ها (Modules)

قابلیت‌های کسب‌وکار باید به عنوان محیط‌های متناظر (Bounded Contexts) مستقل پیاده‌سازی شوند.

هر ماژول در درون خود از معماری پاک پیروی می‌کند:

```text
Modules

AssetManagement

AssetManagement.Domain

AssetManagement.Application

AssetManagement.Infrastructure

AssetManagement.Presentation
```

همین ساختار باید برای تمامی ماژول‌های کسب‌وکار دنبال شود.

---

## میزبان (Host)

```text
Host

MachineryManager.Server

MachineryManager.Client
```

لایه Host برنامه را ترکیب کرده و تزریق وابستگی، میان‌افزارها (Middleware) و راه‌اندازی برنامه (Startup) را پیکربندی می‌کند.

---

# ۶. جهت وابستگی (Dependency Direction)

وابستگی‌ها باید همواره به سمت داخل اشاره کنند:

```text
Presentation (ارائه)

↓

Application (کاربرد)

↓

Domain (دامنه)

↓

BuildingBlocks (بلاک‌های ساختمانی)
```

لایه زیرساخت (Infrastructure) از لایه‌های بالادستی پشتیبانی می‌کند اما نباید منطق کسب‌وکار وارد آن شود.

---

# ۷. بلاک‌های ساختمانی (BuildingBlocks)

لایه BuildingBlocks شامل کامپوننت‌های قابل استفاده مجدد در سراسر راهکار است و شامل موارد زیر می‌باشد:

- SharedKernel
- Contracts
- Abstractions
- UI Shared Components

بلاک‌های ساختمانی هرگز نباید به هیچ ماژول کسب‌وکاری وابسته باشند.

---

# ۸. لایه دامنه (Domain Layer)

لایه دامنه شامل موارد زیر است:

- موجودیت‌ها (Entities)
- اشیاء مقداری (Value Objects)
- سنگدانه / تجمع‌ها (Aggregates)
- سرویس‌های دامنه (Domain Services)
- رویدادهای دامنه (Domain Events)
- قوانین کسب‌وکار (Business Rules)

لایه دامنه نباید شامل هیچ کد زیرساختی باشد.

---

# ۹. لایه کاربرد (Application Layer)

لایه کاربرد شامل موارد زیر است:

- موارد کاربری (Use Cases)
- دستورات (Commands)
- پرس‌وجوها (Queries)
- اعتبارسنج‌ها (Validators)
- اشیاء انتقال داده (DTOs)
- رابط‌ها (Interfaces)
- نگاشت‌ها (Mapping)

گردش‌کارهای کسب‌وکار متعلق به این لایه هستند.

---

# ۱۰. لایه زیرساخت (Infrastructure Layer)

لایه زیرساخت شامل پیاده‌سازی‌های فنی است.

مثال‌ها:

- Entity Framework Core
- مخازن داده (Repositories)
- سرویس‌های خارجی (External Services)
- ذخیره‌سازی فایل (File Storage)
- ثبت رویدادها (Logging)
- کش‌سازی (Caching)

زیرساخت باید انتزاع‌های تعریف‌شده توسط لایه‌های بالادستی را پیاده‌سازی کند.

---

# ۱۱. لایه ارائه (Presentation Layer)

لایه ارائه شامل موارد زیر است:

- رابط کاربری Blazor
- کامپوننت‌ها
- صفحات
- مدل‌های نمایشی (View Models)

لایه ارائه نباید شامل قوانین کسب‌وکار باشد.

---

# ۱۲. پروژه‌های آزمون (Test Projects)

پروژه‌های آزمون باید نظیر پروژه‌های اصلی تولید باشند:

```text
tests

SharedKernel.Tests

AssetManagement.Tests

Maintenance.Tests

Inventory.Tests

Fleet.Tests

Procurement.Tests

Workshop.Tests

Reporting.Tests

Identity.Tests
```

---

# ۱۳. اصول نام‌گذاری

پروژه‌ها باید:

- از PascalCase استفاده کنند؛
- با فضای نام‌ها (Namespaces) مطابقت داشته باشند؛
- منعکس‌کننده مسئولیت‌ها باشند؛
- از نام‌های مبهم اجتناب کنند.

---

# ۱۴. مقیاس‌پذیری

ساختار راهکار به‌گونه‌ای طراحی شده است که از توسعه آتی بدون نیاز به تغییرات ساختاری عمده پشتیبانی کند.

ماژول‌های جدید باید از طریق پروژه‌ها یا Bounded Contextهای جدید اضافه شوند نه از طریق تغییر کامپوننت‌های نامرتبط.

هر Bounded Context باید به عنوان یک ماژول مستقل پیاده‌سازی شود.

ماژول‌ها تنها از طریق قراردادها (Contracts) و مرزهای لایه کاربرد با یکدیگر ارتباط برقرار می‌کنند.

استخراج آتی به سرویس‌های مستقل نباید نیازمند تجدید نظر ساختاری در معماری باشد.
