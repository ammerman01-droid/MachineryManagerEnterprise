# هدف (Purpose)

این سند، استراتژی رسمی لاگ‌گیری را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

یک استراتژی منسجم لاگ‌گیری موارد زیر را بهبود می‌بخشد:

- پایش و مانیتورینگ (Monitoring)
- امور تشخیصی و دیاگنوستیک (Diagnostics)
- پشتیبانی محیط عملیاتی (Production Support)
- بررسی و ریشه‌یابی رخدادها (Incident Investigation)
- ممیزی امنیت (Security Auditing)

لاگ‌گیری باید قابلیت دید عملیاتی را بدون افشای اطلاعات حساس فراهم سازد.

---

# اهداف (Objectives)

سیستم لاگ‌گیری باید:

- لاگ‌های ساختاریافته (Structured logs) تولید کند.
- از تجمیع متمرکز لاگ‌ها پشتیبانی نماید.
- نویز و داده‌های زائد را به حداقل برساند.
- زمینه و بافت تشخیصی را حفظ کند.
- از اطلاعات محرمانه محافظت نماید.

---

# اصول لاگ‌گیری (Logging Principles)

لاگ‌ها باید به سه پرسش اساسی پاسخ دهند:

1. چه چیزی رخ داد؟ (?What happened)
2. چه زمانی رخ داد؟ (?When did it happen)
3. چرا رخ داد؟ (?Why did it happen)

هر مدخل لاگ باید اطلاعات عملیاتی مفیدی ارائه دهد.

---

# لاگ‌گیری ساختاریافته (Structured Logging)

این راهکار باید از لاگ‌گیری ساختاریافته استفاده کند.

نمونه:

```csharp
logger.LogInformation(
    "Machine {MachineId} created by {UserId}",
    machineId,
    userId);
```

از الحاق رشته‌ها (String concatenation) پرهیز کنید.

نادرست:

```csharp
logger.LogInformation(
    "Machine " + machineId + " created");
```

# سطوح لاگ (Log Levels)

| سطح | کاربرد |
|---|---|
| Trace | جریان دقیق اجرای برنامه |
| Debug | عیب‌یابی و دیاگنوستیک زمان توسعه |
| Information | عملیات عادی تجاری |
| Warning | شرایط غیرعادی اما قابل بازیابی |
| Error | شکست در عملیات |
| Critical | ناپایداری کلی برنامه |

---

# لاگ‌های اطلاعاتی (Information Logs)

لاگ‌های اطلاعاتی باید موارد زیر را ثبت کنند:

- عملیات تجاری موفق
- رخدادهای مهم چرخه حیات سیستم
- اقدامات کاربران
- کارهای پس‌زمینه (Background jobs)

لاگ‌های اطلاعاتی نباید بیش از حد طولانی و پرحجم شوند.

---

# لاگ‌های هشدار (Warning Logs)

هشدارها نشان‌دهنده موقعیت‌های غیرعادی اما قابل بازیابی هستند.

نمونه‌ها:

- انجام تلاش مجدد (Retry)
- فقدان پیکربندی اختیاری
- پاسخ کند
- نزدیک شدن یک قید تجاری به حد آستانه

---

# لاگ‌های خطا (Error Logs)

خطاها نشان‌دهنده شکست عملیات هستند.

هر لاگ خطا باید شامل موارد زیر باشد:

- استثنا (Exception)
- شناسه همبستگی (Correlation Id)
- عملیات مربوطه (Operation)
- زمینه و کانتکست (Context)

---

# لاگ‌های بحرانی (Critical Logs)

لاگ‌های بحرانی نشان می‌دهند که برنامه ممکن است از دسترس خارج شود.

نمونه‌ها:

- عدم دسترسی به پایگاه داده
- شکست در راه‌اندازی برنامه (Startup failure)
- مخدوش شدن داده‌ها
- استثنای کشنده مدیریت‌نشده

---

# اطلاعات حساس (Sensitive Information)

هرگز موارد زیر را در لاگ ثبت نکنید:

- گذرواژه‌ها
- توکن‌های دسترسی (Access Tokens)
- توکن‌های نوسازی (Refresh Tokens)
- کلیدهای سری و اسرار (Secrets)
- رشته‌های اتصال (Connection Strings)
- شماره‌های شناسایی شخصی
- اطلاعات پرداخت

---

# شناسه همبستگی (Correlation ID)

هر درخواست باید دارای یک شناسه همبستگی (Correlation Id) باشد.

شناسه همبستگی باید در هر مدخل لاگ مرتبط با آن درخواست ظاهر شود.

این امر قابلیت ردیابی سرتاسری درخواست‌ها را امکان‌پذیر می‌سازد.

---

# لاگ‌گیری استثناها (Exception Logging)

استثناهای غیرمنتظره همواره باید شامل موارد زیر باشند:

- نوع استثنا
- پیام خطا
- ردیابی پشته (Stack trace)
- استثنای داخلی (Inner exception)
- شناسه همبستگی

---

# لاگ‌گیری کارایی و عملکرد (Performance Logging)

عملیات طولانی‌مدت باید مدت زمان اجرا را ثبت کنند.

نمونه:

```text
GenerateMonthlyReport completed in 2143 ms.
```

---

# لاگ‌گیری تجاری (Business Logging)

رخدادهای تجاری می‌توانند مستقل از لاگ‌های فنی ثبت شوند.

نمونه‌ها:

- ماشین ثبت شد (Machine Registered)
- برنامه نگهداری زمان‌بندی شد (Maintenance Scheduled)
- کاربر وارد سیستم شد (User Logged In)

این رخدادها از امور ممیزی و گزارش‌گیری پشتیبانی می‌کنند.

---

# لاگ‌گیری ممیزی (Audit Logging)

اقدامات حساس از نظر امنیتی همواره باید لاگ شوند.

نمونه‌ها:

- احراز هویت (Authentication)
- شکست در مجوزیابی (Authorization failure)
- تغییرات نقش‌ها
- تغییرات پیکربندی
- مدیریت کاربران

لاگ‌های ممیزی هرگز نباید به صورت دستی حذف شوند.

---

# نگهداری لاگ‌ها (Log Retention)

خط‌مشی‌های نگهداری باید قابل پیکربندی باشند.

پیش‌فرض‌های پیشنهادی:

| نوع لاگ | مدت نگهداری |
|---|---|
| Trace | کوتاه‌مدت |
| Debug | کوتاه‌مدت |
| Information | میان‌مدت |
| Warning | میان‌مدت |
| Error | بلندمدت |
| Audit | بلندمدت |

---

# مقاصد لاگ (Log Destinations)

زیرساخت لاگ‌گیری باید از چندین مقصد از طریق پشته مشاهده‌پذیری تصویب‌شده (ADR-0033) پشتیبانی کند:

- کنسول (Console - زمان توسعه)
- فایل (File - پشتیبان محلی)
- Grafana Tempo (ردیابی‌های توزیع‌شده، از طریق OpenTelemetry)
- Prometheus (معیارها و متریک‌ها)
- Grafana (داشبوردها / بصری‌سازی)

انتزاع لاگ‌گیری باید مستقل از هر ارائه‌دهنده خاصی باقی بماند. ابزارهای Elasticsearch، Seq و Azure Monitor استانداردهای تصویب‌شده پلتفرم نیستند و نباید بدون ارزیابی فناوری و ADR جدید وارد شوند.

---

# پشته فناوری تصویب‌شده (Approved Technology Stack)

رسمی‌شده توسط ADR-0009 و ADR-0033:

| مسئولیت | فناوری تصویب‌شده |
|---|---|
| انتزاع لاگ‌گیری | Microsoft.Extensions.Logging |
| ارائه‌دهنده لاگ‌گیری ساختاریافته | Serilog |
| استاندارد تله‌متری | OpenTelemetry |
| بک‌اند متریک‌ها | Prometheus |
| داشبوردها | Grafana |
| بک‌اند ردیابی توزیع‌شده | Grafana Tempo |

ماژول‌های تجاری هرگز نباید مستقیماً به SDKهای Serilog، OpenTelemetry، Prometheus یا Grafana Tempo وابسته باشند؛ این موارد باید در لایه زیرساخت (Infrastructure) ایزوله بمانند و تنها از طریق انتزاع‌های `Microsoft.Extensions.Logging` مصرف شوند.
