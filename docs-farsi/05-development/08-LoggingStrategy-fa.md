# ۱. هدف

این سند استراتژی رسمی ثبت رویدادها (لاگینگ) را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

یک استراتژی یکنواخت و سازگار در ثبت لاگ موارد زیر را بهبود می‌بخشد:

- پایش و مانیتورینگ (Monitoring)
- عیب‌یابی (Diagnostics)
- پشتیبانی عملیاتی و تولید (Production Support)
- بررسی و پیگیری حوادث (Incident Investigation)
- حسابرسی امنیتی (Security Auditing)

ثبت لاگ باید دید عملیاتی بدون افشای اطلاعات حساس فراهم سازد.

---

# ۲. اهداف

سیستم لاگینگ باید:

- لاگ‌های ساختاریافته (Structured logs) تولید کند.
- از تجمیع متمرکز لاگ‌ها پشتیبانی نماید.
- نویز و پیام‌های اضافی را به حداقل برساند.
- زمینه عیب‌یابی (Diagnostic context) را حفظ کند.
- از اطلاعات محرمانه محافظت نماید.

---

# ۳. اصول ثبت لاگ

لاگ‌ها باید به ۳ سوال پاسخ دهند:

۱. چه اتفاقی افتاد؟ (What happened?)
۲. چه زمانی اتفاق افتاد؟ (When did it happen?)
۳. چرا اتفاق افتاد؟ (Why did it happen?)

هر درایه لاگ (Log entry) باید اطلاعات عملیاتی مفیدی ارائه دهد.

---

# ۴. ثبت لاگ ساختاریافته (Structured Logging)

راهکار باید از لاگینگ ساختاریافته استفاده کند.

مثال:

```csharp
logger.LogInformation(
    "Machine {MachineId} created by {UserId}",
    machineId,
    userId);
```

از الحاق رشته‌ها (String concatenation) اجتناب کنید.

نادرست:

```csharp
logger.LogInformation(
    "Machine " + machineId + " created");
```

---

# ۵. سطوح لاگ (Log Levels)

| سطح | کاربرد |
|---------|--------------------------------|
| Trace | جریان اجرای باجزئیات بالا |
| Debug | عیب‌یابی زمان توسعه |
| Information | عملیات معمولی کسب‌وکار |
| Warning | شرایط غیرعادی اما قابل بازیابی |
| Error | عملیات با شکست مواجه شد |
| Critical | ناپایداری کلی برنامه |

---

# ۶. لاگ‌های اطلاعاتی (Information Logs)

لاگ‌های اطلاعاتی باید موارد زیر را ثبت کنند:

- عملیات موفقیت‌آمیز کسب‌وکار
- رویدادهای مهم چرخه حیات
- اقدامات کاربر
- کارهای پس‌زمینه (Background jobs)

لاگ‌های اطلاعاتی نباید بیش از حد پرحجم و شلوغ شوند.

---

# ۷. لاگ‌های هشدار (Warning Logs)

هشدارها نشان‌دهنده شرایط غیرعادی اما قابل بازیابی هستند.

مثال‌ها:

- انجام تلاش مجدد (Retry)
- پیکربندی اختیاری مفقودشده
- پاسخ کند (Slow response)
- نزدیک شدن محدودیت‌های کسب‌وکار به آستانه‌ها

---

# ۸. لاگ‌های خطا (Error Logs)

خطاها نشان‌دهنده شکست عملیات هستند.

هر لاگ خطا باید شامل موارد زیر باشد:

- استثنا (Exception)
- شناسه همبستگی (Correlation Id)
- نوع عملیات (Operation)
- زمینه و متن خروجی (Context)

---

# ۹. لاگ‌های بحرانی (Critical Logs)

لاگ‌های بحرانی نشان‌دهنده احتمال از دسترس خارج شدن برنامه هستند.

مثال‌ها:

- عدم دسترسی به دیتابیس
- شکست در راه‌اندازی (Startup failure)
- فساد داده‌ها (Data corruption)
- استثنای کشنده‌ی مدیریت‌نشده (Unhandled fatal exception)

---

# ۱۰. اطلاعات حساس (Sensitive Information)

هرگز موارد زیر را لاگ نکنید:

- کلمه‌های عبور (Passwords)
- توکن‌های دسترسی (Access Tokens)
- توکن‌های بازنشانی (Refresh Tokens)
- کلیدها و اسرار (Secrets)
- رشته‌های اتصال (Connection Strings)
- کدهای ملی و شناسه افراد (Personal Identification Numbers)
- اطلاعات پرداخت (Payment Information)

---

# ۱۱. شناسه همبستگی (Correlation ID)

هر درخواست باید دارای یک شناسه همبستگی (Correlation Id) باشد.

شناسه همبستگی باید در تمامی لاگ‌های مرتبط ظاهر شود.

این امر قابلیت ردیابی سرتاسری (End-to-end tracing) درخواست‌ها را امکان‌پذیر می‌سازد.

---

# ۱۲. ثبت استثناها (Exception Logging)

استثناهای غیرمنتظره همواره باید شامل موارد زیر باشند:

- نوع استثنا
- پیام
- ردپای پشته (Stack trace)
- استثنای داخلی (Inner exception)
- شناسه همبستگی (Correlation Id)

---

# ۱۳. ثبت لاگ کارایی (Performance Logging)

عملیات‌های زمان‌بر باید مدت زمان اجرا را ثبت کنند.

مثال:

```text
GenerateMonthlyReport completed in 2143 ms.
```

---

# ۱۴. لاگ‌های کسب‌وکار (Business Logging)

رویدادهای کسب‌وکار می‌توانند به صورت مستقل از لاگ‌های فنی ثبت شوند.

مثال‌ها:

- ثبت ماشین جدید
- زمان‌بندی نت
- ورود کاربر به سیستم

این رویدادها از حسابرسی و گزارش‌گیری پشتیبانی می‌کنند.

---

# ۱۵. لاگ‌های حسابرسی (Audit Logging)

اقدامات حساس امنیتی همواره باید لاگ شوند.

مثال‌ها:

- احراز هویت (Authentication)
- عدم تایید دسترسی (Authorization failure)
- تغییرات نقش‌ها
- تغییرات پیکربندی
- مدیریت کاربران

لاگ‌های حسابرسی هرگز نباید به صورت دستی پاک شوند.

---

# ۱۶. نگهداری لاگ‌ها (Log Retention)

خط‌مشی‌های نگهداری باید قابل پیکربندی باشند.

پیش‌فرض‌های پیشنهادی:

| نوع لاگ | مدت نگهداری |
|-----------|-----------|
| Trace | کوتاه‌مدت |
| Debug | کوتاه‌مدت |
| Information | میان‌مدت |
| Warning | میان‌مدت |
| Error | بلندمدت |
| Audit | بلندمدت |

---

# ۱۷. مقاصد لاگ‌ها (Log Destinations)

زیرساخت لاگینگ باید از مقاصد چندگانه پشتیبانی کند.

مثال‌ها:

- Console
- File
- Seq
- OpenTelemetry
- Elasticsearch
- Azure Monitor

انتزاع لاگینگ باید مستقل از هر ارائه‌دهنده خاص باقی بماند.

---

# ۱۸. خط‌مشی متن‌باز (Open Source Policy)

تنها ارائه‌دهندگان لاگینگ متن‌باز تاییدشده می‌توانند استفاده شوند.

انتخاب فناوری نیازمند موارد زیر است:

- ارزیابی فناوری (TE)
- سند تصویب‌شده ADR

---
