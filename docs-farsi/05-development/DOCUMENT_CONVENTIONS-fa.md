# ۱. هدف

این سند استاندارد رسمی مستندسازی را برای پروژه **MachineryManagerEnterprise** تعریف می‌کند.

هر سندی که در این مخزن ایجاد می‌شود باید مطابق با قوانین توصیف‌شده در این استاندارد باشد.

هدف این است که اطمینان حاصل شود مستندات پروژه به صورت زیر باقی می‌مانند:

- سازگار و یکنواخت (Consistent)
- قابل ردیابی (Traceable)
- قابل نگهداری (Maintainable)
- قابل بازبینی (Reviewable)
- در سطح سازمانی (Enterprise-grade)

---

# ۲. محدوده

این استاندارد شامل تمامی اسناد موجود در پوشه `docs/` می‌شود، از جمله:

- اسناد چشم‌انداز (Vision Documents)
- اسناد معماری (Architecture Documents)
- اسناد دامنه (Domain Documents)
- مشخصات ماژول‌ها (Module Specifications)
- ارزیابی‌های فناوری (Technology Evaluations - TE)
- سوابق تصمیمات معماری (Architecture Decision Records - ADR)
- اثبات‌های مفهوم (Proof of Concepts - POC)
- مستندات API
- مستندات انتشار (Release Documentation)

# ۵. قرارداد نام‌گذاری فایل‌ها

هر سند باید از الگوی نام‌گذاری زیر پیروی کند:

```text
PREFIX-NUMBER-ShortName.md
```

مثال‌ها:

```text
ADR-0008-Use-MudBlazor.md

TE-0005-PersianDatePickerSelection.md

POC-0001-JalaliMudDatePicker.md
```

قوانین:

- استفاده از PascalCase
- بدون فاصله (Space)
- بدون کاراکترهای خاص
- نام‌های مختصر و صریح
- نام‌فایل‌های ثابت و بدون تغییر مداوم

# ۷. استاندارد نسخه‌گذاری

مستندسازی از نسخه‌گذاری معنایی (Semantic Versioning) پیروی می‌کند:

```text
Major.Minor.Patch
```

مثال‌ها:

| نسخه | معنی |
|----------|---------|
| 1.0.0 | انتشار اولیه |
| 1.1.0 | افزودن محتوای جدید |
| 1.2.0 | بهبودهای قابل توجه |
| 2.0.0 | بازسازی و تجدید ساختار عمده |

- انگلیسی / فارسی (بر اساس ساختار چندزبانه پروژه)

- انگلیسی

- صرفاً انگلیسی

---

## مارک‌داون (Markdown)

مستندسازی باید از موارد زیر استفاده کند:

- عناوین ATX (`#`)
- GitHub Markdown
- جداول Markdown
- لینک‌های نسبی (Relative links)
- بلوک‌های کد دارای زبان (Fenced code blocks)

از کد HTML اجتناب کنید مگر در موارد کاملاً ضروری.

# ۱۰. ارجاعات متقابل (Cross References)

در صورت لزوم، اسناد باید به مستندات مرتبط ارجاع دهند.

مثال:

```markdown
---

# خلاصه تصمیمات

- ✔ معماری پاک (Clean Architecture)
- ✔ سازگاری با .NET 10
- ✔ رعایت استانداردها
- ✔ خنثی بودن نسبت به ابر (Cloud Neutrality)
- ✔ آمادگی برای هوش مصنوعی
- ✔ قابلیت نگهداری بلندمدت

# اسناد مرتبط

- ADR-0002
- TE-0004
- POC-0001
```

به جای نام فایل‌ها باید از شناسه اسناد (Document IDs) استفاده شود.

# ۱۲. چرخه حیات مستندسازی

تمامی تصمیمات فنی مهم باید از چرخه حیات یکسانی پیروی کنند:

```text
نیازمندی کسب‌وکار (Business Requirement)
        │
        ▼
ارزیابی فناوری (TE)
        │
        ▼
اثبات مفهوم (POC)   (اختیاری)
        │
        ▼
سند تصمیم‌گیری معماری (ADR)
        │
        ▼
پیاده‌سازی (Implementation)
```

---

## ارزیابی فناوری (Technology Evaluation)

ارزیابی‌های فناوری گزینه‌های فنی موجود را مقایسه می‌کنند.

یک ارزیابی فناوری **هرگز نشان‌دهنده تصمیم نهایی معماری نیست**.

---

## اثبات مفهوم (Proof of Concept)

اثبات مفهوم تنها زمان وجود عدم قطعیت فنی مورد نیاز است.

مثال‌های متداول:

- اعتبارپذیری کارایی (Performance validation)
- ارزیابی زیرساخت
- امکان‌پذیری معماری
- ریسک‌های یکپارچه‌سازی

---

## سند تصمیم‌گیری معماری (Architecture Decision Record)

یک ADR تصمیم نهایی تصویب‌شده را مستند می‌سازد.

هر ADR باید به موارد زیر ارجاع دهد:

- ارزیابی فناوری مرتبط (TE)
- اثبات مفهوم مرتبط (POC - در صورت وجود)

سند ADR به مرجع معتبر تصمیمات معماری تبدیل می‌شود.

---

## پیاده‌سازی

پیاده‌سازی تنها پس از تصویب ADR مربوطه آغاز خواهد شد.

کد محیط تولید باید همواره از تصمیمات معماری مستندشده پیروی کند.

---

# ۱۳. اصول مستندسازی

هر سند پروژه باید دارای ویژگی‌های زیر باشد:

- سازگار و یکنواخت (Consistent)
- مبتنی بر شواهد (Evidence-based)
- قابل ردیابی (Traceable)
- قابل بازبینی (Reviewable)
- قابل نگهداری (Maintainable)
- بازتولیدپذیر (Reproducible)

تصمیمات معماری مستندنشده به عنوان بخشی از معماری رسمی پروژه تلقی نمی‌شوند.
