# هدف (Purpose)

این سند، قواعد وابستگی را برای راهکار **MachineryManagerEnterprise** تعریف می‌نماید.

مدیریت صحیح وابستگی‌ها یکی از مهم‌ترین محدودیت‌های معماری در این پروژه به شمار می‌رود.

هر پروژه باید از این قواعد پیروی کند.

---

# اصل معماری (Architectural Principle)

این راهکار از **وارونگی وابستگی (Dependency Inversion)** و **معماری تمیز (Clean Architecture)** پیروی می‌کند.

وابستگی‌ها همواره به سمت هسته تجاری (Business Core) جهت‌گیری دارند.

ماژول‌های سطح بالا هرگز به جزئیات پیاده‌سازی وابسته نیستند.

---

# جهت وابستگی (Dependency Direction)

جهت مجاز وابستگی به صورت زیر است:

```text
لایه ارائه (Presentation)
        │
        ▼
لایه کاربرد (Application)
        │
        ▼
لایه دامنه (Domain)
        │
        ▼
هسته مشترک (SharedKernel)
```

لایه زیرساخت (Infrastructure) پیاده‌سازی‌ها را فراهم می‌کند اما خود به انتزاع‌های تعریف‌شده توسط لایه‌های کاربرد یا دامنه وابسته است.

---

# وابستگی‌های مجاز (Allowed Dependencies)

| پروژه | مجاز به ارجاع به |
|---|---|
| SharedKernel | — |
| Domain | SharedKernel |
| Application | Domain, SharedKernel |
| Infrastructure | Application, Domain, SharedKernel |
| Web (Presentation) | Application |

---

# وابستگی‌های ممنوع (Forbidden Dependencies)

وابستگی‌های زیر اکیداً ممنوع هستند:

## دامنه (Domain)

لایه دامنه هرگز نباید به موارد زیر ارجاع دهد:

- زیرساخت (Infrastructure)
- لایه ارائه (Presentation)
- فریم‌ورک‌های رابط کاربری (UI Frameworks)
- فریم‌ورک Entity Framework
- فریم‌ورک‌های لاگ‌گیری (Logging Frameworks)
- سرویس‌های خارجی (External Services)

---

## هسته مشترک (SharedKernel)

لایه SharedKernel هرگز نباید به هیچ پروژه دیگری ارجاع دهد.

این لایه پایین‌ترین لایه در معماری است.

---

## کاربرد (Application)

لایه کاربرد هرگز نباید به موارد زیر وابسته باشد:

- پیاده‌سازی‌های زیرساخت
- مؤلفه‌های رابط کاربری (UI Components)
- ارائه‌دهندگان پایگاه داده (Database Providers)

لایه کاربرد تنها به انتزاع‌ها (Abstractions) وابسته است.

---

## ارائه (Presentation)

لایه ارائه هرگز نباید شامل موارد زیر باشد:

- قواعد تجاری (Business Rules)
- منطق پایداری داده‌ها (Persistence Logic)
- پیاده‌سازی‌های مخزن (Repository Implementations)

---

# زیرساخت (Infrastructure)

لایه زیرساخت می‌تواند اینترفیس‌های تعریف‌شده در بخش‌های زیر را پیاده‌سازی کند:

- کاربرد (Application)
- دامنه (Domain)

لایه زیرساخت نباید قواعد تجاری تعریف کند.

---

# گراف وابستگی (Dependency Graph)

```text
                 Web
                  │
                  ▼
             Application
                  │
                  ▼
                Domain
                  │
                  ▼
             SharedKernel

Infrastructure
      │
      └──────────────►
   Application / Domain
```

زیرساخت از هسته پشتیبانی می‌کند اما هرگز مرکز معماری نیست.

---

# وابستگی‌های چرخه‌ای (Circular Dependencies)

ارجاعات چرخه‌ای بین پروژه‌ها ممنوع است.

نمونه (نامعتبر):

```text
Application

↓

Infrastructure

↓

Application
```

هر گراف وابستگی باید بدون چرخه (Acyclic) باقی بماند.

---

# تزریق وابستگی (Dependency Injection)

پیاده‌سازی‌های عینی باید از طریق تزریق وابستگی ثبت شوند.

لایه Application اینترفیس‌ها را تعریف می‌کند.

لایه Infrastructure پیاده‌سازی‌ها را ارائه می‌دهد.

لایه Presentation انتزاع‌ها را مصرف می‌کند.

---

# کتابخانه‌های شخص ثالث (Third-Party Libraries)

کتابخانه‌های شخص ثالث تا جای ممکن باید ایزوله شوند.

نمونه:

```text
Infrastructure

Entity Framework

Serilog

FluentValidation

Redis
```

لایه‌های تجاری باید از کتابخانه‌های پیاده‌سازی بی‌خبر و مستقل باقی بمانند.

---

# وابستگی‌های زمان کامپایل (Compile-Time Dependencies)

وابستگی‌های زمان کامپایل باید به حداقل برسند.

پروژه‌ها باید تنها انتزاع‌های مورد نیاز مصرف‌کنندگان را افشا نمایند.

---

# وابستگی‌های زمان اجرا (Runtime Dependencies)

سیم‌کشی و اتصال زمان اجرا باید از طریق موارد زیر انجام شود:

- تزریق وابستگی (Dependency Injection)
- پیکربندی (Configuration)
- ریشه ترکیب (Composition Root)

هرگز نباید ساخت مستقیم اشیاء در درون منطق تجاری انجام شود.

---

# توسعه‌های آینده (Future Expansion)

با معرفی زمینه‌های مرزبندی‌شده جدید، همان قواعد وابستگی اعمال خواهد شد.

هر ماژول باید به صورت مستقل قابل نگهداری باقی بماند.

---
