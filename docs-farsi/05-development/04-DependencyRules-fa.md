# ۱. هدف

این سند قوانین وابستگی بین لایه‌ها و پروژه‌ها را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

مدیریت صحیح وابستگی‌ها یکی از مهم‌ترین محدودیت‌های معماری پروژه است.

هر پروژه باید با این قوانین انطباق داشته باشد.

---

# ۲. اصل معماری

این راهکار از **وارونگی وابستگی (Dependency Inversion)** و **معماری پاک (Clean Architecture)** پیروی می‌کند.

وابستگی‌ها همواره به سمت هسته کسب‌وکار اشاره می‌کنند.

ماژول‌های سطح بالا هرگز به جزئیات پیاده‌سازی وابسته نیستند.

---

# ۳. جهت وابستگی (Dependency Direction)

جهت مجاز برای وابستگی عبارت است از:

```text
Presentation (ارائه)
        │
        ▼
Application (کاربرد)
        │
        ▼
Domain (دامنه)
        │
        ▼
SharedKernel (هسته مشترک)
```

زیرساخت (Infrastructure) پیاده‌سازی‌ها را ارائه می‌دهد اما خود به انتزاع‌های تعریف‌شده توسط لایه‌های کاربرد یا دامنه وابسته است.

---

# ۴. وابستگی‌های مجاز (Allowed Dependencies)

| پروژه | مجاز به ارجاع به |
|----------|---------------|
| SharedKernel | — |
| Domain | SharedKernel |
| Application | Domain, SharedKernel |
| Infrastructure | Application, Domain, SharedKernel |
| Web (Presentation) | Application |

---

# ۵. وابستگی‌های ممنوع (Forbidden Dependencies)

وابستگی‌های زیر به صورت اکید ممنوع هستند:

## دامنه (Domain)

دامنه هرگز نباید به موارد زیر ارجاع دهد:

- Infrastructure
- Presentation
- فریم‌ورک‌های UI
- Entity Framework
- فریم‌ورک‌های ثبت رویداد (Logging)
- سرویس‌های خارجی

---

## هسته مشترک (SharedKernel)

SharedKernel هرگز نباید به هیچ پروژه دیگری ارجاع دهد.

این لایه پایین‌ترین لایه معماری است.

---

## کاربرد (Application)

لایه کاربرد هرگز نباید به موارد زیر وابسته باشد:

- پیاده‌سازی‌های زیرساختی
- کامپوننت‌های UI
- ارائه‌دهندگان دیتابیس (Database Providers)

لایه کاربرد تنها به انتزاع‌ها وابسته است.

---

## ارائه (Presentation)

لایه ارائه هرگز نباید شامل موارد زیر باشد:

- قوانین کسب‌وکار
- منطق ماندگاری داده (Persistence Logic)
- پیاده‌سازی‌های مخازن داده (Repository)

---

# ۶. زیرساخت (Infrastructure)

زیرساخت می‌تواند رابط‌های (Interfaces) تعریف‌شده در لایه‌های زیر را پیاده‌سازی کند:

- Application
- Domain

لایه زیرساخت نباید قوانین کسب‌وکار را تعریف کند.

---

# ۷. گراف وابستگی (Dependency Graph)

```text
                Web (ارائه)
                  │
                  ▼
           Application (کاربرد)
                  │
                  ▼
              Domain (دامنه)
                  │
                  ▼
           SharedKernel (هسته مشترک)

Infrastructure (زیرساخت)
       │
       └──────────────►
  Application / Domain
```

زیرساخت از هسته پشتیبانی می‌کند اما هرگز مرکز معماری نیست.

---

# ۸. وابستگی‌های چرخه ای (Circular Dependencies)

ارجاعات چرخه‌ای بین پروژه‌ها ممنوع است.

مثال (نامعتبر):

```text
Application

↓

Infrastructure

↓

Application
```

گراف وابستگی باید همواره بدون چرخه (Acyclic) باقی بماند.

---

# ۹. تزریق وابستگی (Dependency Injection)

پیاده‌سازی‌های واقعی باید از طریق تزریق وابستگی (DI) ثبت شوند.

لایه Application رابط‌ها را تعریف می‌کند.

لایه Infrastructure پیاده‌سازی‌ها را ارائه می‌دهد.

لایه Presentation از انتزاع‌ها استفاده می‌کند.

---

# ۱۰. کتابخانه‌های شخص ثالث (Third-Party Libraries)

کتابخانه‌های شخص ثالث تا حد امکان باید ایزوله شوند.

مثال:

```text
Infrastructure

Entity Framework

Serilog

FluentValidation

Redis
```

لایه‌های کسب‌وکار باید از کتابخانه‌های پیاده‌سازی ناآگاه بمانند.

---

# ۱۱. وابستگی‌های زمان زمان کامپایل (Compile-Time Dependencies)

وابستگی‌های زمان کامپایل باید به حداقل برسند.

پروژه‌ها تنها باید انتزاع‌های مورد نیاز مصرف‌کنندگان را افشا کنند.

---

# ۱۲. وابستگی‌های زمان اجرا (Runtime Dependencies)

سیم‌کشی زمان اجرا باید از طریق موارد زیر انجام شود:

- تزریق وابستگی (DI)
- پیکربندی
- ریشه ترکیب (Composition Root)

هرگز نباید ساخت مستقیم اشیاء درون منطق کسب‌وکار انجام شود.

---

# ۱۳. توسعه آتی (Future Expansion)

با ورود Bounded Contextهای جدید، همین قوانین وابستگی اعمال خواهد شد.

هر ماژول باید به صورت مستقل قابل نگهداری باقی بماند.

---

# ۱۴. استثناهای معماری

هرگونه استثنا در این قوانین نیازمند سند تصویب‌شده تصمیم معماری (ADR) است.

استثناهای مستندنشده مجاز نیستند.
