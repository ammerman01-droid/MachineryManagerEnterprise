# هدف (Purpose)

این سند، استراتژی رسمی مدیریت خطا را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

یک استراتژی منسجم مدیریت خطا موارد زیر را بهبود می‌بخشد:

- قابلیت اطمینان (Reliability)
- قابلیت نگهداری (Maintainability)
- اشکال‌زدایی و عیب‌یابی (Debugging)
- تجربه کاربری (User Experience)
- پایش و مانیتورینگ عملیاتی (Operational Monitoring)

خطاها همواره باید قابل پیش‌بینی، قابل ردگیری و معنادار باشند.

---

# اهداف (Objectives)

این راهکار باید:

- خطاها را زودهنگام شناسایی کند.
- اطلاعات تشخیصی و دیاگنوستیک را حفظ نماید.
- از شکست‌های خاموش و پنهان جلوگیری کند.
- از ایجاد وضعیت ناسازگار در سیستم جلوگیری نماید.
- بازخورد معنادار به کاربران بازگرداند.
- لاگ‌های ساختاریافته برای عیب‌یابی تولید کند.

---

# دسته‌بندی خطاها (Error Classification)

خطاها به چهار دسته تقسیم می‌شوند:

| دسته | نمونه |
|---|---|
| خطاهای اعتبارسنجی (Validation Errors) | ورودی نامعتبر |
| خطاهای تجاری (Business Errors) | نقض قواعد تجاری |
| خطاهای زیرساختی (Infrastructure Errors) | عدم دسترسی به پایگاه داده |
| خطاهای غیرمنتظره (Unexpected Errors) | باگ برنامه‌نویسی |

هر دسته باید به شیوه متفاوتی مدیریت شود.

---

# خطاهای اعتبارسنجی (Validation Errors)

خطاهای اعتبارسنجی مورد انتظار هستند.

این خطاها باید:

- هرگز استثنا (Exception) پرتاب نکنند.
- به فراخوان‌کننده بازگردانده شوند.
- شامل پیام‌های اعتبارسنجی شفاف باشند.

اعتبارسنجی عمدتاً با استفاده از FluentValidation پیاده‌سازی خواهد شد.

---

# خطاهای تجاری (Business Errors)

نقض قواعد تجاری به منزله شکست سیستم نیست.

نمونه‌ها:

- ماشین قبلاً تخصیص یافته است
- شماره سریال تکراری
- انتقال نامعتبر گردش کار

خطاهای تجاری در موارد مناسب می‌توانند از استثناهای مختص دامنه استفاده کنند.

---

# خطاهای زیرساختی (Infrastructure Errors)

شکست‌های زیرساختی شامل موارد زیر است:

- اتصال پایگاه داده
- سیستم فایل
- رابط‌های برنامه‌نویسی خارجی (External APIs)
- خرابی‌های شبکه

زیرساخت هرگز نباید جزئیات پیاده‌سازی را به لایه‌های بالاتر افشا کند.

---

# خطاهای غیرمنتظره (Unexpected Errors)

خطاهای غیرمنتظره نشان‌دهنده نقص و باگ هستند.

نمونه‌ها:

- NullReferenceException
- InvalidOperationException
- اشتباهات برنامه‌نویسی

این خطاها باید همراه با اطلاعات تشخیصی کامل لاگ شوند.

---

# نحوه استفاده از استثناها (Exception Usage)

استثناها تنها باید برای شرایط استثنایی واقعی استفاده شوند.

از استثناها برای موارد زیر استفاده نکنید:

- اعتبارسنجی
- جریان عادی کنترل برنامه
- نتایج تجاری مورد انتظار

---

# پیام‌های استثنا (Exception Messages)

پیام‌ها باید:

- شکست را به روشنی توضیح دهند.
- از اطلاعات حساس پرهیز کنند.
- به عیب‌یابی کمک نمایند.

نمونه ضعیف:

```text
Something went wrong.
```

نمونه بهتر:

```text
Machine with Id '42' could not be found.
```

---

# استثناهای سفارشی (Custom Exceptions)

استثناهای سفارشی باید از کلاس زیر مشتق شوند:

```text
Exception
```

نمونه:

```text
MachineNotFoundException

LicenseExpiredException
```

هر استثنای سفارشی باید نمایانگر یک شکست مشخص و معین باشد.

---

# استثناهای داخلی (Inner Exceptions)

هنگام بسته‌بندی و پوشش دادن استثناها، همواره استثنای اصلی را حفظ کنید.

نمونه:

```csharp
throw new MachineSynchronizationException(
    "Synchronization failed.",
    ex);
```

---

# لاگ‌گیری (Logging)

هر استثنای غیرمنتظره باید لاگ شود.

لاگ‌گیری باید شامل موارد زیر باشد:

- برچسب زمان (Timestamp)
- سطح اهمیت (Severity)
- شناسه همبستگی (Correlation Id)
- نوع استثنا (Exception Type)
- پیام (Message)
- ردیابی پشته (Stack Trace)

داده‌های حساس هرگز نباید لاگ شوند.

---

# پیام‌های کاربر (User Messages)

کاربران باید پیام‌های دوستانه و قابل فهم دریافت کنند.

جزئیات داخلی استثناها هرگز نباید افشا شوند.

نمونه:

به جای:

```text
SqlException...
```

نمایش داده شود:

```text
An unexpected error occurred.
Please contact your administrator.
```

---

# مدیریت سراسری استثناها (Global Exception Handling)

استثناهای مدیریت‌نشده باید از طریق یک مدیریت‌کننده متمرکز (Centralized Handler) پردازش شوند.

مسئولیت‌ها:

- لاگ‌گیری
- تولید شناسه همبستگی (Correlation Id)
- پاسخ کاربرپسند
- قالب‌بندی منسجم و یکپارچه

---

# رابط کاربری Blazor (Blazor UI)

مؤلفه‌های Blazor باید:

- شکست‌های مورد انتظار را با ظرافت مدیریت کنند.
- اعلان‌های معنادار نمایش دهند.
- هرگز ردیابی پشته (Stack Traces) را افشا نکنند.

---

# خط‌مشی تلاش مجدد (Retry Policy)

تلاش‌های مجدد تنها باید برای شکست‌های گذرا (Transient Failures) استفاده شوند.

نمونه‌ها:

- اتمام مهلت زمانی HTTP (Timeout)
- مشکل موقت شبکه

تلاش‌های مجدد هرگز نباید به صورت کورکورانه اعمال شوند.

---

# شکست سریع (Fail Fast)

وضعیت نامعتبر برنامه باید بلافاصله با شکست روبرو شود (متوقف گردد).

شکست زودهنگام بسیار بهتر از ادامه کار با وضعیت آسیب‌دیده و مخدوش است.

---
