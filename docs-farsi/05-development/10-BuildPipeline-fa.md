# هدف (Purpose)

این سند، استراتژی خط لوله یکپارچه‌سازی مداوم (CI) و تحویل مداوم (CD) را برای راهکار **MachineryManagerEnterprise** تعریف می‌نماید.

هدف این است که اطمینان حاصل شود هر تغییر کد پیش از ادغام در شاخه‌های اصلی توسعه به صورت خودکار اعتبارسنجی می‌شود.

---

# اهداف (Objectives)

خط لوله باید:

- راهکار را به صورت خودکار بسازد (Build).
- آزمون‌های خودکار را اجرا نماید.
- قواعد معماری را اعتبارسنجی کند.
- مشکلات وابستگی را شناسایی نماید.
- از ادغام کدهای معیوب و شکسته جلوگیری کند.
- ساخت‌های بازتولیدپذیر (Reproducible builds) ایجاد نماید.

---

# پشته فناوری تصویب‌شده (Approved Technology Stack)

رسمی‌شده توسط ADR-0025 (معماری ساخت و استقرار):

| مسئولیت | فناوری تصویب‌شده |
|---|---|
| پلتفرم CI/CD | GitHub Actions |
| کانتینرسازی | Docker |
| ارکستراسیون چندسرویسی محلی | .NET Aspire |

**کوبرنتیز (Kubernetes) یک استاندارد پلتفرمی تصویب‌شده نیست.** در حال حاضر هیچ سند ADR کوبرنتیز را مجاز ندانسته است؛ معرفی آن نیازمند ارزیابی فناوری (TE) و ADR جدید است.

---

# اصول خط لوله (Pipeline Principles)

خط لوله ساخت باید دارای ویژگی‌های زیر باشد:

- خودکار (Automated)
- تکرارپذیر (Repeatable)
- قطعی و مشخص (Deterministic)
- سریع (Fast)
- شفاف (Transparent)

اعتبارسنجی دستی ساخت هرگز نباید الزامی باشد.

---

# استراتژی شاخه‌بندی (Branch Strategy)

خط لوله از استراتژی شاخه‌بندی Git پیروی می‌کند:

```text
main
    │
develop
    │
feature/*
```

شاخه‌های مختلف مراحل متفاوتی از خط لوله را اجرا می‌کنند.

---

# خط لوله شاخه ویژگی (Feature Branch Pipeline)

هر شاخه ویژگی (Feature Branch) باید موارد زیر را اجرا کند:

- بازیابی بسته‌ها (Restore packages)
- ساخت راهکار (Build solution)
- تحلیل ایستا (Static analysis)
- آزمون‌های واحد (Unit tests)
- آزمون‌های معماری (Architecture tests)

هیچ استقراری در این مرحله رخ نخواهد داد.

---

# خط لوله شاخه توسعه (Develop Branch Pipeline)

خط لوله شاخه Develop علاوه بر موارد فوق اقدامات زیر را انجام می‌دهد:

- آزمون‌های یکپارچه‌سازی (Integration tests)
- اعتبارسنجی بسته‌ها (Package validation)
- تولید مصنوعات ساخت (Artifact generation)

---

# خط لوله شاخه اصلی (Main Branch Pipeline)

خط لوله شاخه Main موارد زیر را اجرا می‌کند:

- ساخت کامل (Full build)
- اجرای کامل مجموعه آزمون‌های خودکار
- تولید مصنوعات انتشار (Release artifact generation)
- برچسب‌گذاری نسخه (Version tagging)
- تأییدیه استقرار (Deployment approval - در صورت فعال بودن)

---

# مراحل خط لوله (Pipeline Stages)

ترتیب متداول اجرا:

```text
بازیابی بسته‌ها (Restore)

↓

ساخت راهکار (Build)

↓

تحلیل ایستا (Static Analysis)

↓

آزمون‌های معماری (Architecture Tests)

↓

آزمون‌های واحد (Unit Tests)

↓

آزمون‌های یکپارچه‌سازی (Integration Tests)

↓

انتشار مصنوعات (Publish Artifacts)
```

---

# پیکربندی ساخت (Build Configuration)

پیکربندی پیش‌فرض:

```text
Release
```

ساخت‌های Debug تنها باید در طول توسعه محلی مورد استفاده قرار گیرند.

چارچوب هدف (`TargetFramework`) به صورت متمرکز در `Directory.Build.props` تعریف شده است.

فایل‌های پروژه مجزا نباید `TargetFramework` را مجدداً تعریف کنند مگر اینکه صریحاً مستند شده باشد.

---

# تحلیل ایستا (Static Analysis)

تحلیل ایستا باید پیش از آزمون‌های خودکار اجرا شود.

ابزارهای توصیه‌شده:

- تحلیل‌گرهای .NET SDK Analyzers
- تحلیل‌گرهای Roslyn Analyzers

هشدارها تا جای ممکن باید به عنوان نقص تلقی شوند.

---

# اعتبارسنجی معماری (Architecture Validation)

اعتبارسنجی معماری باید موارد زیر را راستی‌آزمایی کند:

- قواعد وابستگی (Dependency Rules)
- مرزهای لایه‌ها (Layer Boundaries)
- قواعد فضای نام (Namespace Rules)

ابزارهای توصیه‌شده:

- NetArchTest
- ArchUnitNET

---

# اجرای آزمون‌ها (Test Execution)

خط لوله باید موارد زیر را اجرا کند:

- آزمون‌های واحد (Unit Tests)
- آزمون‌های یکپارچه‌سازی (Integration Tests - شاخه‌های Develop/Main)
- آزمون‌های معماری (Architecture Tests)

موارد افزودنی در آینده می‌تواند شامل موارد زیر باشد:

- آزمون‌های رابط کاربری (UI Tests)
- آزمون‌های کارایی و عملکرد (Performance Tests)
- اسکن‌های امنیتی (Security Scans)

---

# مصنوعات ساخت (Artifacts)

ساخت‌های موفق باید مصنوعات بازتولیدپذیر ایجاد کنند.

نمونه‌ها:

- برنامه منتشرشده
- نمادهای دیباگ (Symbols)
- بسته‌ها (Packages)

مصنوعات باید تغییرناپذیر (Immutable) باقی بمانند.

---

# نسخه‌بندی (Versioning)

نسخه‌بندی از استاندارد نسخه‌بندی معنایی (Semantic Versioning) پیروی می‌کند:

```text
MAJOR.MINOR.PATCH
```

نمونه:

```text
1.4.2
```

---

# امنیت (Security)

خط لوله هرگز نباید موارد زیر را افشا کند:

- اسرار و کلیدهای محرمانه (Secrets)
- کلیدهای API
- توکن‌ها
- رشته‌های اتصال

اسرار در طول اجرای خط لوله باید توسط مخزن اسرار بومی پلتفرم CI مدیریت شوند، و در زمان اجرا بر اساس ADR-0034 (معماری مدیریت پیکربندی و اسرار) توسط HashiCorp Vault (یا جایگزین Azure Key Vault) مدیریت گردند.
