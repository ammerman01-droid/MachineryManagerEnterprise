# ۱. هدف

این سند استانداردهای رسمی کدنویسی را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

هدف اطمینان از این است که تمامی مشارکت‌کنندگان، کدهایی با سبک یکنواخت، ساختار قابل پیش‌بینی و قابلیت نگهداری بالا بنویسند.

استانداردهای کدنویسی به منظور کاهش بار شناختی در طول توسعه، بازبینی کد (Code Review)، دیباگ و نگهداری بلندمدت در نظر گرفته شده‌اند.

---

# ۲. اصول عمومی

هر فایل سورس باید:

- خوانا باشد.
- قابل پیش‌بینی باشد.
- کوچک و کم‌حجم باشد.
- متمرکز بر یک هدف باشد.
- به راحتی قابل بازبینی باشد.
- به راحتی قابل آزمون باشد.

کد باید همواره برای قابلیت نگهداری بهینه‌سازی شود نه برای هوشمندی یا پیچیدگی.

---

# ۳. قالب‌بندی کد (Code Formatting)

این پروژه از قوانین قالب‌بندی پیش‌فرض ارائه شده توسط .NET SDK پیروی می‌کند.

قالب‌بندی از طریق موارد زیر اعمال می‌شود:

- فایل `.editorconfig`
- دستور `dotnet format`

تفاوت‌های قالب‌بندی دستی نباید در درخواست‌های ادغام (Pull Requests) ظاهر شوند.

---

# ۴. سازماندهی فایل (File Organization)

یک فایل سورس معمولاً باید شامل یک تایپ عمومی (Public Type) باشد.

ترتیب پیشنهادی درون فایل:

۱. دستورات `using`
۲. فضای نام (`namespace`)
۳. تعریف کلاس (`class declaration`)
۴. مقادیر ثابت (`constants`)
۵. فیلدها (`fields`)
۶. سازنده‌ها (`constructors`)
۷. ویژگی‌های عمومی (`public properties`)
۸. متدهای عمومی (`public methods`)
۹. متدهای خصوصی (`private methods`)

---

# ۵. طراحی کلاس (Class Design)

کلاس‌ها باید:

- دارای مسئولیت واحد باشند.
- همبستگی (Cohesiveness) داشته باشند.
- از اندازه بیش از حد اجتناب کنند.
- ترکیب را بر ارث‌بری ترجیح دهند.

کلاس‌های بزرگ باید بازسازی (Refactor) شوند.

---

# ۶. متدها (Methods)

متدها باید:

- یک کار منطقی انجام دهند.
- دارای نام‌های توصیفی باشند.
- تو در تویی (Nesting) را به حداقل برسانند.
- در صورت لزوم خروج زودهنگام (Return early) داشته باشند.
- تا حد امکان کوتاه باقی بمانند.

متدها نباید بدون دلیل توجیه‌کننده از حدود ۴۰ سطر تجاوز کنند.

---

# ۷. نام‌گذاری (Naming)

نام‌ها باید قصد و هدف را صریحاً توضیح دهند.

ترجیح داده می‌شود:

```csharp
CalculateMachineAvailability()
```

اجتناب شود:

```csharp
Calc()
```

---

# ۸. کامنت‌گذاری (Comments)

کد باید *علت (why)* را توضیح دهد، نه *چیستی (what)* را.

اجتناب شود:

```csharp
// Increment counter
counter++;
```

ترجیح داده می‌شود:

```csharp
// شمارنده تلاش مجدد از چرخه‌های بی‌نهایت همگام‌سازی جلوگیری می‌کند.
counter++;
```

کدهای مرده و خروج از خدمت‌رسانی هرگز نباید کامنت‌شده باقی بمانند.

---

# ۹. اعداد جادویی (Magic Numbers)

استفاده از اعداد جادویی (Magic numbers) ممنوع است.

به جای:

```csharp
if (count > 5)
```

استفاده شود از:

```csharp
const int MaximumRetries = 5;
```

---

# ۱۰. مدیریت Null

قابلیت Nullable Reference Types باید فعال باقی بماند.

مقادیر Null باید به صورت صریح مدیریت شوند.

از سرکوب هشدارهای کامپایلر با اپراتور بخشش نال (`!`) اجتناب کنید مگر اینکه کاملاً ضروری باشد.

---

# ۱۱. استثناها (Exceptions)

استثناها باید:

- نشان‌دهنده شرایط استثنایی باشند.
- شامل پیام‌های معنادار باشند.
- در صورت پرتاب مجدد (Rethrow)، استثناهای داخلی (Inner exceptions) را حفظ کنند.

هرگز استثناها را به صورت خاموش نادیده نگیرید (Swallow مکنید).

---

# ۱۲. برنامه‌نویسی ناهمگام (Async Programming)

APIهای ناهمگام (Asynchronous) ترجیح داده می‌شوند.

راهنماها:

- از `.Result` اجتناب کنید.
- از `.Wait()` اجتناب کنید.
- از مسدود کردن تردها اجتناب کنید.
- در صورت لزوم از `CancellationToken` استفاده کنید.

---

# ۱۳. تزریق وابستگی (Dependency Injection)

هرگز سرویس‌های زیرساختی را به صورت مستقیم نمونه‌سازی (Instantiate) نکنید.

نادرست:

```csharp
var repository = new MachineRepository();
```

درست:

```csharp
public MachineService(IMachineRepository repository)
```

---

# ۱۴. ثبت رویدادها (Logging)

ثبت رویدادها باید:

- ساختاریافته (Structured) باشد.
- از اطلاعات حساس اجتناب کند.
- از سطوح لاگ مناسب استفاده کند.

منطق کسب‌وکار نباید به پیاده‌سازی‌های لاگینگ وابسته باشد.

---

# ۱۵. آزمون‌سازی (Testing)

کد باید با در نظر داشتن آزمون‌ پذیری نوشته شود.

از وضعیت ایستا (Static state) اجتناب کنید.

از وابستگی‌های پنهان اجتناب کنید.

رفتار قطعی (Deterministic) را ترجیح دهید.

---

# ۱۶. کارایی و عملکرد (Performance)

تنها زمانی بهینه‌سازی کنید که شواهد وجود داشته باشد.

بهینه‌سازی کارایی نیازمند اندازه‌گیری و سنجش است.

خوانایی، اولویت پیش‌فرض باقی می‌ماند.

---

# ۱۷. خط‌مشی متن‌باز (Open Source Policy)

تنها کتابخانه‌های متن‌باز تاییدشده می‌توانند وارد شوند.

هر وابستگی جدید باید دارای موارد زیر باشد:

- ارزیابی فناوری (TE)
- تاییدیه معماری (ADR)

ببینید:

- ADR-0002 — خط‌مشی متن‌باز در اولویت

---

# ۱۸. تحلیل ایستا (Static Analysis)

هشدارها باید به عنوان نقص (Defect) تلقی شوند.

ابزارهای پیشنهادی:

- Roslyn Analyzers
- .NET SDK Analyzers

هشدارهای جدید نباید وارد کدبیس شوند.

---

# ۱۹. بازبینی کد (Code Reviews)

هر درخواست ادغام (Pull Request) باید موارد زیر را بررسی کند:

- خوانایی
- سادگی
- انطباق با معماری
- انطباق با قوانین وابستگی
- آزمون‌پذیری

سازگاری و یکنواختی بر سبک کدنویسی فردی ارجحیت دارد.

---

# ۲۰. انطباق و رعایت

تمامی مشارکت‌کنندگان باید از این استانداردها پیروی کنند.
