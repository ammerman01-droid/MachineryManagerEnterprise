# هدف (Purpose)

این سند، استانداردهای رسمی کدنویسی را برای راهکار **MachineryManagerEnterprise** تعریف می‌کند.

هدف این است که اطمینان حاصل شود تمامی مشارکت‌کنندگان کدی با سبک منسجم، ساختار قابل پیش‌بینی و قابلیت نگهداری بالا می‌نویسند.

استانداردهای کدنویسی به منظور کاهش بار شناختی در طول توسعه، بازبینی‌های کد، اشکال‌زدایی و نگهداری بلندمدت تدوین شده‌اند.

---

# اصول عمومی (General Principles)

هر فایل سورس باید دارای ویژگی‌های زیر باشد:

- خوانا (Readable)
- قابل پیش‌بینی (Predictable)
- کوچک (Small)
- متمرکز (Focused)
- با قابلیت بازبینی آسان (Easy to review)
- با قابلیت آزمون آسان (Easy to test)

کد باید همواره برای قابلیت نگهداری بهینه‌سازی شود تا برای زیرکی و پیچیدگی فردی.

---

# قالب‌بندی کد (Code Formatting)

این پروژه از قواعد پیش‌فرض قالب‌بندی ارائه‌شده توسط NET SDK. پیروی می‌کند.

قالب‌بندی کد باید از طریق ابزارهای زیر اعمال شود:

- `.editorconfig`
- `dotnet format`

تفاوت‌های قالب‌بندی دستی نباید در درخواست‌های ادغام (Pull Requests) ظاهر شوند.

---

# سازمان‌دهی فایل (File Organization)

یک فایل سورس معمولاً باید شامل یک نوع عمومی (Public Type) باشد.

ترتیب توصیه‌شده:

1. دستورات using
2. فضای نام (namespace)
3. اعلان کلاس (class declaration)
4. مقادیر ثابت (constants)
5. فیلدها (fields)
6. سازنده‌ها (constructors)
7. ویژگی‌های عمومی (public properties)
8. متدهای عمومی (public methods)
9. متدهای خصوصی (private methods)

---

# طراحی کلاس (Class Design)

کلاس‌ها باید:

- دارای یک مسئولیت یگانه باشند.
- منسجم (Cohesive) باشند.
- از حجم بیش از حد دوری کنند.
- ترکیب (Composition) را بر وراثت (Inheritance) ترجیح دهند.

کلاس‌های بزرگ باید ریفکتور و بازسازی شوند.

---

# متدها (Methods)

متدها باید:

- یک وظیفه منطقی واحد را انجام دهند.
- دارای نام‌های توصیفی باشند.
- تودرتویی را به حداقل برسانند.
- در زمان مناسب زودتر بازگشت داده شوند (Return early).
- تا جای ممکن کوتاه باقی بمانند.

متدها نباید بدون توجیه منطقی از حدود ۴۰ خط تجاوز کنند.

---

# نام‌گذاری (Naming)

نام‌ها باید به وضوح نیت و قصد را توصیف کنند.

ترجیح داده می‌شود:

```csharp
CalculateMachineAvailability()
```

اجتناب شود:

```csharp
Calc()
```

---

# توضیحات و کامنت‌ها (Comments)

کد باید چرایی (*why*) را توضیح دهد، نه چیستی (*what*) را.

اجتناب شود:

```csharp
// Increment counter
counter++;
```

ترجیح داده می‌شود:

```csharp
// Retry counter prevents infinite synchronization loops.
counter++;
```

کدهای مرده و منسوخ هرگز نباید به صورت کامنت‌شده باقی بمانند.

---

# اعداد جادویی (Magic Numbers)

استفاده از اعداد جادویی ممنوع است.

به جای:

```csharp
if (count > 5)
```

استفاده شود از:

```csharp
const int MaximumRetries = 5;
```

---

# مدیریت مقادیر تهی (Null Handling)

قابلیت انواع ارجاعی با امکان تهی (Nullable Reference Types) باید فعال باقی بماند.

مقدار Null باید به صورت صریح مدیریت شود.

از غیرفعال‌سازی هشدارهای کامپایلر با عملگر نادیده‌گیری تهی (`!`) پرهیز کنید مگر اینکه کاملاً ضروری باشد.

---

# استثناها (Exceptions)

استثناها باید:

- نمایانگر وضعیت‌های استثنایی واقعی باشند.
- شامل پیام‌های معنادار باشند.
- در هنگام پرتاب مجدد، استثناهای داخلی (Inner exceptions) را حفظ کنند.

هرگز استثناها را به صورت خاموش و پنهانی نبلعید (Swallow نکنید).

---

# برنامه‌نویسی ناهمگام (Async Programming)

رابط‌های برنامه‌نویسی ناهمگام (Asynchronous APIs) را ترجیح دهید.

رهنمودها:

- از `.Result` پرهیز کنید
- از `.Wait()` پرهیز کنید
- از بلاک کردن ریسمان‌ها (Threads) خودداری نمایید
- در جاهای مناسب از `CancellationToken` استفاده کنید

---

# تزریق وابستگی (Dependency Injection)

هرگز سرویس‌های زیرساختی را مستقیماً نمونه‌سازی (Instantiate) نکنید.

نادرست:

```csharp
var repository = new MachineRepository();
```

درست:

```csharp
public MachineService(IMachineRepository repository)
```

---

# لاگ‌گیری (Logging)

لاگ‌گیری باید:

- ساختاریافته (Structured) باشد.
- از ثبت اطلاعات حساس پرهیز نماید.
- از سطوح لاگ مناسب استفاده کند.

منطق تجاری نباید به پیاده‌سازی‌های لاگ‌گیری وابسته باشد.

---

# آزمون (Testing)

کد باید با در نظر داشتن قابلیت آزمون نوشته شود.

از وضعیت ایستا (Static state) دوری کنید.

از وابستگی‌های پنهان پرهیز نمایید.

رفتار قطعی و مشخص را ترجیح دهید.

---

# کارایی و عملکرد (Performance)

بهینه‌سازی تنها زمانی مجاز است که شواهد وجود داشته باشد.

بهینه‌سازی‌های کارایی نیازمند سنجش و اندازه‌گیری دقیق است.

خوانایی همواره اولویت پیش‌فرض باقی می‌ماند.
