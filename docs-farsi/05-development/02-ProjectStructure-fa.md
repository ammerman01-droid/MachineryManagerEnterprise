# ۱. هدف

این سند ساختار داخلی اجباری برای هر پروژه را در راهکار **MachineryManagerEnterprise** تعریف می‌کند.

یک ساختار پروژه یکنواخت و سازگار موارد زیر را بهبود می‌بخشد:

- قابلیت نگهداری (Maintainability)
- قابلیت کشف و پیمایش (Discoverability)
- بازبینی‌های کد (Code Reviews)
- مقیاس‌پذیری (Scalability)
- همکاری تیمی (Team Collaboration)

هر پروژه باید از این قراردادها پیروی کند مگر اینکه یک سند ثبت تصمیمات معماری (ADR) تصویب‌شده، صریحاً یک استثنا تعریف کرده باشد.

---

# ۲. اهداف

ساختار پروژه باید:

- کد مرتبط را در کنار هم نگه دارد.
- پیچیدگی پیمایش را به حداقل برساند.
- همبستگی ویژگی‌ها (Feature Cohesion) را تشویق کند.
- وابستگی‌های تصادفی را کاهش دهد.
- از قابلیت نگهداری بلندمدت پشتیبانی کند.

---

# ۳. اصول عمومی

هر پروژه باید:

- دارای مسئولیت واحد باشد.
- تنها شامل فایل‌های مرتبط با آن مسئولیت باشد.
- از تو در تویی غیرضروری پوشه‌ها اجتناب کند.
- از قراردادهای نام‌گذاری پروژه پیروی کند.
- به صورت سازگار با پروژه‌های مشابه سازماندهی شود.

---

# ۴. چیدمان استاندارد پروژه (Standard Project Layout)

یک پروژه معمولی باید از ساختار زیر پیروی کند:

```text
Project

│
├── Abstractions
│
├── Configuration
│
├── Constants
│
├── Contracts
│
├── Exceptions
│
├── Extensions
│
├── Features
│
├── Interfaces
│
├── Mapping
│
├── Models
│
├── Options
│
├── Services
│
├── Utilities
│
└── Validation
```

نیازی نیست هر پروژه تمام پوشه‌ها را داشته باشد.

پوشه‌ها تنها در صورت نیاز باید وجود داشته باشند.

# ۶. سازماندهی بر اساس ویژگی (Feature Organization)

قابلیت‌های کسب‌وکار تا حد امکان باید بر اساس ویژگی (Feature) گروه‌بندی شوند.

مثال:

```text
Features

Inventory

Maintenance

Users

Reports

Dashboard
```

هر ویژگی باید تا حد امکان عملیاتی و مستقل باقی بماند.

---

# ۷. چیدمان ویژگی (Feature Layout)

یک ویژگی می‌تواند شامل موارد زیر باشد:

```text
Inventory

Commands

Queries

DTOs

Validators

Mappings

Services
```

این چیدمان از معماری برش عمودی (Vertical Slice Architecture) پشتیبانی کرده و در عین حال با معماری پاک سازگار است.

---

# ۸. پیکربندی (Configuration)

کلاس‌های پیکربندی باید ایزوله باشند:

```text
Configuration

DependencyInjection

OptionsConfiguration

MiddlewareConfiguration
```

---

# ۹. افزونه‌ها (Extensions)

متدهای توسعه/افزونه باید بر اساس مسئولیت گروه‌بندی شوند.

مثال:

```text
Extensions

ServiceCollectionExtensions

ApplicationBuilderExtensions

StringExtensions
```

---

# ۱۰. نگاشت (Mapping)

نگاشت اشیاء باید متمرکز باشد.

کتابخانه‌های پشتیبانی‌شده نگاشت باید از همان سازماندهی پیروی کنند.

مثال:

```text
Mapping

InventoryProfile

UserProfile

MachineProfile
```

---

# ۱۱. اعتبارسنجی (Validation)

اعتبارسنج‌ها (Validators) باید در یک جا گروه‌بندی شوند.

مثال:

```text
Validation

CreateMachineValidator

UpdateMachineValidator

DeleteMachineValidator
```

---

# ۱۲. سرویس‌ها (Services)

تنها سرویس‌های مرتبط با کسب‌وکار باید در اینجا قرار گیرند.

سرویس‌های زیرساختی متعلق به پروژه Infrastructure هستند.

---

# ۱۳. ابزارها (Utilities)

کلاس‌های ابزاری باید کوچک و بدون وضعیت (Stateless) باقی بمانند.

منطق کسب‌وکار هرگز نباید درون کلاس‌های ابزاری پیاده‌سازی شود.

---

# ۱۴. قوانین نام‌گذاری

پوشه‌ها:
- PascalCase

فایل‌ها:
- PascalCase

کلاس‌ها:
- PascalCase

رابط‌ها (Interfaces):
- پیشوند `I`

مثال‌ها:

```text
MachineService

IMachineRepository

MachineProfile

MachineValidator
```

---

# ۱۵. خط‌مشی ایجاد پوشه

پوشه‌ها نباید به پیش‌واز الزامات آتی و به صورت پیش‌دستانه ایجاد شوند.

پوشه تنها زمانی باید ایجاد شود که:
- شامل محتوای معنادار باشد.
- وجود چندین فایل، ایجاد آن را توجیه کند.
- سازماندهی را بهبود بخشد.

از ایجاد پوشه‌های خالی اجتناب کنید.

---

# ۱۶. مقیاس‌پذیری

ساختار پروژه به صورت هدفمند برای پشتیبانی از رشد آتی طراحی شده است.

با تکامل ماژول‌ها، ویژگی‌های جدید باید بدون نیاز به تجدید ساختار در بخش‌های نامرتبط اضافه شوند.

---

# ۱۷. انطباق و رعایت

هر پروژه جدید ایجادشده باید از این ساختار پیروی کند مگر اینکه یک ADR تصویب‌شده، سازماندهی جایگزینی را تعریف کند.
