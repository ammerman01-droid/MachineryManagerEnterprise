# هدف (Purpose)

این سند به ارزیابی فناوری مورد استفاده برای فراهم‌سازی قابلیت جستجوی متنی آزاد (Free-Text Search) در سراسر پلتفرم MachineryManagerEnterprise — شامل جستجو در ماشین‌آلات و دارایی‌ها (Assets)، دستور کارهای تعمیراتی (Work Orders)، سوابق نگهداری (Maintenance Records)، اقلام انبار (Inventory) و موجودیت‌های مشابه بر اساس نام، شرح، یادداشت‌ها و سایر فیلدهای متنی آزاد — می‌پردازد.

برخلاف سند TE-0026 (ذخیره‌سازی فایل)، این قابلیت پیش‌تر در سند `03-TechnologyGapAnalysis.md` به‌عنوان یک شکاف ثبت نشده بود، بلکه در اینجا به‌صورت پیش‌دستانه مطرح شده است؛ زیرا تمامی ماژول‌های تشریح‌شده در `02-CapabilityModel.md` دارای نماهای فهرستی و تفصیلی هستند که با رشد حجم داده‌ها، فراتر از فیلترهای ساده مبتنی بر `LIKE` نیازمند جستجوی متنی کارآمد خواهند بود.

هدف از این ارزیابی عبارت است از:

- ارزیابی فناوری جستجوی موجود با هزینه زیرساختی صفر از طریق موتور پایگاه داده مصوب پلتفرم (SQL Server Full-Text Search) با توجه به ADR-0006؛
- ارزیابی PostgreSQL Full-Text Search، Elasticsearch و OpenSearch؛
- ارزیابی تکمیلی Azure AI Search با توجه به همخوانی پلتفرم با اکوسیستم دات‌نت/آژور و همچنین استراتژی جستجوی ترکیبی (Hybrid Search) که جستجوی واژگانی (کلیدواژه‌ای) را با قابلیت جستجوی معنایی/برداری (Semantic/Vector Search) منتخب در سند آتی TE-0028 ترکیب می‌کند؛
- انتخاب فناوری و استراتژی جستجو برای پلتفرم، با حفظ بی‌طرفی نسبت به ابر و پایبندی به سیاست اولویت با متن‌باز (ADR-0002).

# دامنه (Scope)

این ارزیابی موارد زیر را پوشش می‌دهد:

- جستجوی متنی آزاد (مبتنی بر کلیدواژه و واژگانی) روی فیلدهای موجودیت‌ها از قبیل نام/شرح ماشین‌آلات، یادداشت‌های دستور کار و سایر محتواهای متنی؛
- رتبه‌بندی و امتیازدهی ارتباط (Relevance Scoring) در نتایج جستجو؛
- لایه انتزاعی که لایه کاربرد برای ارسال کوئری‌های جستجو، مستقل از فناوری زیرین از آن استفاده می‌کند.

موارد خارج از دامنه:

- جستجوی شباهت معنایی / برداری — در سند TE-0028 پوشش داده می‌شود؛ این ارزیابی صرفاً نحوه ترکیب جستجوی واژگانی با جستجوی برداری در قالب کاندید جستجوی ترکیبی را تعریف می‌کند؛
- ارائه‌دهنده هوش مصنوعی و فناوری تولید Embedding برای تولید بردارهای جستجوی معنایی — در سند TE-0029 پوشش داده می‌شود.

# نیازمندی‌های کارکردی (Functional Requirements)

راهکار انتخاب‌شده باید موارد زیر را پشتیبانی کند:

- جستجوی متنی آزاد در چندین نوع موجودیت و چندین فیلد با رتبه‌بندی ارتباط، به جای تطبیق ساده زیررشته؛
- ترکیب فیلترها با جستجوی متنی (مثلاً جستجو درون یک سازمان خاص، دسته‌بندی خاص ماشین‌آلات یا بازه تاریخی مشخص)؛
- تأخیر پاسخگویی مناسب برای سناریوهای تعاملی Search-as-you-type در رابط کاربری Blazor Server؛
- ایزولاسیون کامل چندمستأجری (Multi-Tenant Isolation) مطابق با مدل داده‌ای تفکیک‌شده بر اساس Organization، به‌گونه‌ای که نتایج هرگز مرزهای سازمانی را نقض نکنند.

# نیازمندی‌های غیرکارکردی (Non-Functional Requirements)

راهکار باید موارد زیر را فراهم آورد:

- حداقل پیچیدگی عملیاتی اضافی برای مشتریان کوچک محلی (On-premise)، منطبق با رویکرد TE-0026؛

- انطباق با سیاست اولویت با متن‌باز (ADR-0002)؛
- مسیر ارتقای شفاف از رویکرد جستجوی مستقیم در دیتابیس به یک موتور جستجوی اختصاصی، بدون نیاز به بازنویسی منطق کوئری‌ها در لایه کاربرد.

# اصل معماری (Architecture Principle)

دسترسی به قابلیت‌های جستجو باید منحصراً از طریق یک انتزاع در لایه کاربرد صورت پذیرد تا فناوری زیرین کاملاً قابل جایگزینی باشد.

```text
Application Layer (لایه کاربرد)
   ISearchService  (SearchAssets / SearchWorkOrders / ...)
        │
        ▼
Infrastructure Layer (لایه زیرساخت)
   SqlServerFullTextSearchService | ElasticsearchService | ...
        │
        ▼
   SQL Server Full-Text Index | Elasticsearch Cluster | ...
```

- موجودیت‌های دامنه هرگز نباید به فناوری جستجو رفرنس داشته باشند.
- پروژه SharedKernel هرگز نباید به فناوری جستجو رفرنس داشته باشد.
- ایندکس‌های جستجو باید همواره از داده‌های معتبر تحت مالکیت EF Core (ADR-0006) مشتق شده و با آن همگام باشند — هیچ فناوری جستجویی نباید به منبع مستقل حقیقت برای داده‌های تجاری تبدیل شود.

---

## سازگاری با هوش مصنوعی در آینده (Future AI Compatibility)

معماری آینده پلتفرم باید از موارد زیر پشتیبانی کند:

- جستجوی معنایی (Semantic Search)
- جستجوی برداری (Vector Search)
- تولید تقویت‌شده با بازیابی (Retrieval Augmented Generation - RAG)
- یکپارچگی با دستیار هوش مصنوعی (AI Assistant Integration)
- جستجوی ترکیبی (Hybrid Search)

بنابراین، فناوری‌های جستجو نه تنها برای جستجوی کلیدواژه‌ای، بلکه برای توانمندی بلندمدت در یکپارچگی با سامانه‌های بازیابی داده مبتنی بر هوش مصنوعی مورد ارزیابی قرار می‌گیرند.

# ۵. ارزیابی SQL Server Full-Text Search (کاندید پیش‌فرض)

## نمای کلی و نقاط قوت

- **نقاط قوت:** صفر درصد زیرساخت اضافی؛ عدم نیاز به خط لوله همگام‌سازی داده‌ها میان پایگاه داده و ایندکس خارجی؛ پایداری تراکنشی بالا؛ هماهنگی کامل با استراتژی پایداری ترکیبی TE-0024 / ADR-0019 از طریق کوئری‌های بهینه Dapper؛ هزینه مالی صفر (شامل لایسنس موجود SQL Server).
- **نقاط ضعف:** الگوریتم‌های رتبه‌بندی و قابلیت‌های خطایابی تایپی (Typo-tolerance) و Faceting محدودتر نسبت به موتورهای اختصاصی جستجو؛ بارگذاری محاسباتی ایندکس روی همان سرور دیتابیس OLTP.

---

# ۶. ارزیابی PostgreSQL Full-Text Search

## نمای کلی و دلایل رد

- استفاده از `tsvector` و ایندکس‌های GIN قابلیت‌های جستجوی بسیار خوبی ارائه می‌دهد و در صورت استفاده از `pgvector` پتانسیل هم‌افزایی دارد؛
- اما نیازمند استقرار یک موتور پایگاه داده رابطه‌ای دوم در کنار SQL Server و راه‌اندازی خط لوله پیچیده همگام‌سازی (CDC/Outbox) است که برای نیازهای فعلی توجیه‌پذیر نیست؛
- با توجه به انتخاب Qdrant در سند TE-0028، شرط هم‌افزایی با `pgvector` منتفی بوده و این گزینه **رد می‌شود**.

---

# ۷. ارزیابی Elasticsearch

## نمای کلی و دلایل عدم انتخاب به‌عنوان پیش‌فرض

- قابلیت‌های رتبه‌بندی بی‌نظیر، جستجوی هم‌زمان در موجودیت‌های مختلف، سرعت بسیار بالا؛
- **نقاط ضعف:** تغییر مدل لایسنس به SSPL/AGPLv3 و قرار گرفتن برخی قابلیت‌های پیشرفته پشت پرداخت تجاری (تضاد با ADR-0002)؛ نیازمند مدیریت یک کلاستر سنگین مبتنی بر JVM؛ پیچیدگی بیش از حد برای استقرارهای کوچک.

---

# ۸. ارزیابی OpenSearch

## نمای کلی و نقاط قوت

- فورک کاملاً متن‌باز Elasticsearch تحت لایسنس شفاف Apache 2.0 (انطباق کامل با ADR-0002)؛
- سازگاری با API الستیک‌سرچ، بدون قفل‌شدگی تجاری؛
- گزینه‌ای عالی برای ارتقا و مقیاس‌پذیری افقی در استقرارهای بسیار بزرگ.

---

# ۹. ارزیابی Azure AI Search

## نمای کلی و دلایل عدم انتخاب به‌عنوان پیش‌فرض

- سرویس کاملاً مدیریت‌شده ابری با قابلیت‌های فوق‌العاده جستجوی برداری و ترکیبی بدون نیاز به مدیریت سرور؛
- **نقاط ضعف:** عدم بی‌طرفی ابری (قفل به مایکروسافت آژور)، هزینه‌های متغیر مبتنی بر مصرف، عدم امکان اجرا در محیط‌های محلی و شبکه‌های ایزوله آفلاین (Air-gapped).

---

# ۱۰. ارزیابی جستجوی ترکیبی (Hybrid Search)

## نمای کلی

جستجوی ترکیبی یک استراتژی معماری است که در آن نتایج جستجوی واژگانی (کلمات کلیدی) با نتایج جستجوی معنایی/برداری (مبتنی بر مدل‌های هوش مصنوعی TE-0028) ترکیب و با الگوریتم‌هایی نظیر Reciprocal Rank Fusion (RRF) ادغام و رتبه‌بندی مجدد می‌شوند.

این رویکرد به‌عنوان جهت‌گیری آینده پلتفرم تصویب می‌شود و پس از تکمیل پایگاه داده برداری (TE-0028) عملیاتی خواهد شد.

## پشته اصلی فناوری‌ها

|---|---|---|

# تصمیم نهایی (Final Decision)

| مولفه | تصمیم |
|---|---|
| SQL Server Full-Text Search | **به‌عنوان فناوری پیش‌فرض جستجوی واژگانی تصویب شد** |
| OpenSearch | **به‌عنوان مسیر ارتقا برای استقرارهای بزرگ سازمانی تصویب شد** |
| Elasticsearch | رد شد — تغییرات لایسنس نسبت به OpenSearch مزیت کمتری دارد |
| PostgreSQL Full-Text Search | رد شد — در سند TE-0028 ابزار Qdrant انتخاب شد و شرط pgvector منتفی گردید |
| Azure AI Search | به‌عنوان پیش‌فرض سامانه تصویب نشد (عدم بی‌طرفی ابری) |
| جستجوی ترکیبی (Hybrid Search) | **به‌عنوان مسیر و استراتژی آینده پلتفرم تصویب شد** |
