# هدف (Purpose)

این سند فناوری مورد استفاده برای فراهم ساختن جستجوی متن آزاد (Free-text Search) را در سراسر پلتفرم MachineryManagerEnterprise ارزیابی می‌کند — جستجو در دارایی‌ها (Assets)، سفارش‌های کار (Work Orders)، سوابق تعمیر و نگهداری (Maintenance Records)، اقلام موجودی انبار (Inventory Items) و موجودیت‌های مشابه از طریق نام، توضیحات، یادداشت‌ها و سایر فیلدهای متن آزاد.

برخلاف سند TE-0026 (ذخیره‌سازی فایل)، این قابلیت هنوز به عنوان یک شکاف در `03-TechnologyGapAnalysis.md` ثبت نشده است؛ این موضوع در اینجا به صورت پیش‌دستانه (Proactively) معرفی می‌شود، زیرا هر ماژول شرح‌داده‌شده در `02-CapabilityModel.md` نماهای فهرست و جزئیاتی را ارائه می‌دهد که با رشد حجم داده‌های پلتفرم فراتر از آنچه فیلترسازی ساده مبتنی بر `LIKE` می‌تواند به طور قابل قبولی پاسخ دهد، نیازمند جستجوی متن آزاد خواهند بود.

هدف از این ارزیابی عبارت است از:

- ارزیابی فناوری جستجویی که هم‌اکنون با صفر هزینه زیرساختی اضافی از طریق موتور پایگاه داده تصویب‌شده پلتفرم (SQL Server Full-Text Search) بر اساس ADR-0006 در دسترس است؛
- ارزیابی PostgreSQL Full-Text Search، Elasticsearch و OpenSearch همان‌طور که در ابتدا درخواست شده بود؛
- علاوه بر این، ارزیابی Azure AI Search با توجه به گرایش و قرابت پلتفرم با .NET/Azure، و یک استراتژی جستجوی ترکیبی (Hybrid Search) که جستجوی لغوی/کلیدواژه‌ای (Lexical) را با قابلیت جستجوی معنایی/برداری (Semantic/Vector Search) که قرار است در سند آتی TE-0028 (ارزیابی فناوری پایگاه داده برداری) انتخاب شود، ترکیب می‌نماید؛
- انتخاب فناوری و استراتژی جستجو برای پلتفرم، یا یک ترکیب صریح و مشخص، همسو با رویکرد بی‌طرف نسبت به ابر (Cloud-neutral) و اولویت متن‌باز (ADR-0002).

# اصل معماری (Architecture Principle)

دسترسی به جستجو باید منحصراً از طریق یک انتزاع در لایه Application انجام شود و هرگز نباید مستقیماً توسط هیچ لایه‌ای بالاتر از Infrastructure مورد دسترسی قرار گیرد، تا فناوری جستجوی زیرین کاملاً قابل تعویض باقی بماند.

```text
Application Layer
   ISearchService  (SearchAssets / SearchWorkOrders / ...)
        │
        ▼
Infrastructure Layer
   SqlServerFullTextSearchService | ElasticsearchService | ...
        │
        ▼
   SQL Server Full-Text Index | Elasticsearch Cluster | ...
```

موجودیت‌های دامنه (Domain entities) هرگز نباید به یک فناوری جستجو ارجاع دهند. هسته مشترک (SharedKernel) هرگز نباید به فناوری جستجو ارجاع دهد. ایندکس‌های جستجو باید همواره از داده‌های معتبر و مرجع تحت مالکیت EF Core (سند ADR-0006) مشتق شده و با آنها همگام نگه داشته شوند — هیچ فناوری جستجویی نباید به یک منبع مستقل حقیقت برای داده‌های تجاری تبدیل شود.

معماری آینده باید موارد زیر را پشتیبانی نماید:

# 5. ارزیابی SQL Server Full-Text Search (SQL Server Full-Text Search Evaluation)

## نمای کلی (Overview)

قابلیت SQL Server Full-Text Search یک ویژگی بومی نمایه‌سازی و کوئری است که مستقیماً در دل SQL Server، یعنی موتور پایگاه داده از پیش تصویب‌شده پلتفرم (ADR-0006)، تعبیه شده است. این قابلیت نمایه‌سازی زبانی و کلمه‌محور و گزاره‌های کوئری (`CONTAINS`، `FREETEXT`) را بدون نیاز به هیچ سرویس یا زیرساخت اضافی فراهم می‌سازد.

## نقش معماری (Architectural Role)

```text
Application Layer

   SearchAssetsQueryHandler
          │
          ▼
   ISearchService.SearchAsync("hydraulic pump")
          │
          ▼
Infrastructure Layer
   SqlServerFullTextSearchService
          │
          ▼
   SELECT ... FROM Assets
   WHERE CONTAINS(SearchVector, @query)
          │
          ▼
   SQL Server Full-Text Index (same database as EF Core)
```

## نقاط قوت معماری (Architectural Strengths)

- صفر زیرساخت اضافی: این قابلیت هم‌اکنون در داخل موتور پایگاه داده‌ای که تحت ADR-0006 تایید شده وجود دارد و تنها نیازمند فعال‌سازی ویژگی Full-Text و ایجاد کاتالوگ‌ها و ایندکس‌های تمام‌متن است.
- داده‌ها در یک سیستم واحد باقی می‌مانند: هیچ خط لوله همگام‌سازی (synchronization pipeline) میان داده‌های معتبر تحت مالکیت EF Core و یک ایندکس جستجوی مجزا مورد نیاز نیست، که این امر دسته‌ای کامل از ریسک‌های کهنگی ایندکس (index-staleness) را که هر کاندیدای موتور جستجوی خارجی باید به آن بپردازد از بین می‌برد.
- یکپارچگی تراکنشی با عملیات نوشتن در بیشتر سناریوهای کاربردی، زیرا ایندکس تمام‌متن توسط همان موتور پایگاه داده‌ای نگهداری می‌شود که مالک داده‌ها است (با در نظر گرفتن ردیابی ناهمگام جمعیت داده‌های SQL Server برای جداولی با حجم نوشتن بسیار بالا).
- پشتیبانی از ویژگی‌های زبانی به صورت پیش‌فرض: ریشه‌یابی کلمات (stemming)، اصطلاح‌نامه (thesaurus)، فهرست کلمات توقف (stopword lists) و رتبه‌بندی از طریق `CONTAINSTABLE`/`FREETEXTTABLE`.
- قابلیت ترکیب مستقیم با کوئری‌های موجود LINQ در EF Core و استراتژی پایداری ترکیبی (ADR-0019)، زیرا گزاره‌های تمام‌متن را می‌توان از طریق بخش‌های خام SQL یا کوئری‌های Dapper روی همان پایگاه داده بیان کرد.

## نقاط ضعف معماری (Architectural Weaknesses)

- رتبه‌بندی ارتباط و قابلیت‌های کوئری به طور محسوسی نسبت به یک موتور جستجوی اختصاصی کمتر پیشرفته است: عدم وجود فیلترسازی چندوجهی بومی (native faceting)، امتیازدهی چندفیلدی وزن‌دار محدودتر است، و تطابق فازی / تحمل خطای املایی نسبت به Elasticsearch یا OpenSearch ضعیف‌تر است.
- نمایه‌سازی تمام‌متن بار سربار را مستقیماً روی مسیر نوشتن پایگاه داده اصلی تراکنشی اضافه می‌کند و بر سر منابع با بار کاری اصلی OLTP پلتفرم رقابت می‌نماید، بر خلاف یک موتور جستجوی خارجی که بار جستجو را روی زیرساخت مجزا ایزوله می‌کند.
- جستجوی چندموجودیتی و چندجدولی (به عنوان مثال یک کوئری واحد که به طور همزمان دارایی‌ها، سفارش‌های کار و موجودی انبار را با رتبه‌بندی یکپارچه ارتباط پوشش دهد) برای پیاده‌سازی بسیار نامناسب‌تر و دشوارتر از یک موتور جستجوی هدفمند است.
- عدم پشتیبانی بومی از جستجوی معنایی/برداری، به این معنی که استراتژی جستجوی ترکیبی آینده در هر صورت نیازمند یک نقطه یکپارچگی مجزا خواهد بود.

## ویژگی‌های عملیاتی (Operational Characteristics)

بدون سرویس جدید برای استقرار؛ کاتالوگ‌ها و ایندکس‌های تمام‌متن به عنوان بخشی از نمونه موجود SQL Server و روال‌های پشتیبان‌گیری/نگهداری موجود آن مدیریت می‌شوند.

## مقیاس‌پذیری (Scalability)

برای حجم داده‌ها و نرخ کوئری‌های کوچک تا متوسط کافی است؛ به طور مستقل از پایگاه داده اصلی مقیاس نمی‌یابد، به این معنی که بار جستجو در زمان همروندی بالا مستقیماً با بار تراکنشی رقابت می‌کند.

## انعطاف‌پذیری استقرار (Deployment Flexibility)

عالی: در هر ویرایش SQL Server که پلتفرم هم‌اکنون هدف قرار داده در دسترس است، با رفتار کاملاً یکسان در استقرارهای محلی (on-premise)، ایزوله (air-gapped) و ابری، بدون نیاز به تصمیم‌گیری زیرساختی اضافی برای هر استقرار.

## هزینه (Cost)

صفر هزینه اضافی: این ویژگی در نمونه دارای لایسنس SQL Server گنجانده شده است.

## امنیت (Security)

مدل احراز هویت، مجوزدهی و امنیت در سطح سطر (row-level security) موجود پایگاه داده را به ارث می‌برد؛ هیچ سطح دسترسی یا اطلاعات هویتی جدیدی معرفی نمی‌شود.

## ایزولاسیون چندمستاجری (Multi-Tenant Isolation)

عالی: از آنجا که کوئری‌ها روی همان جداولی اجرا می‌شوند که از قبل توسط Organization از طریق فیلترهای کوئری موجود در EF Core محدود شده‌اند، جداسازی چندمستاجری به طور خودکار به ارث برده می‌شود و نیازی به پیکربندی جداگانه در یک سیستم خارجی ندارد.

## سازگاری آینده با جستجوی معنایی (Future Semantic Search Compatibility)

به تنهایی ضعیف است: ابزار SQL Server Full-Text Search قابلیت بومی جستجوی برداری/معنایی ندارد، بنابراین یک استراتژی جستجوی ترکیبی در آینده باید این فناوری و یک مخزن برداری مجزا را به طور مستقل کوئری کرده و نتایج را در لایه Application ادغام نماید.

```csharp
            SELECT a.Id, a.Name, KEY_TBL.RANK
            FROM Assets a
            INNER JOIN CONTAINSTABLE(Assets, (Name, Description), @query) AS KEY_TBL
                ON a.Id = KEY_TBL.[KEY]
            WHERE a.OrganizationId = @organizationId
            ORDER BY KEY_TBL.RANK DESC
            """;

        return (await _connection.QueryAsync<AssetSearchResultDto>(
            sql, new { query, organizationId })).AsList();
    }
}
```

# 6. ارزیابی PostgreSQL Full-Text Search (PostgreSQL Full-Text Search Evaluation)

## نمای کلی (Overview)

قابلیت PostgreSQL Full-Text Search قابلیت بومی جستجوی متن در PostgreSQL است که بر پایه انواع داده `tsvector`/`tsquery`، ایندکس‌های GIN/GiST و فرهنگ‌های لغت متنی قابل پیکربندی بنا شده است. این گزینه در اینجا همان‌طور که در ابتدا درخواست شده بود ارزیابی می‌شود، هرچند پایگاه داده هدف فعلی پلتفرم SQL Server است (ADR-0006)، زیرا این گزینه الگوی معتبری را نشان می‌دهد که توسط برخی سیستم‌های سازمانی استفاده می‌شود: اجرای یک نمونه اختصاصی PostgreSQL صرفاً برای جستجو، در کنار پایگاه داده تراکنشی اصلی SQL Server.

## نقش معماری (Architectural Role)

```text
Application Layer

   SearchAssetsQueryHandler
          │
          ▼
   ISearchService.SearchAsync("hydraulic pump")
          │
          ▼
Infrastructure Layer
   PostgresFullTextSearchService
          │
          ▼
   Synchronization pipeline (change data capture / outbox)
          │
          ▼
   Dedicated PostgreSQL instance (tsvector index, separate from SQL Server)
```

## نقاط قوت معماری (Architectural Strengths)

- مجموعه ویژگی‌های کامل، بالغ، با مستندات عالی و بسیار توانمند در جستجوی تمام‌متن، که عموماً قوی‌تر از معادل آن در SQL Server ارزیابی می‌شود (توابع رتبه‌بندی انعطاف‌پذیرتر، فرهنگ لغت و گزینه‌های پیکربندی غنی‌تر).
- کاملاً متن‌باز (مجوز PostgreSQL License، مجاز و بدون محدودیت)، با همسویی قوی با ADR-0002.
- چنانچه پلتفرم روزی به `pgvector` برای جستجوی معنایی نیاز پیدا کند (کاندیدایی که از هم‌اکنون برای سند آتی TE-0028 فهرست شده است)، همان نمونه PostgreSQL می‌تواند هم به جستجوی لغوی و هم به جستجوی برداری از یک موتور واحد خدمت‌رسانی کند، که یک هم‌افزایی معماری قابل توجه و منحصربه‌فرد برای این کاندیدا محسوب می‌شود.

## نقاط ضعف معماری (Architectural Weaknesses)

- **معرفی یک موتور پایگاه داده رابطه‌ای دوم و کاملاً متفاوت** به پلتفرمی که داده‌های تراکنشی اصلی آن در SQL Server قرار دارد (ADR-0006)، که نیازمند یک خط لوله همگام‌سازی اختصاصی (تغییر داده‌های ضبط‌شده یا CDC، الگوی Outbox یا یک جاب ETL زمان‌بندی‌شده) است تا ایندکس جستجوی PostgreSQL را با داده‌های معتبر SQL Server همگام نگه دارد — دسته جدید و مهمی از ریسک‌های عملیاتی و عدم یکپارچگی داده‌ها که در SQL Server Full-Text Search وجود ندارد.
- دو برابر کردن سطح عملیاتی پایگاه داده پلتفرم: دو موتور برای وصله‌زنی، پشتیبان‌گیری، مانیتورینگ و تهیه منابع، که مستقیماً با رویکرد پیچیدگی عملیاتی پایین که SQL Server Full-Text Search را جذاب کرده بود در تضاد است.
- عدم وجود تخصص تیمی یا سرمایه‌گذاری روی ابزارهای مدیریت PostgreSQL در مقایسه با SQL Server، جایی که تیم از قبل تجربه عمیق و تثبیت‌شده عملیاتی از پایگاه داده اصلی پلتفرم دارد.
- برای مشتریانی با کوچک‌ترین استقرارهای محلی و تک‌سرور (همان بخش مشتریانی که انگیزه بحث Local Storage و MinIO در TE-0026 بودند)، اجرای یک موتور پایگاه داده دوم بار عملیاتی بسیار سنگین‌تری نسبت به SQL Server Full-Text Search یا یک سرویس جستجوی خارجی کاملاً مدیریت‌شده ایجاد می‌کند.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند استقرار، پیکربندی و عملیات یک نمونه اختصاصی PostgreSQL، به اضافه یک مکانیزم همگام‌سازی برای تکرار فیلدهای مربوطه از SQL Server به ستون‌های `tsvector` در PostgreSQL است.

## مقیاس‌پذیری (Scalability)

خوب؛ قابلیت جستجوی تمام‌متن PostgreSQL برای حجم داده‌های متوسط به خوبی مقیاس می‌یابد و می‌تواند به طور مستقل از پایگاه داده اصلی SQL Server مقیاس‌پذیر شود، که این مزیتی نسبت به محدودیت اشتراک منابع در SQL Server Full-Text Search است.

## انعطاف‌پذیری استقرار (Deployment Flexibility)

از نظر تئوری خوب است (PostgreSQL در محیط‌های محلی، در کانتینرها یا در هر ابری اجرا می‌شود)، اما در عمل برای کوچک‌ترین مشتریان پلتفرم ضعیف‌تر از SQL Server Full-Text Search است، چرا که آنها باید یک موتور پایگاه داده دوم را صرفاً برای جستجو نگهداری کنند.

## هزینه (Cost)

هزینه زیرساختی اضافی (یک نمونه اختصاصی PostgreSQL) فراتر از SQL Server دارای لایسنس موجود، اگرچه خود موتور پایگاه داده فاقد هزینه لایسنس است.

## امنیت (Security)

نیازمند پیکربندی احراز هویت و کنترل دسترسی مختص به خود، مجزا از مدل امنیتی موجود SQL Server است، که یک سطح امنیتی دوم را برای بازرسی اضافه می‌کند.

## ایزولاسیون چندمستاجری (Multi-Tenant Isolation)

نیازمند پیکربندی صریح است (به عنوان مثال یک ستون `organization_id` که در کنار ستون `tsvector` ایندکس‌گذاری شده باشد) به جای اینکه به طور خودکار ایزولاسیونی را که SQL Server Full-Text Search از فیلترهای کوئری موجود در EF Core به دست می‌آورد، به ارث ببرد.

## سازگاری آینده با جستجوی معنایی (Future Semantic Search Compatibility)

قوی است، به شکلی منحصربه‌فرد در میان کاندیداهای صرفاً لغوی: افزونه `pgvector` (کاندیدایی که از قبل برای TE-0028 شناسایی شده است) درون همان نمونه PostgreSQL اجرا می‌شود، به این معنی که یک استراتژی جستجو مبتنی بر PostgreSQL می‌تواند جستجوی لغوی و معنایی را در یک موتور واحد یکپارچه سازد به جای اینکه نیازمند ادغام بین‌موتوری باشد که استراتژی جستجوی ترکیبی معمولاً به آن نیاز دارد.

## کاربرد نمونه (Typical Usage)

```sql
ALTER TABLE assets ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (to_tsvector('english', name || ' ' || description)) STORED;

CREATE INDEX assets_search_idx ON assets USING GIN (search_vector);

SELECT id, name, ts_rank(search_vector, query) AS rank
FROM assets, to_tsquery('english', 'hydraulic & pump') query
WHERE search_vector @@ query AND organization_id = $1
ORDER BY rank DESC;
```

## تناسب معماری (Architectural Fit)

## ارتباط با TE-0028 (pgvector)

اگر سند آتی TE-0028 گزینه `pgvector` را به عنوان پایگاه داده برداری پلتفرم انتخاب کند، این کاندیدا به طور محسوسی جذاب‌تر می‌شود، زیرا یک نمونه واحد PostgreSQL می‌تواند هم به نیاز جستجوی لغوی این ارزیابی و هم به نیاز جستجوی معنایی TE-0028 پاسخ دهد و تعداد کل مخازن داده تخصصی پلتفرم را از دو (یک موتور جستجوی مجزا و یک پایگاه داده برداری مجزا) به یک کاهش دهد.

## نتیجه‌گیری اولیه (Preliminary Conclusion)

گزینه PostgreSQL Full-Text Search نقاط قوت فنی واقعی و یک هم‌افزایی معماری حقیقی با تصمیم احتمالی آینده پیرامون `pgvector` ارائه می‌دهد، اما یک موتور پایگاه داده رابطه‌ای دوم و یک خط لوله همگام‌سازی را معرفی می‌کند که پلتفرم در حال حاضر به آن نیازی ندارد، زیرا SQL Server Full-Text Search هم‌اکنون نیازمندی‌های کوتاه‌مدت پلتفرم را با صفر هزینه عملیاتی اضافی برآورده می‌سازد.

موتور Elasticsearch یک موتور توزیع‌شده جستجو و تحلیل مبتنی بر اسناد JSON است که بر روی Apache Lucene ساخته شده و به طور گسترده به عنوان استاندارد صنعتی برای جستجوی تمام‌متن اختصاصی در مقیاس بالا شناخته می‌شود.

## نقاط قوت معماری (Architectural Strengths)

- بهترین رتبه‌بندی ارتباط در کلاس خود، تطابق فازی / تحمل خطای املایی، فیلترسازی چندوجهی (faceting)، تجمیع‌ها (aggregations)، و جستجوی یکپارچه چندموجودیتی — قوی‌ترین کیفیت جستجو در میان تمام کاندیداهای ارزیابی‌شده در این سند.

- پشتیبانی طبیعی از نیازمندی‌های آینده نظیر تکمیل خودکار (autocomplete)، "جستجو هنگام تایپ" (search-as-you-type)، و داشبوردهای تحلیلی روی رفتار جستجوی کاربران، که هیچ‌یک از گزینه‌های SQL Server یا PostgreSQL Full-Text Search به صورت بومی آنها را مدیریت نمی‌کنند.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند استقرار، تعیین اندازه و عملیات یک کلاستر Elasticsearch است (حداقل یک گره با منابع کافی برای استقرارهای کوچک، و چندین گره برای افزونگی در سطح عملیاتی)، به همراه یک مکانیزم همگام‌سازی از SQL Server.

عالی؛ ابزار Elasticsearch به طور خاص برای مقیاس‌پذیری افقی طراحی شده و قوی‌ترین کاندیدای مقیاس‌پذیر در این ارزیابی برای حجم داده‌ها و نرخ کوئری‌های بسیار بالا است.

برای استقرارهای بزرگ‌تر، میزبانی‌شده در ابر یا محلی با منابع کافی خوب است؛ برای کوچک‌ترین مشتریان پلتفرم به دلیل نیازهای منابع و پیچیدگی عملیاتی کلاستر مبتنی بر JVM ضعیف است.

## هزینه (Cost)

سطح متن‌باز Elasticsearch هزینه لایسنس ندارد اما نیازمند زیرساخت اختصاصی (پردازش، حافظه، ذخیره‌سازی) است که هزینه آن با حجم داده مقیاس می‌یابد؛ چندین ویژگی پیشرفته نیازمند اشتراک پولی Elastic هستند.

## امنیت (Security)

ویژگی‌های امنیتی قوی (کنترل دسترسی مبتنی بر نقش، امنیت در سطح فیلد) در دسترس هستند، اما در عمل برای استقرارهای در سطح عملیاتی عمدتاً پشت سطوح اشتراک پولی قرار دارند، که یک شباهت دیگر با دغدغه لایسنس به سبک AutoMapper است.

# 8. ارزیابی OpenSearch (OpenSearch Evaluation)

## نمای کلی (Overview)

موتور OpenSearch یک فورک متن‌باز از Elasticsearch است که در سال 2021 توسط AWS و سایر مشارکت‌کنندگان در پاسخ مستقیم به تغییر لایسنس Elasticsearch ایجاد شد و تحت مجوز کاملاً مجاز Apache 2.0 منتشر گردید. هدف آن دنبال کردن دقیق مجموعه ویژگی‌های متن‌باز Elasticsearch و در عین حال باقی ماندن به صورت بدون ابهام در وضعیت متن‌باز است.

## نقاط قوت معماری (Architectural Strengths)

- لایسنس کاملاً Apache 2.0، بدون لایسنس دوگانه یا قفل کردن ویژگی‌ها پشت اشتراک تجاری — پاک‌ترین تطابق با خط‌مشی اولویت متن‌باز (ADR-0002) در میان کاندیداهای موتور جستجوی اختصاصی، که مستقیماً دغدغه لایسنس شناسایی‌شده برای Elasticsearch را برطرف می‌سازد.
- ساختار API و زبان کوئری (DSL) بسیار نزدیک به Elasticsearch باقی مانده است، به این معنی که همان دانش معماری، الگوهای کوئری و بخش اعظم ابزارهای عملیاتی مستقیماً قابل انتقال هستند و هزینه عملی انتخاب OpenSearch به جای Elasticsearch را به حداقل می‌رسانند.
- برخورداری از حمایت جامعه گسترده چندارائه‌دهنده‌ای (AWS و دیگران) با یک مدل حاکمیتی که به طور صریح برای جلوگیری از تکرار رویداد تغییر لایسنس Elasticsearch ساختاریافته است.
- در دسترس بودن به عنوان یک توزیع واقعاً متن‌باز و قابل خودمیزبانی، و همچنین به عنوان یک پیشنهاد مدیریت‌شده در AWS و سایر ابرها، که انعطاف‌پذیری استقراری مشابه الگوی MinIO / S3-Compatible تثبیت‌شده در TE-0026 فراهم می‌کند.

## نقاط ضعف معماری (Architectural Weaknesses)

- اشتراک در بار سنگین عملیاتی Elasticsearch: یک سیستم توزیع‌شده مبتنی بر JVM که نیازمند زیرساخت اختصاصی، تعیین اندازه و تخصص عملیاتی است و همچنان باری نامتناسب برای کوچک‌ترین مشتریان محلی و تک‌سرور پلتفرم به شمار می‌رود.
- همچنان نیازمند یک خط لوله همگام‌سازی اختصاصی از SQL Server است، همان دسته ریسک کهنگی ایندکس که با Elasticsearch و PostgreSQL Full-Text Search مشترک است.
- اکوسیستم کوچک‌تر و سابقه کوتاه‌تر نسبت به Elasticsearch، هرچند این شکاف از سال 2021 به طور چشمگیری کاهش یافته و بسیار کمتر از زمان پیدایش OpenSearch اهمیت دارد.
- کتابخانه کلاینت دات‌نت (`OpenSearch.Client`) نسبت به کلاینت رسمی دات‌نت Elasticsearch کمتر بالغ بوده و کمتر مورد استفاده قرار گرفته است، هرچند کاملاً کارا بوده و به طور فعال نگهداری می‌شود.

## ویژگی‌های عملیاتی (Operational Characteristics)

## مقیاس‌پذیری (Scalability)

## انعطاف‌پذیری استقرار (Deployment Flexibility)

برای استقرارهای بزرگ‌تر، میزبانی‌شده در ابر یا محلی با منابع کافی خوب است؛ برای کوچک‌ترین مشتریان پلتفرم ضعیف است، دقیقاً همانند پروفایل Elasticsearch.

## هزینه (Cost)

## امنیت (Security)

# 9. ارزیابی Azure AI Search (Azure AI Search Evaluation)

## نمای کلی (Overview)

سرویس Azure AI Search (پیشتر Azure Cognitive Search) پیشنهاد جستجو به عنوان سرویس (Search-as-a-Service) مدیریت‌شده و ابری مایکروسافت است که جستجوی تمام‌متن، فیلترسازی چندوجهی و قابلیت‌های بومی جستجوی برداری/معنایی را بدون نیاز به عملیات مستقیم زیرساخت جستجو توسط پلتفرم فراهم می‌سازد. این گزینه در اینجا به همان دلیلی ارزیابی می‌شود که Azure Blob Storage در TE-0026 ارزیابی شد: استک مبتنی بر .NET پلتفرم یک تمایل طبیعی به سمت سرویس‌های رسمی و بومی Azure ایجاد می‌کند، و این ارزیابی بدون پرداختن مستقیم به آن ناقص خواهد بود.

## نقش معماری (Architectural Role)

```text
Application Layer

   SearchAssetsQueryHandler
          │
          ▼
   ISearchService.SearchAsync("hydraulic pump")
          │
          ▼
Infrastructure Layer

          │
```

## نقاط قوت معماری (Architectural Strengths)

- کاملاً مدیریت‌شده: بدون کلاستر، بدون تنظیم JVM، بدون زیرساخت برای عملیات — کمترین بار عملیاتی در میان کاندیداهای موتور جستجوی اختصاصی.
- یکپارچگی بومی و رسمی هر دو جستجوی لغوی و برداری/معنایی در یک سرویس مدیریت‌شده واحد، که در غیر این صورت نیازمند ترکیب یک موتور لغوی مجزا (این ارزیابی) با یک پایگاه داده برداری مجزا (TE-0028) تحت کاندیدای جستجوی ترکیبی زیر خواهد بود.
- کیت توسعه نرم‌افزار رسمی دات‌نت (`Azure.Search.Documents`)، مستندات عالی و یکپارچگی قوی با اکوسیستم گسترده‌تر Azure.
- پایپ‌لاین‌های غنی‌سازی هوش مصنوعی داخلی (مانند استخراج خودکار موجودیت‌ها)، اگرچه در حال حاضر یک نیازمندی اعلام‌شده برای پلتفرم نیست.

## نقاط ضعف معماری (Architectural Weaknesses)

- **عدم بی‌طرفی نسبت به ابر (Not cloud-neutral)**: دغدغه‌ای کاملاً یکسان با Azure Blob Storage در TE-0026 — سرویس Azure AI Search یک سرویس اختصاصی مایکروسافت است که قفل‌شدگی به ارائه‌دهنده (vendor lock-in) ایجاد می‌کند، رویکرد بی‌طرف نسبت به ابر پلتفرم را نقض می‌نماید و برای استقرارهای محلی یا ایزوله (air-gapped) کاملاً غیرقابل دسترس است، که یک عامل ردکننده قطعی برای سهم قابل توجهی از مشتریان شرکت‌های ساختمانی هدف پلتفرم محسوب می‌شود.
- صورت‌حساب مداوم بر اساس میزان مصرف (سطح‌بندی‌شده بر اساس واحد جستجو / replica / partition)، مدلی اساساً متفاوت و با پیش‌بینی‌پذیری کمتر نسبت به هر دو کاندیدای جستجوی تمام‌متن یا یک کلاستر خودمیزبان OpenSearch با هزینه زیرساختی ثابت.
- عدم متن‌باز بودن از هر جهت، در تضاد مستقیم با ADR-0002، بیش از هر کاندیدای دیگری که در این سند ارزیابی شده است.
- نیازمند اشتراک فعال Azure و اتصال اینترنتی از سوی سرور Host، همانند نقطه ضعف انعطاف‌پذیری استقرار شناسایی‌شده برای Azure Blob Storage.

برای استقرارهای محلی یا ایزوله ضعیف است؛ صرفاً برای مشتریانی که از قبل متعهد به استقرار میزبانی‌شده در Azure خود برنامه Host هستند عالی است — همان الگویی که قبلاً برای Azure Blob Storage در TE-0026 ارزیابی شد.

# 10. ارزیابی جستجوی ترکیبی (Hybrid Search Evaluation)

## نمای کلی (Overview)

جستجوی ترکیبی (Hybrid Search) یک فناوری منفرد نیست بلکه یک استراتژی است: ترکیب یک فناوری جستجوی لغوی (مبتنی بر کلیدواژه) — انتخاب‌شده از کاندیداهای فوق — با یک فناوری جستجوی معنایی/برداری، که قرار است در سند آتی TE-0028 (ارزیابی فناوری پایگاه داده برداری) انتخاب شود، به طوری که نتایج جستجو هم از تطابق دقیق کلیدواژه‌ها و هم از شباهت مفهومی/معنایی بهره‌مند شوند (به عنوان مثال جستجوی عبارت "engine won't start" سفارش‌های کاری با برچسب "ignition failure" را حتی بدون وجود تطابق دقیق کلیدواژه‌ای برمی‌گرداند).

## نقش معماری (Architectural Role)

```text
Application Layer
   ISearchService.SearchAsync(query, organizationId)
        │
        ├──► Lexical Search (SQL Server FTS, OpenSearch, or similar)
        │        │
        │        ▼
        │    Keyword-ranked results
        │
        └──► Semantic Search (vector database, selected in TE-0028)
                 │
                 ▼
             Similarity-ranked results
                 │
                 ▼
        Result fusion (e.g. reciprocal rank fusion)
                 │
                 ▼
        Unified, ranked search results
```

## نقاط قوت معماری (Architectural Strengths)

- ترکیب دقت تطابق دقیق کلیدواژه با مزیت بازخوانی (recall) شباهت معنایی، که مستقیماً به دامنه تعمیر و نگهداری و بازرسی پلتفرم مربوط می‌شود، جایی که تکنسین‌های میدانی اغلب با استفاده از عبارات غیررسمی و غیردقیق جستجو می‌کنند.
- ترکیب تمیز با انتزاع `ISearchService` تثبیت‌شده: ادغام نتایج (result fusion) یک دغدغه لایه Application است که از دو سرویس لایه Infrastructure کوئری گرفته و خروجی آنها را ادغام می‌کند، بدون اینکه هیچ‌یک از فناوری‌های زیرین نیازی به آگاهی از دیگری داشته باشند.
- به پلتفرم اجازه می‌دهد کار را با گزینه لغوی بدون هزینه (SQL Server Full-Text Search) آغاز کند و نیمه معنایی را پس از انتخاب پایگاه داده برداری در TE-0028 به صورت تدریجی اضافه نماید، به جای اینکه نیازمند اتخاذ هر دو تصمیم به طور همزمان باشد.

## نقاط ضعف معماری (Architectural Weaknesses)

- وابسته به تصمیمی است — فناوری پایگاه داده برداری — که هنوز اتخاذ نشده است (موکول به TE-0028)؛ تناسب معماری کامل این کاندیدا تا زمانی که آن ارزیابی تکمیل نشود، نمی‌تواند به طور نهایی بررسی گردد.
- ادغام نتایج (Result fusion - ادغام و رتبه‌بندی مجدد دو مجموعه نتیجه با امتیازدهی مستقل) یک بخش غیربدیهی از منطق لایه Application است که هیچ‌یک از فناوری‌های زیرین آن را به صورت پیش‌فرض ارائه نمی‌دهند، مگر اینکه پایگاه داده برداری یا موتور جستجوی انتخابی از ادغام به صورت بومی پشتیبانی کند (همان‌طور که Azure AI Search انجام می‌دهد).
- ملاحظات عملیاتی و لایسنسی *دو* مخزن داده تخصصی (یک فناوری جستجوی لغوی و یک پایگاه داده برداری) را معرفی می‌کند مگر اینکه یک موتور واحد با توانایی انجام هر دو انتخاب شود — ملاحظه‌ای که مستقیماً به نفع کاندیداهایی مانند PostgreSQL (از طریق `pgvector`) یا Azure AI Search است که می‌توانند هر دو نقش را از یک موتور ایفا کنند، در مقایسه با ترکیبی از مثلاً SQL Server Full-Text Search همراه با یک پایگاه داده برداری کاملاً مجزا.

## ویژگی‌های عملیاتی (Operational Characteristics)

کاملاً به این بستگی دارد که کدام فناوری‌های لغوی و معنایی با یکدیگر ترکیب می‌شوند؛ دامنه‌ای از «بدون زیرساخت اضافی» (SQL Server Full-Text Search همراه با یک مخزن برداری سبک تعبیه‌شده) تا «دو سرویس مجزای مدیریت‌شده یا خودمیزبان» (OpenSearch همراه با یک پایگاه داده برداری اختصاصی) را در بر می‌گیرد، دامنه‌ای که تنها پس از تکمیل TE-0028 به طور کامل مشخص خواهد شد.

## مقیاس‌پذیری (Scalability)

ویژگی‌های مقیاس‌پذیری هر دو فناوری ترکیب‌شده را به ارث می‌برد.

## امنیت (Security)

وضعیت امنیتی ترکیبی هر دو فناوری زیرین را به ارث می‌برد؛ هیچ سطح امنیتی اضافی توسط خود منطق ادغام ایجاد نمی‌شود، زیرا این منطق تنها روی نتایج کوئری‌هایی عمل می‌کند که از قبل مجوزدهی شده‌اند.

## سازگاری آینده با جستجوی معنایی (Future Semantic Search Compatibility)

طبق تعریف، این کاندیدایی است که بیشترین همسویی مستقیم را با نیازهای جستجوی معنایی آینده پلتفرم دارد، زیرا صراحتاً برای گنجاندن فناوری پایگاه داده برداری انتخاب‌شده در TE-0028 طراحی شده است.

## کاربرد نمونه (Typical Usage)

```csharp
public sealed class HybridSearchService : ISearchService
{
    public async Task<IReadOnlyList<AssetSearchResultDto>> SearchAsync(
        string query, Guid organizationId, CancellationToken ct)
    {
        var lexicalTask = _lexicalSearch.SearchAsync(query, organizationId, ct);
        var semanticTask = _semanticSearch.SearchAsync(query, organizationId, ct);

        await Task.WhenAll(lexicalTask, semanticTask);

        return ReciprocalRankFusion.Merge(lexicalTask.Result, semanticTask.Result);
    }
}
```

## ارتباط با TE-0028

این کاندیدا عمداً به عنوان یک **هدف وضعیت آینده (Future-state target)** و نه یک کاندیدای انتخاب‌شده برای پیاده‌سازی فوری باقی مانده است، زیرا نیمه معنایی آن هنوز تصمیم‌گیری نشده است. این موضوع در اینجا ثبت شده است تا فناوری جستجوی لغوی انتخاب‌شده توسط این ارزیابی با در نظر داشتن صریح نیازمندی‌های آینده جستجوی ترکیبی انتخاب شود (توصیه نهایی را ببینید).

## نتیجه‌گیری اولیه (Preliminary Conclusion)

جستجوی ترکیبی (Hybrid Search) مسیر بلندمدت صحیح پلتفرم است، اما ترکیبی از دو تصمیم است که این ارزیابی امروز تنها می‌تواند یکی از آنها (نیمه لغوی) را نهایی کند. این رویکرد باید به صورت تدریجی اتخاذ شود: با فناوری لغوی انتخاب‌شده در زیر آغاز گردد، سپس به محض اینکه TE-0028 یک فناوری معنایی/برداری را انتخاب کرد، به جستجوی ترکیبی گسترش یابد.

## معیارهای تصمیم‌گیری برای ارتقاء آینده به OpenSearch

```text
IF حجم کوئری‌های جستجو یا نیازمندی‌های ارتباط نتایج
   فراتر از آن چیزی رود که SQL Server Full-Text Search بتواند
   به طور قابل قبولی خدمت‌رسانی کند (بر اساس تاخیر جستجو یا
   مشکلات ارتباط گزارش‌شده توسط کاربران)

THEN موتور OpenSearch را به عنوان یک پیاده‌سازی اضافی از
   ISearchService برای استقرار مربوطه اضافه کنید، بدون تغییر
   در کدهای لایه Application.
```

## معیارهای تصمیم‌گیری برای اتخاذ جستجوی ترکیبی در آینده

```text
ONCE سند TE-0028 یک فناوری پایگاه داده برداری را انتخاب کرد

THEN پیاده‌سازی HybridSearchService را انجام دهید، که فناوری
   لغوی انتخاب‌شده در اینجا را با پایگاه داده برداری انتخاب‌شده
   ترکیب می‌کند، با استفاده از reciprocal rank fusion در لایه Application.

IF سند TE-0028 به طور خاص pgvector را انتخاب کرد

THEN قابلیت PostgreSQL Full-Text Search را به عنوان یک جایگزین
   تک‌موتوره برای ترکیب SQL Server Full-Text Search با یک
   مخزن برداری مجزا باز ارزیابی کنید.
```

**نتیجه قطعی (Resolution):** سند TE-0028 پایگاه داده Qdrant را انتخاب کرد، نه pgvector. بنابراین این شرط فعال نشد و PostgreSQL Full-Text Search بر اساس تصمیم نهایی زیر همچنان ردشده باقی می‌ماند؛ هیچ باز ارزیابی برای این سند مورد نیاز نیست.

## توصیه‌های امنیتی (Security Recommendations)

ایزولاسیون چندمستاجری (محدودسازی به دامنه Organization) باید صرف‌نظر از اینکه کدام پیاده‌سازی `ISearchService` فعال است، به طور یکسان اعمال شود و از طریق همان انضباط بازبینی کدی که قبلاً برای فیلترهای کوئری EF Core اعمال شده بود اعتبارسنجی گردد.

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

پیش‌فرض پیشنهادی (SQL Server Full-Text Search، با ارتقاء به OpenSearch) بی‌طرفی کامل نسبت به ابر و پشتیبانی از استقرار محلی/ایزوله را حفظ می‌کند؛ سرویس Azure AI Search بدون تبدیل شدن به پیش‌فرض کل پلتفرم، به عنوان یک گزینه وابسته به استقرار در دسترس باقی می‌ماند.

## آمادگی برای هوش مصنوعی (AI Readiness)

این ارزیابی با تعریف صریح نقطه یکپارچگی جستجوی ترکیبی (Hybrid Search) که با ارزیابی TE-0028 و TE-0029 (ارائه‌دهنده هوش مصنوعی) تکمیل خواهد شد، پلتفرم را مستقیماً برای قابلیت‌های جستجوی مبتنی بر هوش مصنوعی در آینده آماده می‌سازد.
