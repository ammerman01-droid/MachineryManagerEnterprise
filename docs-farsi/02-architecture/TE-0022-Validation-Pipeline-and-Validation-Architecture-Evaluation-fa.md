# ۶. ارزیابی اعتبارسنجی در کنترلر (Controller Validation Evaluation)

## نمای کلی (Overview)

اعتبارسنجی کنترلر رویکرد سنتی در ASP.NET است که در آن هر کنترلر (یا اندپوینت) پیش از فراخوانی منطق برنامه، اعتبارسنجی را به‌صورت صریح فراخوانی می‌کند.

نمونه پیاده‌سازی متداول:

```csharp
var result = await validator.ValidateAsync(request);

if (!result.IsValid)
{
    return BadRequest(result.Errors);
}

await mediator.Send(request);
```

کنترلر مسئول هماهنگی و اجرای اعتبارسنجی می‌شود.

# نقاط ضعف معماری (Architectural Weaknesses)

اعتبارسنجی کنترلر چندین اصل معماری اتخاذشده در MachineryManagerEnterprise را نقض می‌کند.

### تکرار اعتبارسنجی (Validation Duplication)

هر کنترلر موارد زیر را تکرار می‌کند:

- واکشی و حل وابستگی اعتبارسنج؛
- اجرای اعتبارسنجی؛
- مدیریت خطاها و فرمت‌بندی خروجی.

در سیستم‌های بزرگ، کدهای تکراری به‌سرعت انباشته می‌شوند.

---

### تفکیک دغدغه‌ها (Separation of Concerns)

کنترلرها مسئول چندین وظیفه غیرمرتبط می‌شوند:

- دغدغه‌های مربوط به پروتکل HTTP؛
- اعتبارسنجی؛
- ارکستراسیون و هماهنگی.

این امر باعث تداخل مسئولیت‌ها می‌گردد.

---

### عدم تطابق با CQRS (CQRS Inconsistency)

الگوی CQRS جریان زیر را دیکته می‌کند:

```text
Command (دستور)

↓

Validation (اعتبارسنجی)

↓

Handler (پردازنده‌کننده)
```

اما اعتبارسنجی در کنترلر آن را به شکل زیر تغییر می‌دهد:

```text
Controller (کنترلر)

↓

Validation (اعتبارسنجی)

↓

Mediator

↓

Handler
```

در نتیجه، اعتبارسنجی وابسته به لایه نمایش (Presentation Layer) می‌شود.

---

### دور زدن پایپ‌لاین (Pipeline Bypass)

وظایف پس‌زمینه (Background jobs)، رویدادهای یکپارچه‌سازی (Integration events) و درخواست‌های داخلی برنامه ممکن است کنترلرها را به‌طور کامل دور بزنند.

در نتیجه:

- اعتبارسنجی اجرا نمی‌شود؛
- پردازنده‌های کسب‌وکار ممکن است اشیاء نامعتبر را دریافت کنند.

# ۷. ارزیابی اعتبارسنجی در اندپوینت (Endpoint Validation Evaluation)

## نمای کلی (Overview)

اعتبارسنجی در اندپوینت، منطق اعتبارسنجی را به‌جای کنترلرهای MVC مستقیماً در درون اندپوینت‌های Minimal API (یا متدهای پردازنده اندپوینت) قرار می‌دهد.

نمونه پیاده‌سازی متداول:

```csharp
app.MapPost("/machines", async (
    CreateMachineCommand command,
    IValidator<CreateMachineCommand> validator,
    ISender sender) =>
{
    var result = await validator.ValidateAsync(command);

    if (!result.IsValid)
        return Results.ValidationProblem(result.ToDictionary());

    return await sender.Send(command);
});
```

این رویکرد در برنامه‌های Minimal API رواج یافته است.

# نقاط ضعف معماری (Architectural Weaknesses)

اگرچه کنترلرها حذف می‌شوند، اما مشکلات معماری پابرجا هستند.

### تکرار اعتبارسنجی (Validation Duplication)

هر اندپوینت موارد زیر را تکرار می‌کند:

- تزریق و واکشی اعتبارسنج؛
- فراخوانی اعتبارسنج؛
- مدیریت نتیجه اعتبارسنجی؛
- نگاشت و تبدیل خطاها.

با افزایش تعداد اندپوینت‌ها، کدهای تکراری به‌میزان چشمگیری افزایش می‌یابد.

---

### تفکیک دغدغه‌ها (Separation of Concerns)

اندپوینت‌ها مسئول موارد زیر می‌شوند:

- مسیریابی HTTP؛
- اعتبارسنجی؛
- ارکستراسیون و هماهنگی.

این امر اصل تفکیک مسئولیت‌ها را نقض می‌کند.

---

### عدم تطابق با CQRS (CQRS Misalignment)

مدل اجرای مورد نظر به شرح زیر است:

```text
Request (درخواست)

↓

Validation (اعتبارسنجی)

↓

Handler (پردازنده‌کننده)
```

اما اعتبارسنجی در اندپوینت آن را به شکل زیر تغییر می‌دهد:

```text
Endpoint (اندپوینت)

↓

Validation (اعتبارسنجی)

↓

Mediator

↓

Handler
```

اعتبارسنجی همچنان وابسته به لایه انتقال (Transport layer) باقی می‌ماند.

---

### عدم یکپارچگی پایپ‌لاین (Pipeline Inconsistency)

تنها درخواست‌های HTTP به‌صورت خودکار اعتبارسنجی می‌شوند.

سایر مسیرهای اجرایی نظیر:

- وظایف پس‌زمینه (Background jobs)؛
- کارهای زمان‌بندی‌شده (Scheduled tasks)؛
- پردازنده‌های رویدادهای یکپارچه‌سازی (Integration event handlers)؛
- درخواست‌های داخلی برنامه؛

می‌توانند اعتبارسنجی اندپوینت را کاملاً دور بزنند. این امر منجر به رفتار ناسازگار در سیستم می‌شود.

- مستقل از لایه انتقال؛
- مستقل از UI؛
- مستقل از لایه پایداری داده؛
- جلوگیری از ایجاد موجودیت‌های نامعتبر؛
- پشتیبانی از زبان فراگیر (Ubiquitous Language)؛
- تشویق مدل‌های غنی دامنه (Rich Domain Models)؛
- تضمین صحت کسب‌وکار.

# ناوردایی‌های دامنه (Domain Invariants)

نمونه‌ها عبارتند از:

```text
شماره سریال ماشین نمی‌تواند خالی باشد.

بازه زمانی نگهداری نمی‌تواند منفی باشد.

تاریخ خرید نمی‌تواند بعد از تاریخ اسقاط باشد.

واحد پول باید همواره مشخص باشد.

مبلغ پول نمی‌تواند مقدار منفی داشته باشد (زمانی که قوانین کسب‌وکار حکم می‌کند).

ریشه اگریگیت هرگز نباید وارد وضعیت نامعتبر شود.
```

این قوانین متعلق به لایه Domain هستند.

# تفکیک مسئولیت‌ها (Separation of Responsibilities)

اعتبارسنجی لایه کاربرد به این پرسش پاسخ می‌دهد:

```text
آیا این درخواست ساختار معتبری دارد؟
```

اعتبارسنجی دامنه‌ای به این پرسش پاسخ می‌دهد:

```text
آیا این شیء کسب‌وکار اجازه وجود دارد؟
```

این‌ها اساساً دو مسئولیت کاملاً متفاوت هستند.

# تفکیک مسئولیت‌ها (Responsibility Separation)

## اعتبارسنجی کاربرد (Application Validation)

هدف: **آیا این درخواست قابل پردازش است؟**
قوانین: فیلدهای اجباری، طول، محدوده، فرمت، سازگاری DTO، اعتبارسنجی‌های متقابل خصوصیات.
فناوری: **FluentValidation**

---

## اعتبارسنجی دامنه (Domain Validation)

هدف: **آیا این شیء کسب‌وکار اجازه وجود دارد؟**
قوانین: ناوردایی‌های اگریگیت، سازگاری موجودیت، اعتبار Value Objectها، تغییر وضعیت‌های معتبر کسب‌وکار.
فناوری: **Domain Model**

# قوانین معماری اجباری (Architectural Rules)

- **قانون ۱:** کنترلرها و اندپوینت‌های Minimal API هرگز نباید اعتبارسنجی را به‌صورت دستی اجرا کنند.
- **قانون ۲:** تمامی Commands و Queries باید از طریق پایپ‌لاین اعتبارسنجی MediatR اعتبارسنجی شوند.
- **قانون ۳:** پردازنده‌ها (Handlers) هرگز نباید حاوی منطق اعتبارسنجی تکراری باشند.
- **قانون ۴:** موجودیت‌های دامنه باید همواره از ناوردایی‌های خود محافظت نمایند.
- **قانون ۵:** قوانین کسب‌وکار هرگز نباید درون اعتبارسنج‌های FluentValidation پیاده‌سازی شوند (اعتبارسنج‌ها ورودی برنامه را می‌سنجند و دامنه صحت کسب‌وکار را).
