# هدف

این سند به ارزیابی فناوری‌های کاندید برای ارزیابی فناوری Blazor (.NET 10) در MachineryManagerEnterprise می‌پردازد.

هدف، ایجاد یک انتخاب فناوری واحد است که تمام الزامات عملکردی و معماری را برآورده کرده و در عین حال اصول معماری پاک (Clean Architecture) را حفظ کند.

---

# دامنه ارزیابی

این ارزیابی فناوری صرفاً به بررسی انتخاب فناوری می‌پردازد.

جزئیات پیاده‌سازی توسط اسناد تصمیم‌گیری معماری (ADR) مربوطه تعریف می‌شوند.

---

# ارتباط با ارزیابی‌های فناوری پیشین

این ارزیابی بر پایه پی‌ریزی انجام شده در TE-0001 (پلتفرم .NET 10) بنا شده و با قوانین معماری سازمانی تعریف‌شده در سراسر راهکار هم‌راستا است.

# الزامات عملکردی

فناوری انتخاب‌شده باید از موارد زیر پشتیبانی کند:

- قابلیت‌های اصلی سازمانی مورد نیاز در MachineryManagerEnterprise؛
- جداسازی مدل‌های دامنه از جزئیات زیرساخت بر اساس اصول معماری پاک؛
- یکپارچگی بی‌نقص با زمان اجرای .NET 10 و تزریق وابستگی (Dependency Injection)؛
- اجرای با کارایی بالا و عملیات غیرهمگام.

---

# الزامات غیرعملکردی

این راهکار باید موارد زیر را فراهم کند:

- قابلیت اطمینان و مقیاس‌پذیری سازمانی؛
- قابلیت نگهداری بلندمدت و بی‌طرفی نسبت به ابر (Cloud Neutrality)؛
- عدم وابستگی به فروشنده (Zero Vendor Lock-in)؛
- تجربه توسعه‌دهنده بهینه و قابلیت تست‌پذیری.

---

# خلاصه مدیریتی

این سند به ارزیابی **Blazor** به عنوان چارچوب (Framework) اصلی ارائه (Presentation) برای راهکار MachineryManagerEnterprise می‌پردازد.

Blazor به این دلیل انتخاب شد که امکان ساخت برنامه‌های وب مدرن را با استفاده از #C، کامپوننت‌های Razor و اکوسیستم .NET بدون نیاز به معرفی جاوا اسکریپت به عنوان زبان اصلی توسعه، فراهم می‌کند.

---

# بیان مسئله

این پروژه به یک چارچوب رابط کاربری (UI) نیاز دارد که موارد زیر را فراهم کند:

- یکپارچگی بومی با .NET
- ایمنی نوع (Type Safety) قوی
- معماری مبتنی بر کامپوننت
- پشتیبانی بلندمدت مایکروسافت
- قابلیت نگهداری عالی
- بهره‌وری بالای توسعه‌دهنده

# مزایا

- اکوسیستم بومی .NET
- مدل‌های اشتراکی C#
- معماری کامپوننت Razor
- پشتیبانی عالی در Visual Studio
- بررسی دقیق در زمان کامپایل (Strong compile-time checking)
- کاهش وابستگی به JavaScript
- فریم‌ورک اختصاصی مایکروسافت
- پایداری پلتفرم در بلندمدت

---

# معایب

- اکوسیستم شخص‌ثالث کوچک‌تر در مقایسه با React.
- برخی کتابخانه‌های سمت مرورگر همچنان به قابلیت تعامل با JavaScript (JS Interop) نیاز دارند.

---

# ریسک‌ها

ریسک‌های احتمالی عبارتند از:

- جامعه کاربری کوچک‌تر نسبت به React.
- برخی سناریوهای پیشرفته UI ممکن است به قابلیت تعامل با JavaScript نیاز داشته باشند.
- برخی از کامپوننت‌های شخص‌ثالث تجاری هستند.

ریسک کلی پایین ارزیابی می‌شود.

---

# ملاحظات عملکرد

برنامه‌های Blazor Web در .NET 10 عملکردی عالی را از طریق روش‌های زیر فراهم می‌کنند:

- رندرینگ تعاملی سمت سرور (Interactive Server Rendering)
- رندرینگ تعاملی WebAssembly
- رندرینگ تعاملی خودکار (Interactive Auto Rendering)

حالت رندرینگ می‌تواند بر اساس نیازهای برنامه انتخاب شود.

# اثبات مفهوم (PoC)

هیچ اثبات مفهوم اختصاصی مورد نیاز نبود.

پیاده‌سازی‌های مرجع متعددی که آماده بهره‌برداری (Production-ready) هستند، هم‌اکنون در اکوسیستم .NET وجود دارند.

# تأثیر بر معماری

Blazor مستقیماً بر موارد زیر تأثیر می‌گذارد:

- لایه ارائه (Presentation Layer)
- معماری کامپوننت
- ترکیب رابط کاربری (UI Composition)
- جریان احراز هویت

منطق کسب‌وکار (Business logic) همچنان در داخل لایه Application باقی می‌ماند.

# گزینه‌های جایگزین بررسی‌شده
