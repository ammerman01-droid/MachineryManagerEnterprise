# ۵. ارزیابی OpenAPI

## نمای کلی

OpenAPI استاندارد صنعتی برای توصیف APIهای HTTP است.

این استاندارد موارد زیر را تعریف می‌کند:

- نقاط پایانی؛
- پارامترها؛
- بدنه درخواست‌ها؛
- پاسخ‌ها؛
- احراز هویت؛
- شماها (Schemas)؛
- فراداده (Metadata).

OpenAPI یک چارچوب رابط کاربری (UI) نیست.

این استاندارد، قراردادی است که توسط ابزارهای مستندسازی، ابزارهای تست، دروازه‌ها (Gateways) و تولیدکنندگان SDK مصرف می‌شود.

---

# ۵. ارزیابی OpenAPI

## نمای کلی

OpenAPI (که قبلاً با نام مشخصات Swagger شناخته می‌شد) استاندارد صنعتی برای توصیف APIهای RESTful HTTP است.

این مستند یک قرارداد ماشین‌خوان فراهم می‌کند که موارد زیر را به طور کامل توصیف می‌کند:

- نقاط پایانی (Endpoints)؛
- متدهای HTTP؛
- مدل‌های درخواست (Request models)؛
- مدل‌های پاسخ (Response models)؛
- الزامات احراز هویت؛
- قراردادهای خطا (Error contracts)؛
- متادیتا.

سند OpenAPI به توصیف کانونی (Canonical) سطح API عمومی تبدیل می‌شود.

---

# نقش معماری

OpenAPI به لایه قرارداد API (API Contract layer) تعلق دارد.

```text
Minimal APIs / Controllers

          │

          ▼

 ASP.NET Core OpenAPI Generator

          │

          ▼

      OpenAPI Document

          │

 ▼        ▼               ▼

          │

          ▼

```

ماژول‌های تجاری کاملاً از فرآیند تولید OpenAPI بی‌اطلاع باقی می‌مانند.

# ویژگی‌های عملیاتی

OpenAPI موارد زیر را فراهم می‌کند:

- قراردادهای API؛
- متادیتای نقاط پایانی؛
- تولید اسکیما (Schema generation)؛
- توصیفات امنیتی؛
- پشتیبانی از نسخه‌گذاری (Versioning).

پیچیدگی عملیاتی بسیار پایین است، زیرا مشخصات به صورت خودکار تولید می‌شوند.

---

# مقیاس‌پذیری

OpenAPI بدون در نظر گرفتن اندازه API، به طور طبیعی مقیاس‌پذیر است.

صرف‌نظر از اینکه پلتفرم شامل موارد زیر باشد:

- ۲۰ نقطه پایانی؛
- ۲۰۰ نقطه پایانی؛
- ۲,۰۰۰ نقطه پایانی؛

همان فرآیند تولید اعمال می‌شود.

مقیاس‌پذیری در سطح عالی ارزیابی می‌شود.

---

# مستندسازی امنیت

OpenAPI احراز هویت را مستند می‌کند بدون آنکه آن را پیاده‌سازی کند.

نمونه‌ها عبارتند از:

- JWT Bearer؛
- OAuth2؛
- OpenID Connect؛
- API Keys.

این امر به تولیدکنندگان کلاینت و ابزارهای مستندسازی تعاملی اجازه می‌دهد تا به درستی احراز هویت کنند.

---

# تجربه توسعه‌دهنده (DX)

بهره‌وری توسعه‌دهنده به طور قابل توجهی بهبود می‌یابد زیرا:

- مستندات همیشه همگام هستند؛
- قراردادها دارای تایپ قوی (Strongly typed) هستند؛
- مدل‌های درخواست/پاسخ قابل کشف (Discoverable) باقی می‌مانند؛
- کلاینت‌ها می‌توانند به صورت خودکار تولید شوند.

تجربه توسعه‌دهنده در سطح عالی ارزیابی می‌شود.

---

# قابلیت نگهداری

مستندات OpenAPI از سورس‌کد تولید می‌شوند.

در نتیجه:

- هیچ مستندات تکراری وجود ندارد؛
- نیازی به همگام‌سازی دستی نیست؛
- هزینه نگهداری پایین‌تر است.

قابلیت نگهداری در سطح عالی ارزیابی می‌شود.

---

# سازگاری با هوش مصنوعی

ابزارهای هوش مصنوعی به طور فزاینده‌ای به مشخصات OpenAPI متکی هستند.

نمونه‌ها عبارتند از:

- فراخوانی ابزار توسط مدل‌های زبانی (LLM Tool Calling)؛
- عوامل هوش مصنوعی (AI Agents)؛
- کشف API؛
- تولید خودکار SDK؛
- درک معنایی API.

بنابراین، OpenAPI قابلیت‌های یکپارچه‌سازی با هوش مصنوعی را به طور قابل توجهی بهبود می‌بخشد.

---

# بی‌طرفی نسبت به ابر (Cloud Neutrality)

OpenAPI کاملاً مستقل از پلتفرم است.

در همه جا پشتیبانی می‌شود:

- ویندوز؛
- لینوکس؛
- کانتینرها؛
- کوبرنتیز (Kubernetes)؛
- ابر (Cloud)؛
- ترکیبی (Hybrid)؛
- داخلی (On-Premise).

بی‌طرفی نسبت به ابر در سطح عالی است.

# ۶. ارزیابی Scalar

## نمای کلی

Scalar یک رابط مستندسازی تعاملی و مدرن برای API است که به عنوان تجربه مستندسازی توصیه‌شده برای برنامه‌های مدرن ASP.NET معرفی شده است.

برخلاف Swagger UI که عمدتاً بر رندر کردن مشخصات OpenAPI تمرکز دارد، Scalar بر موارد زیر تأکید می‌کند:

- تجربه توسعه‌دهنده (Developer Experience)؛
- خوانایی؛
- رابط کاربری مدرن؛
- رندرینگ با کارایی بالا؛
- جریان کاریِ "OpenAPI-اول".

با شروع نسخه‌های مدرن ASP.NET، Scalar در حال تبدیل شدن به رابط مستندسازی تعاملیِ ترجیحی است.

در MachineryManagerEnterprise، Scalar به عنوان رابط اصلی برای کاوش API ارزیابی می‌شود.

---

# نقش معماری

Scalar در لایه نمایش مستندات API (API Documentation Presentation layer) قرار می‌گیرد.

```text
 OpenAPI Specification

          ▼
```

این ابزار هرگز قراردادهای API را خودش تولید نمی‌کند.

طراحی مدرن، یکپارچه‌سازی بومی با OpenAPI و همسویی آن با .NET 10، این ابزار را به جایگزینی ارجح برای Swagger UI سنتی در اکتشافات روزمره API تبدیل کرده است.

# ۷. ارزیابی سازگاری Swagger UI

## بررسی اجمالی

Swagger UI برای سال‌های متمادی ابزار اصلی و دوفاکتوی تجسم تعاملی OpenAPI در اکوسیستم .NET بوده است.

این ابزار یک رابط مبتنی بر مرورگر برای موارد زیر فراهم می‌کند:

- کاوش در اندپوینت‌ها (Endpoints)؛
- مشاهده طرح‌واره‌ها (Schemas)؛
- ارسال درخواست‌ها؛
- تست تعاملی APIها.

اگرچه این ابزار همچنان بالغ است و به‌طور گسترده مورد استفاده قرار می‌گیرد، اما .NET 10 به طور فزاینده‌ای **Scalar** را به عنوان تجربه مستندسازی تعاملی ترجیحی معرفی می‌کند.

بنابراین، Swagger UI از منظر **سازگاری** ارزیابی می‌شود، نه به عنوان رابط اصلی مستندات.

NSwag یکی از بالغ‌ترین اکوسیستم‌های ابزاری OpenAPI موجود برای دات‌نت (.NET) است.

این ابزار قابلیت‌های زیر را فراهم می‌کند:

در پروژه MachineryManagerEnterprise، ابزار NSwag به عنوان پلتفرم اصلی تولید SDK کلاینت ارزیابی می‌شود.

نمونه‌ها عبارتند از:

- خط لوله‌های هوش مصنوعی پایتون؛
- سرویس‌های Go؛
- سرویس‌های سازمانی C#.

سازگاری با هوش مصنوعی عالی ارزیابی می‌شود.

---

# کاربرد متداول

سناریوهای مناسب:

```text
Multi-language SDKs

Cross-platform APIs

Public API Distribution

Microsoft Graph-style APIs
```

سناریوهای کمتر مناسب:

```text
Single-language Enterprise Systems

Pure .NET Client Ecosystems
```

# ارتباط با NSwag

این دو ابزار مکمل یکدیگر هستند و نه لزوماً جایگزین هم.

```text
OpenAPI

      │

 ┌────┴────────────┐

 ▼                 ▼

NSwag          Kiota

.NET SDK     Multi-language SDKs
```

برای سازمان‌هایی که در درجه اول کلاینت‌های .NET توسعه می‌دهند، NSwag همچنان گزینه پیش‌فرض قدرتمندتری است.

Kiota زمانی جذاب می‌شود که نیاز به توزیع SDKهای رسمی در چندین زبان برنامه‌نویسی مختلف وجود داشته باشد.

---

# نتیجه‌گیری مقدماتی

Kiota یک تولیدکننده SDK کلاینت مدرن و عالی است، به‌ویژه برای سازمان‌هایی که نیاز به پشتیبانی سطح اول (First-class) از چندین زبان دارند.

با این حال، MachineryManagerEnterprise در حال حاضر عمدتاً اکوسیستم .NET را با یک کلاینت دسکتاپ Avalonia و مصرف‌کنندگان سرویس داخلی هدف قرار داده است.

به همین دلیل:

- **NSwag باید فناوری اصلی تولید کلاینت باشد.**
- **Kiota ممکن است در آینده در صورتی که توزیع SDKهای چندزبانه عمومی به یکی از الزامات پروژه تبدیل شود، معرفی گردد.**

# ۱۰. مقایسه کلی فناوری

مستندسازی API و تولید کلاینت دو حوزه متمایز اما به شدت مرتبط هستند.

معماری پیشنهادی این دو را تفکیک می‌کند:

- تولید قرارداد (Contract) API؛
- مستندات تعاملی؛
- تولید SDK کلاینت.

تمام ابزارهای پایین‌دستی باید از یک سند واحد و معتبر OpenAPI استفاده کنند.

# ارزیابی قابلیت نگهداری (Maintainability)

نگهداری یک سند واحد OpenAPI به عنوان قرارداد معتبر (Authoritative Contract) مزایای زیر را فراهم می‌کند:

- حذف کامل مستندات تکراری؛
- همگام‌سازی SDKهای کلاینت؛
- تست‌های منسجم؛
- نسخه‌سازی آسان‌تر؛
- ساده‌سازی فرایندهای CI/CD.

قابلیت نگهداری در سطح «عالی» ارزیابی می‌شود.

---

# بی‌طرفی نسبت به ابر (Cloud Neutrality)

تمامی فناوری‌های ارزیابی‌شده نسبت به زیرساخت ابری بی‌طرف هستند.

آن‌ها از موارد زیر پشتیبانی می‌کنند:

- ویندوز؛
- لینوکس؛
- کانتینرها؛
- کوبرنتیز (Kubernetes)؛
- فضای ابری (Cloud)؛
- محیط‌های ترکیبی (Hybrid)؛
- محیط‌های داخلی (On-Premise).

هیچ‌گونه وابستگی به فروشنده (Vendor Lock-in) ایجاد نمی‌شود.

آمادگی برای هوش مصنوعی در سطح «عالی» است.

# نتیجه‌گیری کلی

فناوری‌های ارزیابی‌شده مکمل یکدیگر هستند و نه رقیب هم.

OpenAPI به عنوان قرارداد رسمی و مرجع API تبدیل می‌شود.

Scalar به عنوان رابط کاربری ترجیحی برای مستندات تعاملی انتخاب می‌گردد.

NSwag به عنوان پلتفرم اصلی تولید SDK در نظر گرفته می‌شود.

Kiota برای سناریوهای توزیع SDKهای چندزبانه در آینده در دسترس باقی می‌ماند.

Swagger UI تنها برای حفظ سازگاری با نسخه‌های قبلی (Backward Compatibility) و در مواردی که الزامات سازمانی آن را ایجاب کنند، پشتیبانی خواهد شد.

# استراتژی قرارداد API

سند OpenAPI به **منبع واحد حقیقت (Single Source of Truth)** برای API عمومی تبدیل می‌شود.

تمامی مصنوعات پایین‌دستی باید از همان قرارداد تولید شوند.

آرتیفکت‌های تولیدشده عبارتند از:

- مستندات تعاملی؛
- SDKهای کلاینت؛
- تست‌های یکپارچه‌سازی (در آینده)؛
- متادیتای ابزارهای هوش مصنوعی (در آینده).

کپی‌برداری دستی از مستندات اندپوینت ممنوع است.

---

# استراتژی مستندسازی

مستندات تعاملی باید از موارد زیر استفاده کنند:

- **Scalar** به عنوان رابط کاربری (UI) پیش‌فرض.

Swagger UI تنها در موارد زیر باید در دسترس باقی بماند:

- نیاز یکپارچه‌سازی‌های قدیمی (Legacy) به آن؛
- وابستگی ابزارهای سازمانی موجود به آن.

این ابزار نباید رابط اصلی مستندسازی باشد.

---

# استراتژی تولید کلاینت

پروژه باید به جای نگهداری کلاینت‌های HTTP دست‌نویس، SDKهای دارای نوع‌داده قوی (Strongly Typed) تولید کند.

فناوری اصلی:

- NSwag

توسعه در آینده:

- Kiota، زمانی که تولید SDKهای چندزبانه رسمی به یکی از الزامات پروژه تبدیل شود.

---

# یکپارچه‌سازی با پایپ‌لاین ساخت (Build Pipeline)

پایپ‌لاین ساخت باید به‌صورت خودکار مراحل زیر را انجام دهد:

1. ساخت APIها.
2. تولید OpenAPI.

4. انتشار مستندات.

```text
   ▼

   ▼

```

هیچ‌گونه تولید دستی SDK نباید انجام شود.

# ملاحظات امنیتی

پلتفرم مستندسازی باید موارد زیر را به‌طور دقیق توصیف کند:

- احراز هویت JWT؛
- OAuth 2.1؛
- OpenID Connect؛
- الزامات مجوزدهی (Authorization).

با این حال:

مستندات هرگز جایگزین پیاده‌سازی امنیت نمی‌شوند.

احراز هویت همچنان توسط خودِ برنامه اعمال می‌شود.

# بی‌طرفی نسبت به ابر (Cloud Neutrality)

پشته (Stack) انتخاب‌شده کاملاً نسبت به ارائه‌دهنده ابری بی‌طرف باقی می‌ماند.

این پشته:

- هیچ‌گونه وابستگی انحصاری (Vendor Lock-in) ایجاد نمی‌کند؛
- هیچ وابستگی ران‌تایم اختصاصی ندارد؛
- هیچ محدودیتی برای پلتفرم ندارد.

مقاصد استقرار شامل موارد زیر است:

- ویندوز؛
- لینوکس؛
- کانتینرها؛
- کوبرنتیز (Kubernetes)؛
- ترکیبی (Hybrid)؛
- داخلی (On-Premise).

---

# آمادگی برای هوش مصنوعی (AI Readiness)

فناوری‌های انتخاب‌شده به‌طور قابل‌توجهی یکپارچه‌سازی آینده با هوش مصنوعی را بهبود می‌بخشند.

نمونه‌هایی از این موارد عبارتند از:

- فراخوانی ابزار (Tool Calling) توسط مدل‌های زبانی بزرگ (LLM) از طریق OpenAPI؛
- کشف خودکار API؛
- تولید SDK برای ایجنت‌های هوش مصنوعی؛
- درک معنایی اندپوینت‌ها.

بنابراین، این معماری با توسعه‌های آتی هوش مصنوعی همسو است.
