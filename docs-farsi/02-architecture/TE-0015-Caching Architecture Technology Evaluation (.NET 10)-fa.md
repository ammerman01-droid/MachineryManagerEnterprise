# هدف (Purpose)

این سند به ارزیابی فناوری‌های کاندید برای ارزیابی فناوری معماری کش‌گذاری (.NET 10) در سامانه MachineryManagerEnterprise می‌پردازد.

هدف، دستیابی به یک انتخاب فناوری یکپارچه است که تمام نیازمندی‌های کارکردی و معماری را برآورده ساخته و در عین حال اصول معماری پاک (Clean Architecture) را حفظ نماید.

# دامنه ارزیابی (Evaluation Scope)

این ارزیابی فناوری صرفاً انتخاب فناوری را مورد ارزیابی قرار می‌دهد.

جزئیات پیاده‌سازی توسط سوابق تصمیمات معماری (ADRs) متناظر تعیین می‌گردد.

# مراجع معماری (Architectural References)

این ارزیابی بر پایه موارد زیر استوار است:

- ADR-0001 — معماری پاک (Clean Architecture)
- ADR-0016 — معماری پیام‌رسانی سازمانی (Enterprise Messaging Architecture)
- ADR-0017 — یکپارچه‌سازی هوش مصنوعی (Artificial Intelligence Integration)
- ADR-0018 — معماری یکپارچه‌سازی خارجی (External Integration Architecture)

معماری کش‌گذاری حاصل باید همواره ویژگی‌های زیر را حفظ کند:

- مستقل از استقرار (deployment independent)؛

- ایزوله از زیرساخت (infrastructure isolated)؛
- بی‌طرف نسبت به ابر / ابرخنثی (cloud neutral).

- ترجیحات و تنظیمات کاربر (user preferences)؛

- داده‌های داشبورد (dashboard data)؛
- بهینه‌سازی نشست‌ها (session optimization).

# اصل معماری (Architectural Principle)

این ارزیابی از یک قاعده بنیادین معماری پیروی می‌کند:

کد برنامه هرگز نباید مستقیماً به یک پیاده‌سازی کش وابسته باشد.

در عوض، سرویس‌های برنامه منحصراً با لایه انتزاع کش (cache abstraction layer) تعامل برقرار می‌کنند.

سپس انتزاع کش آزاد است که از موارد زیر استفاده نماید:

- حافظه محلی (local memory)؛
- کش توزیع‌شده (distributed cache)؛
- کش هیبریدی و ترکیبی (hybrid cache)؛
- ارائه‌دهندگان آینده (future providers).

این تفکیک معماری، استقلال از ارائه‌دهنده و انعطاف‌پذیری استقرار را تضمین و حفظ می‌نماید.

# ۵. ارزیابی Microsoft HybridCache (.NET 10)

## نمای کلی (Overview)

فناوری HybridCache یک لایه انتزاعی یکپارچه کش‌گذاری است که توسط مایکروسافت برای برنامه‌های مدرن ASP.NET Core معرفی شده است.

به جای اینکه به عنوان یک پیاده‌سازی مستقل کش عمل کند، HybridCache یک API منسجم رو به برنامه ارائه می‌دهد که قادر است چندین لایه کش را به شکلی شفاف و خودکار هماهنگ (orchestrate) نماید.

هدف اصلی آن، ساده‌سازی کد برنامه در عین فراهم آوردن امکان ترکیب ارائه‌دهندگان مختلف کش در لایه زیرین است.

بنابراین، برنامه با یک انتزاع واحد کش تعامل دارد در حالی که HybridCache موارد زیر را هماهنگ می‌کند:

- کش درون‌حافظه‌ای محلی (local in-memory cache)؛
- کش توزیع‌شده (distributed cache)؛
- سریال‌سازی (serialization)؛
- محافظت در برابر هجوم هم‌زمان به کش (stampede protection)؛
- بارگذاری و مقداردهی داده‌های کش (cache population).

---

## نقش معماری (Architectural Role)

فناوری HybridCache یک کش توزیع‌شده **نیست**.

فناوری HybridCache جایگزینی برای Redis **نیست**.

فناوری HybridCache یک لایه هماهنگ‌سازی (orchestration layer) است که میان برنامه کاربردی و ارائه‌دهندگان کش قرار می‌گیرد.

```text
Application

      │

      ▼

HybridCache

      │

 ┌───────────────┐
 │ Memory Cache  │
 └───────────────┘
      │
      ▼
Distributed Cache
(Redis / NCache / Future Provider)
```

این معماری میزان وابستگی (coupling) بین منطق کسب‌وکار و زیرساخت را به شکل چشمگیری کاهش می‌دهد.

---

## نقاط قوت معماری (Architectural Strengths)

### مزایا (Advantages)

- پیاده‌سازی بومی .NET 10 (Native .NET 10 implementation).
- پشتیبانی رسمی مایکروسافت.
- مدل برنامه‌نویسی یکپارچه.
- محافظت داخلی در برابر هجوم هم‌زمان به کش (Built-in stampede protection).
- هماهنگ‌سازی خودکار کش‌ها.
- استقلال از ارائه‌دهنده.
- یکپارچگی عالی با تزریق وابستگی (Dependency Injection).
- رابط برنامه‌نویسی (API) ساده.
- بهره‌وری بالای توسعه‌دهندگان.
- قابلیت نگهداری فوق‌العاده.
- معماری تضمین‌شده برای آینده (Future-proof architecture).

---

## نقاط ضعف معماری (Architectural Weaknesses)

فناوری HybridCache به صورت عامدانه مسئولیت‌های ذخیره‌سازی را تفویض می‌کند.

بنابراین:

- برای استقرارهای توزیع‌شده، همچنان وجود یک ارائه‌دهنده توزیع‌شده ضروری است؛
- پیکربندی زیرساخت همچنان لازم است؛
- ماندگاری داده‌ها (persistence) کاملاً به بک‌اند انتخاب‌شده بستگی دارد.

این ویژگی‌ها تصمیمات طراحی معماری هستند و نه محدودیت‌های فنی.

---

## مشخصات عملیاتی (Operational Characteristics)

فناوری HybridCache موارد زیر را فراهم می‌کند:

- رابط ناهمگام (asynchronous API)؛
- هماهنگ‌سازی کش (cache orchestration)؛
- هماهنگی بارگذاری کش (cache population coordination)؛
- محافظت خودکار از هم‌زمانی (automatic concurrency protection)؛
- پایپ‌لاین سریال‌سازی (serialization pipeline)؛
- هماهنگی میان لایه‌های محلی و توزیع‌شده (local/distributed coordination).

پیچیدگی عملیاتی بسیار پایین ارزیابی می‌شود.

---

## مقیاس‌پذیری (Scalability)

خود HybridCache محدودیت مقیاس‌پذیری ناچیزی ایجاد می‌کند.

مقیاس‌پذیری کلی سیستم کاملاً به ارائه‌دهنده کش توزیع‌شده انتخاب‌شده وابسته است.

این تفکیک مسئولیت به خوبی با اصول معماری سازمانی هم‌راستا است.

---

## امنیت (Security)

مسئولیت‌های امنیتی به موارد زیر تفویض می‌شود:

- محیط میزبانی (hosting environment)؛
- ارائه‌دهنده کش توزیع‌شده (distributed cache provider)؛
- اعتبارسنجی و مجوزدهی برنامه (application authorization).

فناوری HybridCache هیچ سطح حمله مضاعفی به سیستم اضافه نمی‌کند.

---

## انعطاف‌پذیری استقرار (Deployment Flexibility)

فناوری HybridCache از محیط‌های زیر پشتیبانی می‌کند:

- دسکتاپ (Desktop)
- موبایل (Mobile)
- ویندوز (Windows)
- لینوکس (Linux)
- کانتینرها (Containers)
- کوبرنتیز (Kubernetes)
- ابر (Cloud)
- درون‌سازمانی (On-Premise)
- ترکیبی (Hybrid)

رفتار استقرار به صورت خودکار با ارائه‌دهندگان پیکربندی‌شده تطبیق می‌یابد.

---

## سازگاری با هوش مصنوعی (AI Compatibility)

فناوری HybridCache به ویژه برای سامانه‌های سازمانی مجهز به هوش مصنوعی بسیار مناسب است.

اهداف بالقوه کش‌گذاری عبارتند از:

- قالب‌های پرامپت (prompt templates)؛
- بردارهای امبدینگ (embedding vectors)؛
- نتایج بازیابی معنایی (semantic retrieval results)؛
- پیکربندی هوش مصنوعی (AI configuration)؛
- متادیتای مدل‌ها (model metadata)؛
- متادیتای استنتاج (inference metadata).

این امر محاسبات تکراری را به حداقل رسانده و تأخیر پاسخگویی را به شکل قابل توجهی کاهش می‌دهد.

---

## قابلیت نگهداری (Maintainability)

فناوری HybridCache انطباق قوی با موارد زیر دارد:

- معماری پاک (Clean Architecture)؛
- وارونگی وابستگی (Dependency Inversion)؛
- ایزولاسیون زیرساخت (Infrastructure Isolation)؛
- استقلال از ارائه‌دهنده (Provider Independence).

ماژول‌های کسب‌وکار کاملاً نسبت به موارد زیر بی‌خبر و مستقل باقی می‌مانند:

- ردیس (Redis)؛
- ان‌کش (NCache)؛
- فناوری‌های آینده کش.

تنها لایه انتزاعی برای آنها قابل مشاهده است.

## تناسب با MachineryManagerEnterprise

فناوری HybridCache تمام اهداف معماری تعیین‌شده برای پلتفرم را برآورده می‌سازد.

این فناوری یک پیاده‌سازی واحد را ممکن می‌سازد که قادر به پشتیبانی از موارد زیر است:

این انعطاف‌پذیری مستقیماً از استراتژی استقرار تعریف‌شده در ADR-0017 پشتیبانی می‌کند.

# ۶. ارزیابی IMemoryCache

## نمای کلی (Overview)

فناوری IMemoryCache پیاده‌سازی داخلی کش‌گذاری درون‌فرآیندی ارائه‌شده توسط مایکروسافت برای ASP.NET Core است.

برخلاف ارائه‌دهندگان کش توزیع‌شده، IMemoryCache اشیاء را منحصراً در حافظه فرآیند جاری ذخیره می‌کند.

این فناوری ویژگی‌های زیر را ارائه می‌دهد:

- دسترسی فوق‌العاده سریع؛
- تأخیر ناچیز؛
- ترافیک شبکه صفر؛
- پیکربندی ساده.

با این حال، طول عمر آن به یک نمونه واحد از برنامه محدود است.

---

## نقش معماری (Architectural Role)

فناوری IMemoryCache نشان‌دهنده **کش سطح ۱ (Level-1 Cache)** در پلتفرم است.

این مؤلفه هرگز نباید به عنوان کش اولیه و اصلی سازمانی در نظر گرفته شود.

در عوض، در معماری .NET 10 در لایه زیرین HybridCache عمل می‌کند.

```text
Application

      │

      ▼

HybridCache

      │

      ▼

IMemoryCache

(Process Local)
```

هنگامی که همراه با یک ارائه‌دهنده توزیع‌شده پیکربندی شود، HybridCache به طور خودکار تعامل بین کش محلی و کش توزیع‌شده را مدیریت می‌کند.

---

## نقاط قوت معماری (Architectural Strengths)

### مزایا (Advantages)

- پیاده‌سازی بومی .NET.
- تأخیر بسیار پایین.
- ترافیک شبکه صفر.
- عدم نیاز به زیرساخت خارجی.
- پشتیبانی عالی از تزریق وابستگی (Dependency Injection).
- پیکربندی بسیار ساده.
- خروجی و توان عملیاتی بالا (High throughput).
- عملکرد عالی در دسترسی به اشیاء.

---

## نقاط ضعف معماری (Architectural Weaknesses)

فناوری IMemoryCache به صورت عامدانه محدود است.

محدودیت‌های عمده عبارتند از:

- عدم ماندگاری داده‌ها (no persistence)؛
- فقط محلی درون فرآیند (process-local only)؛
- نامناسب برای سامانه‌های توزیع‌شده؛
- از بین رفتن داده‌های کش پس از راه‌اندازی مجدد (restart)؛
- عدم یکپارچگی و ناسازگاری داده‌ها میان چندین نمونه از برنامه.

در نتیجه، IMemoryCache به تنهایی برای استقرارهای سازمانی ناکافی است.

---

## مشخصات عملیاتی (Operational Characteristics)

فناوری IMemoryCache موارد زیر را فراهم می‌کند:

- کش‌گذاری اشیاء (object caching)؛
- انقضای مطلق (absolute expiration)؛
- انقضای لغزان (sliding expiration)؛
- سیاست‌های تخلیه حافظه (eviction policies)؛
- مدیریت فشار حافظه (memory pressure management).

پیچیدگی عملیاتی فوق‌العاده پایین است.

---

## مقیاس‌پذیری (Scalability)

فناوری IMemoryCache صرفاً به صورت عمودی (عمودی) مقیاس‌پذیر است.

هر نمونه برنامه صاحب یک کش مستقل است.

در نتیجه:

- همگام‌سازی کش وجود ندارد؛
- مقیاس‌پذیری افقی باعث ایجاد چندین کش مستقل می‌شود؛
- وضعیت مشترک سازمانی قابل نگهداری نیست.

---

## امنیت (Security)

از آنجا که تمام داده‌های کش‌شده درون حافظه فرآیند باقی می‌مانند:

# ۷. ارزیابی Redis

## نمای کلی (Overview)

ردیس (Redis) یک پلتفرم داده درون‌حافظه‌ای است که به طور گسترده به عنوان استاندارد صنعتی برای کش‌گذاری توزیع‌شده استفاده می‌شود.

درون معماری کش‌گذاری .NET 10، ردیس **مستقیماً** توسط ماژول‌های کسب‌وکار استفاده نمی‌شود.

در عوض، Redis به عنوان **ارائه‌دهنده اصلی کش توزیع‌شده سطح ۲ (Level-2 Distributed Cache Provider)** در لایه زیرین HybridCache عمل می‌کند.

مسئولیت‌های سازمانی معمول عبارتند از:

- کش توزیع‌شده؛
- وضعیت کش مشترک؛
- ذخیره‌سازی کلید/مقدار با سرعت بالا؛
- همگام‌سازی کش در میان نمونه‌های مختلف برنامه؛
- کش معنایی هوش مصنوعی (AI semantic cache)؛
- وضعیت نشست‌های توزیع‌شده (distributed session state).

---

## نقش معماری (Architectural Role)

ردیس لایه کش توزیع‌شده معماری را اشغال می‌کند.

```text

        │

        ▼

HybridCache

        │

 ┌───────────────┐
 │ IMemoryCache  │
 └───────────────┘

        │

        ▼

Redis

(Level-2 Distributed Cache)
```

ماژول‌های کسب‌وکار هرگز مستقیماً با Redis ارتباط برقرار نمی‌کنند.

زیرساخت به طور کامل پشت HybridCache ایزوله باقی می‌ماند.

---

## نقاط قوت معماری (Architectural Strengths)

### مزایا (Advantages)

- کارایی و عملکرد فوق‌العاده بالا.
- پلتفرم کش توزیع‌شده بالغ و آزموده‌شده.
- پذیرش اثبات‌شده در سطح سازمانی.
- مقیاس‌پذیری افقی عالی.
- چندسکویی (Cross-platform).
- بی‌طرف نسبت به ابر (Cloud neutral).
- اکوسیستم غنی در .NET.
- پشتیبانی از کلاسترینگ (clustering).
- پشتیبانی از تکثیر و همانندسازی (replication).
- پشتیبانی از دسترسی‌پذیری بالا (High Availability).
- پشتیبانی عالی از داکر (Docker).
- پشتیبانی عالی از کوبرنتیز (Kubernetes).

---

## نقاط ضعف معماری (Architectural Weaknesses)

ردیس زیرساخت اضافی معرفی می‌کند که نیازمند موارد زیر است:

- استقرار؛
- پایش و مانیتورینگ؛
- استراتژی پشتیبان‌گیری؛
- نگهداری عملیاتی.

با توجه به ماهیت متکی به حافظه، ماندگاری (persistence) باید بسته به نیازمندی‌های استقرار به درستی پیکربندی شود.

ردیس یک زیرساخت است و نه یک فریم‌ورک برنامه‌نویسی کاربردی.

---

## مشخصات عملیاتی (Operational Characteristics)

ردیس موارد زیر را فراهم می‌سازد:

- تکثیر و همانندسازی؛

پیچیدگی عملیاتی متوسط ارزیابی می‌شود.

# ۹. ارزیابی ASP.NET Core Output Cache (.NET 10)

## نمای کلی (Overview)

فناوری Output Cache فریم‌ورک مدرن کش پاسخ HTTP است که برای ASP.NET Core معرفی شده و در .NET 10 بهبود یافته است.

برخلاف HybridCache، IMemoryCache، Redis یا NCache، این فناوری اشیاء برنامه را کش **نمی‌کند**.

در عوض، پاسخ‌های کامل تولیدشده HTTP را کش‌گذاری می‌نماید.

هدف آن کاهش اجرای مکرر اندپوینت‌ها و بهبود چشمگیر تأخیر پاسخگویی برای منابع قابل کش‌گذاری است.

موارد کاربرد متداول عبارتند از:

- APIهای فقط‌خواندنی (read-only APIs)؛
- اندپوینت‌های جستجو و مراجعات (lookup endpoints)؛
- کوئری‌های داشبورد؛
- داده‌های کاتالوگ؛
- منابع عمومی؛
- اطلاعات مرجع.

---

## نقش معماری (Architectural Role)

فناوری Output Cache متعلق به لایه نمایش (Presentation Layer) است.

این فناوری بخشی از معماری کش‌گذاری برنامه **نیست**.

```text
                HTTP Request

                     │

                     ▼

             ASP.NET Core Endpoint

                     │

              Output Cache Layer

                     │

           Cached HTTP Response

                     │

                     ▼

                  Client
```

بنابراین Output Cache باید به عنوان یک مکانیزم بهینه‌سازی برای پاسخ‌های API دیده شود تا یک کش همه‌منظوره.

- حداقل پیکربندی.

- سیاست‌های کش داخلی.
- یکپارچگی عالی با ASP.NET Core.
- پشتیبانی از تزریق وابستگی.
- پیکربندی در سطح اندپوینت.
- کاهش مصرف CPU.

- کاهش بار استنتاج هوش مصنوعی.

- پاسخ‌های تولیدشده توسط هوش مصنوعی.
