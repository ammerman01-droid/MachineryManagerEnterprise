# هدف (Purpose)

این سند به ارزیابی مجدد فناوری نگاشت اشیاء (Object Mapping) مورد استفاده در سراسر راهکار MachineryManagerEnterprise می‌پردازد.

نگاشت اشیاء یک دغدغه عرضی (Cross-cutting concern) است که تقریباً تمام ماژول‌های پلتفرم را تحت تاثیر قرار می‌دهد: ماژول‌های دارایی‌ها (Assets)، ناوگان (Fleet)، نگهداری پیشگیرانه (Preventive Maintenance)، نگهداری اصلاحی (Corrective Maintenance)، انبارداری (Inventory)، تدارکات (Procurement)، دستورات کار (Work Orders) و گزارش‌گیری (Reporting) همگی به تبدیل موجودیت‌ها (Entities) و ریشه‌های تجمیعی (Aggregates) به اشیاء انتقال داده (DTOs)، و تبدیل فرمان‌ها (Commands) و درخواست‌ها (Requests) به اشیاء دامنه وابسته هستند. از آنجا که این دغدغه در تمامی هندلرهای لایه کاربرد (Application layer handlers) در تمام ماژول‌ها حضور دارد، درستی، کارایی و پایداری بلندمدت فناوری نگاشت انتخابی، تاثیری چندبرابر کننده بر قابلیت نگهداری کل پایگاه کد خواهد داشت.

هدف از این ارزیابی عبارت است از:
- تایید اینکه آیا Mapster به عنوان فناوری مصوب فعلی نگاشت اشیاء (TE-0006 / ADR-0008)، با رشد پلتفرم به سمت همگام‌سازی فضای کاری توزیع‌شده (Distributed Workspace synchronization)، کلاینت‌های دسکتاپ/موبایل (TE-0010 — .NET MAUI)، و تعداد بسیار بیشتری از DTOها نسبت به زمان ارزیابی اولیه، همچنان انتخاب صحیحی باقی می‌ماند یا خیر؛
- ارزیابی Mapperly، یک نگاشت‌کننده مبتنی بر تولید کد منبع زمان کامپایل (Compile-time source-generated mapper) که از زمان تدوین TE-0006 به بلوغ چشمگیری رسیده و در آن زمان به عنوان یک کاندیدای سازمانی واقعی وجود نداشت؛
- ارزیابی مجدد AutoMapper با توجه به تغییرات اساسی در مدل مجوزدهی (Licensing) که پس از ارزیابی اولیه TE-0006 رخ داده است؛
- تایید مجدد نگاشت دستی (Manual Mapping) به عنوان مبنای مقایسه و به عنوان یک راهکار خروج اضطراری رسمی برای نگاشت‌های پیچیده و سرشار از قوانین تجاری.

این ارزیابی یا تصمیم ADR-0008 را مجدداً تایید می‌نماید یا جایگزینی آن را پیشنهاد می‌دهد. این سند به خودی خود معماری مصوب را تغییر نمی‌دهد؛ هرگونه تغییر در فناوری مصوب نیازمند یک ADR جدید یا اصلاح‌شده خواهد بود.

# ارتباط با TE-0006 / ADR-0008 (Relationship with TE-0006 / ADR-0008)

نگاشت اشیاء در ابتدا در **TE-0006 — Mapster** ارزیابی شد و به طور رسمی از طریق **ADR-0008 — استفاده از Mapster** (وضعیت: پذیرفته‌شده) به تصویب رسید.

این ارزیابی آن تصمیم را باطل تلقی نمی‌کند و نشان‌دهنده یک بازطراحی معماری بی‌دلیل نیست. این سند به این دلیل وجود دارد که معمار راهکار خواستار یک ارزیابی مجدد کامل و متقارن شامل Mapster به عنوان گزینه مستقر در کنار تمامی جایگزین‌های واقعی، با همان عمق ارزیابی اعمال‌شده برای سایر ارزیابی‌های فناوری پروژه شده است.

بنابراین Mapster در ادامه به عنوان کاندیدای **مستقر (Incumbent)** گنجانده شده و دقیقاً بر اساس همان معیارها و با همان عمق سایر کاندیداها ارزیابی می‌شود. سند TE-0006 به عنوان سابقه تاریخی تصمیم اولیه باقی می‌ماند. این سند تنها در صورتی جایگزین TE-0006 خواهد شد که توصیه نهایی در ادامه، فناوری متفاوتی از Mapster را برگزیند.

# محدوده (Scope)

این ارزیابی نگاشت شیء به شیء (Object-to-object mapping) مورد استفاده برای موارد زیر را پوشش می‌دهد:
- پروجکشن Entity → DTO (سمت خواندن / کوئری‌ها)
- ساخت Command / Request → Entity یا Value Object (سمت نوشتن)
- تبدیل DTO → DTO در مرزهای ماژول‌ها
- پروجکشن Aggregate → Read Model برای سناریوهای گزارش‌گیری
- نگاشت‌های مورد استفاده صرفاً در داخل لایه کاربرد (Application layer)

موارد زیر صراحتاً **خارج از محدوده (Out of scope)** این ارزیابی هستند:
- نگاشت پایداری داده (پیکربندی موجودیت‌های EF Core، نگاشت فلوئنت، مبدل‌های مقادیر) — پوشش داده شده در TE-0004 / ADR-0006 و سند آتی TE-0024 (ارزیابی فناوری دسترسی به داده).
- سریال‌سازی مورد استفاده برای بسته‌های همگام‌سازی فضای کاری توزیع‌شده — پوشش داده شده به صورت جداگانه تحت GAP-003 (فرمت بسته همگام‌سازی).
- سریال‌سازی JSON برای پاسخ‌های API (با System.Text.Json) — یک دغدغه متعامد که در مرز لایه نمایش مدیریت می‌شود نه توسط کتابخانه نگاشت اشیاء.

# نیازمندی‌های کارکردی (Functional Requirements)

راهکار انتخابی باید از موارد زیر پشتیبانی نماید:
- تخت‌سازی (Flattening) و بازسازی ساختار (Unflattening) گراف‌های اشیاء تو در تو؛
- پروجکشن به `IQueryable` به طوری که عبارات نگاشت بتوانند توسط Entity Framework Core به جای اجرا در حافظه، به دستورات SQL ترجمه شوند؛
- نگاشت مجموعه‌ها، از جمله مجموعه‌های تو در تو از اشیاء مقداری (Value Objects)؛
- نگاشت شرطی و منطق تبدیل سفارشی (مانند تبدیل Enum به String، فیلدهای محاسباتی، قالب‌بندی ارز)؛
- نگاشت دوطرفه (Two-way mapping) در مواردی که صراحتاً توسط یک ماژول الزام شده است؛
- یکپارچگی با خطوط لوله FluentValidation (سند TE-0005 / ADR-0007) و MediatR (سند TE-0009 / ADR-0011) بدون نقض مرزهای لایه‌ها؛
- مدیریت مناسب انواع مرجع با قابلیت پذیرش مقدار تهی تحت `Nullable enable`.

---

# نیازمندی‌های غیرکارکردی (Non-Functional Requirements)

راهکار باید موارد زیر را فراهم آورد:
- کارایی زمان اجرای بالا با حداقل تخصیص حافظه هیپ (Heap allocations)، با توجه به حجم عملیات نگاشت مورد انتظار در خوانش‌های کنتور، سوابق نگهداری و کوئری‌های گزارش‌گیری ناوگان؛
- سربار پایین در زمان راه‌اندازی (Startup overhead)، هم برای برنامه Host و هم برای کلاینت‌های دسکتاپ/موبایل که زمان Cold-start در آنها اهمیت بیشتری نسبت به سرور دارد؛
- ایمنی زمان کامپایل (Compile-time safety) تا حد امکان، جهت کاهش خطاهای ناشی از تغییر نام ویژگی و فراموشی به‌روزرسانی نگاشت؛
- پایداری بلندمدت مجوز استفاده سازگار با سیاست اولویت متن‌باز (ADR-0002)؛
- سازگاری عالی با .NET 10، از جمله سازگاری با Native AOT و Trimming برای بیلد‌های آتی دسکتاپ/موبایل؛
- بار نگهداری پایین با رشد مدل دامنه در بین حوزه‌های متنی محدود (Bounded Contexts) متعدد.

# اصل معماری (Architecture Principle)

نگاشت اشیاء باید منحصراً در لایه کاربرد (Application layer) محصور بماند.

```text
Domain Layer (Entities, Aggregates, Value Objects)
        │
        ▼
Application Layer
   Commands / Queries / Handlers
   Mapping happens here only
        │
        ▼
Presentation Layer (DTOs / View Models / API Contracts)
```

موجودیت‌های دامنه هرگز نباید به کتابخانه‌های نگاشت ارجاع داشته باشند.
پروژه SharedKernel هرگز نباید به کتابخانه نگاشت ارجاع دهد.
لایه زیرساخت (Infrastructure) هرگز نباید نگاشت DTO را انجام دهد؛ مسئولیت آن در لایه پایداری داده خاتمه می‌یابد.
پیکربندی نگاشت باید در هر ماژول در یک کلاس نگاشت اختصاصی یا نگاشت‌کننده تولیدشده به صورت متمرکز باقی بماند، نه اینکه به صورت پراکنده و موردی در داخل هندلرهای جداگانه دستور/کوئری تعریف شود.

# 6. ارزیابی Mapster (گزینه مستقر) (Mapster Evaluation - Incumbent)

## نمای کلی (Overview)

ابزار Mapster یک نگاشت‌کننده مبتنی بر قرارداد برای دات‌نت است. این ابزار از هر دو حالت نگاشت بازتابی/عبارت‌های کامپایل‌شده در زمان اجرا (حالت پیش‌فرض) و تولید کد منبع زمان کامپایل مبتنی بر Roslyn از طریق `Mapster.Tool` و `MapsterMapper` با ویژگی‌های `[AdaptTo]` / `[AdaptFrom]` / `[MapperAttribute]` پشتیبانی می‌کند. این ابزار در ابتدا بر اساس TE-0006 تحت ADR-0008 برای MachineryManagerEnterprise تصویب شده بود.

## نقش معماری (Architectural Role)

```text
Application Layer
   CreateAssetCommandHandler
          │
          ▼
   entity.Adapt<AssetDto>()
          │
          ▼
   Presentation Layer (DTO)
```

برای کوئری‌های سمت خواندن، Mapster مستقیماً در برابر `IQueryable<T>` استفاده می‌شود:

```text
Repository (IQueryable<Asset>)
          │
          ▼
   query.ProjectToType<AssetListItemDto>()
          │
          ▼
   Translated to SQL by EF Core
          │
          ▼
   Executed against SQL Server
```

ابزار Mapster منحصراً در داخل هندلرهای لایه کاربرد و کلاس‌های اختصاصی الحاقی نگاشت (مانند `AssetMappingExtensions`) استفاده می‌شود و هرگز توسط پروژه‌های Domain یا Infrastructure ارجاع داده نمی‌شود.

## نقاط قوت معماری (Architectural Strengths)

- کارایی زمان اجرای عالی که در بنچمارک‌های مستقل همواره با کدهای نگاشت دست‌نویس رقابت می‌کند.
- پشتیبانی از نگاشت مبتنی بر قرارداد بدون نیاز به پیکربندی (`Adapt<T>()`) برای حالت‌های معمول و پیکربندی صریح `TypeAdapterConfig` برای مواردی که نیازمند قوانین سفارشی هستند.
- قابلیت اختیاری تولید کد منبع زمان کامپایل که در صورت فعال‌سازی، بازتاب (Reflection) را کاملاً حذف کرده و بیشتر فاصله کارایی و زمان راه‌اندازی با Mapperly را جبران می‌کند.
- پشتیبانی بومی از `ProjectToType<T>()` برای `IQueryable` که به طور تمیز از طریق EF Core به SQL ترجمه می‌شود — امری حیاتی برای کوئری‌های گزارش‌گیری و نمایش لیست که نباید تمام گراف موجودیت را در حافظه لود کنند.
- تشریفات کدنویسی بسیار ناچیز در حالت‌های عمومی: تغییر نام یا افزودن یک فیلد به DTO معمولاً به هیچ تغییر پیکربندی نیاز ندارد زیرا Mapster بر اساس تطابق نام نگاشت می‌کند.
- پشتیبانی پیش‌فرض از تخت‌سازی (`Engine.SerialNumber` → `EngineSerialNumber`) که به وفور در DTOهای دارایی و قطعات استفاده می‌شود.
- پیکربندی سراسری می‌تواند از طریق `TypeAdapterConfig.GlobalSettings.Compile()` تست واحد شود تا نگاشت‌های ناموجود پیش از اجرای برنامه کشف شوند.

## نقاط ضعف معماری (Architectural Weaknesses)

- هنگامی که تولید کد منبع به صورت صریح فعال نشده باشد، نگاشت همچنان به درخت‌های عبارت کامپایل‌شده در زمان راه‌اندازی متکی است و به طور کامل در زمان کامپایل بررسی نمی‌شود — خطاهای نگاشت در گراف‌های پیچیده ممکن است در زمان اجرا ظاهر شوند نه در زمان ساخت.
- جامعه کاربری و منابع آموزشی کوچک‌تر نسبت به AutoMapper، هرچند این فاصله نسبت به زمان ارزیابی اولیه TE-0006 بسیار کاهش یافته است.
- ثبت سراسری `TypeAdapterConfig` در صورت عدم رعایت نظم در ماژول‌ها می‌تواند به منبعی ضمنی و نامشخص از رفتارهای ناخواسته تبدیل شود.
- فعال‌سازی تولید کد منبع به بسته زمان ساخت اضافه (`Mapster.Tool`) و راه‌اندازی اولیه نیاز دارد.

## ویژگی‌های عملیاتی (Operational Characteristics)

ابزار Mapster نیازمند هیچ زیرساخت زمان اجرای اختصاصی نیست. پیکربندی نگاشت یک بار در زمان راه‌اندازی برنامه (معمولاً در `DependencyInjection.cs` هر ماژول) ثبت شده و در طول عمر فرآیند استفاده می‌شود. هیچ سرویس خارجی، حافظه موقت یا پایگاه داده‌ای درگیر نیست.

## مقیاس‌پذیری (Scalability)

کارایی با افزایش تعداد انواع نگاشت‌شده پایدار می‌ماند. هزینه راه‌اندازی اولیه به میزان ناچیزی با افزایش قوانین ثبت‌شده افزایش می‌یابد که حتی در مقیاس بیش از ۲۰ ماژول تعریف‌شده در سند 02-CapabilityModel.md کاملاً قابل چشم‌پوشی است. توان عملیاتی نگاشت زمان اجرا به صورت خطی با اندازه گراف اشیاء مقیاس می‌پذیرد و هیچ افتی تحت بارهای همزمان مورد انتظار از یک میزبان Blazor Server با کاربران متعدد نشان نمی‌دهد.

## امنیت (Security)

ابزار Mapster صرفاً نگاشت اشیاء درون حافظه را انجام می‌دهد. این ابزار ورودی‌های غیرقابل اعتماد را به عنوان کد اجرا نمی‌کند، داده‌های خارجی را مستقیماً سریال‌زدایی نمی‌کند و هیچ سطح حمله معنی‌داری ایجاد نمی‌نماید. هیچ آسیب‌پذیری شناخته‌شده‌ای (CVE) در نسخه فعلی وجود ندارد.

## تجربه توسعه‌دهنده (Developer Experience)

حالت مبتنی بر قرارداد پیش‌فرض Mapster بدین معنی است که توسعه‌دهندگان به ندرت کدهای نگاشت صریح می‌نویسند؛ دستور `entity.Adapt<Dto>()` برای اکثر قریب به اتفاق سناریوها کافی است. در صورت نیاز به منطق سفارشی، `TypeAdapterConfig` یک API روان و قابل کشف ارائه می‌دهد. منحنی یادگیری برای تیمی که با پایگاه کد فعلی آشناست عملاً صفر است.

## قابلیت نگهداری (Maintainability)

خوب است، به شرطی که پیکربندی نگاشت به جای تعریف موردی در هندلرها، در هر ماژول به صورت متمرکز نگه داشته شود. این نظم بر اساس قراردادهای تعیین‌شده در پروژه به خوبی پیاده‌سازی شده است.

## سازگاری با هوش مصنوعی (AI Compatibility)

ارتباط مستقیمی با ابزارهای AI ندارد زیرا نگاشت یک جزئیات پیاده‌سازی داخلی است و هیچ قرارداد خارجی که توسط عامل‌های AI یا LLM Tool Calling مصرف شود ایجاد نمی‌کند.

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

کاملاً چندسکویی: ویندوز، لینوکس، کانتینرها و تمام اهداف .NET 10 از جمله کلاینت‌های دسکتاپ/موبایل (.NET MAUI). ابزار Mapster هیچ وابستگی به ارائه‌دهندگان ابری ایجاد نمی‌کند.

## کاربرد معمول (Typical Usage)

```csharp
public sealed class AssetMappingExtensions
{

    {
        config.NewConfig<Asset, AssetDto>()
            .Map(dest => dest.EngineSerialNumber, src => src.Engine.SerialNumber)
            .Map(dest => dest.CurrentOperatingHours, src => src.MeterReadings.Latest().Value);

// Application layer handler
public async Task<AssetDto> Handle(GetAssetByIdQuery request, CancellationToken ct)
{
    var asset = await _repository.GetByIdAsync(request.AssetId, ct);
    return asset.Adapt<AssetDto>();
}

// IQueryable projection, translated to SQL
public async Task<List<AssetListItemDto>> Handle(ListAssetsQuery request, CancellationToken ct)
{
    return await _dbContext.Assets
        .Where(a => a.OrganizationId == request.OrganizationId)
        .ProjectToType<AssetListItemDto>()
        .ToListAsync(ct);
}
```

## ارتباط با Entity Framework Core

## نتیجه‌گیری اولیه (Preliminary Conclusion)

ابزار Mapster همچنان تمامی نیازمندی‌های کارکردی و غیرکارکردی اولیه را برآورده ساخته و ریسک جدیدی ایجاد نمی‌کند. بلوغ پروجکشن `IQueryable` و پیش‌فرض‌های مبتنی بر قرارداد بدون زحمت آن، تطابق فوق‌العاده‌ای با مونولیت ماژولار مبتنی بر Clean Architecture و CQRS در این مقیاس دارد و گزینه مستقر قدرتمندی باقی می‌ماند.

# 7. ارزیابی Mapperly (Mapperly Evaluation)

## نمای کلی (Overview)

ابزار Mapperly (`Riok.Mapperly`) یک مولد منبع افزایشی Roslyn (Incremental source generator) است که کدهای نگاشت زمان کامپایل را از روی اعلان کلاس‌ها یا اینترفیس‌های جزئی (`partial`) تولید می‌کند. برخلاف تولید منبع اختیاری در Mapster، ابزار Mapperly بر اساس رویکرد اولویت با تولید کد طراحی شده است — هیچ مسیر بازتابی پشتیبان وجود ندارد و هیچ مرحله پیکربندی در زمان اجرا وجود ندارد. این ابزار از زمان ارزیابی اولیه TE-0006 به بلوغ بالایی دست یافته و اکنون یک کاندیدای سازمانی واقعی است.

## نقش معماری (Architectural Role)

```text
Application Layer
   [Mapper]
   public partial class AssetMapper
   {
       [MapProperty(nameof(Asset.Engine.SerialNumber), nameof(AssetDto.EngineSerialNumber))]
       public partial AssetDto ToDto(Asset entity);
       public partial IQueryable<AssetListItemDto> ProjectToListItem(IQueryable<Asset> query);
   }
          │  (generated entirely at compile time)
          ▼
   Generated mapping method
   (plain C#, no reflection, no expression tree compilation)
```

## نقاط قوت معماری (Architectural Strengths)

- کدهای نگاشت به طور کامل در زمان کامپایل تولید می‌شوند؛ ویژگی‌های نگاشت‌نشده، عدم تطابق انواع داده و اعضای غیرقابل دسترس هشدارهای زمان ساخت تولید می‌کنند (قابل تنظیم به عنوان خطا یا هشدار). این امر مستقیماً با سیاست `TreatWarningsAsErrors` پروژه همسو بوده و اشتباه نگاشت را به خطای ساخت تبدیل می‌کند نه نقص در محیط عملیاتی.
- عدم استفاده از بازتاب و عدم کامپایل عبارات در زمان اجرا — متدهای نگاشت تولیدشده کدهای معمولی C# هستند و کارایی هم‌تراز با کدهای دست‌نویس با حداقل تخصیص حافظه ارائه می‌دهند.
- قابلیت اشکال‌زدایی کامل: کدهای تولیدشده در IDE قابل مشاهده بوده و مانند هر فایل منبع دیگری قابل Step-through هستند.
- مجوز MIT، نگهداری فعال، بدون لایه تجاری و بدون برنامه تجاری‌سازی.
- ردپای وابستگی بسیار ناچیز: یک بسته تحلیل‌گر که فقط در زمان ساخت استفاده می‌شود و هیچ موتور بازتاب زمان اجرایی به همراه برنامه مستقر نمی‌شود.
- هشدارهای قابل تنظیم برای هر نگاشت (مانند الزام به نگاشت تمام ویژگی‌های مقصد).

## نقاط ضعف معماری (Architectural Weaknesses)

- صریح‌تر بودن نسبت به Mapster: هر سطح نگاشت نیازمند اعلان یک متد partial در یک کلاس یا اینترفیس partial است که تشریفات بیشتری نسبت به دستور تک‌خطی `Adapt<T>()` دارد.
- پشتیبانی از پروجکشن `IQueryable` هرچند به درستی کار می‌کند، اما برای پروجکشن‌های عمیقاً تو در تو و شرطی ترکیب‌شده انعطاف کمتری نسبت به `ProjectToType<T>()` در Mapster دارد.
- جامعه کاربری کوچک‌تر و سابقه کوتاه‌تر در سیستم‌های سازمانی بزرگ دات‌نت در مقایسه با Mapster و AutoMapper.
- مهاجرت کل پایگاه کد از Mapster به Mapperly نیازمند تغییر تمامی فراخوانی‌های `Adapt<T>()` و ثبت‌های DI در تمام ماژول‌ها است.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند هیچ پیکربندی در زمان اجرا نیست؛ تمام رفتارهای نگاشت در زمان کامپایل تثبیت می‌شوند. این امر دسته‌ای از خطاهای مربوط به ترتیب راه‌اندازی و انحراف پیکربندی را کاملاً از بین می‌برد.

## مقیاس‌پذیری (Scalability)

از نظر زمان اجرا بسیار عالی مقیاس می‌پذیرد زیرا نگاشت برای هر ماژول تولید شده و هیچ هزینه جستجوی پیکربندی در زمان اجرا وجود ندارد. زمان کامپایل نیز با افزایش ماژول‌ها به صورت خطی و قابل پیش‌بینی افزایش می‌یابد.

## امنیت (Security)

نگاشت صرفاً درون حافظه است و به دلیل عدم وجود موتور بازتاب در زمان اجرا، سطح حمله امنیتی آن از نظر تئوری حتی از Mapster نیز کوچک‌تر است.

## تجربه توسعه‌دهنده (Developer Experience)

نیازمند تشریفات اولیه بیشتری نسبت به Mapster است (تعریف کلاس/متد partial)، اما بازخورد فوری کامپایلر در IDE هنگام ناقص بودن نگاشت، این هزینه را جبران می‌کند.

## قابلیت نگهداری (Maintainability)

برای نگهداری بلندمدت عالی است: تغییرات شکننده در انواع نگاشت‌شده (تغییر نام ویژگی، حذف فیلد، تغییر قابلیت پذیرش مقدار تهی) توسط کامپایلر شناسایی می‌شوند نه در محیط عملیاتی یا تست‌های یکپارچگی.

## سازگاری با هوش مصنوعی (AI Compatibility)

ارتباط مستقیمی ندارد؛ همانند Mapster یک دغدغه پیاده‌سازی داخلی است.

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

کاملاً چندسکویی و ذاتاً سازگار با Native AOT و Trimming به دلیل تولید کدهای C# معمولی بدون بازتاب. این یک مزیت معنادار برای برنامه‌های آتی دسکتاپ/موبایل (.NET MAUI, TE-0010) است.

# 8. ارزیابی AutoMapper (AutoMapper Evaluation)

## نمای کلی (Overview)

ابزار AutoMapper شناخته‌شده‌ترین نگاشت‌کننده مبتنی بر قرارداد در اکوسیستم دات‌نت است که در ابتدا در TE-0006 به دلایل کارایی و عملکردی رد شد. این ابزار در اینجا جهت تکمیل ارزیابی و به دلیل تغییر بنیادین در مدل مجوزدهی آن مجدداً ارزیابی می‌شود.

## تغییر اساسی از زمان TE-0006: وضعیت مجوزدهی (Material Change Since TE-0006: Licensing)

از زمان ارزیابی اولیه TE-0006، مدل مجوزدهی AutoMapper دستخوش تغییر اساسی شده است. از تاریخ ۲ ژوئیه ۲۰۲۵، AutoMapper (به همراه MediatR) تحت شرکت Lucky Penny Software به یک مدل تجاری تغییر یافته است. نسخه‌های جدید تحت مجوز Reciprocal Public License 1.5 (RPL 1.5) که یک مجوز کپی‌لفت است توزیع می‌شوند نه مجوز مجاز قبلی (MIT). یک سطح رایگان برای جامعه کاربری وجود دارد، اما سازمان‌های با درآمد بالاتر از آستانه معین موظف به خرید مجوز تجاری هستند. نسخه‌های قبلی منتشرشده با مجوز MIT همچنان قابل استفاده هستند اما هیچ به‌روزرسانی یا وصله امنیتی جدیدی دریافت نمی‌کنند. این پروژه همچنین به دلیل عدم تطابق RPL 1.5 با معیارهای بنیاد، از .NET Foundation خارج شده است.

این موضوع مستقیماً با **ADR-0002 — سیاست اولویت متن‌باز** در تعارض است که کتابخانه‌های متن‌باز را الزامی می‌داند مگر اینکه استثنایی صراحتاً در یک ADR تصویب شده باشد.

## نقش معماری (Architectural Role)

```text
Application Layer
   CreateAssetCommandHandler
          │
          ▼
   _mapper.Map<AssetDto>(entity)      (IMapper, reflection-based)
          │
          ▼
   Presentation Layer (DTO)
```

## نقاط قوت معماری (Architectural Strengths)

- جامعه کاربری بسیار وسیع، مستندات غنی و بیشترین تعداد آموزش‌ها.
- مدل پیکربندی بالغ مبتنی بر Profile.
- پشتیبانی قوی از پروجکشن `IQueryable` از طریق `ProjectTo<T>()`.
- قابلیت اعتبارسنجی داخلی پیکربندی (`AssertConfigurationIsValid()`) در زمان راه‌اندازی برنامه.

## نقاط ضعف معماری (Architectural Weaknesses)

- متکی بر بازتاب و کامپایل درخت عبارات در زمان اجرا؛ به طور مداوم کندتر و دارای تخصیص حافظه بیشتر نسبت به Mapster و Mapperly در بنچمارک‌ها.
- اعتبارسنجی فقط در زمان راه‌اندازی رخ می‌دهد نه در زمان کامپایل.
- **ریسک مجوزدهی**: پذیرش نسخه‌های جدید نیازمند مجوز تجاری مداوم و استثنا در ADR-0002 است.
- تثبیت روی آخرین نسخه دارای مجوز MIT باعث از دست رفتن به‌روزرسانی‌ها، وصله‌های امنیتی و بهبودهای .NET 10 می‌شود که این خود یک ریسک معماری برای نگهداری وابستگی رهاشده است.
- پیچیدگی پیکربندی با افزایش کلاس‌های Profile و مبدل‌های سفارشی در سیستم‌های بزرگ به طور غیرخطی رشد می‌کند.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند ثبت سینگلتون `IMapper` در زمان راه‌اندازی با هزینه اعتبارسنجی متناسب با تعداد نگاشت‌ها.

## مقیاس‌پذیری (Scalability)

توان عملیاتی پایین‌تر نسبت به Mapster و Mapperly تحت بارهای معادل به دلیل سربار بازتاب، که در گراف‌های بزرگ اشیاء دارایی‌ها محسوس‌تر می‌شود.

## امنیت (Security)

تثبیت بر روی نسخه قدیمی MIT به منظور اجتناب از هزینه مجوزدهی به معنای از دست دادن تمامی وصله‌های امنیتی آینده است — رویکردی که برای یک پلتفرم سازمانی با نقشه راه چندساله غیرقابل قبول است.

## تجربه توسعه‌دهنده (Developer Experience)

برای اکثر توسعه‌دهندگان دات‌نت آشناست، اما این مزیت به دلیل تغییرات مجوزدهی و هشدارهای تجاری تحت الشعاع قرار گرفته است.

## قابلیت نگهداری (Maintainability)

# 9. ارزیابی نگاشت دستی (Manual Mapping Evaluation)

## نمای کلی (Overview)

نگاشت دستی به معنای نگارش دست‌نویس کدهای نگاشت است که معمولاً به صورت متدهای الحاقی استاتیک یا کلاس‌های نگاشت اختصاصی بدون استفاده از هیچ‌گونه کتابخانه خارجی پیاده‌سازی می‌شود.

## نقش معماری (Architectural Role)

```text
Application Layer
   CreateAssetCommandHandler
          │
          ▼
   AssetMappingExtensions.ToDto(entity)   (plain static method, hand-written)
          │
          ▼
   Presentation Layer (DTO)
```

## نقاط قوت معماری (Architectural Strengths)

- حداکثر کنترل و شفافیت؛ بدون پیچیدگی‌های پنهان (No magic)، کاملاً قابل اشکال‌زدایی و قابل فهم برای هر برنامه‌نویس C#.
- عدم وجود وابستگی شخص ثالث و در نتیجه عدم وجود هرگونه ریسک مجوزدهی — قوی‌ترین موضع در رابطه با ADR-0002.
- ایمنی زمان کامپایل به صورت ذاتی: کامپایلر انتساب هر ویژگی را دقیقاً کنترل می‌کند.
- منحنی یادگیری صفر برای نیروهای جدید.
- تست‌پذیری بسیار ساده با تست‌های واحد معمولی بدون نیاز به زیرساخت خاص کتابخانه‌ای.

## نقاط ضعف معماری (Architectural Weaknesses)

- حجم بالای کدهای تکراری (Boilerplate) برای گراف‌های بزرگ یا متغیر اشیاء به ویژه در DTOهای دارایی‌ها.
- ریسک بالاتر فراموشی نگاشت فیلدهای تازه اضافه‌شده به دلیل نبود موتور تطبیق خودکار.
- هزینه نگهداری بلندمدت بسیار بالا با افزایش تعداد DTOها در ماژول‌های متعدد (دارایی‌ها، نگهداری، انبار، تدارکات و...).
- عدم پشتیبانی توکار از پروجکشن `IQueryable`؛ عبارات باید به صورت دستی برای هر کوئری نوشته شوند که خطر عدم یکنواختی را افزایش می‌دهد.

## ویژگی‌های عملیاتی (Operational Characteristics)

هیچ زیرساختی در زمان اجرا یا زمان ساخت فراتر از کامپایل معمولی C# نیاز نیست؛ بدون مرحله ثبت و بدون شیء پیکربندی.

## مقیاس‌پذیری (Scalability)

از نظر تلاش توسعه‌دهندگان (نه کارایی زمان اجرا) با افزایش تعداد انواع نگاشت‌ها در ماژول‌های پرتعداد پلتفرم مقیاس‌پذیری ضعیفی دارد و نیازمند ده‌ها کلاس دست‌نویس بدون زیرساخت یکپارچه خواهد بود.

## امنیت (Security)

قوی‌ترین موضع امنیتی ممکن زیرا هیچ کتابخانه شخص ثالثی در درخت وابستگی وجود ندارد.

## تجربه توسعه‌دهنده (Developer Experience)

برای DTOهای کوچک و ثابت سرراست است، اما برای DTOهای با ده‌ها ویژگی یا تغییرات مکرر خسته‌کننده می‌شود.

## قابلیت نگهداری (Maintainability)

برای تعداد اندکی از DTOهای ساده قابل قبول است، اما در مقیاس این پلتفرم با Bounded Contextهای متعدد به یک بار سنگین نگهداری تبدیل می‌شود.

## سازگاری با هوش مصنوعی (AI Compatibility)

ارتباطی ندارد.

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

کاملاً بی‌طرف و مستقل.

## کاربرد معمول (Typical Usage)

```csharp
public static class AssetMappingExtensions
{
    public static AssetDto ToDto(this Asset entity)
    {
        return new AssetDto
        {
            Id = entity.Id,
            Name = entity.Name,
            EngineSerialNumber = entity.Engine?.SerialNumber,
            CurrentOperatingHours = entity.MeterReadings.Latest()?.Value ?? 0
        };
    }
}

public async Task<AssetDto> Handle(GetAssetByIdQuery request, CancellationToken ct)
{
    var asset = await _repository.GetByIdAsync(request.AssetId, ct);
    return asset.ToDto();
}
```

## معیارهای تصمیم برای پذیرش آتی Mapperly

```text
IF Native AOT / trimming becomes a hard requirement
   for Desktop or Mobile clients (ADR-0013 / TE-0010)
THEN re-open this evaluation and evaluate a phased
   migration from Mapster to Mapperly for the affected
   client-side mapping surfaces only.
```

## توصیه‌های امنیتی (Security Recommendations)

## آمادگی برای هوش مصنوعی (AI Readiness)

برای این ارزیابی قابل اعمال نیست.

این ارزیابی تصمیم **ADR-0008 — استفاده از Mapster** را بدون تغییر **مجدداً تایید می‌نماید**. این امر نیازمند ADR جدید نیست زیرا تصمیم و دلایل آن تغییری نکرده است؛ این سند صرفاً دلایل ثبت‌شده را برای پاسخگویی به تغییرات Mapperly و AutoMapper بسط داده و نگاشت دستی را به عنوان مکمل رسمی مستند می‌سازد.

پیشنهاد می‌شود به سند **ADR-0008** یک الحاقیه کوتاه اضافه شود که تایید مجدد آن را از طریق TE-0023 در تاریخ 2026-07-27 قید کند.
