# گزینه ۱ — SQLite

## نمای کلی

SQLite یک موتور پایگاه داده رابطه‌ایِ تعبیه‌شده و سبک است که به‌عنوان یک کتابخانه بدون سرور (Serverless) پیاده‌سازی شده است.

این فناوری یکی از پرکاربردترین فناوری‌های پایگاه داده تعبیه‌شده است و تقریباً بر روی تمامی سیستم‌عامل‌های مدرن در دسترس می‌باشد.

SQLite داده‌ها را در یک فایل پایگاه داده واحد و قابل‌حمل ذخیره می‌کند و در عین حال تضمین‌های کامل تراکنشی ACID را ارائه می‌دهد.

---

## مزایا

- بسیار بالغ و پایدار.
- دارای مجوز مالکیت عمومی (Public Domain).
- دسترس‌پذیری عالی در پلتفرم‌های مختلف.
- پشتیبانی بومی در ویندوز، اندروید و iOS.
- عملکرد عالی برای بارهای کاری تعبیه‌شده.
- سازگار با تراکنش‌های ACID.
- حجم بسیار کم برای استقرار (Deployment).
- یکپارچگی عالی با اکوسیستم .NET.
- جامعه کاربری بزرگ و مستندات گسترده.
- پذیرش اثبات‌شده در سطح سازمانی.
- عدم نیاز به سرور پایگاه داده مجزا.
- پشتیبانی عالی از پشتیبان‌گیری و بازیابی اطلاعات.

---

## معایب

- معماری تک‌نویسنده (Single-writer).
- پشتیبانی محدود برای بارهای کاری با نوشتار همزمان بسیار بالا.
- عدم وجود مدل ذخیره‌سازی سند (Document) داخلی.
- مقیاس‌پذیری افقی در این مورد کاربرد ندارد.

این محدودیت‌ها قابل‌قبول هستند؛ زیرا پایگاه‌های داده فضای کاری (Workspace) برای عملیات محلی تعبیه‌شده طراحی شده‌اند، نه برای بارهای کاری سروری با همزمانی بالا.

# کاندیدای ۲ — LiteDB

## نمای کلی (Overview)

LiteDB یک پایگاه‌داده اسناد NoSQL داخلی است که به‌طور کامل در .NET پیاده‌سازی شده است.

این پایگاه‌داده، اسناد BSON را در یک فایل واحد ذخیره می‌کند و به هیچ سرور خارجی نیاز ندارد.

LiteDB بر سادگی برای توسعه‌دهندگان و یکپارچگی بومی با .NET تأکید دارد.

---

## مزایا (Advantages)

- پیاده‌سازی خالص .NET.
- مجوز MIT.
- استقرار بسیار آسان.
- پایگاه‌داده تک‌فایلی.
- ماندگاری (Persistence) بومی اشیاء.
- یکپارچگی قدرتمند با C#.
- ردپای حافظه (Footprint) کوچک.
- کارایی مناسب برای بارهای کاری مبتنی بر اسناد.
- استراتژی پشتیبان‌گیری ساده.

---

## معایب (Disadvantages)

- اکوسیستم کوچک‌تر نسبت به SQLite.
- پذیرش سازمانی (Enterprise adoption) کمتر.
- فاقد زبان پرس‌وجوی SQL.
- اکوسیستم ابزاری محدود.
- ابزارهای تشخیص (Diagnostic) کمتر.
- تاریخچه پشتیبانی بلندمدت با بلوغ کمتر.

# کاندیدای ۳ — Realm Database

## نمای کلی (Overview)

Realm Database یک پایگاه‌داده شیءگرا و داخلی است که توسط MongoDB توسعه یافته است.

این پایگاه‌داده در درجه اول برای اپلیکیشن‌های موبایل طراحی شده است و یک مدل ماندگاری اشیاء را با قابلیت‌های همگام‌سازی خودکار از طریق اکوسیستم MongoDB فراهم می‌کند.

---

## مزایا (Advantages)

- کارایی عالی در موبایل.
- مدل داده‌ای شیءگرای بومی.
- ماندگاری بسیار کارآمد اشیاء.
- در دسترس بودن میان‌‌پلتفرمی.
- تجربه کاربری قوی برای توسعه‌دهندگان موبایل.
- قابلیت‌های همگام‌سازی خودکار (اختیاری).
- معماری مدرن.

---

## معایب (Disadvantages)

- پایگاه‌داده شیءگرا است، نه رابطه‌ای (Relational).
- اکوسیستم .NET کوچک‌تر در مقایسه با SQLite.
- قابلیت‌های سازمانی به‌شدت با پلتفرم MongoDB گره خورده‌اند.
- پیچیدگی معماری اضافی برای سازمان‌هایی که از MongoDB استفاده نمی‌کنند.
- جامعه کاربری محدودتر در داخل اکوسیستم .NET.

## سازگاری

| نیازمندی | نتیجه |
|------------|--------|
| سازگاری با معماری تمیز (Clean Architecture) | خوب |
| دسترسی چندسکویی (Cross Platform) | عالی |
| قابلیت آفلاین-اول (Offline First) | عالی |
| تراکنش‌های ACID | خوب |
| کارایی | عالی |
| مقیاس‌پذیری | خوب |
| یکپارچگی با دات‌نت (.NET) | قابل قبول |
| لایسنس | خوب |
| ابزارها و تشخیص خطا | خوب |

سازگاری کلی **خوب** ارزیابی می‌شود.

## ریسک‌ها

| ریسک | احتمال | تأثیر | کاهش اثر |
|------|-------------|--------|------------|
| وابستگی به اکوسیستم فروشنده | متوسط | متوسط | از قابلیت‌های اختیاری همگام‌سازی ابری اجتناب شود مگر در صورت ضرورت |
| بلوغ کمتر در اکوسیستم دات‌نت | متوسط | متوسط | استفاده محدود به APIهای دارای پشتیبانی رسمی |

---

## ارزیابی مقدماتی

Realm عملکرد جاسازی‌شده (Embedded) بسیار خوبی را ارائه می‌دهد، به‌ویژه در پلتفرم‌های موبایل.

با این حال، وابستگی شدیدتر آن به اکوسیستم MongoDB، نسبت به SQLite مزایای معماری کمتری برای یک پلتفرم سازمانی مستقل از فناوری فراهم می‌کند.

# کاندیدای ۴ — SQL Server LocalDB

## بررسی اجمالی

SQL Server LocalDB نسخه سبک‌وزن مایکروسافت از SQL Server است که در درجه اول برای سناریوهای توسعه محلی در نظر گرفته شده است.

اگرچه این گزینه سازگاری کامل با SQL Server را فراهم می‌کند، اما فقط در ویندوز در دسترس است.

---

## مزایا

- سازگاری کامل با SQL Server.
- موتور رابطه‌ای بالغ.
- قابلیت‌های عالی SQL.
- ابزارهای قدرتمند از طریق اکوسیستم SQL Server.
- یکپارچگی عالی با Entity Framework.

---

## معایب

- انحصاری برای ویندوز.
- عدم پشتیبانی از اندروید.
- عدم پشتیبانی از iOS.
- عدم مناسب بودن برای پیاده‌سازی جاسازی‌شده (Embedded) چندسکویی.
- نیازمند مؤلفه‌های زمان اجرای (Runtime) SQL Server.
- حجم پیاده‌سازی (Deployment) بیشتر.

# جایگزین‌های بررسی‌شده

## LiteDB

LiteDB یک دیتابیس سند-محور (Document Database) تعبیه‌شده و متمرکز بر .NET ارائه می‌دهد.

با این حال، بلوغ اکوسیستم و پذیرش سازمانی بلندمدت آن همچنان پایین‌تر از SQLite است.

---

## دیتابیس Realm

Realm امکان پایداری اشیاء (Object Persistence) عالی و عملکرد موبایل قدرتمندی را فراهم می‌کند.

وابستگی آن به اکوسیستم MongoDB، یک جفت‌شدگی (Coupling) معماری اضافی ایجاد می‌کند که برای معماری پلتفرم فعلی غیرضروری است.

---

## SQL Server LocalDB

SQL Server LocalDB به دلیل سازگاری عالی با SQL Server مورد ارزیابی قرار گرفت.

این گزینه رد شد زیرا نمی‌تواند الزامات استقرار اجباری در ویندوز، اندروید و iOS را برآورده کند.

# توصیه نهایی

## فناوری انتخاب‌شده

**SQLite**

---

### منطق تصمیم‌گیری

SQLite تمامی الزامات معماری اجباری تعیین‌شده توسط موارد زیر را برآورده می‌کند:

- ADR-0001 — معماری تمیز (Clean Architecture)
- ADR-0012 — معماری فضای کاری توزیع‌شده
- ADR-0013 — معماری برنامه کلاینت
- ADR-0014 — معماری داده‌های فضای کاری

SQLite موارد زیر را ارائه می‌دهد:

- در دسترس بودن عالی در پلتفرم‌های مختلف.
- بلوغ اثبات‌شده در سطح سازمانی.
- سازگاری تراکنشی ACID.
- قابلیت‌های آفلاین برجسته.
- استقلال تکنولوژیک.
- پیچیدگی استقرار حداقلی.
- پایداری بلندمدت.
- یکپارچگی عالی با اکوسیستم .NET.

هیچ‌کدام از جایگزین‌های ارزیابی‌شده، تناسب معماری کلی برتری نسبت به آن ندارند.

بنابراین، SQLite به عنوان فناوری پایداری داده‌های تعبیه‌شده (Embedded) برای پیاده‌سازی‌های Workspace تایید می‌شود.

---

## راهنمای پیاده‌سازی

پیاده‌سازی باید معماری منطقی داده‌های فضای کاری (Workspace Data Architecture) تعریف‌شده در ADR-0014 را حفظ کند.

انتخاب SQLite تغییری در تفکیک منطقی بین موارد زیر ایجاد **نمی‌کند**:

- داده‌های اصلی (Master Data)
- داده‌های پروژه (Project Data)
- داده‌های کاربر (User Data)

توپولوژی ذخیره‌سازی فیزیکی باید در طول پیاده‌سازی و در عین حفظ مرزهای معماری تعریف‌شده در ADR-0014 تعیین گردد.
