# هدف (Purpose)

این سند به ارزیابی فناوری مورد استفاده برای ذخیره‌سازی محتوای فایل‌های باینری — تصاویر، اسناد بازرسی، دفترچه‌های راهنما و پیوست‌های مشابه — در سراسر راهکار MachineryManagerEnterprise می‌پردازد.

سند `03-TechnologyGapAnalysis.md` پیش‌تر **ذخیره‌سازی تعبیه‌شده فایل (Embedded File Storage)** را به‌عنوان یک شکاف مستندشده (اولویت: متوسط) شناسایی کرده که نیازمند یک **استراتژی همگام‌سازی فایل (File Synchronization Strategy)** به‌عنوان پیش‌ران قابلیت است. همچنین سند `ADR-0012 — Distributed Workspace Architecture` تعیین نموده که پیوست‌های تجاری (تصاویر، اسناد بازرسی، راهنماها) به‌صورت مجزا از متادیتای تجاری انتقال می‌یابند؛ به این صورت که متادیتای پیوست در بسته همگام‌سازی باقی می‌ماند در حالی که محتوای باینری به‌صورت مستقل و محتوا-پایه انتقال می‌یابد. این ارزیابی فناوری ذخیره‌سازی ملموسی را انتخاب می‌کند که این نیازمندی معماری از پیش تعیین‌شده را برآورده سازد.

هدف از این ارزیابی عبارت است از:

- انتخاب فناوری ذخیره‌سازی برای پیوست‌های باینری در استقرار سرور (Host)؛
- اطمینان از ترکیب و انطباق صحیح فناوری منتخب با مدل همگام‌سازی فضاهای کاری توزیع‌شده (ADR-0012)؛
- حفظ بی‌طرفی نسبت به ارائه‌دهندگان ابری (Cloud Neutrality) و انطباق حداکثری با سیاست اولویت با متن‌باز (ADR-0002).

# دامنه (Scope)

این ارزیابی موارد زیر را پوشش می‌دهد:

- ذخیره‌سازی و بازیابی محتوای باینری پیوست‌ها (تصاویر، اسناد بازرسی، راهنماها و فایل‌های مشابه) در استقرار سرور؛
- لایه انتزاعی که لایه کاربرد برای خواندن و نوشتن فایل‌ها استفاده می‌کند؛
- انتقال محتوای باینری برای بسته‌های همگام‌سازی در فضاهای کاری توزیع‌شده مطابق با ADR-0012.

موارد خارج از دامنه:

- پایداری **متادیتای** پیوست‌ها (نام فایل، اندازه، نوع محتوا، اگریگیت مالک) — داده‌های متادیتا در جداول رابطه‌ای توسط EF Core مدیریت می‌شوند (ADR-0006 / TE-0024)؛
- ایندکس‌گذاری متن کامل یا جستجو روی محتوای اسناد — در TE-0027 پوشش داده می‌شود؛
- پردازش تصویر و سند (تولید تصویر بندانگشتی، OCR) — در حال حاضر جزو نیازمندی‌های تعریف‌شده نیست.

# نیازمندی‌های کارکردی (Functional Requirements)

راهکار انتخاب‌شده باید موارد زیر را پشتیبانی کند:

- آپلود، دانلود و حذف فایل‌های باینری با استفاده از یک شناسه یکتا، پایدار و مات (Opaque Identifier) به جای مسیرهای سیستم فایل محلی؛
- خواندن و نوشتن به‌صورت استریم (Streaming) جهت جلوگیری از لود کامل فایل‌های سنگین در حافظه RAM؛
- تعریف یک اینترفیس انتزاعی (`IFileStorage`) در لایه کاربرد جهت استقلال کامل کدهای دامنه و کاربرد از پیاده‌سازی ذخیره‌سازی؛
- پشتیبانی بومی از مدل همگام‌سازی توزیع‌شده و آدرس‌پذیری بر اساس محتوا (Content-addressable) جهت راستی‌آزمایی یکپارچگی داده‌ها (ADR-0012).

# نیازمندی‌های غیرکارکردی (Non-Functional Requirements)

راهکار باید موارد زیر را فراهم آورد:

- انعطاف‌پذیری در استقرار (On-premise، تک‌سرور محلی و میزبانی ابری)، با توجه به تنوع بلوغ فناوری اطلاعات در شرکت‌های پیمانکاری هدف؛
- بی‌طرفی نسبت به ارائه‌دهندگان ابری (Cloud Neutrality)؛
- قابلیت پیش‌بینی هزینه‌ها در محیط‌های محلی بدون تحمیل هزینه‌های جاری ابری؛
- توان عملیاتی و کارایی بالا در آپلود هم‌زمان تصاویر بازرسی توسط تکنسین‌های میدانی با کلاینت‌های دسکتاپ/موبایل (ADR-0013 / TE-0010).

# اصل معماری (Architecture Principle)

دسترسی به ذخیره‌سازی فایل باید منحصراً از طریق یک انتزاع در لایه کاربرد صورت پذیرد و لایه‌های بالاتر هرگز نباید مستقیماً با سرویس فیزیکی در ارتباط باشند.

```text
Application Layer (لایه کاربرد)
   IFileStorage  (آپلود / دانلود / حذف / دریافت URL موقت)
        │
        ▼
Infrastructure Layer (لایه زیرساخت)
   LocalFileStorage | AzureBlobFileStorage | S3CompatibleFileStorage
        │
        ▼
   ذخیره‌سازی فیزیکی (دیسک محلی / Azure Blob / MinIO / اندپوینت سازگار با S3)
```

- موجودیت‌های دامنه هرگز نباید به فناوری ذخیره‌سازی رفرنس داشته باشند؛ آن‌ها صرفاً یک شناسه پایدار پیوست را نگهداری می‌کنند.
- پروژه SharedKernel هرگز نباید به فناوری ذخیره‌سازی رفرنس داشته باشد.

# ۵. ارزیابی ذخیره‌سازی محلی (Local Storage)

## نقاط قوت و ضعف

- **نقاط قوت:** صفر درصد وابستگی به سرویس خارجی، صفر هزینه اضافی، سادگی بی‌نظیر برای مشتریان کوچک تک‌سرور، پشتیبانی‌گیری آسان روی دیسک محلی.
- **نقاط ضعف:** عدم مقیاس‌پذیری افقی روی چند سرور؛ فقدان افزونگی داخلی؛ دشواری در ارائه لینک‌های مستقیم دانلود امن برای کلاینت‌های آفلاین در مدل همگام‌سازی ADR-0012 بدون ایجاد اندپوینت‌های اختصاصی و سفارشی.

---

# ۶. ارزیابی Azure Blob Storage (Azure Blob Storage Evaluation)

## نقاط قوت و ضعف

- **نقاط قوت:** سرویس کاملاً مدیریت‌شده ابری، افزونگی جغرافیایی و دوام فوق‌العاده داده‌ها، پشتیبانی بومی از SAS Tokenها برای دانلود مستقیم و مستقل کلاینت‌ها (ADR-0012)، SDK بسیار باکیفیت دات‌نت از مایکروسافت.
- **نقاط ضعف:** عدم بی‌طرفی ابری و قفل شدن به مایکروسافت آژور؛ هزینه‌های متغیر و جاری بر اساس ترافیک و حجم داده؛ عدم امکان اجرا در شبکه‌های کاملاً محلی یا ایزوله (Air-gapped) بدون اتصال به اینترنت.

---

# ۷. ارزیابی MinIO (MinIO Evaluation)

## نمای کلی و نقاط قوت

سرور MinIO یک سیستم ذخیره‌سازی شیء متن‌باز، بسیار سریع و منطبق با API استاندارد S3 آمازون است که قابلیت استقرار On-premise، در کانتینرها، کوبرنتیز و محیط‌های ابری خصوصی را دارد.

- **نقاط قوت:** متن‌باز بودن و انطباق با سیاست ADR-0002؛ سازگاری کامل با API پروتکل S3؛ قابلیت استقرار در محیط‌های کاملاً محلی و ایزوله آفلاین؛ پشتیبانی بومی از Pre-signed URLها برای همگام‌سازی کلاینت‌های ADR-0012؛ هزینه زیرساختی کاملاً ثابت و قابل پیش‌بینی.
- **نقاط ضعف:** نیازمند مدیریت کانتینر و پیکربندی افزونگی/کلاستر توسط تیم عملیات (در مقایسه با سرویس تماماً مدیریت‌شده ابری).

---

# ۸. ارزیابی انتزاع ذخیره‌سازی سازگار با S3 (S3-Compatible Storage Abstraction)

## نمای کلی و رویکرد معماری

این گزینه یک سرویس خاص نیست، بلکه یک **الگوی معماری** است: پیاده‌سازی اینترفیس `IFileStorage` در لایه زیرساخت با استفاده از پکیج استاندارد `AWSSDK.S3` بر اساس پروتکل استاندارد S3. از آنجا که MinIO، AWS S3، Cloudflare R2 و Wasabi همگی از این پروتکل پشتیبانی می‌کنند، برنامه با یک پیاده‌سازی واحد و صرفاً از طریق تغییر کانفیگ (`ServiceUrl` و کلیدها) می‌تواند به هر یک از این سرویس‌ها متصل شود.

```text
Application Layer
   IFileStorage
        │
        ▼
Infrastructure Layer
   S3CompatibleFileStorage (یک پیاده‌سازی واحد با AWS SDK for .NET)
        │
        ├──► MinIO (استقرار محلی سلف‌هاستد در سرور مشتری)
        ├──► AWS S3 (سرویس مدیریت‌شده ابری)
        ├──► Cloudflare R2 (سرویس ابری با ترافیک خروجی رایگان)
        └──► هر اندپوینت استاندارد سازگار با S3
```

# ۱۰. پیشنهاد و تصمیم نهایی (Final Recommendation & Decision)

## پشته اصلی فناوری‌ها

| مسئولیت | فناوری انتخاب‌شده | دلیل انتخاب |
|---|---|---|
| پیاده‌سازی اصلی `IFileStorage` | ذخیره‌سازی سازگار با S3 (با AWS SDK for .NET) | پیاده‌سازی واحد، بی‌طرفی کامل ابری، بیشترین انعطاف در استقرار |
| اندپوینت پیش‌فرض محلی (On-Premise) | MinIO | متن‌باز، سازگار با شبکه‌های ایزوله، هزینه ثابت، پشتیبانی بومی از URLهای زمان‌دار |
| اندپوینت ابری مدیریت‌شده (اختیاری) | AWS S3 یا سایر سرویس‌های سازگار | قابل فعال‌سازی صرفاً با تغییر تنظیمات بدون تغییر کد |
| ذخیره‌سازی محلی دیسک (Local Storage) | حفظ به‌عنوان گزینه یدکی برای سرورهای بسیار کوچک | راه‌اندازی بدون نیاز به سرور شیء در سناریوهای حداقلی |
