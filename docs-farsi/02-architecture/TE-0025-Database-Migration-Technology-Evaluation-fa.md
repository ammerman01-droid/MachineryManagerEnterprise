# هدف (Purpose)

این سند فناوری مورد استفاده برای مدیریت تکامل اسکیمای پایگاه داده رابطه‌ای (relational database schema evolution) را در سراسر راهکار MachineryManagerEnterprise ارزیابی می‌کند.

سند TE-0004 / ADR-0006 فریم‌ورک Entity Framework Core را به عنوان ORM پلتفرم تایید کرد و به طور گذرا اشاره نمود که EF Core «پشتیبانی بالغی از مهاجرت (mature migration support)» ارائه می‌دهد. این ارزیابی آن دغدغه خاص را به صورت مجزا و با همان عمقی که در سایر اسناد ارزیابی فناوری انجام شده است بررسی می‌کند و صراحتاً این پرسش را مطرح می‌سازد که آیا ابزار مهاجرت‌های EF Core (یعنی EF Core Migrations) همچنان مکانیزم صحیح برای تکامل اسکیما باقی می‌ماند یا اینکه یک ابزار مهاجرت اختصاصی و مستقل از ORM (نظیر DbUp، Flyway یا Liquibase) خدمات بهتری به پلتفرم ارائه خواهد داد — به ویژه با توجه به اینکه سند TE-0024 فریم‌ورک Dapper را به عنوان یک مکمل حاکمیت‌پذیر و فقط‌خواندنی (read-only) برای EF Core معرفی کرده است، که این امر موضوع «چه کسی مالک اسکیما است» را به یک سوال صریح معماری به جای یک فرض ضمنی تبدیل می‌کند.

هدف از این ارزیابی عبارت است از:

- تایید EF Core Migrations به عنوان مکانیزم تکامل اسکیمای پلتفرم، همسو با ADR-0006 و قانون مالکیت اسکیما که در استراتژی پایداری ترکیبی (Hybrid Persistence Strategy) در سند TE-0024 تعیین شده است؛
- ارزیابی DbUp، Flyway و Liquibase به عنوان ابزارهای اختصاصی و مستقل از ORM برای مهاجرت؛
- تعیین اینکه آیا هر یک از این گزینه‌های جایگزین باید جایگزین EF Core Migrations شوند یا در کنار آن اجرا گردند.

# ارتباط با TE-0004 / ADR-0006 و TE-0024 (Relationship with TE-0004 / ADR-0006 and TE-0024)

سند **TE-0004 / ADR-0006** فریم‌ورک EF Core را به عنوان ORM تصویب کرد و به صورت ضمنی EF Core Migrations را به عنوان ابزار همراه آن برای تکامل اسکیما فرض نمود، بدون اینکه جایگزین‌ها را به طور مستقیم ارزیابی کند.

سند **TE-0024 — ارزیابی فناوری دسترسی به داده (Data Access Technology Evaluation)**، به عنوان یکی از پنج قانون حاکمیتی استراتژی پایداری ترکیبی (Hybrid Persistence Strategy) خود، تعیین کرد که «مالکیت اسکیما نزد EF Core Migrations باقی می‌ماند» و توجیه کامل این مالکیت را صراحتاً به این ارزیابی موکول کرد.

این ارزیابی وجود دارد تا این تصمیم مالکیت را به جای یک فرض، به تصمیمی صریح و ارزیابی‌شده تبدیل کند. در صورتی که EF Core Migrations به عنوان انتخاب صحیح تایید شود، قانون حاکمیتی TE-0024 مجدداً مورد تاکید قرار می‌گیرد.

# محدوده (Scope)

این ارزیابی موارد زیر را پوشش می‌دهد:

- مکانیزم مورد استفاده برای ایجاد، نسخه‌بندی، اعمال و بازگردانی (rollback) تغییرات اسکیمای پایگاه داده رابطه‌ای در تمام محیط‌ها (توسعه محلی، CI، محیط آزمایشی Staging و محیط عملیاتی Production)؛
- ارتباط بین مهاجرت‌های اسکیما و مدل EF Core مورد استفاده برای پایداری در سمت نوشتن (write-side) و مسیر پیش‌فرض کوئری در سمت خواندن (read-side).

- استراتژی مقداردهی اولیه داده‌ها (data seeding) برای داده‌های مرجع/پایه‌ای (یک دغدغه مرتبط اما مجزا که در اینجا ارزیابی نمی‌شود)؛

# اصل معماری (Architecture Principle)

تکامل اسکیما باید دقیقاً یک مالک داشته باشد. هر ابزاری که انتخاب شود، مجموعه تغییرات معتبر و دارای ترتیب اسکیما را تولید یا اعمال می‌کند؛ هیچ ابزار یا فرآیند دستی دیگری مجاز به تغییر اسکیما در خارج از آن مکانیزم نیست.

```text
EF Core Model (Domain-driven entity shape)
        │
        ▼
Migration Tool (generates/applies ordered SQL scripts)
        │
        ▼
SQL Server Database (single authoritative schema)
        ▲
        │
Dapper (TE-0024) — read-only, never alters schema
```

# 5. ارزیابی EF Core Migrations (گزینه فعلی - Incumbent)

## نمای کلی (Overview)

ابزار EF Core Migrations مکانیزم داخلی و رسمی (first-party) تکامل اسکیما است که درون Entity Framework Core تعبیه شده است. این ابزار کلاس‌های مهاجرت C# را مستقیماً از تغییرات شناسایی‌شده در مدل EF Core تولید می‌کند و آنها را به ترتیب از طریق `dotnet ef database update` یا `context.Database.Migrate()` اعمال می‌نماید.

## نقش معماری (Architectural Role)

```text
Domain / Application Layer
   Entity model changes (e.g. new property on Asset)
          │
          ▼
Infrastructure Layer
   dotnet ef migrations add AddAssetWarrantyExpiryDate
          │
          ▼
   Generated C# Migration (Up/Down methods)
          │
          ▼
   dotnet ef database update  →  SQL Server
```

## نقاط قوت معماری (Architectural Strengths)

- مستقیماً از مدل EF Core تولید می‌شود و تضمین می‌کند که اسکیما و نگاشت موجودیت هرگز نمی‌توانند به صورت خاموش از یکدیگر انحراف پیدا کنند — که این بزرگ‌ترین مزیت معماری منفرد نسبت به هر ابزار مستقل از ORM است.
- مهاجرت‌ها به صورت کد C# هستند و از طریق همان فرآیند Pull-Request مشابه با سایر تغییرات قابل بازبینی می‌باشند و از پشتیبانی کامل IDE (مانند IntelliSense و ایمنی بازآفرینی کد حین تغییر نام ویژگی‌های موجودیت‌ها) برخوردارند.
- متدهای توکار `Up()` و `Down()` یک مکانیزم بازگردانی بومی بدون نیاز به ابزار دوم یا اسکریپت‌های معکوس دست‌نویس فراهم می‌کنند.
- صفر پکیج یا زیرساخت اضافی: در حال حاضر به عنوان بخشی از وابستگی EF Core که قبلاً تحت ADR-0006 تصویب شده بود، وجود دارد.
- متد `context.Database.Migrate()` به سادگی درون یک سرویس میزبان زمان راه‌اندازی (startup hosted service) یا مرحله استقرار CI/CD یکپارچه می‌شود و به هیچ ابزار ارکستراسیون اضافی نیاز ندارد.

## نقاط ضعف معماری (Architectural Weaknesses)

- کدهای SQL تولید شده، هرچند به طور کلی قابل اعتماد هستند، اما برای سناریوهای پیشرفته (مانند پر کردن مجدد و پیچیده داده‌ها همزمان با تغییرات اسکیما، یا ایجاد نمای ایندکس‌شده خاص SQL Server) همیشه در سطح SQL خام به اندازه اسکریپت‌های مهاجرت دست‌نویس قابل تنظیم دقیق یا بازبینی نیستند.
- طبق طراحی با مدل EF Core جفت شده است — این یک نقطه قوت برای تضمین سازگاری است، اما به این معنی است که تغییر اسکیمایی که از تغییر مدل EF Core نشات نمی‌گیرد (مانند ایندکس عملکردی ایجاد شده توسط DBA) همچنان باید به عنوان یک مهاجرت EF Core بیان شود تا در منبع واحد حقیقت باقی بماند، که این موضوع ممکن است برای متخصصان پایگاه داده که بیشتر به ابزارهای SQL دست‌نویس عادت دارند غیرمستقیم به نظر برسد.
- اجرای مهاجرت‌های رو به عقب (Down-migrations) در برابر داده‌های محیط عملیاتی همیشه ایمن نیست (مثلاً حذف یک ستون نمی‌تواند داده‌ها را بازگرداند)؛ محدودیتی که بین تمام کاندیداهای ارزیابی‌شده در اینجا مشترک است و مختص EF Core نیست.

## ویژگی‌های عملیاتی (Operational Characteristics)

در حال حاضر کاملاً عملیاتی است؛ مهاجرت‌ها از طریق `AppDbContext` موجود و ابزار استاندارد `dotnet ef` اعمال می‌شوند و به هیچ کامپوننت زمان اجرای جدیدی نیاز ندارند.

## مقیاس‌پذیری (Scalability)

در حجم تغییرات اسکیمای مورد انتظار برای این پلتفرم بدون هیچ مشکلی مقیاس‌پذیر است؛ زمان اعمال مهاجرت متناسب با SQL تولید شده است که در این زمینه با هر ابزار دیگری در این ارزیابی یکسان است.

## ایمنی بازگردانی / اصلاح رو به جلو (Rollback / Forward-Fix Safety)

متدهای بومی `Down()` یک مسیر بازگردانی برای تغییرات برگشت‌پذیر فراهم می‌کنند. برای تغییرات غیرقابل برگشت (عملیات‌های تخریب‌کننده داده)، همان انضباط اصلاح رو به جلو (forward-fix) که توسط هر کاندیدای دیگری لازم است، در اینجا نیز به همان اندازه صدق می‌کند — این یک دغدغه فرآیندی است نه ابزاری.

## امنیت (Security)

مهاجرت‌ها با همان اعتبارسنجی‌های پایگاه داده (database credentials) که در حال حاضر رشته اتصال برنامه را کنترل می‌کنند اجرا می‌شوند؛ هیچ گواهی یا حساب کاربری سرویس اضافی معرفی نمی‌شود.

## تجربه توسعه‌دهنده (Developer Experience)

برای تیم عالی است، زیرا مهاجرت‌ها به زبان C# و درون همان پایگاه کد و همان گردش کار pull-request که برای سایر تغییرات استفاده می‌شود نوشته می‌شوند، بدون نیاز به تغییر زمینه (context-switch) به یک DSL مهاجرت مجزا یا ابزار خارجی.

## قابلیت نگهداری (Maintainability)

عالی: از آنجا که مهاجرت‌ها از مدل EF Core مشتق می‌شوند، مدل و اسکیما هرگز نمی‌توانند به صورت خاموش از یکدیگر فاصله بگیرند، که این امر دسته‌ای کامل از نقص‌های ناشی از «عدم تطابق اسکریپت مهاجرت با موجودیت» را که ابزارهای مستقل از ORM از نظر ساختاری در معرض آن هستند، از بین می‌برد.

## یکپارچگی با CI/CD (CI/CD Integration)

ساده و سرراست: دستور `dotnet ef database update` (یا فراخوانی `Migrate()` در زمان راه‌اندازی با محافظت بررسی محیط) مستقیماً و بدون نیاز به نصب ابزار اضافی در پایپ‌لاین ساخت و استقرار موجود .NET ادغام می‌شود که مستقیماً به سند آتی TE-0031 مرتبط است.

## سازگاری با هوش مصنوعی (AI Compatibility)

قابل اعمال نیست (Not applicable).

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

کاملاً چندسکویی (cross-platform)؛ ابزار EF Core Migrations بر روی ویندوز، لینوکس و عامل‌های کانتینری CI/CD به صورت یکسان اجرا می‌شود و تا حدی که مدل ارائه‌دهنده EF Core اجازه می‌دهد مستقل از ارائه‌دهنده است.

## ارتباط با استراتژی پایداری ترکیبی (TE-0024)

ابزار EF Core Migrations مستقیماً قانون حاکمیتی سند TE-0024 مبنی بر اینکه «مالکیت اسکیما نزد EF Core Migrations باقی می‌ماند» را پیاده‌سازی می‌کند. مخازن داده خواندنی مبتنی بر Dapper که تحت آن استراتژی معرفی شدند، هرگز تغییرات اسکیما را ایجاد یا اعمال نمی‌کنند؛ آنها فقط اسکیمایی را که EF Core Migrations تولید می‌کند مصرف می‌نمایند.

ابزار EF Core Migrations همچنان به عنوان منبع واحد حقیقت معتبر، مشتق‌شده از مدل و صحیح برای تکامل اسکیما باقی می‌ماند و تعهد حاکمیتی که پیشتر در TE-0024 ایجاد شده بود را مستقیماً برآورده می‌سازد.

# 6. ارزیابی DbUp (DbUp Evaluation)

## نمای کلی (Overview)

کتابخانه DbUp یک کتابخانه سبک و متن‌باز در اکوسیستم .NET است که پوشه‌ای از اسکریپت‌های SQL نسخه‌بندی‌شده و مرتب را روی پایگاه داده اعمال می‌کند و اسکریپت‌های اجرا شده را در یک جدول ژورنال اختصاصی ردیابی می‌نماید.

## نقش معماری (Architectural Role)

```text
scripts/
  0001_CreateAssetsTable.sql
  0002_AddEngineTable.sql
  0003_AddAssetWarrantyExpiryDate.sql
          │
          ▼
DbUp.Run()  →  applies unrun scripts in order  →  SQL Server
          │
          ▼
   SchemaVersions journal table (tracks applied scripts)
```

## نقاط قوت معماری (Architectural Strengths)

- کنترل کامل بر SQL خام، که برای تیم‌ها یا تغییرات خاصی که به جای کدهای مهاجرت تولید شده نیاز به SQL بهینه‌سازی‌شده دست‌نویس و قابل بازبینی دارند، جذاب است.
- مدل ذهنی فوق‌العاده ساده: پوشه‌ای از فایل‌های `.sql` مرتب‌شده و یک جدول ژورنال؛ حداقل انتزاع برای یادگیری.
- مستقل از ORM: اصلاً نیازی به EF Core ندارد، به این معنی که حتی اگر پروژه در آینده ORM خود را تغییر دهد، به همان شکل کار خواهد کرد.
- دارای مجوز MIT، کم‌حجم، پایدار و با سابقه طولانی در اکوسیستم .NET.

## نقاط ضعف معماری (Architectural Weaknesses)

- کاملاً از مدل EF Core جدا شده است: هیچ چیز مانع از این نمی‌شود که یک توسعه‌دهنده شکل یک موجودیت را بدون نوشتن اسکریپت SQL متناظر تغییر دهد، یا برعکس. این امر دقیقاً همان ریسک انحراف مدل/اسکیما را بازمی‌گرداند که EF Core Migrations از نظر ساختاری آن را حذف کرده بود.
- فاقد مکانیزم بازگردانی بومی؛ بازگرداندن یک تغییر نیازمند نگارش و اجرای یک اسکریپت جدید رو به جلو است که فرآیندی دستی‌تر از متد `Down()` در EF Core محسوب می‌شود.
- معرفی DbUp در کنار EF Core به معنای نگهداری دو مکانیزم همپوشان با قابلیت تغییر اسکیما خواهد بود که مستقیماً اصل «مالک واحد اسکیما» را که این ارزیابی تعیین می‌کند، نقض می‌نماید.
- فاقد ایمنی زمان کامپایل در سطح IDE؛ یک اسکریپت `.sql` دارای خطای تایپی فقط در زمان شکست در اجرا شناسایی می‌شود.

## ویژگی‌های عملیاتی (Operational Characteristics)

به جدول ژورنال مخصوص به خود و مرحله فراخوانی مجزا در پایپ‌لاین استقرار نیاز دارد که مستقل از و علاوه بر هر آنچه EF Core انجام می‌دهد، اجرا شود.

## مقیاس‌پذیری (Scalability)

برای هر حجم واقع‌بینانه از تغییرات اسکیما کافی است؛ به خودی خود یک عامل تمایز نیست.

## ایمنی بازگردانی / اصلاح رو به جلو (Rollback / Forward-Fix Safety)

ضعیف‌تر از EF Core Migrations: فاقد معادل بومی `Down()` است؛ هر بازگردانی باید به عنوان یک اسکریپت جدید رو به جلو نوشته شود.

## امنیت (Security)

معادل با EF Core Migrations: با همان اعتبارسنجی‌های پایگاه داده مشابه بقیه بخش‌های برنامه اجرا می‌شود.

## تجربه توسعه‌دهنده (Developer Experience)

برای توسعه‌دهندگانی که ترجیح می‌دهند SQL خام را مستقیماً بنویسند جذاب است، اما تجربه نگارش مهاجرت همراه با کمک IDE و ایمن در برابر بازآفرینی کد را که EF Core هنگام تغییر نام ویژگی‌های موجودیت‌ها ارائه می‌دهد، حذف می‌کند.

## قابلیت نگهداری (Maintainability)

ضعیف‌تر از EF Core Migrations، دقیقاً به دلیل ریسک انحراف که در بالا توضیح داده شد — تغییر اسکیما و تغییر مدل موجودیت متناظر با آن باید هر دو به صورت دستی به یاد سپرده شده و همگام نگه داشته شوند، بدون اینکه کامپایلر یا ابزاری این دو را به هم پیوند دهد.

## یکپارچگی با CI/CD (CI/CD Integration)

خوب: ابزار DbUp یک API ساده به نام `UpgradeEngine.PerformUpgrade()` ارائه می‌دهد که برای مرحله استقرار مبتنی بر کنسول بسیار مناسب است، اما این یک نقطه یکپارچگی دوم و مجزا علاوه بر مرحله‌ای است که قبلاً EF Core Migrations را اعمال می‌کند — که به جای ساده‌سازی پایپ‌لاین، پیچیدگی آن را افزایش می‌دهد.

## سازگاری با هوش مصنوعی (AI Compatibility)

قابل اعمال نیست (Not applicable).

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

کاملاً چندسکویی؛ یک عامل تمایز نیست.

ابزارهای DbUp و EF Core Migrations برای ترکیب شدن با یکدیگر طراحی نشده‌اند؛ به‌کارگیری DbUp در کنار EF Core Migrations باعث ایجاد دو مکانیزم مستقل و هماهنگ‌نشده می‌شود که قادر به تغییر همان اسکیما هستند، که این امر مستقیماً اصل معماری این ارزیابی مبنی بر وجود یک مالک واحد برای اسکیما را نقض می‌کند.

## نتیجه‌گیری اولیه (Preliminary Conclusion)

ابزار DbUp یک ابزار توانمند و شناخته‌شده است، اما به‌کارگیری آن باعث کنار گذاشتن قوی‌ترین ویژگی EF Core Migrations — یعنی تضمین سازگاری مدل/اسکیما — بدون دریافت یک مزیت معماری جبران‌کننده برای این پلتفرم می‌شود.

# 7. ارزیابی Flyway (Flyway Evaluation)

## نمای کلی (Overview)

ابزار Flyway یک ابزار بسیار پرکاربرد و مبتنی بر قرارداد برای مهاجرت پایگاه داده است که فایل‌های مهاجرت SQL (یا مبتنی بر جاوا) نسخه‌بندی‌شده را طبق یک قرارداد نام‌گذاری دقیق (`V1__Description.sql`) اعمال می‌کند و نسخه‌های اعمال‌شده را در یک جدول `flyway_schema_history` ردیابی می‌نماید. این ابزار به طور گسترده در محیط‌های سازمانی چندزبانه (polyglot)، از جمله استک‌های Java و Node.js و نه منحصراً .NET، استفاده می‌شود.

## نقش معماری (Architectural Role)

```text
db/migration/
  V1__CreateAssetsTable.sql
  V2__AddEngineTable.sql
  V3__AddAssetWarrantyExpiryDate.sql
          │
          ▼
Flyway CLI / Maven-Gradle-style migrate command
          │
          ▼
   flyway_schema_history table  →  SQL Server
```

## نقاط قوت معماری (Architectural Strengths)

- فوق‌العاده بالغ و به طور گسترده در کل صنعت نرم‌افزار پذیرفته شده است، با مستندات قوی و حجم زیادی از تجربیات عملیاتی در موتورهای پایگاه داده مختلف.
- قرارداد نام‌گذاری/نسخه‌بندی دقیق و اجباری، ابهام در مورد ترتیب مهاجرت‌ها را در مقایسه با یک پوشه اسکریپت با ساختار آزاد کاهش می‌دهد.
- در اصل مستقل از موتور پایگاه داده است، که در صورت نیاز پلتفرم به پشتیبانی از موتور پایگاه داده‌ای غیر از SQL Server در آینده اهمیت خواهد داشت.

## نقاط ضعف معماری (Architectural Weaknesses)

- یک ابزار بومی .NET نیست: Flyway یک ابزار مبتنی بر Java (یا در نسخه Community به صورت CLI) است و یک وابستگی زمان اجرای غیر-.NET را وارد پروژه‌ای می‌کند که استک، ابزارها و پایپ‌لاین CI/CD آن (Directory.Build.props، Directory.Packages.props) کاملاً متمرکز بر .NET هستند.
- همانند DbUp، کاملاً از مدل EF Core جدا است و همان ریسک انحراف مدل/اسکیما را که در بالا مشخص شد مجدداً معرفی می‌کند.
- ویژگی‌های پیشرفته Flyway (مهاجرت‌های بازگشت یا undo، برخی قابلیت‌های اعتبارسنجی) در پشت نسخه‌های تجاری Flyway Teams/Enterprise محدود شده‌اند و همان دغدغه حاکمیت مجوز را ایجاد می‌کنند که قبلاً برای AutoMapper در TE-0023 مطرح شده بود و در صورت عدم کفایت Community Edition، تضاد مستقیمی با ADR-0002 ایجاد می‌نماید.
- یک ابزار CI/CD دوم و یک زمان اجرای دوم (جاوا یا یک باینری مستقل) صرفاً برای مدیریت اسکیما معرفی می‌کند که پیچیدگی عملیاتی نامتناسبی را با نیازهای فعلی پلتفرم به همراه دارد.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند نصب و فراخوانی یک CLI مجزای Flyway (یا زمان اجرای جاوا) در هر محیطی است که مهاجرت‌ها در آن اعمال می‌شوند (از جمله ماشین‌های توسعه‌دهندگان محلی)، علاوه بر .NET SDK که قبلاً برای سایر بخش‌های راهکار لازم است.

## مقیاس‌پذیری (Scalability)

برای هر حجم واقع‌بینانه از تغییرات اسکیما کافی است؛ به خودی خود یک عامل تمایز نیست.

## ایمنی بازگردانی / اصلاح رو به جلو (Rollback / Forward-Fix Safety)

مهاجرت‌های Undo وجود دارند اما در عمل برای اکثر سناریوهای عملیاتی یک ویژگی سطح تجاری (Flyway Teams) هستند؛ نسخه رایگان Community Edition عموماً مانند DbUp بر مهاجرت‌های اصلاح رو به جلو (forward-fix) تکیه می‌کند.

## امنیت (Security)

نیازمند پیکربندی اعتبارسنجی پایگاه داده مخصوص به خود است که جدا از پیکربندی رشته اتصال برنامه بوده و یک سطح دسترسی و اعتبارسنجی دوم را برای مدیریت و حسابرسی اضافه می‌کند.

## تجربه توسعه‌دهنده (Developer Experience)

برای توسعه‌دهندگانی با پیش‌زمینه زبان‌های مختلف یا جاوا آشنا است؛ اما برای تیمی که کاملاً درون اکوسیستم .NET/EF Core فعالیت می‌کند، یک ابزار، قرارداد نام‌گذاری و CLI کاملاً جدید معرفی می‌نماید.

## قابلیت نگهداری (Maintainability)

ضعیف‌تر از EF Core Migrations به همان دلیل انحراف مدل/اسکیما که برای DbUp مشخص شد، همراه با بار عملیاتی نگهداری یک ابزار غیر-.NET در یک زنجیره ابزار یکدست .NET.

## یکپارچگی با CI/CD (CI/CD Integration)

به طور کلی به خوبی مستند شده است، اما نیازمند اضافه کردن یک مرحله مجزا به پایپ‌لاین، یک گواهی دسترسی مجزا و نصب ابزار مجزا در پایپ‌لاین CI/CD است (که برای ارزیابی تحت سند آتی TE-0031 برنامه‌ریزی شده است) و با توجه به اینکه EF Core Migrations در حال حاضر به صورت بومی یکپارچه است، یک پیچیدگی غیرضروری خواهد بود.

## سازگاری با هوش مصنوعی (AI Compatibility)

قابل اعمال نیست (Not applicable).

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

بی‌طرف نسبت به موتور پایگاه داده است، که از نظر اصولی یک نقطه قوت واقعی است، اما پلتفرم در حال حاضر به آن نیازی ندارد، زیرا منحصراً SQL Server را هدف قرار داده و هیچ نیازمندی مشخصی برای پشتیبانی از چند موتور پایگاه داده ندارد.

# 8. ارزیابی Liquibase (Liquibase Evaluation)

## نمای کلی (Overview)

ابزار Liquibase یک ابزار بالغ و مستقل از پایگاه داده برای مدیریت اسکیما است که مهاجرت‌ها را از طریق یک فایل لاگ تغییرات یا changelog (با فرمت‌های XML، YAML، JSON یا SQL) توصیف می‌کند و تغییرات اعمال‌شده را در جدول `DATABASECHANGELOG` ردیابی می‌نماید. مانند Flyway، این ابزار به طور گسترده در محیط‌های سازمانی چندزبانه استفاده می‌شود.

## نقش معماری (Architectural Role)

```text
changelog/
  changelog-master.yaml
    - changeset: create-assets-table
    - changeset: add-engine-table
    - changeset: add-asset-warranty-expiry-date
          │
          ▼
Liquibase CLI  →  applies unrun changesets  →  SQL Server
          │
          ▼
   DATABASECHANGELOG table
```

## نقاط قوت معماری (Architectural Strengths)

- فرمت مبتنی بر Changelog از تعاریف بازگردانی واقعی و اعلانی (declarative) به ازای هر changeset (بلوک‌های `<rollback>`) پشتیبانی می‌کند که نسبت به Community Edition ابزار Flyway، قابلیت بازگردانی قوی‌تری در نسخه رایگان دارد.
- مستقل از موتور پایگاه داده با پشتیبانی گسترده از ارائه‌دهندگان در میان پایگاه‌های داده رابطه‌ای متعدد و برخی پایگاه‌های داده غیررابطه‌ای.
- بالغ، اثبات‌شده در سطح سازمانی و با ویژگی‌های قوی حسابرسی و گزارش‌گیری (`liquibase history`، `diff`، `status`).

## نقاط ضعف معماری (Architectural Weaknesses)

- بومی .NET نیست: مانند Flyway، ابزار Liquibase یک ابزار مبتنی بر Java است (با اینکه یک متغیر قابل میزبانی در .NET وجود دارد، اما مرکز ثقل اکوسیستم و غنی‌ترین ابزارهای آن ابتدا برای جاوا هستند)، که همان دسته از وابستگی‌های زمان اجرای غیر-.NET را وارد یک زنجیره ابزار یکدست .NET می‌کند.
- نگارش Changelog در قالب XML/YAML نسبت به SQL خام (DbUp/Flyway) یا C# (در EF Core Migrations) طولانی‌تر و برای تیم ناآشناتر است.
- کاملاً از مدل EF Core جدا شده است و همان ریسک انحراف مدل/اسکیما را که برای DbUp و Flyway مشخص شد، تکرار می‌کند.
- نسخه تجاری Liquibase Pro برخی ویژگی‌های پیشرفته (تشخیص انحراف یا drift detection، بررسی‌های کیفی اضافی) را محدود کرده است که مجدداً همان سوال حاکمیت مجوز مطرح‌شده برای AutoMapper و Flyway را برمی‌انگیزد، اگرچه Community Edition رایگان برای نیازهای اصلی مهاجرت کاملاً کاربردی است.

## ویژگی‌های عملیاتی (Operational Characteristics)

نیازمند نصب و فراخوانی Liquibase CLI (یا زمان اجرای جاوا) در هر محیط، به علاوه نگارش changelogها در یک فرمت نشانه‌گذاری متمایز از بقیه کدهای C# است.

## مقیاس‌پذیری (Scalability)

برای هر حجم واقع‌بینانه از تغییرات اسکیما کافی است؛ به خودی خود یک عامل تمایز نیست.

## ایمنی بازگردانی / اصلاح رو به جلو (Rollback / Forward-Fix Safety)

در نسخه رایگان خود از طریق بلوک‌های اعلانی `<rollback>` به ازای هر changeset واقعاً قوی است — بهترین قابلیت بازگردانی در میان سه کاندیدای مستقل از ORM ارزیابی‌شده در اینجا، هرچند همچنان به جای اشتقاق خودکار (مشابه `Down()` در EF Core) به صورت دستی نگارش می‌شود.

## امنیت (Security)

همانند Flyway، نیازمند پیکربندی اعتبارسنجی مخصوص به خود و مجزا از رشته اتصال برنامه است.

## تجربه توسعه‌دهنده (Developer Experience)

نگارش طولانی changelog (با فرمت XML/YAML) برای تیمی که با EF Core Migrations مبتنی بر C# کار می‌کند یک مهارت کاملاً جدید است و منحنی یادگیری تندتری نسبت به رویکرد SQL ساده در DbUp یا Flyway دارد.

## قابلیت نگهداری (Maintainability)

ضعیف‌تر از EF Core Migrations به همان دلیل ساختاری مشابه DbUp و Flyway: هیچ ابزاری تضمین نمی‌کند که یک changelog با مدل EF Core هماهنگ بماند.

## یکپارچگی با CI/CD (CI/CD Integration)

به خوبی مستند شده است، اما — همانند Flyway — به یک مرحله مجزا در پایپ‌لاین، نصب ابزار و اعتبارسنجی جداگانه از ادغام بومی EF Core Migrations در .NET (که بدون هیچ هزینه اضافی در دسترس است) نیاز دارد.

## سازگاری با هوش مصنوعی (AI Compatibility)

قابل اعمال نیست (Not applicable).

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

به شدت نسبت به موتور پایگاه داده بی‌طرف است که از نظر اصولی یک مزیت واقعی است، اما همانند Flyway، نیازی نیست که پلتفرم در حال حاضر داشته باشد.

## کاربرد نمونه (Typical Usage)

```yaml
# changelog/changelog-master.yaml
databaseChangeLog:
  - changeSet:
      id: add-asset-warranty-expiry-date
      author: solution-architect
      changes:
        - addColumn:
            tableName: Assets
            columns:
              - column:
                  name: WarrantyExpiryDate
                  type: date
      rollback:
        - dropColumn:
            tableName: Assets
            columnName: WarrantyExpiryDate
```

| بازگردانی | اعلانی، به ازای هر changeset | متد بومی `Down()` |
| فرمت نگارش | XML / YAML / JSON | C# |

## تناسب معماری (Architectural Fit)

| معیار | ارزیابی |
|-----------|------------|
| معماری تمیز (Clean Architecture) | خوب (در هر صورت دغدغه لایه Infrastructure است) |
| یکپارچگی با .NET / EF Core | ضعیف (ابزار غیر-.NET، عدم آگاهی از مدل) |
| منبع واحد حقیقت | ضعیف (Poor) |
| یکپارچگی با CI/CD | متوسط (Fair)، یک ابزار و گواهی جدید اضافه می‌کند |
| پایداری مجوز | خوب (نسخه Community برای نیازهای اصلی کافی است) |
| هزینه مهاجرت | بالا — بازنویسی کامل به همراه ابزارهای جدید CI/CD |

## ارتباط با EF Core Migrations

همانند DbUp و Flyway، ابزار Liquibase نیز با EF Core Migrations ترکیب نمی‌شود و در صورت انتخاب به عنوان مکانیزم مهاجرت پلتفرم، نیازمند کنار گذاشتن کامل تضمین سازگاری مشتق‌شده از مدل خواهد بود.

## نتیجه‌گیری اولیه (Preliminary Conclusion)

ابزار Liquibase قوی‌ترین قابلیت بازگردانی را در میان سه کاندیدای مستقل از ORM ارائه می‌دهد، اما با همان عدم تطابق بنیادین معماری مشابه DbUp و Flyway مواجه است: این ابزار یک ابزار غیر-.NET و ناآگاه از مدل است که برای پلتفرمی در نظر گرفته می‌شود که مدل موجودیت آن — و بنابراین منبع واحد حقیقت معتبر اسکیمای آن — هم‌اکنون به طور بومی در EF Core قرار دارد.

## ارزیابی کلی (Overall Evaluation)

ابزار EF Core Migrations تنها کاندیدایی است که تغییرات اسکیما را مستقیماً از همان مدلی که بر موجودیت‌های پلتفرم حاکم است استخراج می‌کند و ریسک انحراف مدل/اسکیما را که در تمامی جایگزین‌های مستقل از ORM وجود دارد، از بین می‌برد. ابزارهای DbUp، Flyway و Liquibase همگی ابزارهای بالغ و معتبری هستند، اما هیچ‌یک مزیت معماری جبران‌کننده‌ای ارائه نمی‌دهند که به اندازه کافی بزرگ باشد تا معرفی مکانیزم دوم مالک اسکیما، وابستگی‌های زمان اجرای اضافی، یا (برای Flyway و Liquibase) یک ابزار غیر-.NET را در یک پلتفرم یکدست .NET/EF Core توجیه نماید.

# 10. توصیه نهایی (Final Recommendation)

## استک فناوری اصلی (Core Technology Stack)

| مسئولیت | فناوری انتخاب‌شده | منطق انتخاب (Rationale) |
|-----------------|----------------------|-----------|
| تکامل اسکیما (تنها مالک) | EF Core Migrations | مشتق از مدل، صفر ابزار اضافی، بازگردانی بومی، تاکید مجدد بر قانون حاکمیتی TE-0024 |

## معماری پیشنهادی (Recommended Architecture)

```text
EF Core Model (Domain-driven entity shape)
        │
        ▼
EF Core Migrations (dotnet ef migrations add / database update)
        │
        ▼
SQL Server Database (single authoritative schema)
        ▲
        │
Dapper (TE-0024) — read-only, never alters schema
```

## یکپارچگی با پایپ‌لاین ساخت (Build Pipeline Integration)

دستور `dotnet ef database update` (یا `Database.MigrateAsync()` محافظت‌شده با بررسی‌های محیطی) به عنوان یک مرحله استقرار صریح پیشنهاد می‌شود که در سند آتی TE-0031 (ارزیابی فناوری ساخت، بسته‌بندی و استقرار) رسمیت خواهد یافت و نیازمند نصب هیچ ابزار جدیدی در پایپ‌لاین CI/CD نیست.

## توصیه‌های امنیتی (Security Recommendations)

مهاجرت‌ها همچنان با استفاده از همان اعتبارسنجی‌های حسابرسی‌شده پایگاه داده برنامه اجرا می‌شوند؛ هیچ سطح دسترسی یا گواهی جدیدی معرفی نمی‌شود.

## بی‌طرفی نسبت به ابر (Cloud Neutrality)

ابزار EF Core Migrations برای ترکیب .NET/SQL Server که در حال حاضر استفاده می‌شود کاملاً چندسکویی باقی می‌ماند؛ بی‌طرفی در برابر چندین موتور پایگاه داده (نقطه قوت اصلی Flyway و Liquibase) نیازمندی فعلی پلتفرم نیست.

## آمادگی برای هوش مصنوعی (AI Readiness)

برای این ارزیابی قابل اعمال نیست.
