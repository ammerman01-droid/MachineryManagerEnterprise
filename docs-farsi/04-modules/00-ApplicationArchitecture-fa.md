# ۱. هدف

این سند مسئولیت‌های لایه کاربرد (Application Layer) را تعریف می‌کند.

لایه کاربرد موارد استفاده کسب‌وکار (Business Use Cases) را بدون داشتن قوانین کسب‌وکار هماهنگ و مدیریت می‌کند.

این لایه به عنوان لایه هماهنگ‌کننده (Orchestration Layer) بین بخش‌های زیر عمل می‌کند:

- رابط کاربری (User Interface)
- لایه دامنه (Domain Layer)
- لایه زیرساخت (Infrastructure Layer)

---

# فلسفه ماژول‌ها

ماژول‌ها واحدهای پیاده‌سازی هستند.

ماژول‌ها قابلیت‌های کسب‌وکار تعریف‌شده توسط دامنه را پیاده‌سازی می‌کنند.

یک ماژول مالک موارد زیر است:

- لایه کاربرد (Application)
- لایه دامنه (Domain)
- لایه زیرساخت (Infrastructure)
- رابط‌های برنامه‌نویسی (API)

ماژول‌ها هرگز مالک مفاهیم کسب‌وکار خارج از مرز قابلیت خود نیستند.

---

# ۲. مسئولیت‌ها

لایه کاربرد مسئول موارد زیر است:

- اجرای موارد استفاده (Executing Use Cases)
- هماهنگ‌سازی مجموعه‌ها (Coordinating Aggregates)
- مدیریت تراکنش‌ها (Managing Transactions)
- فراخوانی خدمات دامنه (Calling Domain Services)
- انتشار رویدادهای دامنه (Publishing Domain Events)
- فراخوانی خدمات زیرساخت (Calling Infrastructure Services)
- احراز صلاحیت و دسترسی (Authorization)
- اعتبارسنجی درخواست‌های کاربردی (Validation of Application Requests)

لایه کاربرد هرگز نباید شامل قوانین کسب‌وکار باشد.

قوانین کسب‌وکار منحصراً به لایه دامنه تعلق دارند.

---

# ۳. جایگاه معماری

```text
لایه ارائه / رابط کاربری (Presentation Layer)

        │

        ▼

لایه کاربرد (Application Layer)

        │

        ▼

لایه دامنه (Domain Layer)

        │

        ▼

لایه زیرساخت (Infrastructure Layer)
```

---

# ۴. اصول اصلی

لایه کاربرد از اصول زیر پیروی می‌کند:

- لایه هماهنگ‌کننده سبک (Thin Orchestration Layer)
- عدم وجود منطق کسب‌وکار (No Business Logic)
- مستقل از فناوری (Technology Independent)
- مبتنی بر موارد استفاده (Use Case Oriented)
- مالک مرزهای تراکنش (Transaction Boundary Owner)
- وارونگی وابستگی (Dependency Inversion)

---

# ۵. اجزای اصلی سازنده

لایه کاربرد شامل اجزای زیر است:

```text
لایه کاربرد (Application)

├── موارد استفاده (Use Cases)
├── دستورات (Commands)
├── پرس‌وجوها (Queries)
├── پردازنده‌های دستور (Command Handlers)
├── پردازنده‌های پرس‌وجو (Query Handlers)
├── خدمات کاربردی (Application Services)
├── هماهنگ‌کننده‌های جریان کاری (Workflow Coordinators)
└── سیاست‌های دسترسی (Authorization Policies)
```

هر جزء دارای یک مسئولیت واحد است.

---

# ۶. جریان کاربرد (Application Flow)

یک درخواست نمونه از توالی زیر پیروی می‌کند:

```text
کاربر (User)

↓

کنترلر / رابط (Controller)

↓

دستور کاربردی (Application Command)

↓

پردازنده دستور (Command Handler)

↓

مجموعه دامنه (Domain Aggregate)

↓

رویدادهای دامنه (Domain Events)

↓

زیرساخت (Infrastructure)

↓

پاسخ (Response)
```

هیچ کنترلری نباید مستقیماً با لایه دامنه ارتباط برقرار کند.

---

# ۷. مرز تراکنش (Transaction Boundary)

لایه کاربرد مالک مرزهای تراکنش است.

یک مورد استفاده معمولاً در قالب یک تراکنش اجرا می‌شود.

اگر چندین مجموعه مشارکت داشته باشند، یکپارچگی مطابق با قوانین دامنه مدیریت خواهد شد.

---

# ۸. مدیریت خطاها (Error Handling)

لایه کاربرد مسئول موارد زیر است:

- ترجمه استثناهای دامنه (Domain Exceptions)
- بازگرداندن نتایج کاربردی (Application Results)
- ثبت خطاهای اجرا (Logging Execution Failures)
- حفظ یکپارچگی تراکنش‌ها (Preserving Transaction Integrity)

خطاهای اعتبارسنجی کسب‌وکار هرگز نباید به خطاهای زیرساختی تبدیل شوند.

# ۱۰. قوانین وابستگی ماژول‌ها

ماژول‌ها باید:

- از طریق قراردادهای کاربردی (Application Contracts) ارتباط برقرار کنند.
- هرگز به زیرساخت ماژول دیگری ارجاع ندهند.
- تبادل داده را تنها از طریق قراردادها انجام دهند.
- در صورت نیاز رویدادهای یکپارچه‌سازی انتشار دهند.
