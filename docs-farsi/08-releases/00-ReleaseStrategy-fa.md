# ۱. هدف (Purpose)

این سند استراتژی انتشار را برای MachineryManagerEnterprise تعریف می‌کند.

این سند خط‌مشی‌های حاکم بر نسخه‌بندی نرم‌افزار، کیفیت انتشار، آمادگی استقرار و نگهداری بلندمدت را پایه‌گذاری می‌کند.

تمامی انتشارات باید از این استراتژی پیروی کنند.

---

# ۲. اهداف (Objectives)

فرآیند انتشار باید ویژگی‌های زیر را فراهم آورد:

- قابلیت پیش‌بینی (Predictability)
- تکرارپذیری (Repeatability)
- پایداری (Stability)
- ردیابی‌پذیری (Traceability)
- تضمین کیفیت (Quality Assurance)
- سازگاری با گذشته (Backward Compatibility)

---

# ۳. فلسفه انتشار (Release Philosophy)

هر نسخه منتشرشده باید نمایانگر یک محصول پایدار و قابل استقرار باشد.

قابلیت‌های ناقص و تکمیل‌نشده نباید منتشر شوند.

هر نسخه منتشرشده باید از طریق سیستم کنترل نسخه (Source Control) قابل بازتولید باشد.

---

# حاکمیت انتشار (Release Governance)

هر انتشار باید:

- قابل بازتولید (Reproducible) باشد؛
- تصویب‌شده (Approved) باشد؛
- مستندسازی‌شده (Documented) باشد؛
- قابل ردیابی (Traceable) باشد؛
- به‌طور مستقل قابل استقرار (Independently Deployable) باشد.

---

# ۴. چرخه عمر انتشار (Release Lifecycle)

هر انتشار از چرخه عمر زیر پیروی می‌کند:

```text
برنامه‌ریزی (Planning)

↓

توسعه (Development)

↓

آزمون (Testing)

↓

اعتبارسنجی (Validation)

↓

کاندیدای انتشار (Release Candidate)

↓

انتشار عملیاتی (Production Release)

↓

نگهداری (Maintenance)

↓

پایان پشتیبانی (End of Support)
```

هیچ مرحله‌ای نباید نادیده گرفته شود.

---

# ۵. انواع انتشار (Release Types)

این پروژه سه نوع انتشار را به رسمیت می‌شناسد:

## انتشار اصلی (Major Release)

انتشارات اصلی موارد زیر را معرفی می‌کنند:

- قابلیت‌های جدید کسب‌وکار
- تکامل و تحول معماری
- تغییرات شکننده در API

مثال:

```
2.0.0
```

---

## انتشار فرعی (Minor Release)

انتشارات فرعی موارد زیر را معرفی می‌کنند:

- قابلیت‌ها و ویژگی‌های جدید
- بهبودهای سازگار با گذشته
- ماژول‌های جدید

مثال:

```
1.4.0
```

---

## انتشار وصله (Patch Release)

انتشارات وصله موارد زیر را معرفی می‌کنند:

- رفع باگ‌ها و ایرادات
- اصلاحات امنیتی
- بهبودهای عملکردی

انتشارات وصله نباید عملکرد و قابلیت‌های جدید کسب‌وکار معرفی کنند.

مثال:

```
1.4.3
```

---

# ۶. نسخه‌بندی معنایی (Semantic Versioning)

این راهکار از سیستم نسخه‌بندی معنایی (Semantic Versioning) پیروی می‌کند:

```
MAJOR.MINOR.PATCH
```

مثال:

```
1.0.0

1.2.0

1.2.5

2.0.0
```

---

# ۷. الزامات انتشار (Release Requirements)

یک انتشار باید شرایط زیر را برآورده سازد:

- بیلد موفق (Successful Build)
- آزمون‌های خودکار موفق (Successful Automated Tests)
- اعتبارسنجی معماری (Architecture Validation)
- به‌روزرسانی مستندات (Documentation Update)
- به‌روزرسانی نسخه (Version Update)
- یادداشت‌های انتشار (Release Notes)

---

# ۸. کاندیدای انتشار (Release Candidate)

یک نسخه کاندیدای انتشار (RC) از نظر امکانات و قابلیت‌ها کامل در نظر گرفته می‌شود.

تنها تغییرات زیر در این مرحله مجاز هستند:

- رفع باگ‌ها
- اصلاحات مستندات
- تنظیمات پیکربندی

هیچ قابلیت جدیدی نباید در این مرحله معرفی شود.

---

# ۹. انتشار عملیاتی (Production Release)

انتشار عملیاتی نشان‌دهنده یک نسخه رسماً پشتیبانی‌شده است.

هر نسخه عملیاتی باید موارد زیر را دریافت کند:

- تگ گیت (Git Tag)
- شماره نسخه (Version Number)
- یادداشت‌های انتشار (Release Notes)
- آرتیفکت بیلد (Build Artifact)

---

# ۱۰. انتشارات فوری (Hotfix Releases)

نواقص و ایرادات بحرانی در محیط عملیاتی ممکن است نیازمند انتشارات فوری (Hotfix) باشند.

انتشارات فوری باید:

- تنها نقص شناسایی‌شده را رفع کنند؛
- تغییرات نامربوط را به حداقل برسانند؛
- سازگاری با گذشته را حفظ کنند.

---

# ۱۱. خط‌مشی پشتیبانی (Support Policy)

هر نسخه عملیاتی باید یک دوره پشتیبانی تعریف‌شده داشته باشد.

نسخه‌های تحت پشتیبانی موارد زیر را دریافت می‌کنند:

- اصلاحات امنیتی
- رفع باگ‌های بحرانی
- به‌روزرسانی‌های مستندات

---

# ۱۲. پایان پشتیبانی (End of Support)

یک نسخه زمانی به پایان پشتیبانی می‌رسد که:

- نسخه جایگزین در دسترس باشد؛
- دوره پشتیبانی منقضی شده باشد؛
- به ذینفعان اطلاع‌رسانی شده باشد.

نسخه‌های خارج از پشتیبانی هیچ به‌روزرسانی دیگری دریافت نخواهند کرد.

---

# ۱۳. ردیابی‌پذیری (Traceability)

هر انتشار باید نسبت به موارد زیر قابل ردیابی باشد:

- کامیت گیت (Git Commit)
- تگ گیت (Git Tag)
- شماره بیلد (Build Number)
- نسخه مستندات (Documentation Version)
- یادداشت‌های انتشار (Release Notes)

---

# ۱۴. تکامل آتی (Future Evolution)

نسخه‌های آتی ممکن است موارد زیر را معرفی کنند:

- پشتیبانی بلندمدت (LTS)
- انتشارات پیش‌نمایش (Preview Releases)
- انتشارات بتا (Beta Releases)
- استقرارهای قناری (Canary Deployments)
- عرضه تدریجی (Progressive Rollout)

---

# ۱۵. اقلام تحویلی انتشار (Release Deliverables)

| مرحله | اقلام تحویلی |
|---|---|
| برنامه‌ریزی (Planning) | محدوده مصوب (Approved Scope) |
| توسعه (Development) | قابلیت‌های پیاده‌سازی‌شده (Implemented Features) |
| آزمون (Testing) | گزارش آزمون (Test Report) |
| اعتبارسنجی (Validation) | تاییدیه اعتبارسنجی (Validation Approval) |
| کاندیدای انتشار (Release Candidate) | بیلد RC (RC Build) |
| عملیات (Production) | پکیج انتشار (Release Package) |
| نگهداری (Maintenance) | انتشار وصله (Patch Release) |
