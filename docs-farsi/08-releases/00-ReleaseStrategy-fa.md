# ۱. هدف (Purpose)

این مستند استراتژی انتشار را برای پلتفرم MachineryManagerEnterprise تعیین می‌کند.

این مستند سیاست‌های حاکم بر نسخه‌گذاری نرم‌افزار، کیفیت انتشار، آمادگی استقرار و نگهداری بلندمدت را مشخص می‌سازد.

تمامی انتشارها باید از این استراتژی تبعیت کنند.

---

# ۲. اهداف (Objectives)

فرآیند انتشار باید ویژگی‌های زیر را ارائه دهد:

- قابل پیش‌بینی بودن (Predictability)
- تکرارپذیری (Repeatability)
- پایداری (Stability)
- قابلیت ردگیری (Traceability)
- تضمین کیفیت (Quality Assurance)
- سازگاری با نسخه‌های قبلی (Backward Compatibility)

---

# ۳. فلسفه انتشار (Release Philosophy)

هر انتشار باید یک محصول کامل، پایدار و قابل استقرار ارائه دهد.

قابلیت‌ها و ویژگی‌های ناقص هرگز نباید منتشر شوند.

هر نسخه منتشرشده باید قابل بازتولید مستقیم از روی سیستم کنترل نسخه (Source Control) باشد.

---

# حاکمیت انتشار (Release Governance)

هر انتشار باید دارای ویژگی‌های زیر باشد:

- قابل بازتولید باشد؛
- تاییدشده باشد؛
- مستندشده باشد؛
- قابل ردگیری باشد؛
- به صورت مستقل قابل استقرار باشد.

---

# ۴. چرخه حیات انتشار (Release Lifecycle)

هر انتشار از چرخه حیات زیر تبعیت می‌کند:

```text
برنامه‌ریزی (Planning)

↓

توسعه (Development)

↓

تست (Testing)

↓

اعتبارسنجی (Validation)

↓

کاندیدای انتشار (Release Candidate)

↓

انتشار پروداکشن (Production Release)

↓

نگهداری (Maintenance)

↓

پایان پشتیبانی (End of Support)
```

هیچ مرحله‌ای نباید نادیده گرفته شود.

---

# ۵. انواع انتشار (Release Types)

پروژه سه نوع انتشار را به رسمیت می‌شناسد.

## انتشار اصلی (Major Release)

انتشارهای اصلی موارد زیر را معرفی می‌کنند:

- قابلیت‌های جدید کسب‌وکار
- تکامل معماری
- تغییرات مخرب در API

مثال:

```text
2.0.0
```

---

## انتشار فرعی (Minor Release)

انتشارهای فرعی موارد زیر را معرفی می‌کنند:

- ویژگی‌ها و قابلیت‌های جدید
- بهبودهای سازگار با نسخه‌های قبلی
- ماژول‌های جدید

مثال:

```text
1.4.0
```

---

## انتشار وصله (Patch Release)

انتشارهای وصله موارد زیر را معرفی می‌کنند:

- رفع باگ‌ها و خطاها
- وصله‌های امنیتی
- بهبودهای کارایی و عملکرد

انتشارهای وصله هرگز نباید قابلیت‌های جدید کسب‌وکار معرفی کنند.

مثال:

```text
1.4.3
```

---

# ۶. نسخه‌گذاری معنایی (Semantic Versioning)

این راهکار از سیستم نسخه‌گذاری معنایی تبعیت می‌کند:

```text
MAJOR.MINOR.PATCH
```

مثال:

```text
1.0.0

1.2.0

1.2.5

2.0.0
```

---

# ۷. الزامات انتشار (Release Requirements)

یک انتشار باید الزامات زیر را برآورده سازد:

- ساخت موفقیت‌آمیز (Successful Build)
- تست‌های خودکار موفق (Successful Automated Tests)
- اعتبارسنجی معماری (Architecture Validation)
- به‌روزرسانی مستندات (Documentation Update)
- به‌روزرسانی نسخه (Version Update)
- یادداشت‌های انتشار (Release Notes)

---

# ۸. کاندیدای انتشار (Release Candidate)

یک نسخه کاندیدای انتشار (RC) از نظر قابلیت‌ها کامل تلقی می‌شود.

تنها تغییرات زیر در نسخه RC مجاز هستند:

- رفع باگ‌ها
- اصلاحات مستندات
- تنظیمات و پیکربندی‌ها

هیچ قابلیت جدیدی نباید معرفی شود.

---

# ۹. انتشار پروداکشن (Production Release)

انتشار پروداکشن نشان‌دهنده یک نسخه رسمی و تحت پشتیبانی است.

هر انتشار پروداکشن موارد زیر را دریافت می‌کند:

- برچسب گیت (Git Tag)
- شماره نسخه (Version Number)
- یادداشت‌های انتشار (Release Notes)
- مصنوع ساخت (Build Artifact)

---

# ۱۰. انتشارهای اضطراری (Hotfix Releases)

نقص‌های بحرانی محیط پروداکشن ممکن است نیازمند انتشارهای اضطراری (Hotfix) باشند.

انتشارهای اضطراری باید:

- صرفاً نقص شناسایی‌شده را برطرف کنند؛
- تغییرات غیرمرتبط را به حداقل برسانند؛
- سازگاری با نسخه‌های قبلی را حفظ کنند.

---

# ۱۱. سیاست پشتیبانی (Support Policy)

هر نسخه پروداکشن دارای یک دوره پشتیبانی مشخص است.

نسخه‌های تحت پشتیبانی موارد زیر را دریافت می‌کنند:

- وصله‌های امنیتی
- رفع باگ‌های بحرانی
- به‌روزرسانی مستندات

---

# ۱۲. پایان پشتیبانی (End of Support)

یک نسخه زمانی به پایان پشتیبانی می‌رسد که:

- نسخه جایگزین در دسترس قرار گیرد؛
- دوره پشتیبانی منقضی شده باشد؛
- ذینفعان مطلع شده باشند.

نسخه‌های بدون پشتیبانی هیچ‌گونه به‌روزرسانی دیگری دریافت نخواهند کرد.

---

# ۱۳. قابلیت ردگیری (Traceability)

هر انتشار باید به موارد زیر قابل ردگیری باشد:

- کامیت گیت (Git Commit)
- برچسب گیت (Git Tag)
- شماره ساخت (Build Number)
- نسخه مستندات (Documentation Version)
- یادداشت‌های انتشار (Release Notes)

---

# ۱۴. تکامل آتی (Future Evolution)

نسخه‌های آینده ممکن است موارد زیر را معرفی کنند:

- پشتیبانی بلندمدت (Long-Term Support - LTS)
- انتشارهای پیش‌نمایش (Preview Releases)
- انتشارهای بتا (Beta Releases)
- استقرارهای کاناری (Canary Deployments)
- انتشار تدریجی (Progressive Rollout)

---

# ۱۵. خروجی‌های تحویلی انتشار (Release Deliverables)

| مرحله | خروجی تحویلی |
| ----------- | -------------------- |
| برنامه‌ریزی (Planning) | محدوده تاییدشده |
| توسعه (Development) | قابلیت‌های پیاده‌سازی‌شده |
| تست (Testing) | گزارش تست |
| اعتبارسنجی (Validation) | تاییدیه اعتبارسنجی |
| کاندیدای انتشار (Release Candidate) | ساخت نسخه RC |
| پروداکشن (Production) | پکیج انتشار |
| نگهداری (Maintenance) | انتشار وصله |
