# ۱. هدف (Purpose)

این مستند استراتژی استقرار را برای MachineryManagerEnterprise تعیین می‌کند.

استراتژی استقرار تضمین می‌کند که نرم‌افزار به صورتی امن، یکنواخت و قابل پیش‌بینی در تمامی محیط‌های مورد پشتیبانی تحویل داده شود.

---

# اصول استقرار (Deployment Principles)

استقرارها باید دارای ویژگی‌های زیر باشند:

- تکرارپذیر؛
- خودکار؛
- قابل ردگیری؛
- قابل بازگشت (Reversible)؛
- مستقل از محیط.

استقرار هرگز نباید فایل‌های باینری برنامه را تغییر دهد.

---

# ۲. اهداف (Objectives)

فرآیند استقرار باید موارد زیر را فراهم کند:

- قابلیت اطمینان (Reliability)
- تکرارپذیری (Repeatability)
- قابلیت ردگیری (Traceability)
- خودکارسازی (Automation)
- حداقل زمان قطعی (Minimal Downtime)
- بازگشت امن (Safe Rollback)

---

# ۳. فلسفه استقرار (Deployment Philosophy)

استقرار همواره باید از موارد زیر استفاده کند:

- مصنوعات تاییدشده
- پیکربندی تاییدشده
- زیرساخت تاییدشده

کد منبع هرگز نباید به طور مستقیم استقرار یابد.

---

# ۴. پایپ‌لاین استقرار (Deployment Pipeline)

هر استقرار از جریان کاری زیر تبعیت می‌کند:

```text
ساخت (Build)

↓

پکیج‌سازی (Package)

↓

انتشار مصنوع (Publish Artifact)

↓

استقرار (Deploy)

↓

اعتبارسنجی (Verify)

↓

پایش و مانیتورینگ (Monitor)
```

هر مرحله باید قبل از شروع مرحله بعدی با موفقیت به پایان برسد.

---

# مسئولیت‌های استقرار (Deployment Responsibilities)

| فعالیت | مسئول |
|----------|-------------|
| ساخت | پایپ‌لاین CI |
| پکیج‌سازی | پایپ‌لاین ساخت (Build Pipeline) |
| انتشار مصنوع | مخزن مصنوعات (Artifact Repository) |
| استقرار | تیم دوآپس (DevOps) |
| اعتبارسنجی | تیم تضمین کیفیت / عملیات |
| بازگشت (Rollback) | تیم دوآپس (DevOps) |

---

# ۵. محیط‌های استقرار (Deployment Environments)

سیستم از چندین محیط استقرار پشتیبانی می‌کند:

```text
توسعه (Development)

↓

تست (Testing)

↓

میانی / استیجینگ (Staging)

↓

پروداکشن (Production)
```

هر محیط باید کاملاً ایزوله باقی بماند.

---

# ۶. پیکربندی محیط (Environment Configuration)

پیکربندی برنامه باید خارج از فایل‌های باینری برنامه نگهداری شود.

نمونه‌های پیکربندی عبارتند از:

- رشته‌های اتصال دیتابیس (Database Connection Strings)
- نقاط پایانی API
- پیکربندی ذخیره‌سازی
- پیکربندی کش (Cache)
- پیکربندی لاگ‌گیری

مقادیر پیکربندی هرگز نباید در کد هاردکد شوند.

---

# ۷. مصنوعات تغییرناپذیر (Immutable Artifacts)

مصنوعات استقرار باید تغییرناپذیر باشند.

یک مصنوع که در طول محیط‌ها ارتقا می‌یابد نباید مجدداً ساخته شود.

---

# ۸. استقرار دیتابیس (Database Deployment)

به‌روزرسانی‌های اسکیما و ساختار دیتابیس باید از طریق Migrationهای تاییدشده اجرا شوند.

تغییرات دستی اسکیما در محیط پروداکشن ممنوع است.

اجرای Migrationها باید تحت کنترل نسخه باشد.

---

# ۹. اعتبارسنجی استقرار (Deployment Verification)

پس از استقرار، سیستم باید موارد زیر را اعتبارسنجی کند:

- راه‌اندازی و استارت برنامه
- دسترس‌پذیری API
- اتصال به دیتابیس
- احراز هویت
- پردازش‌های پس‌زمینه

شکست در اعتبارسنجی باید پیشرفت فرآیند انتشار را متوقف سازد.

---

# ۱۰. استراتژی بازگشت (Rollback Strategy)

هر استقرار باید دارای یک طرح بازگشت باشد.

طرح بازگشت باید شامل موارد زیر باشد:

- نسخه قبلی برنامه
- پیکربندی استقرار قبلی
- استراتژی بازیابی دیتابیس

رویکردهای بازگشت باید قبل از استقرار پروداکشن مستند شوند.

---

# ۱۱. سیاست زمان قطعی (Downtime Policy)

استقرارها باید اختلال در ارائه خدمات را به حداقل برسانند.

در صورت امکان، از استراتژی‌های زیر استفاده می‌شود:

- استقرار غلتان (Rolling deployment)
- استقرار آبی-سبز (Blue-Green deployment)
- مهاجرت بدون قطعی (Zero-downtime migration)

استراتژی انتخاب‌شده به قابلیت‌های زیرساختی و حساسیت خدمات بستگی دارد.

---

# ۱۲. امنیت (Security)

اعتبارنامه‌های استقرار باید به صورتی امن مدیریت شوند.

اطلاعات حساس (Secrets) هرگز نباید در موارد زیر وجود داشته باشند:

- سیستم کنترل نسخه
- مصنوعات ساخت
- کد منبع برنامه

مدیریت اطلاعات حساس باید از ذخیره‌سازی امن تاییدشده استفاده کند.

---

# ۱۳. قابلیت ممیزی (Auditability)

هر استقرار باید موارد زیر را ثبت کند:

- نسخه
- شماره ساخت
- کامیت گیت
- زمان استقرار
- محیط
- اپراتور (در صورت دستی بودن)

تاریخچه استقرار باید به طور دائمی قابل ردگیری باقی بماند.

---

# ۱۴. مدیریت خطاها و شکست‌ها (Failure Handling)

اگر استقرار با شکست مواجه شود:

- استقرار بلافاصله متوقف می‌شود.
- استقرار ناقص نباید ادامه یابد.
- رویکردهای بازگشت در صورت نیاز آغاز می‌شوند.
- رخداد باید ثبت و لاگ شود.

---

# ۱۵. بهبودهای آتی

بهبودهای آتی استقرار ممکن است شامل موارد زیر باشند:

- استقرار آبی-سبز (Blue-Green Deployment)
- استقرار کاناری (Canary Deployment)
- انتشار تدریجی (Progressive Rollout)
- بررسی‌های خودکار سلامت (Automatic Health Checks)
- بازگشت خودکار (Automatic Rollback)
- استقرار مبتنی بر GitOps

---

# ۱۶. چک‌لیست درگاه استقرار (Deployment Gate Checklist)

| درگاه (Gate) | الزامی |
| ------------------------ | -------- |
| مصنوع تولیدشده | ✅ |
| پیکربندی اعتبارسنجی‌شده | ✅ |
| اطلاعات حساس در دسترس | ✅ |
| Migration دیتابیس آماده | ✅ |
| بررسی‌های سلامت (Health Checks) | ✅ |
| طرح بازگشت آماده | ✅ |
| تاییدیه | ✅ |
