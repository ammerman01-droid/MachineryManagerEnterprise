# ۱. هدف (Purpose)

این سند استراتژی استقرار را برای MachineryManagerEnterprise تعریف می‌کند.

استراتژی استقرار تضمین می‌کند که نرم‌افزار به‌صورت امن، سازگار و قابل پیش‌بینی در سراسر تمامی محیط‌های پشتیبانی‌شده تحویل داده شود.

---

# اصول استقرار (Deployment Principles)

استقرارها باید:

- تکرارپذیر (Repeatable) باشند؛
- خودکار (Automated) باشند؛
- قابل ردیابی (Traceable) باشند؛
- برگشت‌پذیر (Reversible) باشند؛
- مستقل از محیط (Environment Independent) باشند.

استقرار هرگز نباید باینری‌های برنامه را تغییر دهد.

---

# ۲. اهداف (Objectives)

فرآیند استقرار باید موارد زیر را فراهم آورد:

- قابلیت اطمینان (Reliability)
- تکرارپذیری (Repeatability)
- قابلیت ردیابی (Traceability)
- اتوماسیون (Automation)
- حداقل زمان خرابی/توقف (Minimal Downtime)
- بازگردانی امن (Safe Rollback)

---

# ۳. فلسفه استقرار (Deployment Philosophy)

استقرار همواره باید از موارد زیر استفاده کند:

- آرتیفکت‌های مصوب
- پیکربندی‌های مصوب
- زیرساخت‌های مصوب

کد منبع هرگز نباید مستقیماً استقرار یابد.

---

# ۴. پایپ‌لاین استقرار (Deployment Pipeline)

هر استقرار از گردش کار زیر پیروی می‌کند:

```text
بیلد (Build)

↓

بسته‌بندی (Package)

↓

انتشار آرتیفکت (Publish Artifact)

↓

استقرار (Deploy)

↓

راستی‌آزمایی (Verify)

↓

پایش و مانیتورینگ (Monitor)
```

هر مرحله باید پیش از آغاز مرحله بعد با موفقیت کامل شود.

---

# مسئولیت‌های استقرار (Deployment Responsibilities)

| فعالیت | مسئول |
|---|---|
| بیلد | پایپ‌لاین CI (CI Pipeline) |
| بسته‌بندی | پایپ‌لاین بیلد (Build Pipeline) |
| انتشار آرتیفکت | مخزن آرتیفکت (Artifact Repository) |
| استقرار | تیم دواپس (DevOps) |
| راستی‌آزمایی | تیم QA / عملیات |
| بازگردانی (Rollback) | تیم دواپس (DevOps) |

---

# ۵. محیط‌های استقرار (Deployment Environments)

این سیستم از چندین محیط استقرار پشتیبانی می‌کند:

```text
توسعه (Development)

↓

آزمون (Testing)

↓

پیش‌تولید (Staging)

↓

عملیات (Production)
```

هر محیط باید ایزوله باقی بماند.

---

# ۶. پیکربندی محیط (Environment Configuration)

پیکربندی برنامه باید در خارج از باینری‌های برنامه نگهداری شود.

نمونه‌های پیکربندی عبارتند از:

- رشته‌های اتصال پایگاه داده (Database Connection Strings)
- اندپوینت‌های API
- پیکربندی ذخیره‌سازی داده (Storage Configuration)
- پیکربندی کش (Cache Configuration)
- پیکربندی لاگ‌گیری (Logging Configuration)

مقادیر پیکربندی هرگز نباید هاردکد (Hardcode) شوند.

---

# ۷. آرتیفکت‌های تغییرناپذیر (Immutable Artifacts)

آرتیفکت‌های استقرار باید تغییرناپذیر باشند.

همان آرتیفکتی که در میان محیط‌ها ارتقا می‌یابد، نباید مجدداً بیلد شود.

---

# ۸. استقرار پایگاه داده (Database Deployment)

به‌روزرسانی‌های اسکیمای پایگاه داده باید از طریق مایگریشن‌های مصوب اجرا شوند.

تغییرات دستی اسکیمای عملیاتی ممنوع است.

اجرای مایگریشن باید تحت کنترل نسخه باشد.

---

# ۹. راستی‌آزمایی استقرار (Deployment Verification)

پس از استقرار، سیستم باید موارد زیر را راستی‌آزمایی کند:

- راه‌اندازی برنامه
- دسترس‌پذیری API
- اتصال به پایگاه داده
- احراز هویت
- پردازش‌های پس‌زمینه

شکست در راستی‌آزمایی باید پیشروی انتشار را متوقف کند.

---

# ۱۰. استراتژی بازگردانی (Rollback Strategy)

هر استقرار باید دارای یک طرح بازگردانی باشد.

بازگردانی باید شامل موارد زیر باشد:

- نسخه پیشین برنامه
- پیکربندی استقرار پیشین
- استراتژی بازیابی پایگاه داده

رویه‌های بازگردانی باید پیش از استقرار عملیاتی مستندسازی شوند.

---

# ۱۱. خط‌مشی زمان توقف (Downtime Policy)

استقرارها باید قطعی و اختلال در سرویس را به حداقل برسانند.

در صورت امکان:

- استقرار چرخشی (Rolling deployment)
- استقرار آبی-سبز (Blue-Green deployment)
- مایگریشن بدون زمان توقف (Zero-downtime migration)

استراتژی استقرار انتخابی به قابلیت‌های زیرساختی و اهمیت سرویس بستگی دارد.

---

# ۱۲. امنیت (Security)

اعتبارنامه‌های استقرار باید به‌طور امن مدیریت شوند.

اسرار (Secrets) هرگز نباید در موارد زیر وجود داشته باشند:

- کنترل نسخه (Source Control)
- آرتیفکت‌های بیلد (Build Artifacts)
- کد منبع برنامه (Application Source Code)

مدیریت اسرار باید از فضای ذخیره‌سازی امن مصوب استفاده کند.

---

# ۱۳. قابلیت حسابرسی (Auditability)

هر استقرار باید موارد زیر را ثبت کند:

- نسخه
- شماره بیلد
- کامیت گیت
- زمان استقرار
- محیط
- مجری/اپراتور (در صورت دستی بودن)

تاریخچه استقرار باید برای همیشه قابل ردیابی باقی بماند.

---

# ۱۴. مدیریت شکست (Failure Handling)

در صورت شکست استقرار:

- استقرار فوراً متوقف می‌شود.
- استقرار جزئی نباید ادامه یابد.
- رویه‌های بازگردانی در صورت نیاز آغاز می‌شوند.
- رخداد باید در لاگ‌ها ثبت شود.

---

# ۱۵. بهبودهای آتی (Future Enhancements)

بهبودهای آتی استقرار ممکن است شامل موارد زیر باشد:

- استقرار آبی-سبز (Blue-Green Deployment)
- استقرار قناری (Canary Deployment)
- عرضه تدریجی (Progressive Rollout)
- بررسی خودکار سلامت سیستم (Automatic Health Checks)
- بازگردانی خودکار (Automatic Rollback)
- استقرار مبتنی بر گیت‌اوپس (GitOps Deployment)

---

# ۱۶. چک‌لیست گیت‌های استقرار (Deployment Gate Checklist)

| گیت (Gate) | الزامی |
|---|---|
| آرتیفکت تولید شده است | ✅ |
| پیکربندی اعتبارسنجی شده است | ✅ |
| اسرار در دسترس هستند | ✅ |
| مایگریشن پایگاه داده آماده است | ✅ |
| بررسی‌های سلامت سیستم (Health Checks) | ✅ |
| بازگردانی آماده شده است | ✅ |
| تصویب رسمی | ✅ |
