# ۱. هدف (Purpose)

این سند خط‌مشی نسخه‌بندی را برای MachineryManagerEnterprise تعریف می‌کند.

خط‌مشی نسخه‌بندی رویکردی سازگار برای شناسایی انتشارات نرم‌افزاری، سازگاری API و آرتیفکت‌های استقرار فراهم می‌آورد.

---

# فلسفه نسخه‌بندی (Versioning Philosophy)

شماره‌های نسخه سازگاری و تطابق را مخابره می‌کنند.

آن‌ها پیچیدگی پیاده‌سازی را توصیف نمی‌کنند.

هر آرتیفکت منتشرشده باید نسخه‌ای قطعی و قابل بازتولید ارائه دهد.

---

# ۲. اهداف (Objectives)

استراتژی نسخه‌بندی باید موارد زیر را فراهم آورد:

- تکامل و تحول قابل پیش‌بینی
- قابلیت ردیابی
- سازگاری و یکدستی در انتشار
- سازگاری برای کلاینت‌ها
- شفافیت استقرار

---

# ۳. نسخه‌بندی معنایی (Semantic Versioning)

این راهکار از نسخه‌بندی معنایی (Semantic Versioning) پیروی می‌کند:

```
MAJOR.MINOR.PATCH
```

مثال:

```
1.0.0

1.3.0

1.3.5

2.0.0
```

---

# ۳. سلسله‌مراتب نسخه (Version Hierarchy)

نسخه برنامه (Application Version)

↓

نسخه آرتیفکت (Artifact Version)

↓

شماره بیلد (Build Number)

↓

شناسه کامیت (Commit SHA)

---

# ۴. نسخه اصلی (Major Version)

نسخه اصلی زمانی تغییر می‌کند که:

- تغییرات شکننده در API رخ دهد.
- بازطراحی معماری اتفاق بیفتد.
- قراردادهای دامنه ناسازگار شوند.
- یکپارچه‌سازی‌های موجود نیازمند اصلاح شوند.

مثال:

```
1.x.x

↓

2.0.0
```

---

# ۵. نسخه فرعی (Minor Version)

نسخه فرعی زمانی تغییر می‌کند که:

- قابلیت‌های کسب‌وکار جدید اضافه شوند.
- ماژول‌های جدید معرفی شوند.
- اندپوینت‌های جدید افزوده شوند.
- عملکردهای موجود سازگار باقی بمانند.

مثال:

```
1.2.0

↓

1.3.0
```

---

# ۶. نسخه وصله (Patch Version)

نسخه‌های وصله شامل موارد زیر هستند:

- رفع باگ‌ها
- اصلاحات امنیتی
- بهبودهای عملکردی
- اصلاحات مستندات

هیچ رفتار کسب‌وکاری نباید عمداً دستخوش تغییر شود.

مثال:

```
1.3.2

↓

1.3.3
```

---

# ۷. شناسایی بیلد (Build Identification)

هر بیلد باید شامل موارد زیر باشد:

- شماره بیلد (Build Number)
- شناسه کامیت (Commit SHA)
- برچسب زمانی بیلد (Build Timestamp)

مثال:

```
Version

1.3.0

Build

20260718.45

Commit

8c93bfa
```

---

# ۸. تگ‌های گیت (Git Tags)

هر انتشار عملیاتی باید یک تگ گیت دریافت کند.

مثال:

```
v1.0.0

v1.4.0

v2.0.0
```

تگ‌ها باید به کامیت‌های تغییرناپذیر ارجاع دهند.

---

# ۹. نسخه آرتیفکت (Artifact Version)

آرتیفکت‌های منتشرشده باید شامل نسخه نرم‌افزار باشند.

مثال‌ها:

```
Docker Image

1.3.0

NuGet Package

1.3.0

Application Package

1.3.0
```

نسخه‌های آرتیفکت باید با تگ گیت مربوطه مطابقت داشته باشند.

---

# ۱۰. نسخه مستندات (Documentation Version)

مستندات منتشرشده باید با نسخه نرم‌افزار منتشرشده مطابقت داشته باشند.

به‌روزرسانی‌های مستندات باید نسبت به همان انتشار قابل ردیابی باشند.

---

# ۱۱. نسخه API (API Version)

نسخه‌بندی API از نسخه‌بندی برنامه مستقل است.
تغییرات در اجزای داخلی برنامه هرگز نباید نیازمند تغییر نسخه عمومی API باشند مگر اینکه قرارداد خارجی دچار تغییر شود.

مثال:

```
Application

2.3.1

API

v1
```

یک برنامه می‌تواند بدون تغییر در نسخه عمومی API تکامل یابد.

---

# ۱۲. نسخه پایگاه داده (Database Version)

تکامل اسکیمای پایگاه داده باید از طریق مایگریشن‌ها (Migrations) مدیریت شود.

تاریخچه مایگریشن‌ها باید با نسخه‌های منتشرشده برنامه همگام باقی بماند.

شماره نسخه‌های پایگاه داده نباید جایگزین شماره نسخه‌های برنامه شوند.

---

# ۱۳. خط‌مشی سازگاری (Compatibility Policy)

در چارچوب یک نسخه اصلی (Major Version):

- ارتقاهای فرعی (Minor) باید سازگار باقی بمانند.
- ارتقاهای وصله (Patch) باید سازگار باقی بمانند.

شکستن سازگاری مستلزم انتشار یک نسخه اصلی جدید است.

---

# ۱۴. نسخه‌های پیش از انتشار (Pre-release Versions)

نسخه‌های آتی ممکن است از شناسه‌های پیش از انتشار استفاده کنند.

مثال‌ها:

```
2.0.0-alpha

2.0.0-beta

2.0.0-rc1
```

نسخه‌های پیش از انتشار نباید انتشارات عملیاتی در نظر گرفته شوند.

---

# ۱۵. بهبودهای آتی (Future Enhancements)

نسخه‌های آتی ممکن است موارد زیر را معرفی کنند:

- پشتیبانی بلندمدت (LTS)
- دوره‌های انتشار ماهانه
- شماره‌گذاری خودکار انتشارات
- آرتیفکت‌های انتشار دارای امضای دیجیتال
- کانال‌های انتشار (Release Channels)

---

# ماتریس تغییر نسخه (Version Change Matrix)

| تغییر | نسخه |
|---|---|
| تغییر شکننده در API | اصلی (Major) |
| تغییر شکننده در قرارداد دامنه | اصلی (Major) |
| قابلیت جدید | فرعی (Minor) |
| اندپوینت جدید | فرعی (Minor) |
| رفع باگ | وصله (Patch) |
| مستندات | وصله (Patch) |
| اصلاح امنیتی | وصله (Patch) |
