# ۱. هدف (Purpose)

این مستند سیاست نسخه‌گذاری را برای MachineryManagerEnterprise تعیین می‌کند.

سیاست نسخه‌گذاری روشی یکنواخت برای شناسایی انتشارهای نرم‌افزاری، سازگاری API و مصنوعات استقرار ارائه می‌دهد.

---

# فلسفه نسخه‌گذاری (Versioning Philosophy)

شماره‌های نسخه میزان سازگاری را نشان می‌دهند.

آن‌ها پیچیدگی پیاده‌سازی را توصیف نمی‌کنند.

هر مصنوع منتشرشده باید یک نسخه معین و قابل بازتولید افشا کند.

---

# ۲. اهداف (Objectives)

استراتژی نسخه‌گذاری ویژگی‌های زیر را ارائه می‌دهد:

- تکامل قابل پیش‌بینی
- قابلیت ردگیری
- یکنواختی در انتشار
- سازگاری با کلاینت‌ها
- شفافیت استقرار

---

# ۳. نسخه‌گذاری معنایی (Semantic Versioning)

این راهکار از سیستم نسخه‌گذاری معنایی تبعیت می‌کند:

```text
MAJOR.MINOR.PATCH
```

مثال:

```text
1.0.0

1.3.0

1.3.5

2.0.0
```

---

# ۴. سلسله‌مراتب نسخه (Version Hierarchy)

```text
نسخه برنامه (Application Version)

↓

نسخه مصنوع (Artifact Version)

↓

شماره ساخت (Build Number)

↓

هش کامیت (Commit SHA)
```

---

# ۵. نسخه اصلی (Major Version)

شماره نسخه اصلی تغییر می‌کند زمانی که:

- تغییرات مخرب در API رخ دهد.
- بازطراحی معماری رخ دهد.
- قراردادهای دامنه ناسازگار شوند.
- یکپارچه‌سازی‌های موجود نیازمند تغییر باشند.

مثال:

```text
1.x.x

↓

2.0.0
```

---

# ۶. نسخه فرعی (Minor Version)

شماره نسخه فرعی تغییر می‌کند زمانی که:

- قابلیت‌های جدید کسب‌وکار اضافه شوند.
- ماژول‌های جدید معرفی شوند.
- نقاط پایانی جدید اضافه شوند.
- عملکرد و قابلیت‌های موجود همچنان سازگار باقی بمانند.

مثال:

```text
1.2.0

↓

1.3.0
```

---

# ۷. نسخه وصله (Patch Version)

نسخه‌های وصله شامل موارد زیر هستند:

- رفع باگ‌ها و خطاها
- وصله‌های امنیتی
- بهبودهای کارایی و عملکرد
- اصلاحات مستندات

رفتار کسب‌وکار به صورت عمدی تغییر نخواهد کرد.

مثال:

```text
1.3.2

↓

1.3.3
```

---

# ۸. شناسایی ساخت (Build Identification)

هر ساخت باید دارای ویژگی‌های زیر باشد:

- شماره ساخت (Build Number)
- هش کامیت (Commit SHA)
- برچسب زمانی ساخت (Build Timestamp)

مثال:

```text
Version: 1.3.0

Build: 20260718.45

Commit: 8c93bfa
```

---

# ۹. برچسب‌های گیت (Git Tags)

هر انتشار پروداکشن باید یک برچسب گیت دریافت کند.

مثال:

```text
v1.0.0

v1.4.0

v2.0.0
```

برچسب‌ها باید به کامیت‌های تغییرناپذیر اشاره کنند.

---

# ۱۰. نسخه مصنوعات (Artifact Version)

مصنوعات منتشرشده باید شامل نسخه نرم‌افزار باشند.

مثال‌ها:

```text
Docker Image: 1.3.0

NuGet Package: 1.3.0

Application Package: 1.3.0
```

نسخه مصنوعات باید دقیقاً با برچسب گیت مربوطه مطابقت داشته باشد.

---

# ۱۱. نسخه مستندات (Documentation Version)

مستندات منتشرشده باید با نسخه نرم‌افزار منتشرشده مطابقت داشته باشند.

به‌روزرسانی‌های مستندات باید به همان نسخه انتشار قابل ردگیری باشند.

---

# ۱۲. نسخه API

نسخه‌گذاری API از نسخه‌گذاری برنامه مستقل است.

تغییر در کامپوننت‌های داخلی برنامه هرگز نیازمند تغییر نسخه عمومی API نیست، مگر اینکه قرارداد خارجی تغییر کند.

مثال:

```text
Application: 2.3.1

API: v1
```

یک برنامه می‌تواند بدون تغییر در نسخه عمومی API تکامل یابد.

---

# ۱۳. نسخه دیتابیس (Database Version)

تکامل اسکیما و ساختار دیتابیس از طریق Migrationها مدیریت می‌شود.

تاریخچه Migrationها باید با نسخه‌های نرم‌افزار منتشرشده همگام باقی بماند.

شماره‌های نسخه دیتابیس جایگزین شماره‌های نسخه برنامه نخواهند شد.

---

# ۱۴. سیاست سازگاری (Compatibility Policy)

درون یک نسخه اصلی (Major):

- ارتقاهای فرعی (Minor) باید سازگار باقی بمانند.
- ارتقاهای وصله (Patch) باید سازگار باقی بمانند.

شکست در سازگاری نیازمند ارائه یک نسخه اصلی جدید است.

---

# ۱۵. نسخه‌های پیش‌انتشار (Pre-release Versions)

نسخه‌های آینده ممکن است از شناسه‌های پیش‌انتشار استفاده کنند.

مثال‌ها:

```text
2.0.0-alpha

2.0.0-beta

2.0.0-rc1
```

نسخه‌های پیش‌انتشار به عنوان انتشارهای پروداکشن تلقی نمی‌شوند.

---

# ۱۶. بهبودهای آتی

نسخه‌های آینده ممکن است موارد زیر را معرفی کنند:

- پشتیبانی بلندمدت (LTS)
- چرخه انتشار ماهانه
- شماره‌گذاری خودکار انتشار
- مصنوعات امضاشده انتشار
- کانال‌های انتشار

---
