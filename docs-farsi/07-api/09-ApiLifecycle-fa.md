# ۱. هدف (Purpose)

این مستند چرخه حیات APIهای عمومی ارائه شده توسط MachineryManagerEnterprise را تعریف می‌کند.

هدف ارائه یک فرآیند قابل پیش‌بینی برای معرفی، نگهداری، تکامل و از رده خارج کردن APIها است.

---

# فلسفه چرخه حیات (Lifecycle Philosophy)

APIهای عمومی قراردادهای بلندمدت هستند.

هر API باید به صورتی قابل پیش‌بینی تکامل یابد.

تغییرات مخرب حالت استثنایی دارند و همیشه باید از یک فرآیند حاکمیتی مهاجرت پیروی کنند.

---

# مسئولیت‌های چرخه حیات

| مرحله | مسئول |
|--------|-------------|
| طراحی (Design) | معمار راهکار (Solution Architect) |
| توسعه (Development) | تیم توسعه (Development Team) |
| بازبینی (Review) | شورای بازبینی معماری (Architecture Review Board) |
| انتشار (Release) | مدیر انتشار (Release Manager) |
| نگهداری (Maintenance) | تیم محصول (Product Team) |
| منسوخ‌سازی (Deprecation) | مالکان محصول + معمار |
| از رده خارج کردن (Retirement) | شورای معماری |

---

# ۲. مراحل چرخه حیات (Lifecycle Stages)

هر API عمومی از مراحل زیر عبور می‌کند:

```text
طراحی (Design)

↓

توسعه (Development)

↓

بازبینی (Review)

↓

انتشار (Release)

↓

نگهداری (Maintenance)

↓

منسوخ‌سازی (Deprecation)

↓

از رده خارج کردن (Retirement)
```

هیچ مرحله‌ای نباید نادیده گرفته شود.

---

# ۳. فاز طراحی (Design Phase)

در طول فاز طراحی:

- قابلیت‌های کسب‌وکار شناسایی می‌شوند.
- ساختار نقطه پایانی تعریف می‌شود.
- قراردادهای درخواست/پاسخ مشخص می‌شوند.
- نیازمندی‌های امنیتی مستند می‌شوند.
- سازگاری نسخه‌ها ارزیابی می‌شود.

هیچ پیاده‌سازی قبل از تایید طراحی آغاز نمی‌شود.

---

# ۴. فاز توسعه (Development Phase)

پیاده‌سازی باید طبق مشخصات تاییدشده API انجام شود.

توسعه‌دهندگان نباید نقاط پایانی مستندنشده معرفی کنند.

مستندات OpenAPI تولیدشده باید با پیاده‌سازی همگام باقی بمانند.

---

# ۵. فاز بازبینی (Review Phase)

هر نقطه پایانی جدید باید مورد بازبینی قرار گیرد.

بازبینی موارد زیر را اعتبارسنجی می‌کند:

- رعایت انطباق با REST
- یکنواختی نام‌گذاری
- امنیت
- سازگاری نسخه‌ها
- مدیریت خطاها
- کامل بودن مستندات

---

# ۶. فاز انتشار (Release Phase)

یک نسخه API تنها زمانی می‌تواند منتشر شود که:

- مستندات کامل باشند.
- تست‌های خودکار قبول شده باشند.
- تولید OpenAPI موفقیت‌آمیز باشد.
- بازبینی امنیتی انجام شده باشد.
- پایپ‌لاین ساخت موفق باشد.

---

# ۷. فاز نگهداری (Maintenance Phase)

در طول فاز نگهداری:

- باگ‌ها اصلاح می‌شوند.
- کارایی و عملکرد بهبود می‌یابد.
- فیلدهای پاسخ اختیاری جدید ممکن است اضافه شوند.

یکپارچه‌سازی‌های کلاینت‌های موجود باید بدون مشکل به کار خود ادامه دهند.

---

# ۸. سازگاری با نسخه‌های قبلی (Backward Compatibility)

سازگاری با نسخه‌های قبلی سیاست پیش‌فرض است.

کلاینت‌های موجود باید بتوانند بدون نیاز به تغییر در طول دوره حیات پشتیبانی‌شده یک نسخه API به کار خود ادامه دهند.

---

# ۹. منسوخ‌سازی (Deprecation)

یک نقطه پایانی زمانی وارد حالت منسوخ‌شده می‌شود که:

- جایگزین برتری برای آن وجود داشته باشد.
- قابلیت کسب‌وکار تغییر کرده باشد.
- نسخه جدیدتری از API جایگزین آن شده باشد.

نقاط پایانی منسوخ‌شده در طول دوره پشتیبانی کاملاً کاربردی باقی می‌مانند.

---

# ۱۰. اعلامیه منسوخ‌سازی (Deprecation Notice)

مستندات باید به روشنی موارد زیر را مشخص کنند:

- وضعیت منسوخ‌شده
- نقطه پایانی جایگزین
- نسخه برنامه‌ریزی‌شده برای حذف
- تاریخ پایان پشتیبانی (در صورت مشخص بودن)

مصرف‌کنندگان باید زمان کافی برای مهاجرت دریافت کنند.

---

# ۱۱. از رده خارج کردن (Retirement)

یک نقطه پایانی تنها پس از موارد زیر می‌تواند حذف شود:

- سپری شدن دوره منسوخ‌سازی.
- اطلاع‌رسانی به مصرف‌کنندگان.
- به‌روزرسانی مستندات.
- وجود جایگزین در صورت نیاز.

از رده خارج کردن نیازمند نسخه جدیدی از API است.

---

# ۱۲. تغییرات مخرب (Breaking Changes)

نمونه‌هایی از تغییرات مخرب عبارتند از:

- حذف نقاط پایانی
- حذف ویژگی‌ها و فیلدها
- تغییر در مفهوم و معنای ویژگی‌ها
- تغییر در شناسه‌ها
- تغییر فیلدهای الزامی درخواست

تغییرات مخرب هرگز نباید درون یک نسخه موجود از API رخ دهند.

---

# ۱۳. تغییرات غیرمخرب (Non-Breaking Changes)

نمونه‌ها عبارتند از:

- افزودن ویژگی‌های اختیاری جدید
- افزودن نقاط پایانی جدید
- بهبود مستندات
- بهبود کارایی و عملکرد

این تغییرات می‌توانند درون نسخه فعلی ارائه شوند.

---

# ۱۴. پایش و مانیتورینگ (Monitoring)

APIهای منتشرشده باید برای موارد زیر مانیتور شوند:

- دسترس‌پذیری (Availability)
- زمان پاسخ‌گویی (Response time)
- نرخ خطاها (Error rate)
- میزان استفاده مصرف‌کنندگان (Consumer adoption)
- میزان استفاده از موارد منسوخ‌شده (Deprecation usage)

معیارهای عملیاتی از تصمیمات تکاملی آتی پشتیبانی می‌کنند.

---

# ۱۵. حاکمیت (Governance)

تصمیمات چرخه حیات API نیازمند تاییدیه معماری هستند.

تغییرات عمده باید با استفاده از سند ADR مستند شوند.

چرخه حیات API توسط مستندات معماری پروژه هدایت می‌شود.

---

# ۱۶. خروجی‌ها و تحویلی‌های چرخه حیات

| مرحله | خروجی تحویلی |
| ----------- | -------------------- |
| طراحی (Design) | طراحی تاییدشده API |
| توسعه (Development) | نقطه پایانی پیاده‌سازی‌شده |
| بازبینی (Review) | تاییدیه بازبینی |
| انتشار (Release) | OpenAPI منتشرشده |
| نگهداری (Maintenance) | انتشار وصله (Patch Release) |
| منسوخ‌سازی (Deprecation) | اعلامیه منسوخ‌سازی |
| از رده خارج کردن (Retirement) | نقطه پایانی حذف‌شده |
