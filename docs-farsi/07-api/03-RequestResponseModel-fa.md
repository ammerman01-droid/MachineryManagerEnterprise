# ۱. هدف (Purpose)

این مستند ساختار استاندارد هر درخواست (Request) و پاسخ (Response) API مورد استفاده در MachineryManagerEnterprise را تعریف می‌کند.

یک مدل درخواست/پاسخ یکنواخت، توسعه کلاینت را ساده‌تر، تعامل‌پذیری را بهبود بخشیده و ابهامات پیاده‌سازی را کاهش می‌دهد.

---

# فلسفه قراردادها (Contract Philosophy)

قراردادهای API نشان‌دهنده رابط‌های عمومی کسب‌وکار هستند.

قراردادها باید پایدار، صریح، مستقل از پیاده‌سازی و دارای سازگاری با نسخه‌های قبلی (Backward compatible) باقی بمانند.

موجودیت‌های داخلی دامنه هرگز نباید مستقیماً افشا شوند.

---

# ۲. اصول (Principles)

هر درخواست و پاسخ باید دارای ویژگی‌های زیر باشد:

- قابل پیش‌بینی (Predictable)
- صریح (Explicit)
- یکنواخت (Consistent)
- مستقل از نسخه (Version independent)
- قابل خواندن توسط ماشین (Machine readable)
- قابل فهم برای انسان (Human understandable)

---

# ۳. مدل درخواست (Request Model)

یک درخواست تنها شامل اطلاعاتی است که برای اجرا لازم است.

مثال:

```json
{
  "assetNumber": "AST-000145",
  "organizationId": "ORG-001",
  "engineId": "ENG-0007"
}
```

درخواست‌ها نباید شامل موارد زیر باشند:

- شناسه‌های داخلی
- متاداده‌های دیتابیس
- اطلاعات ممیزی (Audit)
- مقادیر تولیدشده توسط سرور

---

# ۴. مدل پاسخ (Response Model)

پاسخ‌های موفق، منبع کسب‌وکار درخواستی را بازمی‌گردانند.

مثال:

```json
{
  "id": "AST-000145",
  "assetNumber": "AST-000145",
  "status": "Active"
}
```

---

# ۵. پاسخ مجموعه‌ها (Collection Response)

نقاط پایانی مجموعه‌ها آرایه‌ها را بازمی‌گردانند.

مثال:

```json
{
  "items": [
    {
      "id": "AST-0001",
      "assetNumber": "AST-0001"
    },
    {
      "id": "AST-0002",
      "assetNumber": "AST-0002"
    }
  ]
}
```

متاداده‌های مجموعه (`page` ،`pageSize` ،`totalCount` ،`totalPages`) در مستند صفحه‌بندی (Pagination) تعریف شده‌اند و باید همراه با پاسخ‌های صفحه‌بندی‌شده ارسال شوند.

---

# ۶. هویت منبع (Resource Identity)

هر منبع کسب‌وکار باید یک شناسه پایدار ارائه دهد.

مثال:

```json
{
  "id": "AST-000145"
}
```

شناسه‌ها تغییرناپذیر (Immutable) هستند.

---

# ۷. استفاده از DTOها (DTO Usage)

APIهای عمومی DTOها را افشا می‌کنند.

موجودیت‌ها (Entities) هرگز نباید مستقیماً سریال‌سازی شوند.

قرارداد API مستقل از پیاده‌سازی داخلی دامنه باقی می‌ماند.

---

# ۸. مقادیر تهی (Null Values)

تا حد امکان از فیلدهای قابل تهی شدن (Nullable) پرهیز کنید.

روش ترجیحی:

```json
{
  "documents": []
}
```

موارد ممنوع:

```json
{
  "documents": null
}
```

مجموعه‌ها به جای `null` باید آرایه‌های خالی بازگردانند.

---

# ۹. تاریخ و زمان (Date and Time)

مقادیر تاریخ/زمان باید از استاندارد ISO-8601 استفاده کنند.

مثال:

```json
{
  "createdAt": "2026-07-18T09:35:12Z"
}
```

فرمت UTC نمایش پیش‌فرض خواهد بود.

---

# ۱۰. شمارش‌ها (Enumerations)

مقادیر شمارشی (Enum) باید به صورت رشته‌ متنی (String) نشان داده شوند.

روش ترجیحی:

```json
{
  "status": "Active"
}
```

از مقادیر عددی برای enumها پرهیز کنید.

---

# ۱۱. مقادیر بولین (Boolean Values)

ویژگی‌های بولین باید مفهوم شفاف کسب‌وکار ارائه دهند.

مثال‌ها:

```json
{
  "isActive": true,
  "isArchived": false
}
```

از منفی‌های دوگانه (Double negatives) پرهیز شود.

---

# ۱۲. مقادیر عددی (Numeric Values)

اعداد باید از انواع عددی مناسب JSON استفاده کنند.

مقادیر ارزی و مالی باید دقت مورد نیاز را حفظ کنند.

سنجش‌ها و اندازه‌گیری‌ها باید از واحدهای مستندشده کسب‌وکار استفاده کنند.

---

# ۱۳. ویژگی‌های اختیاری (Optional Properties)

ویژگی‌های اختیاری می‌توانند حذف شوند.

کلاینت‌ها نباید فرض کنند هر ویژگی حتماً وجود دارد.

مفهوم ویژگی‌های حذف‌شده باید مستند شود.

---

# ۱۴. هایپرمedia (Hypermedia)

نسخه اولیه API نیازمند HATEOAS نیست.

نسخه‌های آتی ممکن است در صورت نیاز لینک‌های هایپرمحصولات را معرفی کنند.

---

# ۱۵. پایداری قرارداد (Contract Stability)

پس از انتشار، قراردادهای درخواست و پاسخ عمومی تلقی می‌شوند.

تغییرات مخرب نیازمند موارد زیر است:

- نسخه جدید API
- به‌روزرسانی مستندات
- بررسی سازگاری

---

# ۱۶. توسعه‌های آتی

مدل‌های پاسخ در آینده ممکن است شامل موارد زیر باشند:

- متاداده‌های بومی‌سازی (Localization)
- مقادیر ETag
- لینک‌های هایپرمحصولات
- پروژکشن‌های جزئی
- منابع تعبیه‌شده (Embedded resources)

این توسعه‌ها باید سازگاری با نسخه‌های قبلی را حفظ کنند.

---

# ۱۷. سیاست پوشش پاسخ (Response Envelope Policy)

پاسخ‌ها باید مستقیم منبع کسب‌وکار را بازگردانند، مگر اینکه نیازمند پوشش (Envelope) برای موارد زیر باشد:

- صفحه‌بندی
- متاداده‌ها
- عملیات‌های ناهمگام
- گزارش‌های استانداردشده خطا

از بسته‌بندی ناخواسته منابع ساده پرهیز کنید.

---

# نگاشت نوع نقطه پایانی به بدنه درخواست و پاسخ

| نوع نقطه پایانی | بدنه درخواست | بدنه پاسخ |
| -------------- | ------------ | -------------- |
| GET مجموعه | ندارد | DTO مجموعه |
| GET منبع | ندارد | DTO منبع |
| POST ایجاد | DTO ایجاد | DTO منبع |
| PUT جایگزینی | DTO جایگزینی | DTO منبع |
| PATCH به‌روزرسانی | DTO به‌روزرسانی | DTO منبع |
| DELETE | ندارد | No Content (کد ۲۰۴) |
