# ۱. هدف (Purpose)

این مستند اصول معماری حاکم بر تمامی APIهای خارجی ارائه شده توسط MachineryManagerEnterprise را تعریف می‌کند.

هر نقطه پایانی (Endpoint) HTTP، درخواست (Request)، پاسخ (Response) و قرارداد یکپارچه‌سازی باید با این اصول مطابقت داشته باشد.

این اصول بر ترجیحات پیاده‌سازی ارجحیت دارند.

---

# فلسفه طراحی API

API قابلیت‌های کسب‌وکار را به جای پیاده‌سازی نرم‌افزار افشا می‌کند.

قراردادهای API دارایی‌های عمومی بلندمدت هستند.

هر API باید پایدار، صریح، دارای نسخه (Versioned) و مستقل برای استفاده باقی بماند.

---

# ۲. اهداف (Objectives)

رابط‌های API باید دارای ویژگی‌های زیر باشند:

- یکنواخت و یکپارچه (Consistent)
- قابل پیش‌بینی (Predictable)
- پایدار (Stable)
- قابل کشف (Discoverable)
- امن (Secure)
- دارای نسخه (Versionable)
- مستقل از فناوری (Technology Independent)

رابط API نشان‌دهنده قرارداد عمومی (Public Contract) سیستم است.

---

# ۳. فلسفه API

رابط API قابلیت‌های کسب‌وکار را افشا می‌کند.

رابط API هرگز پیاده‌سازی‌های داخلی را افشا نمیکند.

مصرف‌کنندگان به جای ساختارهای دیتابیس، با مفاهیم کسب‌وکار تعامل دارند.

---

# ۴. اصول معماری (Architectural Principles)

رابط API باید:

- از اصول REST پیروی کند؛
- بدون وضعیت (Stateless) باقی بماند؛
- نقاط پایانی مبتنی بر منبع (Resource-oriented) ارائه دهد؛
- از معناشناسی استاندارد HTTP استفاده کند؛
- مستقل از فناوری ماندگاری داده باقی بماند.

---

# ۵. طراحی مبتنی بر کسب‌وکار (Business-Oriented Design)

منابع (Resources) باید نشان‌دهنده مفاهیم کسب‌وکار باشند.

مثال‌ها:

- دارایی‌ها (Assets)
- موتورها (Engines)
- کامپوننت‌ها (Components)
- نگهداری و تعمیرات (Maintenance)
- اسناد (Documents)
- پیش‌بینی‌ها (Forecasts)

منابع هرگز نباید نشان‌دهنده جداول دیتابیس باشند.

---

# ۶. پایداری قرارداد (Contract Stability)

قراردادهای عمومی پایدار تلقی می‌شوند.

از ایجاد تغییرات مخرب (Breaking changes) باید اجتناب شود.

در صورت غیرقابل اجتناب بودن تغییرات مخرب:

- باید نسخه جدیدی از API معرفی شود؛
- نسخه‌های قبلی طبق سیاست انتشار (Release policy) همچنان پشتیبانی شوند.

---

# ۷. یکنواختی و انسجام (Consistency)

موارد زیر باید در سراسر API یکنواخت باقی بمانند:

- ساختار URI
- متدهای HTTP
- کدهای وضعیت (Status codes)
- پاسخ‌های خطا (Error responses)
- صفحه‌بندی (Pagination)
- فیلترسازی (Filtering)
- احراز هویت (Authentication)
- نام‌گذاری (Naming)

---

# ۸. ارتباطات بدون وضعیت (Stateless Communication)

هر درخواست باید شامل تمامی اطلاعات لازم برای اجرا باشد.

سرور نباید به وضعیت نشست (Session state) کلاینت متکی باشد.

---

# ۹. قراردادهای صریح (Explicit Contracts)

هر نقطه پایانی باید به طور صریح موارد زیر را تعریف کند:

- مدل درخواست (Request model)
- مدل پاسخ (Response model)
- کدهای وضعیت (Status codes)
- قوانین اعتبارسنجی (Validation rules)
- نیازمندی‌های مجوزدهی (Authorization requirements)

رفتارهای ضمنی و غیرصریح ممنوع است.

---

# ۱۰. اولویت با امنیت (Security First)

تمامی APIها باید با فرض ناامن بودن کلاینت‌ها طراحی شوند.

احراز هویت (Authentication) همیشه باید مقدم بر مجوزدهی (Authorization) باشد.

اطلاعات حساس هرگز نباید افشا شوند.

---

# ۱۱. نسخه‌گذاری (Versioning)

رابط API باید از نسخه‌گذاری صریح پشتیبانی کند.

شناسه‌های نسخه باید در طول چرخه حیات مورد پشتیبانی پایدار بمانند.

---

# ۱۲. مدیریت خطاها (Error Handling)

خطاها باید دارای ویژگی‌های زیر باشند:

- معین و مشخص (Deterministic)
- قابل خواندن توسط ماشین (Machine-readable)
- قابل خواندن توسط انسان (Human-readable)
- قابل ردگیری (Traceable)

استثناهای غیرمنتظره هرگز نباید مستقیماً به کلاینت‌ها بازگردانده شوند.

---

# ۱۳. قابلیت مشاهده‌پذیری (Observability)

هر درخواست API باید از طریق موارد زیر قابل ردگیری باشد:

- شناسه همبستگی (Correlation Identifier)
- شناسه درخواست (Request Identifier)
- اطلاعات ممیزی (Audit information)
- لاگ‌های ساختاریافته (Structured logs)

---

# ۱۴. مستندسازی (Documentation)

هر نقطه پایانی عمومی باید مستند شود.

مستندات باید همیشه با پیاده‌سازی همگام باقی بمانند.

مستندات تولیدشده بخشی از محصول تحویلی محسوب می‌شوند.

---

# ۱۵. قابلیت توسعه (Extensibility)

رابط API باید از توسعه‌های آتی بدون نیاز به طراحی مجدد پشتیبانی کند.

منابع جدید باید به صورت یکنواخت با کنوانسیون‌های موجود یکپارچه شوند.

---

# ۱۶. استقلال از فناوری (Technology Independence)

کلاینت‌ها نیازی به دانستن موارد زیر ندارند:

- اسکیما و ساختار دیتابیس؛
- فناوری ORM؛
- معماری داخلی؛
- زبان پیاده‌سازی.

تنها قراردادهای کسب‌وکار افشا می‌شوند.

---

# ۱۷. سلسله‌مراتب تصمیم‌گیری (Decision Hierarchy)

در صورت بروز تعارض در تصمیمات طراحی API، اولویت‌ها به ترتیب زیر است:

۱. قوانین کسب‌وکار (Business Rules)
۲. اصول دامنه (Domain Principles)
۳. معماری (Architecture)
۴. اصول API (API Principles)
۵. کنوانسیون‌های REST (REST Conventions)
۶. ترجیحات پیاده‌سازی (Implementation Preferences)

---

# ۱۸. مسئولیت‌های لایه API (API Layer Responsibilities)

لایه API باید:

- درخواست‌های HTTP را به دستورات (Commands) یا پرس‌وجوها (Queries) ترجمه کند.
- نتایج کاربرد (Application Results) را به پاسخ‌های HTTP ترجمه کند.
- هرگز قوانین کسب‌وکار را پیاده‌سازی نکند.
- هرگز مستقیماً به لایه ماندگاری داده دسترسی نداشته باشد.
- هرگز اشیای دامنه (Domain objects) داخلی را افشا نکند.
