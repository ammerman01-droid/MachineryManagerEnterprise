# ۱. هدف (Purpose)

این سند، اصول معماری حاکم بر تمامی APIهای خارجی ارائه‌شده توسط MachineryManagerEnterprise را تعریف می‌کند.

هر اندپوینت HTTP، درخواست، پاسخ و قرارداد یکپارچه‌سازی باید با این اصول مطابقت داشته باشد.

این اصول بر ترجیحات پیاده‌سازی ارجحیت دارند.

---

# فلسفه طراحی API (API Design Philosophy)

این API به‌جای پیاده‌سازی نرم‌افزاری، قابلیت‌های کسب‌وکار را ارائه می‌دهد.

قراردادهای API، دارایی‌های عمومی بلندمدت هستند.

هر API باید پایدار، صریح، نسخه‌بندی‌شده و به‌طور مستقل قابل مصرف باقی بماند.

---

# ۲. اهداف (Objectives)

این API باید ویژگی‌های زیر را دارا باشد:

- سازگار و یکدست (Consistent)
- قابل پیش‌بینی (Predictable)
- پایدار (Stable)
- قابل کشف و پیمایش (Discoverable)
- امن (Secure)
- دارای قابلیت نسخه‌بندی (Versionable)
- مستقل از فناوری (Technology Independent)

این API نشان‌دهنده قرارداد عمومی سیستم است.

---

# ۳. فلسفه API (API Philosophy)

این API قابلیت‌های کسب‌وکار را ارائه می‌دهد.

این API پیاده‌سازی داخلی را افشا نمی‌کند.

مصرف‌کنندگان به‌جای ساختارهای پایگاه داده، با مفاهیم کسب‌وکار تعامل برقرار می‌کنند.

---

# ۴. اصول معماری (Architectural Principles)

این API باید:

- از اصول REST پیروی کند؛
- بدون حالت (Stateless) باقی بماند؛
- اندپوینت‌های مبتنی بر منبع (Resource-Oriented) را ارائه دهد؛
- از معناشناسی استاندارد HTTP استفاده کند؛
- مستقل از فناوری ماندگاری داده (Persistence Technology) باقی بماند.

---

# ۵. طراحی مبتنی بر کسب‌وکار (Business-Oriented Design)

منابع (Resources) باید نمایانگر مفاهیم کسب‌وکار باشند.

مثال‌ها:

- دارایی‌ها (Assets)
- موتورها (Engines)
- قطعات و اجزا (Components)
- تعمیر و نگهداری (Maintenance)
- اسناد (Documents)
- پیش‌بینی‌ها (Forecasts)

منابع هرگز نباید جداول پایگاه داده را نمایندگی کنند.

---

# ۶. پایداری قرارداد (Contract Stability)

قراردادهای عمومی پایدار در نظر گرفته می‌شوند.

باید از تغییرات شکننده (Breaking Changes) اجتناب شود.

هنگامی که تغییرات شکننده اجتناب‌ناپذیر باشند:

- یک نسخه جدید از API معرفی خواهد شد؛
- نسخه‌های قبلی طبق خط‌مشی انتشار همچنان پشتیبانی خواهند شد.

---

# ۷. سازگاری و یکدستی (Consistency)

موارد زیر باید در سراسر کل API سازگار و یکدست باقی بمانند:

- ساختار URI
- متدهای HTTP
- کدهای وضعیت (Status Codes)
- پاسخ‌های خطا (Error Responses)
- صفحه‌بندی (Pagination)
- فیلترسازی (Filtering)
- احراز هویت (Authentication)
- نام‌گذاری (Naming)

---

# ۸. ارتباط بدون حالت (Stateless Communication)

هر درخواست باید حاوی تمامی اطلاعات لازم برای اجرا باشد.

سرور نباید به وضعیت نشست (Session State) کلاینت وابسته باشد.

---

# ۹. قراردادهای صریح (Explicit Contracts)

هر اندپوینت باید موارد زیر را به‌طور صریح تعریف کند:

- مدل درخواست (Request Model)
- مدل پاسخ (Response Model)
- کدهای وضعیت (Status Codes)
- قوانین اعتبارسنجی (Validation Rules)
- الزامات مجوزدهی (Authorization Requirements)

رفتار ضمنی و غیرصریح ممنوع است.

---

# ۱۰. اولویت امنیت (Security First)

تمامی APIها باید با فرض نامعتبر بودن کلاینت‌ها (Untrusted Clients) طراحی شوند.

احراز هویت همواره باید بر مجوزدهی مقدم باشد.

اطلاعات حساس هرگز نباید افشا شوند.

---

# ۱۱. نسخه‌بندی (Versioning)

این API باید از نسخه‌بندی صریح پشتیبانی کند.

شناسه‌های نسخه باید در طول چرخه عمر پشتیبانی‌شده پایدار باقی بمانند.

---

# ۱۲. مدیریت خطا (Error Handling)

خطاها باید:

- قطعی و قابل پیش‌بینی (Deterministic) باشند؛
- ماشین‌خوان (Machine-Readable) باشند؛
- انسان‌خوان (Human-Readable) باشند؛
- قابل ردیابی (Traceable) باشند.

استثناهای غیرمنتظره (Unexpected Exceptions) هرگز نباید مستقیماً به کلاینت‌ها بازگردانده شوند.

---

# ۱۳. قابلیت مشاهده‌پذیری (Observability)

هر درخواست API باید از طریق موارد زیر قابل ردیابی باشد:

- شناسه همبستگی (Correlation Identifier)
- شناسه درخواست (Request Identifier)
- اطلاعات حسابرسی (Audit Information)
- لاگ‌های ساختاریافته (Structured Logs)

---

# ۱۴. مستندسازی (Documentation)

هر اندپوینت عمومی باید مستندسازی شود.

مستندات باید با پیاده‌سازی هماهنگ و همگام باقی بمانند.

مستندات تولیدشده باید بخشی از محصول تحویل داده شده در نظر گرفته شوند.

---

# ۱۵. توسعه‌پذیری (Extensibility)

این API باید بدون نیاز به طراحی مجدد، از گسترش‌های آتی پشتیبانی کند.

منابع جدید باید به‌طور سازگار با قراردادهای موجود یکپارچه شوند.

---

# ۱۶. استقلال از فناوری (Technology Independence)

کلاینت‌ها نباید ملزم به دانستن موارد زیر باشند:

- اسکیمای پایگاه داده؛
- فناوری ORM؛
- معماری داخلی؛
- زبان پیاده‌سازی.

تنها قراردادهای کسب‌وکار افشا می‌شوند.

---

# ۱۷. سلسله‌مراتب تصمیم‌گیری (Decision Hierarchy)

هنگامی که تصمیمات طراحی API دچار تعارض شوند:

۱. قوانین کسب‌وکار (Business Rules)
۲. اصول دامنه (Domain Principles)
۳. معماری (Architecture)
۴. اصول API (API Principles)
۵. قراردادهای REST (REST Conventions)
۶. ترجیحات پیاده‌سازی (Implementation Preferences)

---

# ۱۸. مسئولیت‌های لایه API (API Layer Responsibilities)

لایه API باید:

- درخواست‌های HTTP را به دستورات (Commands) یا پرس‌وجوها (Queries) ترجمه کند.
- نتایج لایه کاربرد (Application Results) را به پاسخ‌های HTTP ترجمه کند.
- هرگز قوانین کسب‌وکار را پیاده‌سازی نکند.
- هرگز مستقیماً به لایه ماندگاری داده دسترسی نداشته باشد.
- هرگز اشیای داخلی دامنه را افشا نکند.
