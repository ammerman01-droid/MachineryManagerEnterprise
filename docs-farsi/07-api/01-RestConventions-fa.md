# ۱. هدف (Purpose)

این سند، قراردادهای REST مورداستفاده در سراسر MachineryManagerEnterprise را تعریف می‌کند.

هر اندپوینت HTTP باید از این قراردادها پیروی کند.

---

# فلسفه REST (REST Philosophy)

منابع REST به‌جای جزئیات پیاده‌سازی، قابلیت‌های کسب‌وکار را ارائه می‌دهند.

شناسه‌های منبع (Resource URIs) مفاهیم کسب‌وکار را مشخص می‌کنند.

متدهای HTTP عملیات درخواستی را توصیف می‌کنند.

پروتکل انتقال داده هرگز نباید معماری نرم‌افزاری داخلی را افشا کند.

---

# قوانین طراحی URI (URI Design Rules)

شناسه‌های منبع (URIs) باید:

- منابع را شناسایی کنند.
- هرگز افعال را افشا نکنند مگر اینکه نمایانگر کنش‌های استثنایی کسب‌وکار باشند.
- پایدار باقی بمانند.
- از افشای جزئیات پیاده‌سازی اجتناب کنند.
- از شناسه‌های وابسته به فناوری اجتناب کنند.

---

# ۲. اصول REST (REST Principles)

این API باید از اصول استاندارد REST پیروی کند.

منابع نمایانگر موجودیت‌های کسب‌وکار هستند.

متدهای HTTP نمایانگر عملیات هستند.

کدهای وضعیت HTTP نمایانگر نتایج هستند.

---

# ۳. نشانی پایه (Base URL)

مثال:

```
/api/v1
```

هر اندپوینت عمومی باید با نسخه API آغاز شود.

---

# ۴. نام‌گذاری منابع (Resource Naming)

منابع باید:

- از اسم‌های جمع (Plural Nouns) استفاده کنند؛
- از حروف کوچک (Lowercase) استفاده کنند؛
- در صورت نیاز، از خط تیره (`-`) به‌عنوان جداکننده استفاده کنند.

مثال‌ها:

```
/assets

/engines

/components

/maintenance-orders

/documents

/forecasts
```

اجتناب شود از:

```
/GetAssets

/AssetList

/AssetManager
```

---

# ۵. شناسه منبع (Resource Identifier)

یک منبع منفرد باید با شناسه اختصاصی خود آدرس‌دهی شود.

مثال:

```
GET /assets/{assetId}
```

مثال:

```
GET /engines/{engineId}
```

---

# ۶. متدهای HTTP (HTTP Methods)

| متد | هدف |
|---|---|
| GET | خواندن (Read) |
| POST | ایجاد (Create) |
| PUT | جایگزینی کامل (Replace) |
| PATCH | به‌روزرسانی جزئی (Partial Update) |
| DELETE | حذف (Remove) |

---

# ۷. متد GET

متد GET هرگز نباید وضعیت سیستم را تغییر دهد.

مثال‌ها:

```
GET /assets

GET /assets/{id}

GET /maintenance-orders
```

درخواست‌های GET باید دارای خاصیت بازگشت‌ناپذیری تأثیر مکرر / هم‌توانی (Idempotent) باشند.

---

# ۸. متد POST

متد POST یک منبع جدید ایجاد می‌کند.

مثال:

```
POST /assets
```

متد POST ملزم به هم‌توان (Idempotent) بودن نیست.

---

# ۹. متد PUT

متد PUT کل منبع را جایگزین می‌کند.

مثال:

```
PUT /assets/{id}
```

متد PUT باید هم‌توان (Idempotent) باشد.

---

# ۱۰. متد PATCH

متد PATCH بخشی از یک منبع را به‌روزرسانی می‌کند.

مثال:

```
PATCH /assets/{id}
```

متد PATCH تنها باید فیلدهایی را که صریحاً ارائه شده‌اند تغییر دهد و هرگز مقادیر حذف‌شده/ارائه‌نشده را بازنشانی نکند.

---

# ۱۱. متد DELETE

متد DELETE یک منبع را حذف کرده یا از رده خارج می‌کند.

مثال:

```
DELETE /documents/{id}
```

قوانین کسب‌وکار تعیین می‌کنند که آیا حذف فیزیکی است یا منطقی (Soft Delete).

---

# ۱۲. منابع تو در تو (Nested Resources)

منابع تو در تو باید نمایانگر رابطه مالکیت (Ownership) باشند.

مثال:

```
GET /assets/{assetId}/engines

GET /assets/{assetId}/documents

GET /assets/{assetId}/maintenance-history
```

از تو در تویی عمیق باید اجتناب شود.

حداکثر عمق توصیه‌شده:

```
2
```

---

# ۱۳. کنش‌ها (Actions)

رویکرد REST منابع را بر افعال ترجیح می‌دهد.

الگوی ترجیحی:

```
POST /maintenance-orders

POST /forecasts
```

اجتناب شود از:

```
POST /create-maintenance

POST /generate-forecast
```

هنگامی که یک کنش صریح کسب‌وکار الزامی باشد:

```
POST /assets/{id}/retire

POST /engines/{id}/rebuild
```

کنش‌های کسب‌وکار باید استثنایی باقی بمانند.

---

# ۱۴. پارامترهای پرس‌وجو (Query Parameters)

فیلترسازی و جستجو باید از پارامترهای پرس‌وجو استفاده کنند.

مثال‌ها:

```
GET /assets?status=Active

GET /assets?organizationId=15

GET /engines?serialNumber=ABC123
```

---

# ۱۵. مرتب‌سازی (Sorting)

مرتب‌سازی باید از ساختار زیر استفاده کند:

```
sort=
```

مثال‌ها:

```
GET /assets?sort=name

GET /assets?sort=-createdAt
```

علامت منفی نمایانگر ترتیب نزولی است.

---

# ۱۶. صفحه‌بندی (Pagination)

مجموعه‌ها باید از صفحه‌بندی پشتیبانی کنند.

مثال:

```
GET /assets?page=1&pageSize=25
```

جزئیات صفحه‌بندی در سندی جداگانه تعریف شده است.

---

# ۱۷. انواع محتوا (Content Types)

درخواست‌ها:

```
application/json
```

پاسخ‌ها:

```
application/json
```

نسخه‌های آتی ممکن است از انواع رسانه (Media Types) بیشتری پشتیبانی کنند.

---

# ۱۸. هم‌توانی (Idempotency)

| متد | هم‌توان (Idempotent) |
|---|---|
| GET | بله |
| PUT | بله |
| PATCH | معمولاً |
| DELETE | بله |
| POST | خیر |

---

# ۱۹. پایداری URI (URI Stability)

شناسه‌های منبع باید پایدار باقی بمانند.

تغییر نام URIهای عمومی نیازمند موارد زیر است:

- نسخه جدید API؛
- استراتژی مهاجرت؛
- به‌روزرسانی مستندات.

---

# ۲۰. گسترش‌های آتی (Future Extensions)

سبک‌های آتی API ممکن است شامل موارد زیر باشد:

- OData
- GraphQL
- gRPC
- Event Streaming

سبک REST همچنان سبک اصلی یکپارچه‌سازی باقی می‌ماند.

---

| HTTP | CQRS |
|---|---|
| GET | پرس‌وجو (Query) |
| POST | دستور (Command) |
| PUT | دستور (Command) |
| PATCH | دستور (Command) |
| DELETE | دستور (Command) |
