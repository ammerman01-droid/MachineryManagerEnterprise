# ۱. هدف (Purpose)

این مستند کنوانسیون‌های REST مورد استفاده در تمامی بخش‌های MachineryManagerEnterprise را تعریف می‌کند.

هر نقطه پایانی (Endpoint) HTTP باید از این کنوانسیون‌ها تبعیت کند.

---

# فلسفه REST

منابع REST قابلیت‌های کسب‌وکار را افشا می‌کنند، نه جزئیات پیاده‌سازی را.

شناسه‌های متنی منابع (Resource URIs) مفاهیم کسب‌وکار را مشخص می‌کنند.

 متدهای HTTP عملیات درخواستی را توصیف می‌کنند.

پروتوکل ترابری هرگز نباید معماری داخلی نرم‌افزار را افشا کند.

---

# قوانین طراحی URI

شناسه‌های URI باید:

- منابع را مشخص کنند.
- هرگز شامل افعال نباشند، مگر زمانی که نشان‌دهنده یک اقدام ویژه کسب‌وکار باشند.
- پایدار بمانند.
- از افشای جزئیات پیاده‌سازی اجتناب کنند.
- از شناسانه‌های وابسته به فناوری خاص اجتناب کنند.

---

# ۲. اصول REST

رابط API باید از اصول استاندارد REST پیروی کند.

منابع، نشان‌دهنده موجودیت‌های کسب‌وکار هستند.

متدهای HTTP، نشان‌دهنده عملیات‌ها هستند.

کدهای وضعیت HTTP، نشان‌دهنده نتایج هستند.

---

# ۳. آدرس پایه (Base URL)

مثال:

```text
/api/v1
```

هر نقطه پایانی عمومی باید با نسخه API شروع شود.

---

# ۴. نام‌گذاری منابع (Resource Naming)

اسامی منابع باید:

- از اسم‌های جمع استفاده کنند؛
- با حروف کوچک نوشته شوند؛
- در صورت نیاز از خط تیره (`-`) به عنوان جداکننده استفاده کنند.

مثال‌ها:

```text
/assets

/engines

/components

/maintenance-orders

/documents

/forecasts
```

موارد ممنوع (Avoid):

```text
/GetAssets

/AssetList

/AssetManager
```

---

# ۵. شناسه منبع (Resource Identifier)

یک منبع منفرد باید با شناسه خود آدرس‌دهی شود.

مثال:

```text
GET /assets/{assetId}
```

مثال:

```text
GET /engines/{engineId}
```

---

# ۶. متدهای HTTP

| متد | هدف |
|----------|---------------------------|
| GET | خواندن (Read) |
| POST | ایجاد (Create) |
| PUT | جایگزینی کامل (Replace) |
| PATCH | به‌روزرسانی جزئی (Partial Update) |
| DELETE | حذف (Remove) |

---

# ۷. متد GET

متد GET هرگز نباید وضعیت سیستم را تغییر دهد.

مثال‌ها:

```text
GET /assets

GET /assets/{id}

GET /maintenance-orders
```

درخواست‌های GET باید بدون اثر جانبی (Idempotent) باشند.

---

# ۸. متد POST

متد POST یک منبع جدید ایجاد می‌کند.

مثال:

```text
POST /assets
```

الزامی به Idempotent بودن متد POST وجود ندارد.

---

# ۹. متد PUT

متد PUT کل منبع را جایگزین می‌کند.

مثال:

```text
PUT /assets/{id}
```

متد PUT باید بدون اثر جانبی تکراری (Idempotent) باشد.

---

# ۱۰. متد PATCH

متد PATCH بخش مشخصی از یک منبع را به‌روزرسانی می‌کند.

مثال:

```text
PATCH /assets/{id}
```

متد PATCH تنها باید فیلدهایی را که به صراحت ارسال شده‌اند تغییر دهد و هرگز نباید مقادیر ارسال‌نشده را بازنشانی کند.

---

# ۱۱. متد DELETE

متد DELETE یک منبع را حذف یا از رده خارج می‌کند.

مثال:

```text
DELETE /documents/{id}
```

قوانین کسب‌وکار تعیین می‌کنند که آیا حذف فیزیکی است یا منطقی (Logical).

---

# ۱۲. منابع توئیده‌شده (Nested Resources)

منابع توئیده‌شده نشان‌دهنده مالکیت (Ownership) هستند.

مثال‌ها:

```text
GET /assets/{assetId}/engines

GET /assets/{assetId}/documents

GET /assets/{assetId}/maintenance-history
```

از توئیده‌سازی عمیق باید پرهیز شود.

عمق حداکثر پیشنهادی:

```text
2
```

---

# ۱۳. اقدام‌ها و عملیات‌ها (Actions)

معماری REST منابع را بر افعال ترجیح می‌دهد.

روش ترجیحی:

```text
POST /maintenance-orders

POST /forecasts
```

موارد ممنوع:

```text
POST /create-maintenance

POST /generate-forecast
```

در صورتی که اجرای یک اقدام صریح کسب‌وکار نیاز باشد:

```text
POST /assets/{id}/retire

POST /engines/{id}/rebuild
```

اقدامات صریح کسب‌وکار باید حالت استثنایی داشته باشند.

---

# ۱۴. پارامترهای پرس‌وجو (Query Parameters)

فیلترسازی و جستجو باید از پارامترهای پرس‌وجو استفاده کنند.

مثال‌ها:

```text
GET /assets?status=Active

GET /assets?organizationId=15

GET /engines?serialNumber=ABC123
```

---

# ۱۵. مرتب‌سازی (Sorting)

مرتب‌سازی باید از ساختار زیر استفاده کند:

```text
sort=
```

مثال‌ها:

```text
GET /assets?sort=name

GET /assets?sort=-createdAt
```

علامت منفی نشان‌دهنده مرتب‌سازی نزولی (Descending) است.

---

# ۱۶. صفحه‌بندی (Pagination)

مجموعه‌ها باید از صفحه‌بندی پشتیبانی کنند.

مثال:

```text
GET /assets?page=1&pageSize=25
```

جزئیات صفحه‌بندی در مستند مجزا تعریف شده است.

---

# ۱۷. انواع محتوا (Content Types)

درخواست‌ها:

```text
application/json
```

پاسخ‌ها:

```text
application/json
```

نسخه‌های آتی ممکن است از media typeهای اضافی پشتیبانی کنند.

---

# ۱۸. عدم اثر جانبی تکراری (Idempotency)

| متد | Idempotent |
|----------|-----------|
| GET | بله |
| PUT | بله |
| PATCH | معمولاً |
| DELETE | بله |
| POST | خیر |

---

# ۱۹. پایداری URI

شناسه‌های URI منابع باید پایدار بمانند.

تغییر نام URIهای عمومی نیازمند موارد زیر است:

- نسخه جدید API؛
- استراتژی مهاجرت (Migration strategy)؛
- به‌روزرسانی مستندات.

---

# ۲۰. توسعه‌های آتی

سبک‌های آینده API ممکن است شامل موارد زیر باشد:

- OData
- GraphQL
- gRPC
- Event Streaming

معماری REST همچنان سبک اصلی یکپارچه‌سازی باقی می‌ماند.

---

# نگاشت متدهای HTTP به الگوی CQRS

| HTTP   | CQRS    |
| ------ | ------- |
| GET    | Query   |
| POST   | Command |
| PUT    | Command |
| PATCH  | Command |
| DELETE | Command |
