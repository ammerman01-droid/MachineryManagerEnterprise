# ۱. هدف (Purpose)

این مستند استراتژی نسخه‌گذاری API را برای MachineryManagerEnterprise تعریف می‌کند.

نسخه‌گذاری API به سیستم اجازه می‌دهد تا بدون ایجاد شکست در برنامه‌های کلاینت موجود، تکامل یابد.

---

# فلسفه نسخه‌گذاری

تکامل API باید اولویت را به سازگاری با نسخه‌های قبلی (Backward compatibility) بدهد.

کلاینت‌ها باید بتوانند به صورت تدریجی مهاجرت کنند.

تغییرات مخرب (Breaking changes) همیشه نیازمند ارائه نسخه اصلی (Major version) جدید برای API خواهند بود.

قراردادهای عمومی بسیار کندتر از پیاده‌سازی‌های داخلی تکامل می‌یابند.

---

# چرخه حیات نسخه (Version Lifecycle)

نسخه جدید (New Version)

↓

پیش‌نمایش (Preview - اختیاری)

↓

پشتیبانی‌شده (Supported)

↓

منسوخ‌شده (Deprecated)

↓

پایان پشتیبانی (Sunset)

↓

از رده خارج‌شده (Retired)

---

# ۲. اهداف (Objectives)

استراتژی نسخه‌گذاری موارد زیر را فراهم می‌کند:

- سازگاری با نسخه‌های قبلی
- ارتقای قابل پیش‌بینی
- یکپارچه‌سازی‌های پایدار
- تکامل کنترل‌شده

---

# ۳. اصل نسخه‌گذاری

تغییرات مخرب هرگز نباید وارد یک نسخه موجود از API شوند.

تغییرات مخرب نیازمند یک نسخه اصلی (Major version) جدید از API هستند.

---

# ۴. نسخه‌گذاری در URL (URL Versioning)

پلتفرم MachineryManagerEnterprise از نسخه‌گذاری مبتنی بر URL استفاده می‌کند.

مثال:

```text
/api/v1/assets

/api/v1/engines

/api/v1/documents
```

نسخه‌های آینده:

```text
/api/v2/assets

/api/v2/engines
```

---

# ۵. فرمت نسخه (Version Format)

نسخه‌های API از الگوی زیر پیروی می‌کنند:

```text
v1

v2

v3
```

تنها شماره نسخه اصلی (Major version) در URL عمومی ظاهر می‌شود.

---

# ۶. نسخه‌های مورد پشتیبانی (Supported Versions)

چندین نسخه از API می‌توانند همزمان وجود داشته باشند.

مثال:

```text
v1

v2
```

هر نسخه پشتیبانی‌شده در طول چرخه حیات پشتیبانی خود به طور مستقل نگهداری می‌شود.

---

# ۷. تغییرات مخرب (Breaking Changes)

نمونه‌هایی از تغییرات مخرب:

- حذف نقاط پایانی
- تغییر نام نقاط پایانی
- حذف ویژگی‌ها و فیلدها از پاسخ
- تغییر مفهوم و معنای ویژگی‌ها
- تغییر شناسه‌های منابع
- تغییر در رفتار کدهای وضعیت HTTP

تغییرات مخرب نیازمند نسخه جدیدی از API هستند.

---

# ۸. تغییرات غیرمخرب (Non-Breaking Changes)

نمونه‌ها:

- افزودن ویژگی‌های اختیاری جدید به پاسخ
- افزودن نقاط پایانی جدید
- افزودن فیلدهای اختیاری به درخواست
- بهبود کارایی و عملکرد
- تغییرات در پیاده‌سازی داخلی

این تغییرات می‌توانند درون نسخه فعلی منتشر شوند.

---

# ۹. منسوخ‌سازی (Deprecation)

نقاط پایانی منسوخ‌شده باید در طول دوره پشتیبانی اعلام‌شده کاملاً فعال و کاربردی باقی بمانند.

مستندات باید به روشنی موارد زیر را مشخص کنند:

- وضعیت منسوخ‌شده (Deprecated status)
- جایگزین پیشنهادی (Recommended replacement)
- نسخه برنامه‌ریزی‌شده برای حذف کامل

---

# ۱۰. نسخه پیش‌فرض (Default Version)

کلاینت‌ها باید به صراحت نسخه API مورد نظر خود را درخواست کنند.

سرور نباید به طور پنهانی درخواست‌ها را بین نسخه‌ها هدایت (Redirect) کند.

---

# ۱۱. مستندسازی (Documentation)

هر نسخه API باید مستندات مستقل خود را نگهداری کند.

مثال‌ها:

```text
OpenAPI v1

OpenAPI v2
```

مستندات باید بازتاب‌دهنده رفتار دقیق همان نسخه باشند.

---

# ۱۲. سیاست سازگاری (Compatibility Policy)

برنامه‌های کلاینت موجود باید بتوانند بدون نیاز به تغییر در طول دوره حیات پشتیبانی‌شده یک نسخه API به کار خود ادامه دهند.

سازگاری با نسخه‌های قبلی بر تغییرات سریع ارجحیت دارد.

---

# ۱۳. سیاست پایان پشتیبانی (Sunset Policy)

هنگامی که یک نسخه API به پایان عمر خود می‌رسد:

- کلاینت‌ها باید اخطار قبلی دریافت کنند.
- مستندات باید تاریخ دقیق پایان پشتیبانی (Sunset date) را مشخص کنند.
- راهنمای مهاجرت باید ارائه شود.

---

# ۱۴. نسخه‌گذاری داخلی (Internal Versioning)

نسخه‌های پیاده‌سازی داخلی از نسخه‌های عمومی API مستقل هستند.

تغییر معماری داخلی نیازمند افزایش نسخه عمومی API نیست.

---

# ۱۵. استراتژی آینده

نسخه‌های آتی ممکن است از موارد زیر پشتیبانی کنند:

- نسخه‌گذاری مبتنی بر Media Type
- نسخه‌گذاری مبتنی بر Header
- پرچم‌های ویژگی (Feature Flags)
- نقاط پایانی آزمایشی (Experimental Endpoints)

استراتژی اصلی همچنان نسخه‌گذاری مبتنی بر URL باقی می‌ماند.
