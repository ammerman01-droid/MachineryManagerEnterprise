# ۱. هدف (Purpose)

این مستند استراتژی احراز هویت (Authentication) و مجوزدهی (Authorization) را برای APIهای MachineryManagerEnterprise تعریف می‌کند.

احراز هویت هویت کاربر یا سیستم را تایید می‌کند.

مجوزدهی مشخص می‌سازد که آیا هویت احرازشده اجازه انجام عملیات درخواستی را دارد یا خیر.

---

# فلسفه امنیت (Security Philosophy)

احراز هویت، هویت کاربر را تثبیت می‌کند.

مجوزدهی، دسترسی‌ها و مجوزها را اعطا می‌نماید.

قوانین کسب‌وکار درون دامنه (Domain) باقی می‌مانند.

سازوکارهای امنیتی هرگز نباید رفتار کسب‌وکار را پیاده‌سازی کنند.

---

# جریان احراز هویت (Authentication Flow)

کلاینت (Client)

↓

توکن حامل (Bearer Token)

↓

احراز هویت (Authentication)

↓

ادعاها (Claims)

↓

مجوزدهی (Authorization)

↓

پردازش‌گر (Handler)

↓

پاسخ (Response)

---

# ۲. اصول (Principles)

مدل امنیتی باید دارای ویژگی‌های زیر باشد:

- بدون وضعیت (Stateless)
- امن (Secure)
- قابل ممیزی (Auditable)
- مقیاس‌پذیر (Scalable)
- مبتنی بر نقش (Role-based)
- مبتنی بر ادعا (Claims-based)

احراز هویت همیشه باید قبل از مجوزدهی انجام شود.

---

# ۳. مدل احراز هویت (Authentication Model)

رابط API هر درخواست حفاظت‌شده را احراز هویت می‌کند.

دسترسی ناشناس (Anonymous) تنها برای نقاط پایانی به صراحت مشخص‌شده مجاز است.

تمامی درخواست‌های احرازشده باید یک بافت کاربر احرازشده (Authenticated user context) تولید کنند.

---

# ۴. سازوکار احراز هویت (Authentication Mechanism)

سازوکار اصلی احراز هویت عبارت است از:

```text
Bearer Token
```

کلاینت‌ها باید توکن دسترسی (Access token) را در هدر Authorization درخواست HTTP ارسال کنند.

مثال:

```text
Authorization: Bearer <access-token>
```

---

# ۵. امنیت سطح ترابری (Transport Security)

تمامی ارتباطات API باید روی پروتکل HTTPS انجام شوند.

پروتکل HTTP معمولی (Plain HTTP) در محیط‌های پروداکشن پشتیبانی نخواهد شد.

---

# ۶. مدل مجوزدهی (Authorization Model)

مجوزدهی بر اساس مجوزهای کسب‌وکار (Business permissions) انجام می‌شود.

جریان مجوزدهی به صورت زیر است:

```text
کاربر (User)

↓

هویت (Identity)

↓

نقش‌ها (Roles)

↓

مجوزها (Permissions)

↓

عملیات کسب‌وکار (Business Operation)
```

قوانین مجوزدهی در مستند زیر تعریف شده‌اند:

```text
docs/04-modules/07-Authorization.md
```

---

# ۷. حفاظت از نقاط پایانی (Endpoint Protection)

نقاط پایانی در سه دسته طبقه‌بندی می‌شوند:

```text
عمومی (Public)

احرازشده (Authenticated)

دارای دسترسی ویژه (Privileged)
```

مثال‌ها:

عمومی:

```text
Health Check
```

احرازشده:

```text
GET /assets
```

دارای دسترسی ویژه:

```text
DELETE /documents/{id}
```

---

# ۸. ادعاها (Claims)

هویت‌های احرازشده می‌توانند شامل ادعاهایی مانند موارد زیر باشند:

```text
UserId

OrganizationId

Roles

Permissions

TenantId
```

منطق کسب‌وکار تنها باید به بافت کاربر کاربرد (Application User Context) وابسته باشد و هرگز نباید مستقیماً به ادعاهای خام JWT متکی باشد.

---

# ۹. بافت چندمستاجری (Multi-Tenant Context)

در صورت فعال بودن قابلیت چندمستاجری (Multi-tenancy):

هر درخواست احرازشده باید دقیقاً درون بافت یک مستاجر (Tenant context) اجرا شود.

دسترسی بین چند مستاجر ممنوع است مگر اینکه به صراحت مجوز آن اعطا شده باشد.

---

# ۱۰. درخواست‌های نا معتبر و احرازلنشده (Unauthorized Requests)

عدم ارائه اطلاعات احراز هویت موارد زیر را بازمی‌گرداند:

```text
401 Unauthorized
```

مثال:

```json
{
  "errorCode": "AUTH-001",
  "title": "Authentication Failed",
  "message": "Authentication is required.",
  "correlationId": "..."
}
```

---

# ۱۱. درخواست‌های ممنوع‌شده (Forbidden Requests)

کاربران احرازشده‌ای که فاقد مجوز لازم هستند کد زیر را دریافت می‌کنند:

```text
403 Forbidden
```

مثال:

```json
{
  "errorCode": "AUTH-003",
  "title": "Access Denied",
  "message": "You do not have permission to perform this operation.",
  "correlationId": "..."
}
```

---

# ۱۲. طول عمر توکن (Token Lifetime)

توکن‌های دسترسی دارای طول عمر قابل تنظیم هستند.

توکن‌های منقضی‌شده پذیرفته نخواهند شد.

کلاینت‌ها باید توکن‌های جدید را با استفاده از جریان‌های کاری احراز هویت پیکربندی‌شده دریافت کنند.

---

# ۱۳. ثبت لاگ‌ها (Logging)

رویدادهای زیر باید لاگ شوند:

- احراز هویت موفق
- احراز هویت ناموفق
- عدم موفقیت در مجوزدهی
- تغییر در مجوزها
- قفل شدن حساب کاربر
- دسترسی‌های مدیریتی

اطلاعات حساس و اعتبارنامه‌ها هرگز نباید لاگ شوند.

---

# ۱۴. حداقل سطح دسترسی (Least Privilege)

کاربران تنها باید مجوزهایی را دریافت کنند که برای انجام مسئولیت‌های کاری‌شان لازم است.

مجوزهای مدیریتی باید به صورت بسیار محدود اعطا شوند.

---

# ۱۵. بهبودهای آتی

نسخه‌های آینده ممکن است از موارد زیر پشتیبانی کنند:

- OpenID Connect
- OAuth 2.1
- احراز هویت چندعاملی (MFA)
- ورود یکپارچه (SSO)
- تامین‌کنندگان هویت خارجی (External Identity Providers)
- کلیدهای API برای یکپارچه‌سازی سیستم‌ها

این قابلیت‌ها کاملاً سازگار با مدل مجوزدهی فعلی خواهند بود.
