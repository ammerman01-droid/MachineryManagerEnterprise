# ۱. هدف (Purpose)

این مستند کنوانسیون‌های استاندارد برای صفحه‌بندی (Pagination)، فیلترسازی (Filtering) و مرتب‌سازی (Sorting) در MachineryManagerEnterprise را تعریف می‌کند.

تمامی نقاط پایانی مجموعه‌ها باید از این کنوانسیون‌ها تبعیت کنند.

---

# فلسفه تکامل API

تکامل APIها اولویت اصلی خود را حفظ سازگاری با نسخه‌های قبلی (Backward compatibility) قرار می‌دهد.

کلاینت‌ها باید بتوانند به صورت تدریجی مهاجرت کنند.

تغییرات مخرب همیشه منجر به ارائه نسخه اصلی (Major version) جدید برای API خواهند شد.

# ۲. اصول (Principles)

نقاط پایانی مجموعه‌ها باید از موارد زیر پشتیبانی کنند:

- صفحه‌بندی (Pagination)
- فیلترسازی (Filtering)
- مرتب‌سازی (Sorting)

این رفتار در تمامی منابع API باید کاملاً یکسان باقی بماند.

---

# ۳. پارامترهای صفحه‌بندی (Pagination Parameters)

پارامترهای استاندارد صفحه‌بندی عبارتند از:

| پارامتر | شرح |
|------------|-------------|
| page | شماره صفحه (شروع از ۱) |
| pageSize | تعداد آیتم‌ها در هر صفحه |

مثال:

```text
GET /assets?page=1&pageSize=25
```

---

# ۴. مقادیر پیش‌فرض (Default Values)

مگر اینکه به طور صریح تغییر داده شوند:

```text
page = 1

pageSize = 25
```

---

# ۵. حداکثر اندازه صفحه (Maximum Page Size)

برای محافظت از منابع سرور:

```text
Maximum pageSize = 200
```

درخواست‌های فراتر از حداکثر به صورت خودکار محدود خواهند شد.

---

# ۶. پاسخ صفحه‌بندی‌شده (Paged Response)

پاسخ‌های صفحه‌بندی‌شده باید از ساختار زیر پیروی کنند:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 25,
  "totalItems": 1543,
  "totalPages": 62,
  "hasNextPage": true,
  "hasPreviousPage": false
}
```

---

# ۷. فیلترسازی (Filtering)

فیلترسازی باید از پارامترهای پرس‌وجو استفاده کند.

مثال‌ها:

```text
GET /assets?status=Active

GET /assets?organizationId=15

GET /documents?category=Insurance

GET /maintenance-orders?priority=High
```

هر فیلتر نشان‌دهنده یک معیار کسب‌وکار است.

---

# ۸. فیلترهای چندگانه (Multiple Filters)

امکان ترکیب چند فیلتر وجود دارد.

مثال:

```text
GET /assets?status=Active&organizationId=15
```

فیلترها با ترکیب منطقی AND ترکیب خواهند شد.

---

# ۹. فیلترسازی تاریخ (Date Filtering)

بازه‌های زمانی باید از پارامترهای صریح استفاده کنند.

مثال:

```text
GET /maintenance-orders?from=2026-01-01&to=2026-12-31
```

تاریخ‌ها باید از فرمت ISO-8601 استفاده کنند.

---

# ۱۰. مرتب‌سازی (Sorting)

مرتب‌سازی باید از ساختار زیر استفاده کند:

```text
sort=
```

مثال‌ها:

صعودی:

```text
GET /assets?sort=name
```

نزولی:

```text
GET /assets?sort=-createdAt
```

وجود علامه منفی (`-`) در ابتدا، نشان‌دهنده مرتب‌سازی نزولی است.

---

# ۱۱. چند فیلد مرتب‌سازی (Multiple Sort Fields)

امکان ارسال چند فیلد برای مرتب‌سازی وجود دارد.

مثال:

```text
GET /assets?sort=status,name
```

ارزیابی از چپ به راست انجام می‌شود.

---

# ۱۲. جستجو (Searching)

جستجوی متنی (Free-text search) باید از ساختار زیر استفاده کند:

```text
search=
```

مثال:

```text
GET /assets?search=CAT320
```

رفتار جستجو باید برای هر منبع مستند شود.

---

# ۱۳. نتایج خالی (Empty Results)

پرس‌وجوهای موفق بدون رکورد منطبق باید کد زیر را بازگردانند:

```text
200 OK
```

مثال:

```json
{
  "items": [],
  "page": 1,
  "pageSize": 25,
  "totalItems": 0,
  "totalPages": 0,
  "hasNextPage": false,
  "hasPreviousPage": false
}
```

مجموعه‌های خالی خطای سیستم محسوب نمی‌شوند.

---

# ۱۴. پارامترهای نامعتبر (Invalid Parameters)

پارامترهای نامعتبر صفحه‌بندی یا مرتب‌سازی کد زیر را بازمی‌گردانند:

```text
400 Bad Request
```

اعتبارسنجی باید پارامتر نامعتبر را مشخص کند.

---

# ۱۵. کارایی و عملکرد (Performance)

فیلترسازی و مرتب‌سازی تا حد امکان باید توسط لایه ماندگاری داده (Persistence Layer) اجرا شوند.

مجموعه داده‌های بزرگ هرگز نباید قبل از صفحه‌بندی به طور کامل بارگذاری در حافظه شوند.

---

# ۱۶. توسعه‌های آتی

نسخه‌های آینده ممکن است از موارد زیر پشتیبانی کنند:

- صفحه‌بندی با نشانگر (Cursor Pagination)
- توکن‌های ادامه (Continuation Tokens)
- پروژکشن‌های داینامیک
- جستجوی پیشرفته
- جستجوی متنی کامل (Full-text Search)

سازگاری با نسخه‌های قبلی حفظ خواهد شد.
