# ۱. هدف (Purpose)

این مستند نحوه تولید، نگهداری و انتشار مشخصات OpenAPI برای MachineryManagerEnterprise را تعریف می‌کند.

مستند OpenAPI توصیف رسمی و قابل خواندن توسط ماشین برای APIهای عمومی HTTP است.

---

# فلسفه OpenAPI

مستند OpenAPI توصیف مرجع و قابل خواندن توسط ماشین از APIهای عمومی HTTP است.

مستندات باید همیشه از کد منبع (Source code) تولید شوند.

مستندات تولیدشده باید به دقت نشان‌دهنده APIهای مستقرشده باشند.

---

# فرآیند تولید مستندات OpenAPI

کد منبع (Source Code)

↓

کامنت‌های XML (XML Comments)

↓

مولد OpenAPI (OpenAPI Generator)

↓

فایل `swagger.json`

↓

رابط کاربری Swagger UI

↓

کلاینت‌های تولیدشده (Generated SDK)

---

# ۲. اهداف (Objectives)

مشخصات OpenAPI موارد زیر را فراهم می‌سازد:

- مستندسازی دقیق API
- تولید SDKهای کلاینت
- قابلیت کشف API (Discoverability)
- اعتبارسنجی قرارداد (Contract validation)
- قابلیت نگهداری بلندمدت

---

# ۳. نسخه مشخصات (Specification Version)

پروژه مشخصات OpenAPI 3.x را تولید خواهد کرد.

مثال:

```text
OpenAPI 3.1
```

نسخه دقیق به قابلیت‌ها و امکانات فریم‌ورک بستگی دارد.

---

# ۴. منبع مستندسازی (Documentation Source)

مستند OpenAPI باید به صورت خودکار از روی کد منبع تولید شود.

ویرایش دستی مستندات تولیدشده ممنوع است.

کد منبع، تنها منبع موثق (Single source of truth) باقی می‌ماند.

---

# ۵. گروه‌بندی‌های API (API Groups)

هر نسخه API یک مشخصات مستقل ارائه می‌دهد.

مثال:

```text
/swagger/v1/swagger.json

/swagger/v2/swagger.json
```

هر نسخه تنها نقاط پایانی متعلق به خود را مستند می‌کند.

---

# ۶. متاداده‌های الزامی نقاط پایانی (Required Endpoint Metadata)

هر نقطه پایانی باید موارد زیر را تعریف کند:

- خلاصه (Summary)
- توصیف (Description)
- برچسب‌ها (Tags)
- مدل درخواست (Request Model)
- مدل پاسخ (Response Model)
- کدهای وضعیت (Status Codes)
- نیازمندی‌های احراز هویت (Authentication Requirements)

نقاط پایانی بدون مستندات غیرقابل قبول هستند.

---

# ۷. تولید اسکیما (Schema Generation)

اسکیماها باید از روی DTOهای عمومی تولید شوند.

موارد زیر هرگز نباید به عنوان اسکیماهای عمومی ظاهر شوند:

- موجودیت‌های دامنه (Domain Entities)
- موجودیت‌های EF Core
- مدل‌های داخلی
- انواع و تایپ‌های زیرساختی

---

# ۸. نمونه داده‌ها (Example Payloads)

نقاط پایانی مهم باید نمونه‌های درخواست و پاسخ ارائه دهند.

نمونه‌های درخواست درک مصرف‌کننده را بهبود می‌بخشند.

نمونه‌های پاسخ باید نشان‌دهنده داده‌های واقعی کسب‌وکار باشند.

---

# ۹. مستندسازی خطاها (Error Documentation)

هر نقطه پایانی باید پاسخ‌های خطای احتمالی خود را مستند کند.

پاسخ‌های معمول مستندشده شامل موارد زیر است:

```text
400 Bad Request

401 Unauthorized

403 Forbidden

404 Not Found

409 Conflict

500 Internal Server Error
```

---

# ۱۰. مستندسازی احراز هویت (Authentication Documentation)

نقاط پایانی حفاظت‌شده باید طرح احراز هویت خود را اعلام کنند.

رابط Swagger UI باید از تست‌های احرازشده پشتیبانی کند.

نیازمندی‌های احراز هویت باید قبل از اجرا قابل مشاهده باشند.

---

# ۱۱. برچسب‌ها (Tags)

نقاط پایانی باید با استفاده از برچسب‌های مبتنی بر کسب‌وکار دسته‌بندی شوند.

مثال‌ها:

```text
Assets

Engines

Components

Maintenance

Documents

Forecasts

Administration
```

از برچسب‌های فنی باید پرهیز شود.

---

# ۱۲. منسوخ‌سازی (Deprecation)

نقاط پایانی منسوخ‌شده باید درون مستند OpenAPI به عنوان Deprecated علامت‌گذاری شوند.

مستندات باید نقطه پایانی جایگزین پیشنهادی را مشخص کنند.

---

# ۱۳. تولید کلاینت (Client Generation)

مستند OpenAPI باید از تولید خودکار کلاینت پشتیبانی کند.

کلاینت‌های تولیدشده باید با قرارداد منتشرشده سازگار باقی بمانند.

تغییر دستی کلاینت‌های تولیدشده توصیه نمی‌شود.

---

# ۱۴. دسترس‌پذیری مستندات (Documentation Availability)

مستندات تعاملی در محیط‌های توسعه در دسترس خواهند بود.

دسترس‌پذیری در محیط پروداکشن به سیاست‌های استقرار بستگی دارد.

انتشار عمومی باید به طور صریح کنترل شود.

---

# ۱۵. اعتبارسنجی (Validation)

مستند OpenAPI تولیدشده باید طبق مشخصات رسمی OpenAPI معتبر باقی بماند.

خطاهای اعتبارسنجی باعث شکست پایپ‌لاین ساخت (Build pipeline) خواهند شد.

---

# ۱۶. بهبودهای آتی

نسخه‌های آینده ممکن است شامل موارد زیر باشند:

- نمونه‌های با فرمت Markdown
- چند زبانه بودن
- لینک‌های مستندات خارجی
- صفحات دانلود SDK
- آموزش‌های تعاملی

---

# ۱۷. قوانین کیفیت مستندسازی (Documentation Quality Rules)

هر نقطه پایانی باید موارد زیر را مستند کند:

- خلاصه (Summary)
- توصیف (Description)
- پارامترها (Parameters)
- بدنه درخواست (Request Body)
- مدل پاسخ (Response Model)
- پاسخ‌های خطا (Error Responses)
- احراز هویت (Authentication)
- نمونه داده‌ها (Example Payloads)
