# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise قابلیت‌های سازمانی هوش مصنوعی را معرفی می‌نماید، از جمله:

- جستجوی معنایی (Semantic Search)
- دستیار دانش سازمانی (Enterprise Knowledge Assistant)
- تولید مبتنی بر بازیابی اطلاعات (RAG)
- کوپایلوت هوش مصنوعی (AI Copilot)
- دستیار هوشمند نگهداری و تعمیرات (Intelligent Maintenance Assistant)
- پیشنهادات حساس به زمینه (Context-Aware Recommendations)

این قابلیت‌ها نیازمند بازیابی معنایی کارآمد بر روی مستندات سازمانی هستند بدون آنکه بر پایگاه داده عملیاتی و تراکنشی تاثیری بگذارند.

پایگاه داده رابطه‌ای عملیاتی قبلاً به صورت زیر تصویب شده است:

**Microsoft SQL Server**

سند TE-0028 ابزار **Qdrant** را به عنوان فناوری پایگاه داده برداری (Vector Database) سازمانی تصویب نمود.

تصمیمات معماری باقی‌مانده مربوط به موارد زیر است:

- مالکیت داده‌های تجاری؛
- مالکیت امبدینگ‌ها (Embeddings)؛
- استراتژی همگام‌سازی؛
- معماری بازیابی اطلاعات؛
- مرزهای زیرساخت.

---

# بیان مسئله (Problem)

پلتفرم نیازمند بازیابی معنایی است در حالی که معماری ماندگاری سازمانی موجود باید حفظ گردد.

معماری باید اطمینان حاصل نماید که:

- داده‌های تجاری عملیاتی معتبر و مرجع باقی می‌مانند؛
- شاخص‌ها و ایندکس‌های معنایی همگام باقی می‌مانند؛
- بازیابی هوش مصنوعی مستقل از ماندگاری تراکنشی باقی می‌ماند؛
- استقلال از فروشندگان حفظ می‌شود؛
- استقرار ترکیبی (Hybrid Deployment) امکان‌پذیر باقی می‌ماند.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

معماری باید نیازمندی‌های زیر را برآورده سازد:

- معماری پاک (Clean Architecture)
- الگوی CQRS
- تفکیک وظایف (Separation of Concerns)
- مقیاس‌پذیری سازمانی (Enterprise Scalability)
- استقلال از فروشنده (Vendor Independence)
- استقرار ترکیبی (Hybrid Deployment)
- آمادگی برای هوش مصنوعی (AI Readiness)
- قابلیت نگهداری عملیاتی (Operational Maintainability)

# تصمیم (Decision)

هیات بازبینی معماری (Architecture Review Board) معماری زیر را تصویب می‌نماید.

## داده‌های عملیاتی (Operational Data)

محیط Microsoft SQL Server به عنوان **سامانه مرجع و ثبت اصلی (System of Record)** باقی می‌ماند.

مسئولیت‌ها شامل موارد زیر است:

- موجودیت‌های تجاری
- تراکنش‌ها
- داده‌های ممیزی
- پیکربندی
- ماندگاری عملیاتی

هیچ بردار معنایی در SQL Server ذخیره نمی‌شود.

---

## ذخیره‌سازی برداری (Vector Storage)

سرویس Qdrant زیرساخت اختصاصی بازیابی معنایی می‌شود.

مسئولیت‌ها شامل موارد زیر است:

- ذخیره‌سازی امبدینگ‌ها
- ایندکس‌های ANN (تقریب نزدیک‌ترین همسایه)
- جستجوی تشابه (Similarity Search)
- فیلترسازی متادیتا
- بازیابی معنایی

سرویس Qdrant هرگز موجودیت‌های تجاری عملیاتی را ذخیره نمی‌کند.

---

## مالکیت امبدینگ‌ها (Embedding Ownership)

امبدینگ‌ها مصنوعات مشتق‌شده (Derived Artifacts) هستند.

آن‌ها **داده‌های تجاری مرجع و اصیل نیستند**.

مالکیت همچنان با سند تجاری مبدا باقی می‌ماند.

پایگاه داده برداری صرفاً حاوی موارد زیر است:

- بردارهای امبدینگ؛
- شناسه‌های اسناد؛
- متادیتای بازیابی.

---

## منبع حقیقت (Source of Truth)

| داده | منبع حقیقت |
|------|-----------------|
| موجودیت تجاری | Microsoft SQL Server |
| سند تجاری | Microsoft SQL Server |
| امبدینگ | مصنوع تولیدشده |
| ایندکس برداری | Qdrant |

# مدل معماری (Architectural Model)

```text
                     Application Layer (لایه کاربرد)

                            │

                            ▼

               Embedding Generation Service
                (سرویس تولید امبدینگ)

                            │

        ┌───────────────────┴───────────────────┐

        ▼                                       ▼

Microsoft SQL Server                      Qdrant

(System of Record - سامانه مرجع)    (Vector Database - پایگاه داده برداری)

        │                                       │

 Structured Business Data            Semantic Embeddings
 (داده‌های ساختاریافته تجاری)           (امبدینگ‌های معنایی)

        └───────────────────┬───────────────────┘

                            ▼

              Retrieval-Augmented Generation
              (تولید مبتنی بر بازیابی اطلاعات - RAG)
```

---

# چرخه حیات امبدینگ (Embedding Lifecycle)

چرخه حیات امبدینگ به شرح زیر است:

```text
Document Created (ایجاد سند)

        │

        ▼

Persist in SQL Server (ذخیره در SQL Server)

        │

        ▼

Generate Embedding (تولید امبدینگ)

        │

        ▼

Store Embedding in Qdrant (ذخیره امبدینگ در Qdrant)

        │

        ▼

Ready for Semantic Retrieval (آماده برای بازیابی معنایی)
```

---

# گردش کار به‌روزرسانی سند (Document Update Workflow)

```text
Document Updated (به‌روزرسانی سند)

        │

        ▼

Update SQL Server (به‌روزرسانی در SQL Server)

        │

        ▼

Regenerate Embedding (تولید مجدد امبدینگ)

        │

        ▼

Replace Existing Vector (جایگزینی بردار موجود)

        │

        ▼

Retrieval Updated (بازیابی به‌روزرسانی شد)
```

---

# گردش کار حذف سند (Document Deletion Workflow)

```text
Document Deleted (حذف سند)

        │

        ▼

Delete SQL Server Record (حذف رکورد از SQL Server)

        │

        ▼

Delete Vector Entry (حذف مدخل برداری)

        │

        ▼

Consistency Restored (سازگاری بازگردانده شد)
```

---

# استراتژی همگام‌سازی (Synchronization Strategy)

همگام‌سازی باید **رویداد-محور (Event-driven)** باشد.

رویدادها شامل موارد زیر است:

- DocumentCreated (سند ایجاد شد)
- DocumentUpdated (سند به‌روزرسانی شد)
- DocumentDeleted (سند حذف شد)

هر رویداد موجب تحریک همگام‌سازی امبدینگ می‌گردد.

---

# گردش کار بازیابی (Retrieval Workflow)

```text
User Question (پرسش کاربر)

        │

        ▼

Embedding Generation (تولید امبدینگ)

        │

        ▼

Qdrant Similarity Search (جستجوی تشابه در Qdrant)

        │

        ▼

Relevant Document IDs (شناسه‌های اسناد مرتبط)

        │

        ▼

Retrieve Documents from SQL Server (بازیابی اسناد از SQL Server)

        │

        ▼

Context Assembly (تجمیع و چینش زمینه/کانتکست)

        │

        ▼

Large Language Model (مدل بزرگ زبانی - LLM)

        │

        ▼

AI Response (پاسخ هوش مصنوعی)
```

---

# استراتژی متادیتا (Metadata Strategy)

متادیتای ذخیره‌شده در Qdrant شامل موارد زیر خواهد بود:

- DocumentId (شناسه سند)
- Module (ماژول)
- Language (زبان)
- DocumentType (نوع سند)
- Security Classification (طبقه‌بندی امنیتی)
- Department (بخش/واحد)
- Tags (برچسب‌ها)

محتوای عملیاتی سند صرفاً در SQL Server ذخیره باقی می‌ماند.

---

# مدل سازگاری (Consistency Model)

معماری از مدل **سازگاری نهایی (Eventual Consistency)** پیروی می‌کند.

نیازمندی‌ها:

- تراکنش SQL Server باید ابتدا تکمیل شود.
- همگام‌سازی برداری به صورت ناهمگام اجرا می‌گردد.
- تاخیر موقت میان ماندگاری و در دسترس بودن معنایی قابل قبول است.

---

# مدیریت خطا (Failure Handling)

اگر تولید امبدینگ با شکست مواجه شود:

- تراکنش SQL Server نباید بازگشت داده شود (Rollback نشود).
- خطا باید ثبت (Log) گردد.
- تلاش مجدد (Retry) باید زمان‌بندی شود.
- داده‌های عملیاتی در دسترس باقی می‌مانند.

---

# امنیت (Security)

اصول امنیتی:

- پایگاه داده SQL Server صدور مجوزهای تجاری را کنترل می‌کند.
- سرویس Qdrant هیچ وضعیت تجاری حساسی را ذخیره نمی‌کند.
- بازیابی معنایی صرفاً از شناسه‌های اسناد استفاده می‌نماید.
- بررسی‌های مجوز قبل از بازیابی اسناد انجام می‌شود.

---

# مزایا (Benefits)

این معماری مزایای زیر را فراهم می‌آورد:

- تفکیک شفاف مسئولیت‌ها.
- مقیاس‌پذیری مستقل ذخیره‌سازی رابطه‌ای و برداری.
- استقلال از فروشندگان.
- توسعه‌پذیری قابلیت‌های هوش مصنوعی.
- سادگی عملیاتی.
- قابلیت نگهداری سازمانی.

---

# پیامدها (Consequences)

مثبت:

- بازیابی معنایی با کارایی و کارآمدی بالا.
- کمترین اثر بر پایگاه داده عملیاتی.
- مرزهای مالکیتی شفاف.
- امکان گسترش قابلیت‌های هوش مصنوعی در آینده.

منفی:

- مولفه زیرساختی اضافی.
- نیاز به همگام‌سازی رویداد-محور.
- سازگاری نهایی به جای سازگاری فوری.

**پذیرفته‌شده (Accepted)**
