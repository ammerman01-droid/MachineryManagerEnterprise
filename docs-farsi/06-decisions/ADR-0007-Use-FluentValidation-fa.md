# زمینه و مسئله (Context)

سامانه MachineryManagerEnterprise نیازمند یک فریم‌ورک اعتبارسنجی مدرن است که قوانین اعتبارسنجی را از موجودیت‌های کسب‌وکار، منطق ارائه و دغدغه‌های ماندگاری داده جدا نگه دارد.

راهکار اعتبارسنجی انتخاب‌شده باید:

- از جداسازی شفاف دغدغه‌ها پشتیبانی کند.
- به صورت طبیعی با ASP.NET Core یکپارچه شود.
- کاملاً قابل آزمون‌پذیری باشد.
- قابلیت توسعه داشته باشد.
- قوانین اعتبارسنجی خوانا و شفاف تولید کند.
- از بومی‌سازی (Localization) پشتیبانی کند.
- با اصول معماری پاک همراستا باشد.

---

# تصمیم (Decision)

لایه کاربرد (Application Layer) باید از **FluentValidation** به عنوان فریم‌ورک استاندارد اعتبارسنجی استفاده کند.

تمامی اعتبارسنجی‌های ورودی باید با استفاده از اعتبارسنج‌های (Validators) FluentValidation پیاده‌سازی شوند.

موجودیت‌های کسب‌وکار نباید شامل منطق اعتبارسنجی مربوط به UI باشند.

---

# محرک‌های تصمیم (Decision Drivers)

- جداسازی دغدغه‌ها (Separation of Concerns)
- خوانایی (Readability)
- آزمون‌پذیری (Testability)
- یکپارچه‌سازی با ASP.NET Core
- متن‌باز بودن (Open Source)
- قابلیت توسعه (Extensibility)
- قابلیت نگهداری (Maintainability)

---

# گزینه‌های جایگزین بررسی‌شده (Alternatives Considered)

## DataAnnotations

رد شد زیرا قوانین اعتبارسنجی به شدت به DTOها وابسته شده و مشخصه‌های Attribute برای سناریوهای پیچیده بیانگری کمتری دارند.

---

## فریم‌ورک سفارشی اعتبارسنجی (Custom Validation Framework)

رد شد زیرا باعث دوباره‌کاری قابلیت‌های موجود و بالغ شده و هزینه نگهداری را افزایش می‌داد.

---

## اعتبارسنجی دستی (Manual Validation)

رد شد زیرا منجر به منطق ناهماهنگ اعتبارسنجی و افزایش دوباره‌کاری کد می‌شد.

---

# پیامدها (Consequences)

## مثبت

- لایه اعتبارسنجی پاک و مستقل
- قوانین اعتبارسنجی قابل استفاده مجدد
- آزمون واحد (Unit Testing) آسان
- بهبود قابلیت نگهداری
- رویکرد یکنواخت در اعتبارسنجی
- قابلیت‌های غنی اعتبارسنجی

## منفی

- توسعه‌دهندگان باید سنتکس FluentValidation را یاد بگیرند.
- اعتبارسنج‌ها نیازمند ثبت صریح (Explicit registration) هستند.

---

# تاثیر بر معماری (Architecture Impact)

فریم‌ورک FluentValidation تنها باید درون **لایه کاربرد (Application Layer)** وجود داشته باشد.

لایه Presentation اعتبارسنجی را از طریق لایه Application فراخوانی می‌کند.

لایه Domain مستقل از FluentValidation باقی می‌ماند.

لایه Infrastructure نباید شامل اعتبارسنج‌های کسب‌وکار باشد.

---

# نکات پیاده‌سازی (Implementation Notes)

اعتبارسنج‌ها باید به صورت خودکار از طریق تزریق وابستگی (Dependency Injection) ثبت شوند.

هر DTO درخواستی (Request DTO) باید دارای یک اعتبارسنج مربوطه باشد.

اعتبارسنجی باید پیش از اجرای منطق کسب‌وکار اجرا شود.

---

# قوانین انطباق (Compliance Rules)

۱. فریم‌ورک FluentValidation تنها باید درون لایه Application وجود داشته باشد.

۲. لایه Domain هرگز نباید به FluentValidation ارجاع دهد.

۳. لایه Presentation هرگز نباید شامل قوانین اعتبارسنجی کسب‌وکار باشد.

۴. هر Request DTO باید دارای یک اعتبارسنج مربوطه باشد.

۵. اعتبارسنجی کسب‌وکار نباید با استفاده از DataAnnotations پیاده‌سازی شود.

۶. منطق اعتبارسنجی باید مستقل از ماندگاری داده باقی بماند.
