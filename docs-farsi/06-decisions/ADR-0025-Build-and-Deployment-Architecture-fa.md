# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise به یک پایپ‌لاین یکپارچه ساخت، بسته‌بندی و استقرار در سطح سازمانی نیاز دارد که قادر به پشتیبانی از توسعه محلی، اعتبارسنجی خودکار، استقرار کانتینری‌شده، و هر دو نوع میزبانی ابری و محلی/ترکیبی (On-premise/Hybrid) باشد، و با رویکرد انعطاف‌پذیری استقرار که قبلاً برای دسترسی به داده‌ها، ذخیره‌سازی فایل و جستجو تثبیت شده بود (ADR-0019، ADR-0020، ADR-0021) همخوانی داشته باشد.

سند `TE-0031 — ارزیابی فناوری ساخت، بسته‌بندی و استقرار` ابزارهای .NET 10 SDK، Docker، .NET Aspire، GitHub Actions و Azure DevOps را در برابر این نیازمندی مورد ارزیابی قرار داد و یک پشته ترکیبی را توصیه نمود، و ثبت رسمی آن تصمیم را به این ADR موکول کرد.

---

# بیان مسئله (Problem)

بدون یک پشته ساخت و استقرار واحد و رسماً تصویب‌شده، ماژول‌ها یا محیط‌های مجزا ممکن بود ابزارهای ساخت، پلتفرم‌های CI/CD یا رویکردهای کانتینرسازی ناسازگاری را اتخاذ کنند که این امر تکرارپذیری را تضعیف کرده و هزینه‌های عملیاتی و ورود نیروهای جدید (Onboarding) را در بلندمدت افزایش می‌دهد.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

معماری ساخت و استقرار باید موارد زیر را برآورده سازد:

- اتوماسیون ساخت سازمانی
- یکپارچه‌سازی مداوم / تحویل مداوم (CI/CD)
- کانتینرسازی (Containerization)
- ساخت‌های تکرارپذیر و قطعی (Deterministic)
- پشتیبانی چندپلتفرمی (Windows، Linux، macOS)
- آمادگی برای استقرار ترکیبی (محلی و ابری)
- قابلیت نگهداری بلندمدت

---

# تصمیم (Decision)

سامانه MachineryManagerEnterprise پشته ساخت، بسته‌بندی و استقرار زیر را اتخاذ می‌نماید:

| مسئولیت | فناوری تصویب‌شده |
|-----------------|------------------------|
| پلتفرم ساخت | **.NET 10 SDK** |
| کانتینرسازی | **Docker** |
| ارکستراسیون محلی توزیع‌شده | **.NET Aspire** |
| یکپارچه‌سازی مداوم | **GitHub Actions** |
| جایگزین سازمانی ALM | **Azure DevOps** (پشتیبانی‌شده، اختیاری) |

مجموعه ابزار **.NET 10 SDK** زنجیره ابزار معتبر و یگانه ساخت برای تک‌تک پروژه‌های درون Solution است (restore، build، test، publish، pack). فناوری **Docker** فناوری استاندارد کانتینرسازی برای بسته‌بندی و ثبات استقرار در سراسر محیط‌ها است. ابزار **.NET Aspire** برای ارکستراسیون برنامه‌های کاربردی توزیع‌شده محلی در حین توسعه اتخاذ شده است. پلتفرم **GitHub Actions** پلتفرم اصلی یکپارچه‌سازی مداوم (CI) است که با استفاده پروژه از گیت‌هاب به عنوان پلتفرم کنترل سورس کد همخوانی دارد. پلتفرم **Azure DevOps** به عنوان یک گزینه سازمانی ALM پشتیبانی‌شده و اختیاری برای مشتریان یا تیم‌هایی که قبلاً بر روی اکوسیستم Azure DevOps استانداردسازی شده‌اند حفظ می‌گردد، اما حالت پیش‌فرض نیست.

# پیامدها (Consequences)

## مثبت (Positive)

- ساخت‌های تکرارپذیر و معین در سراسر تمامی محیط‌ها
- استقرار منسجم و مبتنی بر کانتینر
- اتوماسیون CI فوق‌العاده با حداقل ابزارهای جانبی اضافی
- آمادگی برای استقرار ترکیبی (محلی و ابری)
- همراستایی قوی با اکوسیستم مایکروسافت، همسو با پشته .NET 10 / Blazor پلتفرم

## منفی (Negative)

- معرفی نیازمندی به زمان اجرای داکر (Docker Runtime) در محیط‌های ساخت و استقرار
- ابزار .NET Aspire یک لایه ارکستراسیون اضافی برای توسعه محلی اضافه می‌کند
- پیچیدگی عملیاتی اختیاری در صورتی که Azure DevOps توسط یک مشتری یا تیم خاص اتخاذ شود

---

# گزینه‌های بررسی‌شده (Alternatives Considered)

## پلتفرم Azure DevOps به عنوان پلتفرم اصلی CI/CD

به عنوان پیش‌فرض رد شد زیرا پروژه از GitHub به عنوان پلتفرم اصلی کنترل سورس کد خود استفاده می‌کند؛ GitHub Actions قابلیت‌های فوق‌العاده CI/CD را با پیچیدگی مدیریتی به مراتب کمتری ارائه می‌دهد. پلتفرم Azure DevOps به عنوان یک جایگزین سازمانی کاملاً پشتیبانی‌شده برای سازمان‌هایی که از قبل بر روی آن استانداردسازی شده‌اند باقی می‌ماند.
