# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise یک سیستم در سطح سازمانی (Enterprise-grade) است که بر پایه اصول زیر ساخته شده است:

- معماری پاک (Clean Architecture)
- الگوی CQRS
- طراحی دامنه-محور (Domain-Driven Design)
- معماری رویداد-محور (Event-Driven Architecture)

این پروژه شامل چندین زمینه محدود (Bounded Context)، ماژول‌های مستقل، مولفه‌های زیرساختی و رابط‌های کاربری است.

بنابراین، یک استراتژی یکپارچه آزمون سازمانی برای تضمین موارد زیر مورد نیاز است:

- صحت معماری؛
- صحت عملکرد کسب‌وکار؛
- قابلیت اطمینان زیرساخت؛
- قابلیت نگهداری بلندمدت.

سند ارزیابی فنی TE-0030 فناوری‌های آزمون زیر را انتخاب نمود:

- xUnit v3
- FluentAssertions
- NSubstitute
- Testcontainers
- Playwright

این ADR نحوه استفاده از این فناوری‌ها را در سراسر سیستم تعریف می‌نماید.

---

# بیان مسئله (Problem)

بدون یک استراتژی یکپارچه آزمون:

- ماژول‌های مختلف رویکردهای ناهمگون و ناسازگاری را در آزمون پیاده‌سازی خواهند کرد؛
- شناسایی پس‌رفت‌ها و نقص‌های معماری (Architectural Regressions) دشوار خواهد شد؛
- رفتار زیرساخت با محیط عملیاتی (Production) واگرا خواهد شد؛
- هزینه نگهداری بلندمدت سیستم افزایش خواهد یافت.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

استراتژی آزمون باید از موارد زیر پشتیبانی کند:

- معماری پاک (Clean Architecture)
- بازخورد سریع (Fast Feedback)
- استقرارهای با ضریب اطمینان بالا
- اتوماسیون CI/CD
- اجرای قطعی و معین (Deterministic Execution)
- مقیاس‌پذیری سازمانی
- قابلیت نگهداری بلندمدت

---

# تصمیم (Decision)

سامانه MachineryManagerEnterprise یک استراتژی آزمون لایه‌بندی‌شده بر پایه **هرم آزمون (Test Pyramid)** را اتخاذ می‌نماید.

---

# هرم آزمون (Test Pyramid)

```text
                 End-to-End Tests (آزمون‌های سرتاسری)

                              Playwright

                                   ▲

                 Integration Tests (آزمون‌های یکپارچگی)

                            Testcontainers

                                   ▲

                     Unit Tests (آزمون‌های واحد)

               xUnit + FluentAssertions + NSubstitute
```

اکثریت آزمون‌ها باید به صورت آزمون‌های واحد (Unit Tests) باقی بمانند.

آزمون‌های سرتاسری (End-to-End) باید به اعتبارسنجی گردش کارهای کامل تجاری محدود گردند.

---

# لایه‌های آزمون (Testing Layers)

## آزمون‌های واحد (Unit Tests)

هدف (Purpose)

اعتبارسنجی:

- منطق دامنه (Domain Logic)
- اشیاء مقداری (Value Objects)
- موجودیت‌ها (Entities)
- سرویس‌های دامنه (Domain Services)
- سرویس‌های کاربرد (Application Services)
- قواعد اعتبارسنجی (Validation Rules)

ویژگی‌ها (Characteristics)

- بدون وابستگی به زیرساخت
- بدون پایگاه داده
- بدون شبکه
- بدون سیستم فایل

زمان اجرا (Execution Time)

میلی‌ثانیه

---

## آزمون‌های یکپارچگی (Integration Tests)

هدف (Purpose)

اعتبارسنجی تعامل با زیرساخت واقعی.

نمونه‌ها

- SQL Server
- RabbitMQ
- Redis
- Blob Storage

زیرساخت باید با استفاده از Testcontainers آماده‌سازی و راه‌اندازی شود.

ویژگی‌ها (Characteristics)

- زیرساخت واقعی
- محیط یک‌بارمصرف و موقت (Disposable)
- اجرای قطعی و معین (Deterministic)

---

## آزمون‌های سرتاسری (End-to-End Tests)

هدف (Purpose)

اعتبارسنجی سناریوهای کامل کاربر.

نمونه‌ها

- احراز هویت
- گردش کارهای تجاری
- گزارش‌گیری
- رفتار رابط کاربری (UI Behavior)

اتوماسیون مرورگر باید از Playwright استفاده کند.

---

| مسئولیت | فناوری |
|---------------|------------|
| فریم‌ورک آزمون | xUnit v3 |

| ماک کردن (Mocking) | NSubstitute |
| زیرساخت آزمون | Testcontainers |
| اتوماسیون مرورگر | Playwright |

# ساختار پروژه آزمون (Test Project Structure)

```text
tests/

    Unit/

    Integration/

    Architecture/

    UI/

    Performance/
```

هر پروژه آزمون باید دقیقاً شامل یک مسئولیت آزمون باشد.

---

# قواعد آزمون‌های واحد (Unit Testing Rules)

آزمون‌های واحد باید:

- به صورت مستقل اجرا شوند؛
- به صورت موازی اجرا شوند؛
- از وضعیت به اشتراک گذاشته‌شده (Shared State) اجتناب کنند؛
- از وابستگی‌های خارجی اجتناب نمایند؛
- قطعی و معین (Deterministic) باقی بمانند.

آزمون‌های واحد هرگز نباید به موارد زیر نیاز داشته باشند:

- SQL Server
- RabbitMQ
- Redis
- Docker
- دسترسی به شبکه

---

# استراتژی ماک کردن (Mocking Strategy)

ماک کردن باید از NSubstitute استفاده کند.

تنها وابستگی‌های خارجی مجاز به ماک شدن هستند.

منطق تجاری هرگز نباید ماک شود.

نمونه‌ها

مجاز (Allowed)

- مخزن داده (Repository)
- سرویس خارجی (External Service)
- ساعت سیستم (Clock)
- سرویس ایمیل (Email Service)

غیرمجاز (Not Allowed)

- موجودیت (Entity)
- شیء مقداری (Value Object)
- منطق دامنه (Domain Logic)

---

# استراتژی اعتبارسنجی (Assertion Strategy)

بیانیه‌های اعتبارسنجی باید از FluentAssertions استفاده کنند.

بیانیه‌ها باید بر خوانایی تاکید داشته باشند.

نمونه

```csharp
result.Should().Be(expected);
```

به جای

```csharp
Assert.Equal(expected, result);
```

---

# استراتژی آزمون‌های یکپارچگی (Integration Testing Strategy)

آزمون‌های یکپارچگی باید موارد زیر را اعتبارسنجی نمایند:

- پیاده‌سازی‌های مخازن داده (Repositories)
- نگاشت‌های EF Core
- پرس‌وجوهای SQL
- یکپارچگی با گذرگاه پیام (Message Bus)
- پیکربندی زیرساخت

تمامی زیرساخت‌ها باید با استفاده از Testcontainers ایجاد شوند.

هیچ پایگاه داده اشتراکی نباید مورد استفاده قرار گیرد.

---

# ایزوله‌سازی آزمون (Test Isolation)

هر بار اجرای آزمون یکپارچگی باید زیرساخت مستقل خود را ایجاد کند.

```text
Test Start (شروع آزمون)

      │

Create Containers (ایجاد کانتینرها)

      │

Execute Tests (اجرای آزمون‌ها)

      │

Dispose Containers (حذف و پاکسازی کانتینرها)

      │

Clean Environment (محیط تمیز)
```

---

# آزمون‌های معماری (Architecture Tests)

آزمون‌های معماری باید موارد زیر را اعتبارسنجی نمایند:

- قواعد وابستگی (Dependency Rules)
- مرزهای معماری پاک (Clean Architecture Boundaries)
- ایزوله‌سازی لایه‌ها
- ارجاعات ممنوعه

این آزمون‌ها به عنوان آزمون‌های عادی xUnit اجرا می‌شوند.

---

# استراتژی آزمون‌های سرتاسری (End-to-End Strategy)

ابزار Playwright صرفاً باید موارد زیر را اعتبارسنجی نماید:

- گردش کارهای کامل تجاری؛
- تعاملات مرورگر؛
- سناریوهای احراز هویت؛
- سناریوهای پس‌رفت (Regression).

قواعد تجاری همچنان باید در وهله اول از طریق آزمون‌های واحد (Unit Tests) اعتبارسنجی شوند.

---

---

# یکپارچه‌سازی مداوم (Continuous Integration)

هر درخواست پول ریکوئست (Pull Request) باید موارد زیر را اجرا کند:

۱. آزمون‌های واحد (Unit Tests)
۲. آزمون‌های معماری (Architecture Tests)
۳. آزمون‌های یکپارچگی (Integration Tests)

آزمون‌های سرتاسری ممکن است بسته به پیکربندی پایپ‌لاین به طور جداگانه اجرا شوند.

---

# نام‌گذاری آزمون‌ها (Test Naming)

نام‌های آزمون باید از الگوی زیر پیروی کنند:

```text
MethodName_StateUnderTest_ExpectedBehavior
(نام‌متد_وضعیت‌تحت‌آزمون_رفتار‌مورد‌انتظار)
```

مثال

```text
CreateOrder_InvalidCustomer_ShouldThrowValidationException
```

# کارایی و عملکرد (Performance)

زیرساخت در سطح Fixture در صورتی که ایمن باشد می‌تواند مجدداً استفاده شود.

آزمون‌های طولانی‌مدت باید به حداقل برسند.
