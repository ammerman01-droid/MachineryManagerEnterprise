# زمینه و بستر (Context)

سند `03-TechnologyGapAnalysis.md` مبحث **ذخیره‌سازی فایل تعبیه‌شده (Embedded File Storage)** را به عنوان یک شکاف معماری مستندشده (اولویت: متوسط) شناسایی کرده است که به قابلیت "استراتژی همگام‌سازی فایل" وابسته بود و تا پیش از این توسط هیچ ADR تصویب‌شده‌ای تعیین تکلیف نشده بود.

سند `ADR-0012 — معماری فضای کاری توزیع‌شده` مقرر می‌دارد که پیوست‌های تجاری — عکس‌ها، اسناد بازرسی و دفترچه‌های راهنما — باید در حین همگام‌سازی به صورت جداگانه از متادیتای تجاری انتقال یابند، به طوری که متادیتای پیوست درون بسته همگام‌سازی باقی بماند در حالی که محتوای باینری به صورت مستقل قابل انتقال باشد. آن تصمیم *مدل* انتقال را تعریف کرد اما *فناوری* ذخیره‌سازی عینی را انتخاب نکرد.

سند ارزیابی فنی `TE-0026 — ارزیابی فناوری ذخیره‌سازی فایل` گزینه‌های ذخیره‌سازی محلی (Local Storage)، ذخیره‌سازی حبابی آژور (Azure Blob Storage)، مینیو (MinIO)، و الگوی انتزاع ذخیره‌سازی سازگار با S3 را در برابر این نیازمندی و همراستا با رویکرد بی‌طرفی ابری و اولویت متن‌باز پلتفرم (ADR-0002) و نیازمندی به خدمت‌رسانی به مشتریان با طیف گسترده‌ای از ترجیحات میزبانی (شامل استقرارهای محلی و ایزوله On-premise و Air-gapped) مورد ارزیابی قرار داد. این سند یک انتزاع ذخیره‌سازی سازگار با S3 را به عنوان پیاده‌سازی `IFileStorage` پلتفرم همراه با MinIO به عنوان اندپوینت پیش‌فرض خودمیزبان توصیه نمود و ثبت رسمی این تصمیم را به این ADR موکول کرد.

# تصمیم (Decision)

پلتفرم باید به تمامی محتواهای باینری پیوست‌ها منحصراً از طریق یک انتزاع لایه کاربرد، یعنی `IFileStorage`، دسترسی داشته باشد که در لایه Infrastructure به شرح زیر پیاده‌سازی می‌گردد:

- پیاده‌سازی اصلی `IFileStorage` باید بر پایه **Amazon S3 API** با استفاده از AWS SDK برای دات‌نت ساخته شود، که این پیاده‌سازی را صرفاً از طریق پیکربندی در سراسر هر اندپوینت سازگار با API اس۳ قابل حمل و استفاده می‌سازد.
- سرویس **MinIO** باید اندپوینت ذخیره‌سازی شیء (Object Storage) پیش‌فرض، متن‌باز و خودمیزبان برای استقرارهای محلی (On-premise) و محیط‌های کاملاً ایزوله (Air-gapped) باشد.
- یک ارائه‌دهنده سازگار با S3 کاملاً مدیریت‌شده (مانند AWS S3) می‌تواند به عنوان اندپوینت برای استقرارهای میزبانی‌شده در ابر پیکربندی شود، بدون آنکه نیاز به هیچ‌گونه تغییری در کد برنامه باشد.
- یک پیاده‌سازی ثانویه **ذخیره‌سازی محلی (Local Storage)** از `IFileStorage` برای کوچک‌ترین استقرارهای محلی تک‌سروره که ذخیره‌سازی شیء در آن‌ها توجیه‌پذیر نیست، حفظ می‌گردد.
- سرویس **Azure Blob Storage** به عنوان پیش‌فرض پلتفرم تصویب نمی‌گردد. یک پیاده‌سازی اختصاصی Azure Blob Storage برای `IFileStorage` ممکن است بعداً برای مشتریان خاصی که متعهد به استقرار در آژور هستند اضافه شود، بدون آنکه بر این تصمیم تاثیری بگذارد.

# محرک‌های تصمیم‌گیری (Decision Drivers)

- بی‌طرفی ابری (Cloud Neutrality)
- انعطاف‌پذیری در استقرار (محلی، ایزوله/Air-gapped، و ابری)
- سازگاری با همگام‌سازی فضای کاری توزیع‌شده (ADR-0012)
- انطباق با خط‌مشی اولویت متن‌باز (ADR-0002)
- پیش‌بینی‌پذیری هزینه‌ها در سراسر ترجیحات گوناگون میزبانی مشتریان

# گزینه‌های بررسی‌شده (Alternatives Considered)

## سرویس Azure Blob Storage به عنوان فناوری انحصاری ذخیره‌سازی

به عنوان پیش‌فرض پلتفرم رد شد زیرا یک سرویس مدیریت‌شده اختصاصی و خاص آژور است که قفل‌شدگی به فروشنده (Vendor Lock-in) ایجاد می‌کند و با رویکرد بی‌طرفی ابری پلتفرم در تضاد بوده و برای استقرارهای محلی یا ایزوله مشتریان نامناسب است.

## ذخیره‌سازی محلی (Local Storage) به عنوان فناوری انحصاری ذخیره‌سازی

به عنوان پیش‌فرض در سطح پلتفرم رد شد زیرا فراتر از یک سرور واحد مقیاس نمی‌پذیرد، فاقد پشتیبانی بومی از URLهای پیش‌امضاشده (Presigned URLs) است و نیازمند مهندسی سفارشی برای برآورده ساختن نیازمندی ADR-0012 مبنی بر انتقال مستقل محتوای باینری است. این گزینه صرفاً به عنوان یک پیاده‌سازی ثانویه برای کوچک‌ترین استقرارهای تک‌سروره حفظ شده است.

## یک SDK اختصاصی به ازای هر ابر (نگهداری موازی آژور و AWS)

رد شد زیرا نگهداری دو پیاده‌سازی مجزا و وابسته به ارائه‌دهنده از `IFileStorage` بار نگهداری بلندمدت را بدون ایجاد منفعت معماری جبران‌کننده نسبت به یک پیاده‌سازی واحد سازگار با S3 که هم سناریوهای خودمیزبان و هم اکثر سناریوهای ابری مدیریت‌شده را پوشش می‌دهد، افزایش می‌دهد.

# پیامدها (Consequences)

## مثبت (Positive)

- یک پیاده‌سازی و مسیر کد یکسان برای `IFileStorage` به استقرارهای محلی، ایزوله (Air-gapped) و ابر عمومی خدمت‌رسانی می‌کند که صرفاً از طریق پیکربندی انتخاب می‌شود.
- ابزار MinIO به هر استقراری، از جمله کوچک‌ترین مشتریان، امکان دسترسی به URLهای پیش‌امضاشده و سازگاری بومی همگام‌سازی فضای کاری توزیع‌شده را بدون نیاز به اشتراک ابری می‌دهد.
- مشتریانی که تجربه ابری مدیریت‌شده را ترجیح می‌دهند می‌توانند همان پیاده‌سازی را به سمت AWS S3 یا سایر ارائه‌دهندگان مدیریت‌شده سازگار با S3 بدون هیچ تغییری در کد هدایت کنند.

## منفی (Negative)

- استقرارهایی که MinIO را انتخاب می‌کنند، مسئولیت عملیاتی اجرای یک سرویس خودمیزبان (ارکستراسیون کانتینر، تخصیص دیسک، اعمال وصله‌ها) را بر عهده می‌گیرند، به جای آنکه به یک سرویس کاملاً مدیریت‌شده تکیه کنند.
- پلتفرم به طور پیش‌فرض از ارگونومی SDK دست اول و نگاشته‌شده توسط مایکروسافت برای Azure Blob Storage بهره‌مند نمی‌شود؛ یک پیاده‌سازی خاص آژور، در صورت اضافه شدن در آینده برای مشتریان خاص، کد اضافه‌ای در لایه Infrastructure برای نگهداری خواهد بود.

## سبک‌سنگین‌ها (Trade-offs)

برخی قابلیت‌های پیشرفته و اختصاصی ذخیره‌سازی ارائه‌دهندگان (برای مثال، برخی قابلیت‌های انحصاری آژور) عمداً مورد استفاده قرار نمی‌گیرند، به نفع زیرمجموعه مشترک Amazon S3 API که در سراسر MinIO، AWS S3 و سایر ارائه‌دهندگان سازگار با S3 قابل حمل باقی می‌ماند.

## محدودیت‌های آینده (Future Limitations)

اگر یک مشتری خاص به دلایل سازمانی یا انطباق قانونی به Azure Blob Storage نیاز داشته باشد، یک پیاده‌سازی اختصاصی `AzureBlobFileStorage` از اینترفیس موجود `IFileStorage` می‌تواند بدون تاثیر بر این تصمیم یا پیکربندی سایر استقرارها اضافه گردد.

# تاثیر معماری (Architecture Impact)

- **دامنه (Domain)** — بدون تاثیر. موجودیت‌های دامنه صرفاً به یک شناسه پایدار پیوست ارجاع می‌دهند، هرگز به فناوری ذخیره‌سازی ارجاع نمی‌دهند.
- **کاربرد (Application)** — صرفاً به انتزاع `IFileStorage` وابسته است (Upload / Download / Delete / GetTemporaryDownloadUri).
- **زیرساخت (Infrastructure)** — پیاده‌سازی `S3CompatibleFileStorage` (با استفاده از AWS SDK برای دات‌نت) را به عنوان پیش‌فرض، و پیاده‌سازی `LocalFileStorage` را برای کوچک‌ترین استقرارهای تک‌سروره میزبانی می‌کند. هر دو به ازای هر استقرار از طریق پیکربندی انتخاب می‌شوند.
- **نمایش (Presentation)** — بدون تاثیر؛ فناوری ذخیره‌سازی در بالای لایه Application کاملاً پنهان و نادیدنی باقی می‌ماند.

---

# نکات پیاده‌سازی (Implementation Notes)

- اندپوینت عینی ذخیره‌سازی (MinIO، AWS S3، یا ارائه‌دهنده سازگار دیگر با S3) باید به ازای هر استقرار از طریق پیکربندی (URL سرویس، نام باکت، اعتبارنامه‌ها) انتخاب شود، هرگز از طریق انشعاب کد (Code Branch) انجام نمی‌شود.
- آدرس‌های URL پیش‌امضاشده که برای برآورده ساختن نیازمندی همگام‌سازی ADR-0012 استفاده می‌شوند باید همواره با کوتاه‌ترین پنجره انقضای عملی صادر گردند.
- دسترسی‌ها باید در سطح باکت/پیشوند به ازای هر سازمان محدود و مجزا شود تا از دسترسی میان‌مستاجری به پیوست‌ها جلوگیری به عمل آید.
- متادیتای پیوست (نام فایل، اندازه، نوع محتوا، موجودیت تجمیعی مالک) همچنان به عنوان داده‌های موجودیت معمولی در EF Core ذخیره می‌شود (مطابق با ADR-0006 و ADR-0019)؛ این ADR صرفاً بر محتوای باینری حاکم است.

# قواعد انطباق (Compliance Rules)

۱. کلیه دسترسی‌ها به محتوای باینری پیوست‌ها باید از طریق انتزاع `IFileStorage` انجام شود؛ هیچ لایه‌ای در بالای Infrastructure نباید مستقیماً به SDK ذخیره‌سازی ارجاع دهد.

۲. پیاده‌سازی پیش‌فرض `IFileStorage` باید بر پایه S3 API (با استفاده از AWS SDK برای دات‌نت) ساخته شود و در سراسر MinIO و هر اندپوینت سازگار با S3 دیگر صرفاً از طریق پیکربندی قابل حمل باشد.

۳. سرویس MinIO باید اندپوینت خودمیزبان پیش‌فرض برای استقرارهای محلی و ایزوله (Air-gapped) باشد.

۴. پیاده‌سازی `LocalFileStorage` باید صرفاً برای کوچک‌ترین استقرارهای تک‌سروره که ذخیره‌سازی شیء در آن‌ها توجیه ندارد استفاده شود و هرگز نباید فرض شود که از مقیاس‌پذیری افقی پشتیبانی می‌کند.

۵. هرگونه پیاده‌سازی Azure Blob Storage که برای یک مشتری خاص اضافه می‌شود باید همان اینترفیس `IFileStorage` را پیاده‌سازی کند و بدون یک ADR جدید یا اصلاح‌شده نباید به پیش‌فرض کل پلتفرم تبدیل گردد.
