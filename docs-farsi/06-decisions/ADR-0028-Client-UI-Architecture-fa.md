# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise یک برنامه کاربردی در سطح سازمانی با اولویت دسکتاپ (Desktop-first) است که برای نگهداری بلندمدت و استقرار چندپلتفرمی در نظر گرفته شده است.

لایه نمایش (Presentation Layer) باید:

- کاملاً مستقل از منطق تجاری باقی بماند؛
- از رشد ماژولار برنامه پشتیبانی کند؛
- یک تجربه کاربری مدرن سازمانی را فراهم آورد؛
- از اصول معماری پاک (Clean Architecture) پیروی نماید.

بنابراین، رابط کاربری نیازمند یک شالوده معماری منسجم است.

---

# بیان مسئله (Problem)

بدون یک معماری استانداردسازی‌شده برای UI:

- منطق نمایش به درون نماها (Views) نشت می‌کند؛
- قواعد تجاری به درون مولفه‌های رابط کاربری نفوذ می‌کنند؛
- ماژول‌ها دچار جفت‌شدگی شدید (Tightly Coupled) می‌شوند؛
- آزمون‌پذیری دشوار می‌گردد؛
- قابلیت نگهداری در طول زمان تضعیف می‌شود.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

معماری کلاینت باید موارد زیر را فراهم آورد:

- اجرای چندپلتفرمی (Cross-platform)
- تفکیک پاک MVVM
- ترکیب ماژولار رابط کاربری (Modular UI Composition)
- قابلیت نگهداری بالا
- آزمون‌پذیری فوق‌العاده
- تجربه کاربری بومی دسکتاپ
- رابط کاربری روان (Fluent)
- پایداری بلندمدت معماری

---

# تصمیم (Decision)

برنامه کاربردی کلاینت باید معماری زیر را اتخاذ نماید:

| مسئولیت | فناوری |
|---------------|------------|
| فریم‌ورک دسکتاپ | Avalonia UI |
| کتابخانه مولفه‌های بصری | FluentAvalonia |
| فریم‌ورک MVVM | CommunityToolkit.Mvvm |

فریم‌ورک ReactiveUI اتخاذ نمی‌گردد.

---

# معماری کلاینت (Client Architecture)

```text
             User (کاربر)

              │

              ▼

        Avalonia Views (نماهای اوالونیا)

              │

 Data Binding / Commands (اتصال داده / دستورات)

              │

              ▼

         ViewModels (مدل‌های نما)
  (CommunityToolkit.Mvvm)

              │

              ▼

 Application Layer (لایه کاربرد)

              │

              ▼

   Domain Layer (لایه دامنه)
```

منطق تجاری هرگز نباید در درون Views اجرا شود.

---

# مسئولیت‌های لایه‌ها (Layer Responsibilities)

## نماها (Views)

نماها صرفاً مسئول موارد زیر هستند:

- نمایش بصری؛
- چیدمان کنترل‌ها (Layout)؛
- اتصال داده‌ها (Data Binding)؛
- اتصال دستورات (Command Binding)؛
- وضعیت بصری.

نماها نباید حاوی هیچ‌گونه منطق تجاری باشند.

---

## مدل‌های نما (ViewModels)

مدل‌های نما مسئول موارد زیر هستند:

- وضعیت نمایش؛
- هماهنگی تعاملات کاربر؛
- اجرای دستورات؛
- نمایش نتایج اعتبارسنجی؛
- تعامل با لایه Application.

مدل‌های نما نباید مستقیماً به مولفه‌های لایه Infrastructure دسترسی داشته باشند.

---

## لایه کاربرد (Application Layer)

لایه کاربرد:

- موارد استفاده تجاری (Use Cases) را اجرا می‌کند؛
- عملیات دامنه را هماهنگ می‌سازد؛
- اشیاء انتقال داده (DTOs) را بازمی‌گرداند؛
- کاملاً مستقل از UI باقی می‌ماند.

---

# استراتژی MVVM (MVVM Strategy)

بسته CommunityToolkit.Mvvm باید برای موارد زیر استفاده شود:

- ObservableObject
- ObservableProperty
- RelayCommand
- AsyncRelayCommand
- اعتبارسنجی (Validation)
- پیام‌رسان (Messenger)

تولیدکننده‌های سورس کد (Source Generators) باید در هر جایی که امکان دارد جایگزین کدهای دستی اعلان تغییرات شوند.

---

# استراتژی مولفه‌های رابط کاربری (UI Component Strategy)

مجموعه FluentAvalonia کتابخانه استاندارد مولفه‌ها می‌شود.

کنترل‌های ترجیحی شامل موارد زیر است:

- NavigationView
- ContentDialog
- InfoBar
- CommandBar
- کنترل‌های تنظیمات (Settings Controls)
- آیکون‌های روان (Fluent Icons)

کنترل‌های سفارشی صرفاً زمانی باید ایجاد شوند که کنترل‌های معادل Fluent وجود نداشته باشند.

---

# استراتژی ناوبری (Navigation Strategy)

ناوبری باید هدایت‌شده توسط ViewModel باشد.

نماها (Views) هرگز نباید مستقیماً به نماهای دیگر هدایت شوند.

سرویس‌های ناوبری باید مستقل از منطق تجاری باقی بمانند.

---

# تزریق وابستگی (Dependency Injection)

نماها و مدل‌های نما باید از طریق تزریق وابستگی ایجاد شوند.

ساخت دستی اشیاء ممنوع است مگر در مواردی که توسط زیرساخت فریم‌ورک الزامی باشد.

---

# استراتژی اعتبارسنجی (Validation Strategy)

اعتبارسنجی باید در لایه Application رخ دهد.

مدل‌های نما نتایج اعتبارسنجی را ارائه می‌دهند.

نماها صرفاً وضعیت اعتبارسنجی را به صورت بصری نمایش می‌دهند.

---

# استراتژی ریسه‌ها (Threading Strategy)

عملیات طولانی‌مدت باید به صورت ناهمگام (Asynchronous) اجرا شوند.

به‌روزرسانی‌های UI همواره باید در ریسه رابط کاربری (UI Thread) رخ دهند.

مسدود کردن ریسه UI ممنوع است.

---

# استراتژی تم‌ها (Theme Strategy)

تم‌های پشتیبانی‌شده:

- روشن (Light)
- تاریک (Dark)
- سیستم (System)

انتخاب تم باید متمرکز بوده و به صورت منسجم در سراسر برنامه اعمال گردد.

---

# ماژولار بودن (Modularity)

هر ماژول تجاری می‌تواند موارد زیر را فراهم آورد:

- Views
- ViewModels
- Resources
- مداخل ناوبری (Navigation Entries)

ماژول‌ها نباید مستقیماً به یکدیگر ارجاع دهند.

ارتباطات صرفاً از طریق اینترفیس‌های تصویب‌شده برنامه رخ می‌دهد.

---

# استراتژی آزمون (Testing Strategy)

مدل‌های نما باید کاملاً از طریق آزمون‌های واحد (Unit Tests) آزمون‌پذیر باشند.

نماها به حداقل آزمون نیاز دارند زیرا رفتار تجاری در درون مدل‌های نما قرار دارد.

اتوماسیون UI به طور جداگانه در استراتژی آزمون مورد بررسی قرار می‌گیرد.

---

# استراتژی کارایی (Performance Strategy)

کارایی باید از طریق موارد زیر بهینه‌سازی شود:

- کنترل‌های مجازی‌سازی‌شده (Virtualized Controls)
- دستورات ناهمگام
- حداقل تخصیص حافظه
- بارگذاری تنبل (Lazy Loading) در صورت لزوم

---

# امنیت (Security)

لایه نمایش:

- نباید اسرار را ذخیره کند؛
- نباید عملیات رمزنگاری انجام دهد؛
- نباید منطق صدور مجوز را پیاده‌سازی نماید.

امنیت همچنان مسئولیت لایه‌های پایین‌تر معماری باقی می‌ماند.

---

# مزایا (Benefits)

این معماری مزایای زیر را فراهم می‌آورد:

- تفکیک شفاف وظایف
- قابلیت نگهداری فوق‌العاده
- آزمون‌پذیری بالا
- ساختار ماژولار برنامه دسکتاپ
- تجربه کاربری بومی چندپلتفرمی

---

# پیامدها (Consequences)

مثبت:

- معماری پاک MVVM
- ماژولار بودن قدرتمند
- قابلیت نگهداری بلندمدت عالی
- تجربه کاربری منسجم

منفی:

- لایه اضافی ViewModel
- تفکیک دقیق نیازمند نظم و انضباط معماری است

این سبک‌سنگین‌ها برای نرم‌افزارهای سازمانی قابل قبول هستند.

---

# گزینه‌های بررسی‌شده (Alternatives Considered)

## معماری کدهای پشت صفحه (Code-Behind Architecture)

رد شد.

منطق تجاری به درون Views نشت می‌کرد.

---

## فریم‌ورک ReactiveUI

رد شد.

برنامه‌نویسی واکنشی پیچیدگی‌های معماری غیرضروری را برای نیازمندی‌های این پروژه تحمیل می‌نمود.

---

## فریم‌ورک‌های رابط کاربری منحصر به ویندوز

رد شد.

قابلیت چندپلتفرمی یک نیازمندی معماری است.

- Avalonia UI
