# زمینه و مسئله (Context)

سامانه MachineryManagerEnterprise به عنوان یک پلتفرم سازمانی بلندمدت طراحی می‌شود که باید قابل نگهداری، آزمون‌پذیر، ماژولار و مستقل از فناوری باقی بماند.

انتظار می‌رود این پروژه طی سالیان متمادی تکامل یافته و همزمان از ماژول‌های متعدد، توسعه مستقل تیم‌ها و تغییر فناوری‌های زیرساختی پشتیبانی کند.

بدون داشتن مرزهای معماری شفاف، منطق کسب‌وکار به تدریج با دغدغه‌های زیرساختی درگیر شده، هزینه‌های نگهداری افزایش یافته و قابلیت آزمون‌پذیری کاهش می‌یافت.

بنابراین پیش از آغاز پیاده‌سازی، وجود یک پایه و شالوده معماری ضروری بود.

---

# تصمیم (Decision)

راهکار باید **معماری پاک (Clean Architecture)** را به عنوان سبک معماری اصلی خود بپذیرد.

معماری باید دغدغه‌ها را به لایه‌های مستقل با جهت وابستگی صریح و مشخص تقسیم کند.

قوانین کسب‌وکار باید مستقل از فریم‌ورک‌ها، دیتابیس‌ها، فناوری‌های UI و سرویس‌های خارجی باقی بمانند.

---

# محرک‌های تصمیم (Decision Drivers)

- قابلیت نگهداری (Maintainability)
- آزمون‌پذیری (Testability)
- جداسازی دغدغه‌ها (Separation of Concerns)
- استقلال از فناوری (Technology Independence)
- مقیاس‌پذیری (Scalability)
- توسعه ماژولار (Modular Development)
- پایداری بلندمدت (Long-Term Sustainability)
- وابستگی کم (Low Coupling)
- همبستگی بالا (High Cohesion)

---

# گزینه‌های جایگزین بررسی‌شده (Alternatives Considered)

## معماری سنتی لایه‌ای (Traditional Layered Architecture)

پیاده‌سازی ساده‌ای دارد.

رد شد زیرا منطق کسب‌وکار معمولاً به زیرساخت وابسته و وابسته می‌شود.

---

## معماری برش عمودی (Vertical Slice Architecture)

برای توسعه ویژگی‌محور بسیار عالی است.

رد شد زیرا راهکار نیازمند جداسازی قوی‌تر بین لایه‌های Domain، Application، Infrastructure و Presentation است.

---

## معماری پیازی (Onion Architecture)

بسیار مشابه معماری پاک است.

رد شد زیرا معماری پاک راهنمایی‌های جامع‌تری برای اپلیکیشن‌های سازمانی ارائه داده و با اهداف پروژه همراستاتر است.

---

# پیامدها (Consequences)

## مثبت

- لایه دامنه (Domain) مستقل
- آزمون واحد (Unit Testing) آسان‌تر
- قابلیت نگهداری بهتر
- جهت شفاف وابستگی‌ها
- قابلیت جایگزینی زیرساخت
- بهبود مقیاس‌پذیری
- ماژولارکردن بهتر

## منفی

- تعداد پروژه‌ها و انتزاع‌های بیشتر
- پیچیدگی اولیه بالاتر
- منحنی یادگیری طولانی‌تر برای توسعه‌دهندگان جدید

# تاثیر بر معماری (Architecture Impact)

لایه‌های معماری زیر ایجاد می‌شوند:

- لایه ارائه (Presentation)
- لایه کاربرد (Application)
- لایه دامنه (Domain)
- لایه زیرساخت (Infrastructure)
- لایه مشترک (Shared)

وابستگی‌ها همواره باید به سمت داخل اشاره کنند.

لایه‌های بیرونی می‌توانند به لایه‌های داخلی وابسته باشند.

لایه‌های داخلی هرگز نباید به لایه‌های بیرونی وابسته شوند.

---

# نکات پیاده‌سازی (Implementation Notes)

ساختار راهکار باید منعکس‌کننده مرزهای معماری باشد.

تزریق وابستگی (Dependency Injection) باید درون لایه Infrastructure پیکربندی شود.

قوانین کسب‌وکار باید مستقل از فریم‌ورک باقی بمانند.

مخازن داده (Repositories) تنها از طریق اینترفیس‌ها قابل دسترسی هستند.

---

# قوانین انطباق (Compliance Rules)

قوانین زیر اجباری هستند:

۱. لایه Domain هرگز نباید به Infrastructure ارجاع دهد.

۲. لایه Domain هرگز نباید به Presentation ارجاع دهد.

۳. لایه Domain هرگز نباید به فریم‌ورک‌های خارجی ارجاع دهد.

۴. لایه Infrastructure باید انتزاع‌های Application را پیاده‌سازی کند.

۵. لایه Application تنها باید اینترفیس‌ها را تعریف کند.

۶. قوانین کسب‌وکار تنها باید درون Domain وجود داشته باشند.

۷. اشیاء DTO هرگز نباید درون Domain وجود داشته باشند.

۸. فناوری Entity Framework Core تنها باید درون Infrastructure وجود داشته باشد.

۹. پیاده‌سازی‌های لاگینگ تنها باید درون Infrastructure وجود داشته باشند.

۱۰. فریم‌ورک‌های UI هرگز نباید توسط Application یا Domain ارجاع داده شوند.
