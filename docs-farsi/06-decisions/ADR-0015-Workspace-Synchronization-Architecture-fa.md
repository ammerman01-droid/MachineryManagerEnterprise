# سند ثبت تصمیم معماری (ADR)

# ADR-0015 — معماری همگام‌سازی فضای کاری (Workspace Synchronization Architecture)

---

# هدف (Purpose)

این سند ثبت تصمیم معماری (ADR) استراتژی فنی، طراحی معماری و پروتکل‌های همگام‌سازی را برای همگام‌سازی فضاهای کاری توزیع‌شده در پلتفرم MachineryManagerEnterprise تعریف می‌نماید.

سامانه MachineryManagerEnterprise در محیط‌های با قطع ارتباط، دارای محدودیت پهنای باند و مستقر در محیط‌های میدانی و کارگاهی (مانند سایت‌های اجرایی، کارگاه‌های دورافتاده و خودروهای خدمات سیار) فعالیت می‌کند. معماری همگام‌سازی فضای کاری، کارکرد یکپارچه با اولویت آفلاین (Offline-First)، تکثیر دوطرفه داده‌ها، ردگیری تغییرات تفاضلی (Delta Tracking) و حل قطعی و معین تناقضات میان نمونه‌های ابری مرکزی و نودهای محلی توزیع‌شده فضای کاری را ممکن می‌سازد.

---

# محدوده ارزیابی (Evaluation Scope)

محدوده این تصمیم موارد زیر را در بر می‌گیرد:

- پروتکل‌های همگام‌سازی و ایجاد بسته‌های تغییرات تفاضلی (Delta Packages).
- ردگیری تغییرات در ذخیره‌سازی محلی برای کلاینت‌های با اولویت آفلاین (SQLite / LiteDB).
- کانال‌های ترنسپورت و انتقال دوطرفه (HTTPS / MassTransit / SignalR).
- استراتژی‌های حل تناقض (Last-Write-Wins در برابر قواعد تجاری خاص دامنه).
- تکامل اسکیما و سازگاری نسخه‌ها در نودهای فضای کاری قطع‌شده از شبکه.
- امنیت، رمزنگاری و ایزوله‌سازی چندمستاجری (Tenant Isolation) برای انتقال بسته‌ها.

---

# روابط و وابستگی‌ها (Relationship)

این سند بر اسناد زیر استوار بوده و با آن‌ها همراستاست:

- **ADR-0012 — معماری فضای کاری توزیع‌شده (Distributed Workspace Architecture)**: حاکم بر توپولوژی کلان نودهای توزیع‌شده.
- **ADR-0014 — معماری داده‌های فضای کاری (Workspace Data Architecture)**: مشخص‌کننده موتورهای ذخیره‌سازی محلی (SQLite و LiteDB) مورد استفاده در نودهای آفلاین.
- **TE-0011 — ارزیابی فناوری پایگاه داده درون‌برنامه‌ای فضای کاری (Embedded Workspace Database Technology Evaluation)**: ارزیابی فناوری‌های پایگاه داده محلی پشتیبانی‌کننده از ردگیری همگام‌سازی.
- **ADR-0016 — معماری پیام‌رسانی سازمانی (Enterprise Messaging Architecture)**: حاکم بر صف‌های ناهمگام پیام برای انتقال پس‌زمینه بسته‌های همگام‌سازی.
- **ADR-0026 — استراتژی امنیت سازمانی (Enterprise Security Strategy)**: حاکم بر رمزنگاری در حالت سکون (At-Rest) و در حال انتقال (In-Transit) برای محموله‌های همگام‌سازی.

# محدوده شمول (Scope)

این تصمیم بر تمامی برنامه‌های کلاینت (.NET MAUI Desktop & Mobile و Blazor Hybrid) و سرویس‌های API ابری مرکزی که در تبادل داده‌های فضای کاری مشارکت دارند، اعمال می‌گردد.

---

# نیازمندی‌های کارکردی (Functional Requirements)

معماری همگام‌سازی فضای کاری باید از موارد زیر پشتیبانی نماید:

- کارکرد مطمئن آفلاین با قابلیت کامل خواندن/نوشتن محلی.
- تولید تغییرات تفاضلی (Delta Generation) با ردگیری صرفاً رکوردهای اصلاح‌شده، ایجادشده یا حذف‌شده از زمان آخرین نقطه بازرسی (Checkpoint) همگام‌سازی موفق.
- همگام‌سازی دوطرفه میان فضاهای کاری لبه (Edge Workspaces) و فضاهای کاری ابری مرکزی (Central Cloud Workspaces).
- شناسایی و حل خودکار یا مبتنی بر خط‌مشی تناقضات.
- تاب‌آوری در برابر قطع شبکه با محموله‌های انتقال دارای قابلیت ازسرگیری (Resume-capable).
- ثبت لاگ‌های ممیزی برای کلیه بسته‌های ورودی و خروجی همگام‌سازی.

---

# نیازمندی‌های غیرکارکردی (Non-Functional Requirements)

- **کارایی و عملکرد (Performance)**: تولید و پردازش تغییرات تفاضلی باید در کمتر از ۲ ثانیه برای عملیات میدانی روزمره استاندارد (محموله‌های کمتر از ۵۰ مگابایت) انجام شود.
- **بهره‌وری پهنای باند (Bandwidth Efficiency)**: محموله‌ها باید فشرده‌سازی شوند (GZip/Brotli) و کاملاً باینری یا JSON فشرده باشند.
- **قابلیت اطمینان (Reliability)**: عدم بروز هرگونه خرابی داده در صورت قطع ناگهانی برق یا قطع شبکه در حین پردازش همگام‌سازی.
- **امنیت (Security)**: رمزنگاری محموله‌ها با الگوریتم AES-256 همراه با تایید امضا پیش از درون‌کشی داده‌ها (Ingestion).

# فناوری‌های نامزد (Candidate Technologies)

| گزینه | رویکرد / فناوری | خلاصه ارزیابی |
|--------|----------------------|-------------------|
| **گزینه الف (Option A)** | موتور همگام‌سازی اختصاصی + ردگیری تغییرات SQLite + بسته‌های فشرده دلتا | کنترل بالا، همراستایی دقیق با رویدادهای دامنه DDD، حجم بهینه‌سازی‌شده محموله، عدم وابستگی انحصاری به فروشنده (Zero Vendor Lock-in). |
| **گزینه ب (Option B)** | فریم‌ورک Microsoft Sync Framework / Dotmim.Sync | همگام‌سازی آماده ORM، اما دارای وابستگی‌های سنگین، هوک‌های محدود برای حل سفارشی تناقضات، محدودیت‌های صلب اسکیما. |
| **گزینه ج (Option C)** | پایگاه داده Couchbase Lite / Realm Mobile Database | وابستگی شدید به فروشنده، مستلزم کنار گذاشتن پشته EF Core و SQLite/LiteDB مصوب در ADR-0014. |

# معیارهای ارزیابی (Evaluation Criteria)

- انطباق معماری با Clean Architecture و DDD
- قابلیت سفارشی‌سازی قواعد مدیریت تناقضات
- بهینه‌سازی پهنای باند و فشرده‌سازی بسته‌ها
- سربار نگهداری و ادغام بومی با اکوسیستم دات‌نت ۱۰ (.NET 10)

---

# اصل معماری (Architecture Principle)

همگام‌سازی فضای کاری باید ثوابت و قواعد نامتغیر دامنه (Domain Invariants) را حفظ نماید. هندلرهای همگام‌سازی باید به عنوان موارد کاربری لایه اپلیکیشن عمل کنند و وضعیت‌های ورودی را از طریق قواعد دامنه اعتبارسنجی نمایند، نه اینکه صرفاً تخلیه انبوه داده‌ها را در سطح خام دیتابیس انجام دهند.

---

# مقایسه کلی فناوری‌ها (Overall Technology Comparison)

گزینه الف (موتور همگام‌سازی اختصاصی با استفاده از ردگیری تغییرات SQLite و پایپ‌لاین‌های درون‌کشی مبتنی بر MediatR) حداکثر انعطاف‌پذیری را فراهم ساخته، عدم وابستگی به ارائه‌دهندگان را تضمین می‌کند و به طور یکپارچه با معماری مستقر ما بر پایه MediatR و EF Core تلفیق می‌گردد.

---

# توصیه نهایی (Final Recommendation)

تصویب **گزینه الف (Option A)**: ساخت یک **موتور همگام‌سازی فضای کاری (Workspace Synchronization Engine)** سفارشی با استفاده از متادیتای محلی ردگیری تغییرات (نسخه/برچسب زمانی/ساعت برداری)، بسته‌های تفاضلی فشرده JSON، و پایپ‌لاین‌های دستور MediatR برای درون‌کشی داده‌ها.

---

# تصمیم (Decision)

سامانه MachineryManagerEnterprise باید بر روی یک **موتور همگام‌سازی فضای کاری** سفارشی و با اولویت آفلاین استانداردسازی شود.

محورهای کلیدی تصمیم:

۱. **سازوکار ردگیری تغییرات (Change Tracking Mechanism)**: هر موجودیت با قابلیت همگام‌سازی باید اینترفیس `ISyncableEntity` را پیاده‌سازی کند که ویژگی‌های `Guid Id`، `DateTimeOffset LastModifiedAt`، `long Version` و `bool IsDeleted` را افشا می‌نماید.
۲. **ساختار بسته تفاضلی (Delta Package Structure)**: محموله‌های همگام‌سازی باید شامل اشیاء نسخه‌بندی‌شده `SyncPackage` باشند که حاوی متادیتا، زمینه مستاجر (Tenant Context)، برچسب‌های زمانی ساعت برداری (Vector Clock)، و مجموعه‌های تغییرات تفاضلی موجودیت‌ها هستند.
۳. **کانال انتقال (Transport Channel)**: همگام‌سازی اصلی باید از طریق اندپوینت‌های Web API REST/gRPC با استفاده از HTTPS اجرا شود. همگام‌سازی پس‌زمینه بسته‌های بزرگ می‌تواند از صف‌های MassTransit / RabbitMQ استفاده کند.
۴. **خط‌مشی حل تناقض (Conflict Resolution Policy)**:
   - قاعده پیش‌فرض: **برنده بودن سرور (Server Wins)** برای داده‌های مرجع پایه (مانند کاتالوگ قطعات، انواع دارایی‌ها).
   - عملیات میدانی: **قواعد خاص دامنه (Domain-Specific Rules)** اجراشده از طریق پایپ‌لاین‌های MediatR (مانند: مقادیر کارکرد کنتور به جای رونویسی، تجمیع می‌شوند؛ لاگ‌های تعمیرات پیوست و الحاق می‌گردند).
   - حالت جایگزین (Fallback): تناقضات غیرقابل حل در `SyncConflictLog` ثبت می‌شوند تا توسط سرپرست به صورت دستی بازبینی گردند.
۵. **امنیت (Security)**: بسته‌های همگام‌سازی باید پیش از ارسال با HMAC-SHA256 امضا شده و با استفاده از AES-256 رمزنگاری گردند.

# خلاصه تصمیمات (Decision Summary)

- ✔ فعال‌سازی قابلیت با اولویت آفلاین (Offline-First)
- ✔ تصویب موتور همگام‌سازی سفارشی تفاضلی (Custom Delta Sync Engine)
- ✔ حفظ ثوابت و قواعد نامتغیر دامنه (Domain Invariants)
- ✔ محموله‌های رمزنگاری‌شده با AES-256
- ✔ سازگاری بومی با .NET 10
