# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise یک پلتفرم سازمانی مدیریت دارایی‌ها است که مسئولیت ذخیره‌سازی اطلاعات عملیاتی، مالی و حیاتی کسب‌وکار را بر عهده دارد.

انتظار می‌رود این سیستم در محیط‌های سازمانی به کار گرفته شود که در آن‌ها:

- محرمانگی داده‌ها اجباری است؛
- امنیت ارتباطات الزامی است؛
- بهترین شیوه‌های رمزنگاری باید به اجرا درآیند؛
- استقرار ایمن باید در سراسر چرخه حیات نرم‌افزار حفظ شود.

بنابراین، یک معماری یکپارچه امنیتی مورد نیاز است.

---

# بیان مسئله (Problem)

بدون یک استراتژی یکپارچه امنیتی:

- رویکردهای رمزنگاری ناهمگون و ناسازگار خواهند شد؛
- مدیریت کلیدها مستعد خطا می‌گردد؛
- امنیت انتقال داده در سراسر سرویس‌ها متغیر خواهد بود؛
- حفظ امنیت عملیاتی دشوار می‌گردد؛
- انطباق با قوانین و مقررات در بلندمدت به طور فزاینده‌ای سخت خواهد شد.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

معماری باید موارد زیر را فراهم آورد:

- محرمانگی (Confidentiality)
- یکپارچگی (Integrity)
- دسترس‌پذیری (Availability)
- دفاع در عمق (Defense in Depth)
- امن به صورت پیش‌فرض (Secure by Default)
- حداقل دسترسی (Least Privilege)
- قابلیت نگهداری بلندمدت (Long-Term Maintainability)
- انطباق سازمانی (Enterprise Compliance)

---

# تصمیم (Decision)

سامانه MachineryManagerEnterprise پلتفرم امنیت سازمانی زیر را اتخاذ می‌نماید:

| مسئولیت | فناوری |
|---------------|------------|
| حفاظت از داده‌های برنامه | ASP.NET Core Data Protection |
| رمزنگاری متقارن | AES-256 |
| هویت لایه انتقال | گواهی‌های X.509 |
| چرخه حیات کلید | چرخش خودکار کلید (Automatic Key Rotation) |
| استاندارد امنیتی | توصیه‌های OWASP |

---

# معماری امنیت سازمانی (Enterprise Security Architecture)

```text
                OWASP

                   │

                   ▼

       Enterprise Security Policy
      (خط‌مشی امنیت سازمانی)

                   │

        ┌──────────┼───────────┐

        ▼          ▼           ▼

 Data Protection  AES-256   X.509
(حفاظت از داده)

                   │

                   ▼

             Key Rotation
             (چرخش کلید)
```

هر مولفه امنیتی دارای یک مسئولیت معماری به وضوح تعریف‌شده است.

---

# استراتژی حفاظت از داده‌ها (Data Protection Strategy)

داده‌های حساس برنامه باید با استفاده از ابزار زیر محافظت شوند:

- ASP.NET Core Data Protection

این فریم‌ورک مسئول موارد زیر خواهد بود:

- حفاظت از پی‌لود (Payload Protection)؛
- رمزنگاری احرازشده (Authenticated Encryption)؛
- مدیریت خودکار کلیدها؛
- ایزوله‌سازی اهداف (Purpose Isolation).

پیاده‌سازی‌های سفارشی رمزنگاری ممنوع است.

---

# استراتژی رمزنگاری (Encryption Strategy)

کلیه داده‌های محرمانه برنامه که نیازمند رمزنگاری متقارن هستند باید از الگوریتم زیر استفاده کنند:

**AES-256**

هیچ الگوریتم متقارن ضعیف‌تری نباید معرفی گردد.

پیاده‌سازی‌های رمزنگاری باید منحصراً به کتابخانه‌های رمزنگاری .NET تکیه داشته باشند.

---

# استراتژی امنیت لایه انتقال (Transport Security Strategy)

کلیه ارتباطات رمزنگاری‌شده باید بر پایه موارد زیر باشند:

- TLS
- گواهی‌های دیجیتال X.509

گواهی‌ها باید برای موارد زیر استفاده شوند:

- HTTPS
- gRPC
- ارتباط سرویس با سرویس (Service-to-Service Communication)
- احراز هویت متقابل / Mutual Authentication (در صورت نیاز)

---

# استراتژی مدیریت کلید (Key Management Strategy)

کلیدهای رمزنگاری باید از طریق مدیریت خودکار چرخه حیات مدیریت شوند.

چرخه حیات کلید شامل موارد زیر است:

```text
Generate (تولید)

   │

Active (فعال)

   │

Rotate (چرخش)

   │

Retire (بازنشستگی)

   │

Destroy (تخریب و امحا)
```

تنها کلید فعال داده‌های جدید را رمزنگاری می‌کند.

کلیدهای پیشین تا زمان بازنشستگی برای رمزگشایی در دسترس باقی می‌مانند.

---

# مدیریت اسرار (Secret Management)

اطلاعات زیر هرگز نباید به صورت متن ساده (Plaintext) ذخیره شوند:

- رشته‌های اتصال (Connection Strings)
- کلیدهای رابط‌های برنامه‌نویسی (API Keys)
- کلیدهای رمزنگاری (Encryption Keys)
- گواهی‌ها (Certificates)
- اسرار احراز هویت (Authentication Secrets)

اسرار باید از طریق مکانیسم‌های پیکربندی امن و متناسب با محیط استقرار فراهم گردند.

---

# توسعه امن (Secure Development)

فرایند توسعه باید از توصیه‌های OWASP پیروی کند.

این موارد شامل:

- اعتبارسنجی ورودی‌ها (Input Validation)
- کدگذاری خروجی‌ها (Output Encoding)
- احراز هویت ایمن (Secure Authentication)
- صدور مجوز ایمن (Secure Authorization)
- پیکربندی امن (Secure Configuration)
- مدیریت وابستگی‌ها (Dependency Management)
- ثبت وقایع ایمن (Secure Logging)

---

# قواعد کدنویسی امن (Secure Coding Rules)

توسعه‌دهندگان باید:

- تمامی ورودی‌های خارجی را اعتبارسنجی کنند؛
- از پیاده‌سازی رمزنگاری‌های سفارشی اجتناب نمایند؛
- از هاردکد کردن اسرار و کلیدها خودداری کنند؛
- از پرس‌وجوهای پارامتری‌شده (Parameterized Queries) استفاده نمایند؛
- از اصول حداقل دسترسی (Least Privilege) پیروی کنند.

---

# احراز هویت (Authentication)

معماری احراز هویت باید:

- مستقل از منطق تجاری باقی بماند؛
- هویت کاربر را قبل از صدور مجوز اعتبارسنجی کند؛
- از ذخیره اطلاعات اعتباری در کد برنامه اجتناب نماید.

مکانیسم‌های تفصیلی احراز هویت به صورت جداگانه مستند شده‌اند.

---

# صدور مجوز (Authorization)

صدور مجوز باید:

- از اصل حداقل دسترسی پیروی کند؛
- متمرکز باشد؛
- مستقل از فناوری‌های لایه نمایش باقی بماند.

---

# لاگ‌گیری و ثبت وقایع (Logging)

رویدادهای امنیتی باید ثبت شوند.

نمونه‌ها شامل:

- شکست‌های احراز هویت
- شکست‌های صدور مجوز
- شکست‌های اعتبارسنجی گواهی
- خطاهای رمزنگاری
- استثناهای امنیتی غیرمنتظره

اطلاعات حساس هرگز نباید در لاگ‌ها نوشته شوند.

---

# امنیت زیرساخت (Infrastructure Security)

مولفه‌های زیرساخت باید از موارد زیر پشتیبانی کنند:

- ارتباطات رمزنگاری‌شده؛
- پیکربندی امن؛
- دسترسی احرازشده؛
- ایزوله‌سازی محیط.

---

# انطباق با استانداردها (Compliance)

معماری با استانداردهای زیر همراستا است:

- OWASP ASVS
- OWASP Top 10
- دستورالعمل‌های امنیتی مایکروسافت
- توصیه‌های رمزنگاری NIST
