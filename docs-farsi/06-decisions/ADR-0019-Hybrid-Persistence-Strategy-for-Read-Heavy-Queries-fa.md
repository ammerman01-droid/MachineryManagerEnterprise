# هدف

این ADR استراتژی ماندگاری ترکیبی داده‌ها را برای پرس‌وجوهای سنگین خواندنی (Read-Heavy Queries) در پلتفرم MachineryManagerEnterprise تعریف می‌کند.

---

# ۱. زمینه و مسئله (Context)

در ADR-0006 استفاده از Entity Framework Core به عنوان ORM اصلی پلتفرم تایید شد.

سند TE-0004 جایگزینی کامل EF Core با Dapper را به دلیل هزینه‌های نگاشت دستی و نبود فریم‌ورک مایگریشن رد کرد.

با این حال، برای پرس‌وجوهای پیچیده، چندجدوله و صرفاً خواندنی گزارش‌گیری (مانند گزارش‌های بهره‌برداری کل ناوگان)، بار محاسباتی ردیابی تغییرات (Change Tracking) در EF Core می‌تواند غیرضروری و سنگین باشد.

---

# ۲. تصمیم (Decision)

لایه‌های Application و Infrastructure از یک **استراتژی ماندگاری ترکیبی (Hybrid Persistence Strategy)** تبعیت می‌کنند:

- **Entity Framework Core 10 به عنوان فناوری اجباری برای تمامی عملیات نوشتن، تراکنشی و ردیابی‌شده (Write-side)** بدون استثنا باقی می‌ماند.
- **Entity Framework Core 10 ترکیب‌شده با `ProjectToType<T>()` از Mapster (ADR-0008) فناوری پیش‌فرض برای تمامی پرس‌وجوهای خواندنی است.**
- **Dapper تنها می‌تواند برای پرس‌وجوهای خاص، توجیه‌شده و صرفاً خواندنی گزارش‌گیری** که عملکرد EF Core در آن‌ها یک چالش اثبات‌شده است، استفاده شود.

---

# ۳. قوانین انطباق (Compliance Rules)

1. **پیش‌فرض بودن EF Core**: تمامی پرس‌وجوها با EF Core شروع می‌شوند. Dapper تنها پس از اثبات مشکل عملکردی بررسی می‌شود.
2. **انتخابی بودن Dapper به ازای هر پرس‌وجو**: استفاده از Dapper به صورت مورد به مورد است، نه برای کل یک ماژول.
3. **صرفاً خواندنی بودن مخازن Dapper**: هیچ دستور `INSERT`، `UPDATE` یا `DELETE` مجاز به اجرا از طریق Dapper نیست.
4. **مالکیت انحصاری اسکیما توسط EF Core Migrations**: تغییرات اسکیما تنها از طریق مایگریشن‌های EF Core انجام می‌شود.
5. **مستندساز بودن توجیه عملکرد**: هر مخزن Dapper باید دلیل استفاده از آن را در کامنت بالای فایل مستند کند.

---

# ۴. پیامدها (Consequences)

پیامدهای مثبت:
- بهبود عملکرد پرس‌وجوهای سنگین گزارش‌گیری؛
- حفظ یکپارچگی مدل نوشتن با EF Core؛
- شفاف‌تر شدن تفکیک CQRS.

موازنه و توافق‌ها (Trade-offs):
- اضافه شدن یک الگوی ثانویه دسترسی به داده‌ها که نیازمند انضباط در کدریویو است.
