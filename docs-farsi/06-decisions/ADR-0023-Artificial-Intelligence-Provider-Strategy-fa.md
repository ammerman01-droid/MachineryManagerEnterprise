# زمینه و بستر (Context)

سامانه MachineryManagerEnterprise قابلیت‌های سازمانی هوش مصنوعی را معرفی می‌نماید، از جمله:

- جستجوی معنایی (Semantic Search)
- دستیار هوش مصنوعی سازمانی (Enterprise AI Assistant)
- تولید مبتنی بر بازیابی اطلاعات (RAG)
- توصیه‌های هوشمند نگهداری و تعمیرات (Intelligent Maintenance Recommendations)
- کوپایلوت هوش مصنوعی (AI Copilot)
- بازیابی دانش (Knowledge Retrieval)

سند ارزیابی فنی TE-0029 نتیجه‌گیری کرد که هیچ ارائه‌دهنده منفرد هوش مصنوعی نباید به یک وابستگی دائمی در معماری تبدیل شود.

در عوض، پلتفرم باید از چندین ارائه‌دهنده پشتیبانی کند در حالی که یک ارائه‌دهنده را به عنوان پیش‌فرض عملیاتی انتخاب می‌نماید.

---

# بیان مسئله (Problem)

پلتفرم باید از جفت‌شدگی (Coupling) منطق تجاری به یک ارائه‌دهنده خاص هوش مصنوعی اجتناب کند.

بدون یک لایه انتزاع:

- هر تغییر در ارائه‌دهنده، کد برنامه را تحت تاثیر قرار می‌دهد؛
- قفل‌شدگی به فروشنده ابری (Cloud Vendor Lock-in) افزایش می‌یابد؛
- آزمون‌پذیری سیستم دشوار می‌گردد؛
- استنتاج محلی (Local Inference) بدون بازنویسی و ریفکتورینگ کد قابل معرفی نخواهد بود.

---

# محرک‌های تصمیم‌گیری (Decision Drivers)

معماری باید نیازمندی‌های زیر را برآورده سازد:

- معماری پاک (Clean Architecture)
- وارونگی وابستگی (Dependency Inversion)
- استقلال از ارائه‌دهنده (Provider Independence)
- امنیت سازمانی (Enterprise Security)
- استقرار ترکیبی (Hybrid Deployment)
- قابلیت نگهداری بلندمدت (Long-Term Maintainability)
- توسعه‌پذیری هوش مصنوعی (AI Extensibility)

---

# تصمیم (Decision)

پلتفرم یک **استراتژی ارائه‌دهنده هوش مصنوعی ترکیبی (Hybrid AI Provider Strategy)** را اتخاذ می‌نماید.

برنامه صرفاً با یک انتزاع داخلی ارتباط برقرار می‌کند.

ارائه‌دهندگان عینی هوش مصنوعی کاملاً در درون لایه Infrastructure پیاده‌سازی می‌شوند.

---

# سلسsales-مراتب ارائه‌دهندگان مصوب (Approved Provider Hierarchy)

```text
Application (لایه کاربرد)

      │

      ▼

 IAIProvider (انتزاع ارائه‌دهنده)

      │

 ┌────┼───────────────┐

 ▼    ▼               ▼

Azure OpenAI

OpenAI

Ollama
```

لایه Application هرگز مستقیماً به SDKهای ارائه‌دهندگان ارجاع نمی‌دهد.

---

# ارائه‌دهنده اصلی (Primary Provider)

سرویس **Azure OpenAI** به عنوان ارائه‌دهنده پیش‌فرض محیط عملیاتی تصویب شده است.

دلایل:

- راهبری سازمانی (Enterprise Governance)
- یکپارچگی با Azure Active Directory
- سازگاری با اکوسیستم مایکروسافت
- انطباق با قوانین سازمانی (Enterprise Compliance)
- سادگی عملیاتی
- کیفیت بالای استنتاج

---

# ارائه‌دهنده ثانویه (Secondary Provider)

سرویس **OpenAI** به عنوان یک ارائه‌دهنده ثانویه اختیاری تصویب شده است.

موارد استفاده متداول:

- ارزیابی مدل‌های جدید؛
- انتقال کنترل‌شده در زمان خرابی (Failover)؛
- آزمایش و تجربه (Experimentation)؛
- سناریوهای مهاجرت در آینده.

---

# ارائه‌دهنده محلی (Local Provider)

ابزار **Ollama** به عنوان ارائه‌دهنده استنتاج محلی تصویب شده است.

موارد استفاده متداول:

- محیط‌های آفلاین؛
- استقرارهای کاملاً ایزوله (Air-gapped)؛
- نصب‌های محلی نزد مشتری (On-premise)؛
- بار کاری حساس از نظر حریم خصوصی؛
- محیط‌های توسعه (Development Environments).

---

# انتزاع ارائه‌دهنده (Provider Abstraction)

انتزاع زیر باید معرفی و مستقر گردد:

```text
IAIProvider

    ├── GenerateEmbeddingAsync()

    ├── ChatCompletionAsync()

    ├── StreamingCompletionAsync()

    ├── ToolCallingAsync()
```

منطق تجاری صرفاً باید به این اینترفیس وابسته باشد.

---

# جهت وابستگی (Dependency Direction)

```text
Application (لایه کاربرد)

      │

 IAIProvider

      │

Infrastructure (لایه زیرساخت)

      │

 Azure OpenAI

 OpenAI

 Ollama
```

هیچ پیاده‌سازی خاص وابسته به ارائه‌دهنده‌ای نباید به لایه‌های بالاتر معماری نشت کند.

---

# استراتژی پیکربندی (Configuration Strategy)

انتخاب ارائه‌دهنده باید مبتنی بر پیکربندی باشد.

مثال:

```json
{
  "AI": {
    "Provider": "AzureOpenAI"
  }
}
```

مقادیر آینده ممکن است شامل موارد زیر باشد:

- AzureOpenAI
- OpenAI
- Ollama

در هنگام تغییر ارائه‌دهنده‌ها هیچ تغییری در سورس کد نیاز نخواهد بود.

---

# استراتژی انتقال هنگام خرابی (Failover Strategy)

معماری از انتقال اختیاری در زمان خرابی ارائه‌دهنده پشتیبانی می‌کند.

مثال:

```text
Primary (اصلی)

Azure OpenAI

      │

Failure (خرابی)

      ▼

 OpenAI

      │

Failure (خرابی)

      ▼

 Ollama
```

انتقال خودکار هنگام خرابی اختیاری است و تنها زمانی پیاده‌سازی می‌شود که نیازمندی‌های تجاری، پیچیدگی عملیاتی اضافی آن را توجیه نمایند.

---

# استراتژی امبدینگ (Embedding Strategy)

تولید امبدینگ باید از ارائه‌دهنده پیکربندی‌شده استفاده کند.

بردارهای تولیدشده در پایگاه داده برداری تصویب‌شده (Qdrant) ذخیره می‌شوند.

امبدینگ‌ها به عنوان مصنوعات مستقل از ارائه‌دهنده باقی می‌مانند.

---

# استراتژی پرامپت (Prompt Strategy)

قالب‌های پرامپت باید نسبت به ارائه‌دهنده بی‌طرف و مستقل باشند.

آن‌ها نباید حاوی موارد زیر باشند:

- سینتکس خاص ارائه‌دهنده؛
- وابستگی‌های SDK؛
- قالب‌بندی اختصاصی فروشنده.

---

# امنیت (Security)

اطلاعات هویتی و اعتباری ارائه‌دهندگان هرگز نباید در کد برنامه ذخیره شود.

اسرار و کلیدها باید از طریق راهکار تصویب‌شده مدیریت اسرار سازمانی مدیریت شوند.

احراز هویت محیط عملیاتی در هر جایی که پشتیبانی شود باید از هویت مدیریت‌شده (Managed Identity) استفاده نماید.

---

# لاگ‌گیری و ثبت وقایع (Logging)

پیاده‌سازی‌های ارائه‌دهندگان باید تله‌متری استانداردشده زیر را افشا و ثبت کنند:

- زمان تاخیر (Latency)؛
- میزان استفاده از توکن (Token Usage)؛
- نام مدل (Model Name)؛
- شناسه ارائه‌دهنده (Provider Identifier)؛
- دلیل خطا و شکست (Failure Reason).

لاگ‌گیری برنامه باید مستقل از ارائه‌دهنده باقی بماند.

---

# مزایا (Benefits)

این معماری مزایای زیر را فراهم می‌آورد:

- استقلال از ارائه‌دهنده؛
- تفکیک پاک وظایف؛
- آزمون‌پذیری ساده‌تر؛
- قابلیت استقرار ترکیبی؛
- توسعه‌پذیری در آینده؛
- کاهش قفل‌شدگی به فروشنده (Vendor Lock-in).

---

# پیامدها (Consequences)

مثبت:

- انطباق با معماری پاک (Clean Architecture)
- ارائه‌دهندگان قابل جایگزینی
- انعطاف‌پذیری بلندمدت
- تکامل ساده‌تر قابلیت‌های هوش مصنوعی

منفی:

- لایه انتزاع اضافی
- افزایش اندک در پیچیدگی پیاده‌سازی
- آزمون‌های یکپارچگی بیشتر

# گزینه‌های بررسی‌شده (Alternatives Considered)

## یکپارچه‌سازی مستقیم با Azure OpenAI

رد شد.

دلیل:

اصل وارونگی وابستگی را نقض کرده و جفت‌شدگی بلندمدت با ارائه‌دهنده ایجاد می‌کند.

---

## صرفاً استفاده از OpenAI

رد شد.

دلیل:

با استراتژی تصویب‌شده زیرساخت سازمانی مایکروسافت همراستا نیست.

---

## صرفاً استفاده از Ollama

رد شد.

دلیل:

پیچیدگی عملیاتی آن برای استقرار سازمانی اولیه غیرضروری است.

---

## ارائه‌دهنده منفرد بدون انتزاع

رد شد.

دلیل:

جایگزینی ارائه‌دهنده در آینده نیازمند ریفکتورینگ و بازنویسی کد برنامه خواهد بود.

# نتیجه تصمیم (Decision Outcome)

**پذیرفته‌شده (Accepted)**

سامانه MachineryManagerEnterprise یک استراتژی ترکیبی ارائه‌دهنده هوش مصنوعی را اتخاذ می‌نماید که در آن:

- سرویس Azure OpenAI ارائه‌دهنده پیش‌فرض محیط عملیاتی است.
- سرویس OpenAI ارائه‌دهنده ثانویه تصویب‌شده است.
- ابزار Ollama ارائه‌دهنده تصویب‌شده استنتاج محلی است.
- تمامی پیاده‌سازی‌های ارائه‌دهندگان منحصراً از طریق انتزاع `IAIProvider` مورد دسترسی قرار می‌گیرند.
